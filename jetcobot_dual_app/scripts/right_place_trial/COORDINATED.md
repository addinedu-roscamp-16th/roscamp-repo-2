# Coordinated dual-arm case trial

The current temporary MoveIt scene setting removes `open_tin_case`, sets
both grippers' 14 links to 10 mm padding and both camera links to 15 mm,
while arm links remain at 5 mm.
`dual_real.launch.py` now defaults to `tin_case_enabled:=false` and
`gripper_padding_m:=0.010` and `camera_padding_m:=0.015`. The coordinated case-arrival trial below accepts
the absent case object and still uses `tin_case.yaml` for its target pose.
The physical case is not represented in collision checks while disabled.
The older single-arm `place_right_in_case.py` still requires the case object.

The opt-in mode keeps MoveIt's `both_arms` group and advertises one 12-joint
controller. The PC gate first checks a direct joint-space shortcut from the
measured start to the final goal. If blocked, it checks the path in the live
MoveIt scene and chooses which arm must yield. It joins adjacent portions,
including left/right portions, when every sampled pair of independent arm
positions is valid. The joined portion becomes one gate route; one action is
sent to each moving Pi together, removing a route boundary and its settling
wait. A direct endpoint is used only when its path stays within the existing
3-degree single-arm trial deviation bound of the checked MoveIt portion;
larger detours keep their checked waypoints. The gate seeks safe endpoint
prefix and suffix sections, leaving only the required middle detour as one
continuous Pi drag goal per moving arm. The reduced and rounded drag waypoints
are checked during the one preflight before dispatch. At a
route boundary, the gate requires fresh measured joints within 5 degrees of
the planned start and checks that single measured pose for collision; it does
not repeat the full route scan. After each Pi result, it waits for one new
combined feedback sample so the Pi busy lock can clear; it no longer waits
for three additional stable samples. Pi action success still requires its own
encoder settling. Drift within 5 degrees can change
the actual path from the preflight path. The gate logs when
preflight starts; no arm command is sent during that check. There is no
automatic replan after a failed route. Pi cancellation alone does not prove
physical stop.

During an active Pi route, a brief missing combined state is allowed to recover
for at most 2.5 seconds, matching the existing single-arm gate behavior. No
stale joint value is used to start a new route. A longer gap still aborts.

After an execution abort, the PC gate latches a fault to prevent another
motion goal. Once both physical arms have stopped, clear only that latch with:

```bash
ros2 service call /jetcobot_dual/reset_execution_fault \
  std_srvs/srv/SetBool '{data: true}'
```

The service requires fresh joint feedback, two seconds of stable positions,
and a collision-free MoveIt state. It sends no arm command and does not retry
the failed plan. If MoveIt still reports a collision, the arms must be moved
clear through a separately verified recovery procedure before this service
can succeed. Replan from measured positions after a successful reset. The
service is available only after rebuilding and restarting the PC gate with
the updated package; the currently running old gate still needs one restart.

The minimum-drag route change is in the PC package's `coordinated_route.py`
and `execution_gate.py`. It does not change a Pi bridge file. Both Pi bridge
processes must already expose `sdk_drag_controller` and
`sdk_endpoint_controller` from `sdk_drag_hybrid_bridge.py`. Keep the existing
Pi launch arguments, including the current ROS namespace and drag settings.
The fingertip collision extension is generated by the PC package's `model.py`;
the exported `test_urdf/urdf/jetcobot_dual_real.urdf` used by the trial's FK
checker has the matching four boxes. Rebuild and restart the PC MoveIt launch
after changing the model. The existing running MoveIt process keeps its old
collision geometry until restart.

After rebuilding the PC package, restart the PC MoveIt launch in its existing
terminal with the coordinated flag:

```bash
ros2 launch jetcobot_dual_real dual_real.launch.py \
  execution_arm:=both trajectory_backend:=sdk_drag_hybrid \
  coordinated_execution:=true collision_padding_m:=0.005 rviz:=true
```

To return both arms to `see_center` from the case, use
`coordinated_see_center.py` first without `--execute`. It first tries a shared
dual-arm return with a left-yield goal, then the staged fallback if needed.
Every phase plans one arm while the other is held in the collision scene. It
previews the full sequence. With `--execute`, it replans each phase from fresh
measured joints before sending that phase to the combined controller. The
right arm returns before the left comes back from its yield pose. Neither
gripper is commanded. The controller uses the Pi's configured goal tolerance,
with no 2-degree override.

When the live plan and the physical clearance have been inspected, the same
command with `--execute` sends the combined plan. RViz single-arm moves use
the combined controller with the other arm held at its measured pose. Old
scripts that call `/jetcobot_dual/guarded_left_controller` or
`guarded_right_controller` directly are rejected in coordinated mode.

This is a coordinated case-arrival trial. Camera detection, two-object task
assignment, parallel picking, descent, and release are not part of this
program. Pi drag still follows measured progress rather than MoveIt time. The
gate's sampled checks cover different progress speeds in either arm; they do
not establish the physical SDK endpoint interpolation or held-object clearance.
