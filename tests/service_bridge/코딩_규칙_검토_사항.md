# 서비스 브리지 코딩 규칙 검토 사항

서비스 브리지 단위 테스트로 확인한 규칙을 팀 저장소에 적용할지 검토하는 문서입니다. 검토가 끝난 항목만 코딩 규칙 문서(팀 공유용, 서비스 브리지용)에 올립니다.

| 항목 | 내용 |
|---|---|
| 상태 | 검토 중 |
| 검토자 | central, fleet 담당 (항목별 담당은 5장) |
| 근거 | 이 폴더의 단위 테스트(`unit/`), 서비스 브리지 테스트 계획서 |
| 기준 | 인터페이스 이름·타입·QoS의 원본은 `interfaces/fleet_interfaces/contract.yaml` (docs/개발_규칙.md) |

## 1. 이 문서를 읽는 순서

1. 2장에서 서비스 브리지가 왜 이런 규칙이 필요한지 봅니다.
2. 3장에서 어떤 시험을 했고, 결과가 무엇을 뜻하는지 봅니다.
3. 4장의 방법으로 5장의 항목을 하나씩 검토합니다.
4. 5장의 "결과" 칸에 결정을 적습니다.

## 2. 배경

서비스 브리지는 화면(웹)과 ROS 2 사이에서 주문과 알림을 전달합니다. 화면 쪽은 HTTP·WebSocket, 로봇 쪽은 ROS 2입니다.

이 구간에서는 다음 일이 실제로 생깁니다.
- 사용자가 주문 버튼을 두 번 누르거나, 응답이 늦어 화면이 다시 요청합니다.
- 브리지가 주문을 보낸 직후 FMS가 재시작해서, 주문이 접수됐는지 알 수 없습니다.
- 알림을 받았지만 DB 저장에 실패합니다.
- 관리자 화면이 Wi-Fi 끊김으로 재연결합니다.

규칙은 이런 상황에서도 **주문이 두 번 실행되지 않고, 중요 알림이 사라지지 않게** 하려는 것입니다.

## 3. 무엇을 시험했나

### 3.1 시험 대상과 방법

| 항목 | 내용 |
|---|---|
| 대상 | `reference/sbt_bridge/core/`: 시험용 최소 브리지의 핵심 로직. 팀 제품 코드가 아님 |
| 방법 | ROS 없이 pytest로 함수를 직접 호출. DB는 SQLite 메모리 DB |
| 실행 | `python -m pytest tests/service_bridge -q` |
| 결과 | 24건 중 23건 통과, 1건 미실행(UT-02) |

이 시험은 "이 규칙을 지키면 문제가 막히고, 어기면 문제가 생긴다"를 보여 줍니다. 팀 코드가 규칙을 지키는지는 시험하지 않았습니다.

### 3.2 계획서 항목

| ID | 확인한 규칙 | 시험 방법 | 결과 | 의미 |
|---|---|---|---|---|
| UT-01 | 주문 상태 변경은 한 함수에서만 하고, 허용된 전이만 성공 | 정상 경로 2개와 금지 전이 4개 실행. 5×5 전이 25칸 전체 검사. 상태 변경 SQL이 코드에 한 곳뿐인지 검사 | 통과 | 잘못된 순서(예: 완료된 주문을 다시 전송)가 코드 어디에서도 생기지 않음 |
| UT-02 | Action의 goal_id는 order_id로 정해짐(UUIDv5) | 없음 | 미실행 | 시험용 브리지에 Action 경로가 없어 근거 없음 |
| UT-03 | 같은 Idempotency-Key 요청은 주문 1건 | 같은 키로 주문 3회 요청 | 통과 | 버튼 중복 클릭이나 재요청이 와도 주문이 한 번만 생김 |
| UT-04 | 이미 받은 알림은 다시 저장하지 않고 ACK만 다시 보냄 | 같은 `alert_id`를 2회 수신 | 통과 | 앞선 ACK가 사라져 발신 측이 재전송해도, 저장은 1건이고 재전송은 멈춤 |
| UT-05 | ACK는 DB 커밋 뒤에만 보냄 | 1차 수신에서 커밋 실패를 일으킨 뒤 같은 알림을 다시 수신 | 통과 | 저장에 실패하면 ACK가 없으므로 발신 측이 다시 보내고, 결국 저장됨 |
| UT-05-대조 | (일부러 어긴 경우) 커밋 전에 ACK를 보냄 | 같은 조건에서 순서만 바꿈 | 통과(기대한 실패 관측) | 발신 측은 ACK를 받아 재전송하지 않고, 저장은 0건. **알림이 사라짐** |

UT-01의 전이 표입니다. 행은 현재 상태, 열은 다음 상태입니다.

| 현재 \ 다음 | PENDING | SENT | ACCEPTED | REJECTED | DONE |
|---|---|---|---|---|---|
| PENDING | ✗ | ✓ | ✗ | ✗ | ✗ |
| SENT | ✗ | ✗ | ✓ | ✓ | ✓ (주) |
| ACCEPTED | ✗ | ✗ | ✗ | ✗ | ✓ |
| REJECTED | ✗ | ✗ | ✗ | ✗ | ✗ |
| DONE | ✗ | ✗ | ✗ | ✗ | ✗ |

(주) SENT→DONE은 FMS 응답이 늦은 뒤 상태를 조회해 보니 이미 끝난 경우입니다.

UT-05와 UT-05-대조의 차이입니다.

| 단계 | 규칙 준수 (UT-05) | 규칙 위반 (UT-05-대조) |
|---|---|---|
| 1차 수신 | 커밋 실패 → ACK 안 보냄 → 발신 측이 재전송 | ACK 보냄 → 커밋 실패 → 발신 측은 재전송 안 함 |
| 2차 수신 | 커밋 성공 → ACK | 재전송이 없어 2차 수신 없음 |
| 최종 | 저장 1건 | 저장 0건 = 유실 |

### 3.3 보조 시험 (계획서 ID 없음)

| 파일 | 시험 | 의미 |
|---|---|---|
| `test_orders.py` | 같은 키에 다른 내용이 오면 충돌(409) | 키를 잘못 재사용한 요청이 엉뚱한 주문으로 처리되지 않음 |
| `test_alert_inbox.py` | 재부팅 뒤 같은 seq여도 `boot_id`가 다르면 다른 알림 | 로봇이 재부팅해 seq가 1부터 다시 시작해도 새 알림을 버리지 않음 |
| `test_alert_inbox.py` | seq 순서 조회, 최대 seq | 재연결한 화면에 빠진 알림을 순서대로 다시 보낼 수 있음 |
| `test_ws_queue.py` (12건) | 로봇별 최신 상태만 유지, 큐 상한, 포화 뒤 알림 차단, `since_seq` 재생, 재연결 시 상태 스냅샷, credit 흐름 제어 | 느린 화면이 브리지 메모리를 계속 늘리지 않고, 재연결해도 알림이 빠지거나 중복되지 않음 |

### 3.4 이 시험으로 알 수 없는 것

- **팀 코드:** 팀 코드가 이 규칙을 지키는지는 알 수 없습니다. central 구현이 생기면 같은 시험을 그 코드에 돌려야 합니다.
- **실제 DB:** 실제 DB의 동시 요청 처리는 확인하지 않았습니다. 시험은 SQLite 메모리 DB, 한 스레드로만 했습니다.
- **ROS 2 통신:** QoS, 콜백 그룹, 재시작 복구는 단위 테스트 대상이 아닙니다. 원본 저장소의 통합·부하 시험(IT, LT)에서 따로 확인했고, 이 브랜치에는 들어 있지 않습니다.

## 4. 검토 방법

항목마다 아래 네 가지를 확인합니다.

| 순서 | 확인할 것 | 보는 곳 |
|---|---|---|
| 1 | 근거가 있는가 | 5장 "근거" 칸의 시험. 직접 실행해 보고 시험 코드를 읽음 |
| 2 | 우리 시스템에서 그 문제가 생기는가 | `README.md`의 연결 그림, `docs/관제_동작.md`, `contract.yaml` |
| 3 | 적용하면 무엇을 바꿔야 하는가 | 인터페이스 변경 여부, 영향받는 패키지, 담당 |
| 4 | 적용하지 않으면 무엇을 감수하는가 | 3.2의 "의미" 칸(규칙을 어기면 깨지는 것) |

결과는 다음 넷 중 하나로 적습니다.

| 결과 | 뜻 |
|---|---|
| 채택 | 그대로 규칙으로 올림 |
| 수정 채택 | 팀 구조에 맞게 고쳐서 올림. 고친 내용을 함께 적음 |
| 보류 | 근거가 부족하거나 설계가 정해지지 않음. 다시 볼 조건을 적음 |
| 제외 | 우리 시스템에서는 생기지 않는 문제. 이유를 적음 |

근거 칸에 "단위 테스트 아님"이라고 적힌 항목은 이 브랜치에서 근거를 확인할 수 없습니다. 원본 저장소 결과를 보거나 보류합니다.

## 5. 확인 항목

| ID | 주제 | 규칙 | 근거 | 팀 저장소 현재 상태 | 결정할 것 | 담당 | 결과 |
|---|---|---|---|---|---|---|---|
| K-01 | QoS 원본 | QoS는 공용 정의 한 곳에서만 가져옴 | 단위 테스트 아님 (원본 IT-04) | 원본은 `contract.yaml`. 시험용 `qos.py`는 옮기지 않음 | 서비스 브리지도 `contract.yaml`의 프로필만 쓰는지 | central, fleet | |
| K-02 | 상태 QoS depth | 여러 로봇이 한 토픽을 쓰면 depth ≥ 로봇 수 | 단위 테스트 아님 (원본 LT-02에서 depth 1일 때 상태가 덮어써짐) | STATE depth 5. 상태 토픽이 로봇별(`/{pinky}/state`)이라 토픽 하나에 로봇 1대 | 로봇별 토픽이면 depth 5로 충분한지 | fleet | |
| K-03 | 알림 ACK | 커밋 뒤에만 ACK. 중복 수신 시 ACK만 다시 보냄 | UT-04, UT-05, UT-05-대조 | `Alert`/`AlertAck` 없음. `/central/events`(reliable, volatile, depth 50)만 있음 | 중요 알림에 ACK 경로를 둘지. 둔다면 `contract.yaml`에 추가 | central, fleet, pinky-control | |
| K-04 | 알림 식별자 | 알림마다 `alert_id`(= `boot_id` + seq)와 `seq` | 보조 시험(재부팅 seq, seq 순서) | `FleetEvent`에 ID·seq 필드 없음 | `FleetEvent`에 필드를 추가할지, 중요 알림용 타입을 따로 둘지. `boot_id` 만드는 방법 | central, fleet | |
| K-05 | 발신 측 저장 | 발신 노드는 ACK를 받을 때까지 알림을 보관하고 재전송 | 단위 테스트 아님 (원본 LT-01) | 구현 없음 | K-03을 채택하면 FMS, 핑키, 팔에도 적용할지 | fleet, pinky-control, arm-control | |
| K-06 | 주문 멱등 | 같은 Idempotency-Key 요청은 주문 1건, 같은 응답. 다른 내용이면 409 | UT-03, 보조 시험(409) | `SubmitOrder` 요청은 `items`만 있고, `order_id`는 central이 응답에서 정함 | 화면 요청에 키를 필수로 할지. 키를 `SubmitOrder`에도 넣을지 | central | |
| K-07 | 주문 상태 전이 | 상태 변경은 한 함수에서만, 허용 전이만 성공 | UT-01 | `Order`에 상태 필드 없음. 최종 보고만 `ReportOrder.status`(SHIPPED/PARTIAL/HELD) | 시험용 상태를 central 내부 상태로 둘지. 최종 보고 값과 어떻게 대응시킬지 | central, fleet | |
| K-08 | Action goal_id | goal_id = UUIDv5(order_id) | 없음 (UT-02 미실행) | 액션 클라이언트는 fleet_manager | fleet_manager의 재시도 방식과 맞는지. 맞다면 fleet_manager 시험으로 확인 | fleet | |

| K-11 | 커밋 실패가 계속될 때 | ACK를 보내지 않고 발신 측 재전송에 맡김 | UT-05 (1회 실패만) | 해당 없음 | 재전송 간격·횟수 상한, 운영자에게 알리는 방법 | central, fleet | |
| K-12 | 실제 DB 동시성 | 같은 키 동시 요청을 유니크 제약으로 막음 | 없음 (SQLite, 한 스레드) | central DB 미정 | 제품 DB를 정한 뒤 동시 요청 시험을 추가할지 | central | |

결과 칸에는 4장의 결과 하나와 날짜를 적습니다. 예: `수정 채택 (2026-11-12): FleetEvent에 event_id 추가`

## 7. 병합 기준

- 이 브랜치(단위 테스트 이동)는 규칙 확정과 따로 병합합니다. 테스트가 제품 코드와 `contract.yaml`을 바꾸지 않기 때문입니다.
- 병합 조건
    - `python -m pytest tests/service_bridge -q`가 통과합니다(UT-02는 미실행).
    - 이 문서가 "검토 중" 상태로 함께 들어갑니다.
- 규칙 확정, 인터페이스 변경, 규칙 문서 작성은 각각 별도 PR로 합니다.
