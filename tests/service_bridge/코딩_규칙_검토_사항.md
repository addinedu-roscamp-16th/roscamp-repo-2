# 서비스 브리지 코딩 규칙 검토 사항

서비스 브리지 단위 테스트로 확인한 규칙을 팀 저장소에 적용할지 검토하는 문서입니다. 검토가 끝난 항목만 코딩 규칙 문서(팀 공유용, 서비스 브리지용)에 올립니다.

| 항목 | 내용 |
|---|---|
| 상태 | 검토 중 (1차 검토 반영) |
| 검토자 | central, fleet 담당 (항목별 담당은 5장) |
| 근거 | 이 폴더의 단위 테스트(`unit/`), 원본 공식 실행 결과 사본(`evidence/`), 서비스 브리지 테스트 계획서 |
| 기준 | 인터페이스 이름·타입·QoS의 원본은 `interfaces/fleet_interfaces/contract.yaml` (docs/개발_규칙.md) |

## 1. 이 문서를 읽는 순서

1. 2장에서 서비스 브리지가 왜 이런 규칙이 필요한지 봅니다.
2. 3장에서 어떤 시험을 했고, 결과가 무엇을 뜻하는지 봅니다.
3. 4장의 방법으로 5장의 항목을 하나씩 검토합니다.
4. 5장의 "결과" 칸에 결정을 적습니다.

## 2. 배경

서비스 브리지는 화면(웹)과 ROS 2 사이에서 주문과 알림을 전달합니다. 화면 쪽은 HTTP·WebSocket, 로봇 쪽은 ROS 2입니다.

이 구간에서는 다음 일이 실제로 생깁니다.
- 사용자가 주문 버튼을 두 번 누르거나, 응답이 늦어 화면이 다시 요청합니다.
- 브리지가 주문을 보낸 직후 FMS가 재시작해서, 주문이 접수됐는지 알 수 없습니다.
- 알림을 받았지만 DB 저장에 실패합니다.
- 관리자 화면이 Wi-Fi 끊김으로 재연결합니다.

규칙은 이런 상황에서도 **주문이 두 번 실행되지 않고, 중요 알림이 사라지지 않게** 하려는 것입니다.

## 3. 무엇을 시험했나

근거는 두 종류이며, 서로 섞어 인용하지 않습니다.

| 구분 | 어디서 실행했나 | 무엇을 확인하나 | 위치 |
|---|---|---|---|
| 팀 단위 시험 | 이 브랜치 | 참조 구현의 함수를 직접 호출한 결과 | `unit/` (3.1~3.3) |
| 원본 공식 실행 | 원본 저장소, 장비 2대, 실제 ROS 2 노드 | 통신, 재시작, 부하에서의 동작 | `evidence/20261109-211124/` (3.4) |

### 3.1 시험 대상과 방법

| 항목 | 내용 |
|---|---|
| 대상 | `reference/sbt_bridge/core/`: 시험용 최소 브리지의 핵심 로직. 팀 제품 코드가 아님 |
| 방법 | ROS 없이 pytest로 함수를 직접 호출. DB는 SQLite 메모리 DB, 한 스레드 |
| 실행 | `python -m pytest tests/service_bridge -q` |
| 결과 | 26건 중 25건 통과, 1건 미실행(UT-02) |

이 시험은 "이 규칙을 지키면 문제가 막히고, 어기면 문제가 생긴다"를 참조 구현에서 보여 줍니다. 팀 코드가 규칙을 지키는지는 시험하지 않았습니다.

### 3.2 계획서 항목

| ID | 확인한 규칙 | 시험 방법 | 관측값 | 결과 | 의미와 한계 |
|---|---|---|---|---|---|
| UT-01 | 주문 상태 변경은 한 함수에서만 하고, 허용된 전이만 성공 | 정상 경로 2개와 금지 전이 4개 실행. `Outbox.transition`에서 5×5 전이 25칸 검사([전이 표 시험](unit/test_outbox.py)). 고정 문자열 `UPDATE outbox SET state`가 `core/outbox.py`에만 있는지 소스 검사 | 허용 전이만 성공, 금지 전이는 `InvalidTransition`. 문자열은 `core/outbox.py` 한 곳 | 통과 | 참조 구현의 전이 함수가 표대로 동작함을 보여 줌. 문자열 검사는 대소문자나 열 순서가 다른 SQL을 잡지 못하므로, 제품 전체에서 잘못된 전이가 없다는 보장은 아님 |
| UT-02 | Action의 goal_id는 order_id로 정해짐(UUIDv5) | 없음 | 없음 | 미실행 | 시험용 브리지에 Action 경로가 없어 근거 없음 |
| UT-03 | 같은 Idempotency-Key 요청은 주문 1건 | 같은 키로 주문 3회 요청. 커밋 실패 뒤 재시도(회귀 시험 2건, 3.3) | 3회 응답이 같음(`201`), orders·outbox 각 1건. 커밋 실패 시 미커밋 행 0건, 재시도 후 각 1건 | 통과 | 중복 요청에도 주문이 한 번만 생김. 커밋 실패 경로는 3.5의 결함을 고친 뒤 회귀 시험으로 확인함 |
| UT-04 | 이미 받은 알림은 다시 저장하지 않고 ACK만 다시 보냄 | 같은 `alert_id`로 `receive()`를 2회 직접 호출 | 결과 `STORED`, `DUPLICATE`. 저장 1건, ACK 2회 | 통과 | 중복 수신에 저장은 1건이고 ACK는 다시 나감. 발신 노드의 실제 재전송과 종료는 원본 LT-01(3.4)이 근거 |
| UT-05 | ACK는 DB 커밋 뒤에만 보냄 | 1차 호출에서 커밋 실패를 주입한 뒤 같은 알림으로 다시 호출 | 1차: 저장 0건, ACK 0회. 2차: 커밋 뒤 ACK 1회 | 통과 | 저장에 실패하면 ACK가 없으므로 발신 측이 다시 보낼 근거가 남음 |
| UT-05-대조 | (일부러 어긴 경우) 커밋 전에 ACK를 보냄 | 같은 조건에서 순서만 바꿈 | 저장 0건인데 ACK 1회 | 통과(기대한 실패 관측) | 발신 측은 ACK를 받았으므로 재전송하지 않음. **알림이 사라짐** |

UT-01의 전이 표입니다. 행은 현재 상태, 열은 다음 상태입니다.

| 현재 \ 다음 | PENDING | SENT | ACCEPTED | REJECTED | DONE |
|---|---|---|---|---|---|
| PENDING | ✗ | ✓ | ✗ | ✗ | ✗ |
| SENT | ✗ | ✗ | ✓ | ✓ | ✓ (주) |
| ACCEPTED | ✗ | ✗ | ✗ | ✗ | ✓ |
| REJECTED | ✗ | ✗ | ✗ | ✗ | ✗ |
| DONE | ✗ | ✗ | ✗ | ✗ | ✗ |

(주) SENT→DONE은 FMS 응답이 늦은 뒤 상태를 조회해 보니 이미 끝난 경우입니다.

UT-05와 UT-05-대조의 차이입니다. 단위 시험은 `receive()`를 직접 두 번 호출하므로, "발신 측 재전송"은 시험이 대신 흉내 낸 것입니다.

| 단계 | 규칙 준수 (UT-05) | 규칙 위반 (UT-05-대조) |
|---|---|---|
| 1차 수신 | 커밋 실패 → ACK 안 보냄 → 발신 측이 재전송 | ACK 보냄 → 커밋 실패 → 발신 측은 재전송 안 함 |
| 2차 수신 | 커밋 성공 → ACK | 재전송이 없어 2차 수신 없음 |
| 최종 | 저장 1건 | 저장 0건 = 유실 |

### 3.6 이 시험으로 알 수 없는 것

- **팀 코드:** 팀 코드가 이 규칙을 지키는지는 알 수 없습니다. central 구현이 생기면 같은 시험을 그 코드에 돌려야 합니다.
- **실제 DB:** 실제 DB의 동시 요청 처리는 확인하지 않았습니다. 시험은 SQLite 메모리 DB, 한 스레드로만 했습니다.
- **웹 계층:** HTTP 상태 코드(`409`, 5xx)와 WS 연결 종료는 단위 시험 대상이 아닙니다.
- **WS 재생:** 포화 종료부터 재연결까지의 연속 동작, 큰 재생 목록의 메모리 상한은 확인하지 않았습니다.
- **ROS 2 통신:** QoS, 콜백 그룹, 재시작 복구는 3.4의 원본 결과만 있습니다. 시험용 최소 브리지와 장비 2대 조건의 결과이며, 팀 제품의 성능 기준이 아닙니다.

## 4. 검토 방법

항목마다 아래 네 가지를 확인합니다.

| 순서 | 확인할 것 | 보는 곳 |
|---|---|---|
| 1 | 근거가 있는가 | 5장 "근거" 칸의 시험. 단위 시험은 직접 실행하고 코드를 읽음. 원본 결과는 `evidence/`의 파일로 확인 |
| 2 | 우리 시스템에서 그 문제가 생기는가 | `README.md`의 연결 그림, `docs/관제_동작.md`, `contract.yaml` |
| 3 | 적용하면 무엇을 바꿔야 하는가 | 인터페이스 변경 여부, 영향받는 패키지, 담당 |
| 4 | 적용하지 않으면 무엇을 감수하는가 | 3.2의 "의미와 한계" 칸(규칙을 어기면 깨지는 것) |

결과는 다음 넷 중 하나로 적습니다.

| 결과 | 뜻 |
|---|---|
| 채택 | 그대로 규칙으로 올림 |
| 수정 채택 | 팀 구조에 맞게 고쳐서 올림. 고친 내용을 함께 적음 |
| 보류 | 근거가 부족하거나 설계가 정해지지 않음. 다시 볼 조건을 적음 |
| 제외 | 우리 시스템에서는 생기지 않는 문제. 이유를 적음 |

원본 결과를 인용할 때는 실행 ID, 항목 ID, 관측값, 파일 경로를 함께 적습니다. 예: 실행 `20261109-211124` LT-01: 지정 10건 재전송, 발행 종료 후 2.286초에 미확인 0건, DB 저장 1,000건 ([LT-01.json](evidence/20261109-211124/LT-01.json))

- 이 브랜치(단위 테스트 이동)는 규칙 확정과 따로 병합합니다. 테스트가 제품 코드와 `contract.yaml`을 바꾸지 않기 때문입니다.
