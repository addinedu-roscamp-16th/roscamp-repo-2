# ROS 2 통신 안내 시험 1단계 (L-01, L-03) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** PC 1대에서 L-01(시작 직후 1회 발행)과 L-03(느린 구독자와 depth)을 자동 실행하고, 항목마다 판정이 담긴 JSON을 남기는 시험 도구를 만듭니다.

**Architecture:** 판정·집계·결과 기록은 rclpy 없이 동작하는 순수 Python 모듈(`r2g/`)에 두고 pytest로 시험합니다. ROS 노드(`nodes/`)는 얇은 실행 스크립트로, 지휘 스크립트(`run_l01.py`, `run_l03.py`)가 시도마다 하위 프로세스로 띄우고 표준 출력·JSONL 파일로 결과를 모읍니다. 이 환경에서 `/opt/ros/jazzy`의 rclpy로 프로세스 간 통신이 되므로, 각 작업 끝에 소량(시도 2~3회) 실행으로 확인합니다.

**Tech Stack:** Python 3.12, ROS 2 Jazzy rclpy, `std_msgs/msg/String`, `std_srvs/srv/Trigger`, PyYAML(ROS에 포함), pytest

**Spec:** [ROS2_통신_안내_시험_계획서.md](../ROS2_통신_안내_시험_계획서.md) 3.1절(L-01, L-03), 5장 1단계, 6장

## Global Constraints

- 위치: 팀 저장소 `tests/ros2_guide/`. `package.xml`을 두지 않음(colcon 대상 아님).
- 팀 `ruff.toml`: line-length 100, py312, 규칙 E, F, I, B.
- L 시험은 `std_msgs`(와 서비스 변형의 `std_srvs`)만 사용. 사용자 정의 인터페이스 빌드 없음.
- QoS 프로필 값은 `interfaces/fleet_interfaces/contract.yaml`에서 읽음: `STATE` best_effort/volatile/5, `LATCHED` reliable/transient_local/1, `EVENT` reliable/volatile/50.
- 결과는 `통과`, `실패`, `미실행`, `판정 불가`, `측정` 중 하나. 항목마다 JSON 1개. 포함: 시험 ID, 결과, 관측값, 실행 조건, 환경(`ROS_DISTRO`, `RMW_IMPLEMENTATION`, `ROS_DOMAIN_ID`, 장비).
- 같은 실행 ID에 같은 시험 ID 파일이 있으면 덮어쓰지 않고 오류.
- 실행마다 `ros2 doctor --report` 출력을 결과 폴더에 저장.
- 결과 폴더 `tests/ros2_guide/results/`는 커밋하지 않음.
- L-01: 변형마다 50회. L-03: 조합마다 20초, 규칙 변형 5회 반복, 판정 기준 150 ms.
- 커밋 메시지는 Conventional Commits(영어 제목), 끝에 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

- 하위 프로세스가 멈춤(발행 노드가 끝나지 않음, 구독 노드가 READY를 내지 않음): 전체 실행이 멈추지 않고 그 시도를 손실·시간 초과로 기록하고 다음으로 넘어가야 함 → Task 1 `run_child` 시간 초과 시험.
- 팀원이 같은 네트워크에서 ROS를 쓰는 중: PC 단계 시험이 팀원 노드와 섞이지 않아야 함 → Task 1 `child_env`가 `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`를 넣고 `ROS_DOMAIN_ID`가 없으면 `87`을 쓰는 시험.
- 토픽에 형식이 다른 메시지가 들어옴: 구독 노드가 죽지 않고 건너뛰어야 함 → Task 1 `decode`가 `ValueError`를 내는 시험(노드는 이를 잡아 `bad` 수를 셈).
- 이미 있는 결과를 다시 씀: 공식 실행 결과가 지워지면 안 됨 → Task 1 `write_result`가 `FileExistsError`를 내는 시험.
- 이전 변형의 구독 노드가 남아 다음 변형에 섞임: 변형마다 다른 토픽을 쓰고, 지휘 스크립트가 끝날 때(오류 포함) 하위 프로세스를 모두 정리 → Task 1 `stop_child` 시험, Task 3 토픽 이름 시험.

  - `proc.ChildResult` (dataclass): `rc: int | None`, `stdout: str`, `timed_out: bool`

  - `proc.start_child(cmd: list[str], env: Mapping[str, str]) -> subprocess.Popen` (stdout PIPE, text)
  - `proc.wait_ready(p: subprocess.Popen, timeout: float) -> bool`: stdout에서 `READY` 줄을 기다림.
  - `proc.stop_child(p: subprocess.Popen, grace: float = 3.0) -> None`: SIGINT, `grace`초 뒤에도 살아 있으면 kill.

- Produces:
  - `l01_sub.py --topic T --profile {STATE,LATCHED,EVENT} --out PATH [--duration S]`: 구독 생성 후 stdout에 `READY`. 메시지마다 `{"trial", "seq", "rx_ns"}` 한 줄을 `PATH`(JSONL)에 쓰고 flush. `decode`의 `ValueError`는 `bad` 수로 세고 계속. `--duration`이 없으면 SIGINT까지 실행, 끝날 때 stdout 마지막 줄에 `{"bad": n}`.
  - `l01_pub.py --topic T --profile P --trial N --mode {once,wait_match,stream} [--linger 2.0] [--wait-timeout 5.0] [--rate 10] [--stream-seconds 3]`: 끝날 때 stdout 마지막 줄에 `{"trial", "mode", "pub_start_ns", "matched", "wait_ms", "sent"}` (`matched`, `wait_ms`는 `wait_match`일 때만 값, 그 외 `null`). `pub_start_ns`는 `time.time_ns()`, `create_publisher` 직전.
  - `run_l01.VARIANTS: dict[str, dict]`: 키 `A, B, C, D, E-VOL, E-TL, F, S`. 값은 모두 `{"profile": str | None, "mode": str, "late_sub": bool}`. `mode`는 `once`, `wait_match`, `stream`, `service` 중 하나. `S`는 `{"profile": None, "mode": "service", "late_sub": False}`.
  - `run_l01.topic_for(variant: str) -> str`: `/r2g/l01/` + 소문자, `-`는 `_`. 예: `E-TL` → `/r2g/l01/e_tl`.
  - `run_l01.main(argv: list[str] | None = None) -> int`: 옵션 `--trials 50 --variants A,B,C,D,E-VOL,E-TL,F,S --out-root tests/ros2_guide/results --run-id ID`. 결과 파일 `L-01-<변형>.json`.

변형 설정(계획서 3.1 L-01 표 그대로):

| 변형 | profile | mode | 비고 |
|---|---|---|---|
| A | EVENT | once | 손실 1건 이상이면 notes에 `재현됨` |
| B | EVENT | wait_match | 최대 5초 대기 |
| C | LATCHED | once | |
| D | STATE | once | |
| F | EVENT | stream | 10 Hz, 3초. 시도마다 `first_receive` 기록 |

A~D, F는 변형마다 구독 노드 1개를 계속 띄워 두고, 발행 노드를 시도마다 새로 실행합니다(시도 사이 0.5초 간격). 모든 시도가 끝나면 2초 기다린 뒤 구독 노드를 멈추고 JSONL을 읽습니다. 하위 프로세스는 `try/finally`에서 `stop_child`로 정리합니다.
