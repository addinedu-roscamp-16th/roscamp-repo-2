# ROS 2 통신 안내 시험 계획서

| 항목 | 내용 |
|---|---|
| 개정 | 2판 (2026-11-10): 토픽 손실 시험(L) 추가, 로봇 통합 운영 사전 검토(L-04) 추가, 우선순위와 일정 조정 |
| 대상 | `ROS2_통신_안내.html` (팀 공유용, 사례 10개, 예제 29개) |
| 방식 | 토픽 손실 시험 + 예제 실행 검사 + 사례 재현 시험 + 공식 문서 대조 |
| 범위 | 필수 항목만 (선택 항목은 따로 표시) |
| 환경 | Ubuntu 24.04, ROS 2 Jazzy, PC 1대. 라즈베리파이 1대 추가(L-01-W, L-02, L-04, G-11, 저녁에만 사용 가능). `RMW_IMPLEMENTATION`은 시험마다 기록 |
| 산출물 | 시험 코드, 결과 기록(JSON), 통신 규칙 초안(1장), 사례마다 근거를 표시한 안내 문서, `contract.yaml` 변경 제안 |

## 1. 목적

이전 프로젝트에서 팀원이 토픽을 받지 못해 같은 토픽을 여러 번 보내 겨우 받은 일이 있었습니다(원인은 확인되지 않음). 이번 시험의 목적은 **프로젝트 시작 전에 토픽 손실을 줄이는 통신 규칙을 정하고, 그 규칙에 시험 근거를 붙이는 것**입니다.

- 팀원이 겪은 증상("한 번 보내면 못 받고, 여러 번 보내야 받음")을 재현하고, 규칙을 지키면 한 번만 보내도 받는지 확인합니다.
- 우리 장비와 Wi-Fi에서 QoS 설정별 손실률을 재서, 토픽마다 QoS를 고르는 기준을 만듭니다.
- **로봇 통합 운영 설계의 사전 검토:** 여러 로봇과 관제를 함께 운영할 때 통신 방식(토픽·서비스·액션 선택, QoS, 메시지 크기와 속도)을 정하는 근거로 씁니다.
- 초보 개발자가 안내 문서의 예제를 그대로 복사해도 동작하는지 확인합니다.
- 각 사례의 "잘못된 예"가 설명한 문제를 실제로 일으키고, "바른 예"가 그 문제를 막는지 확인합니다.
- 사례마다 근거의 종류를 표시해, 읽는 사람이 믿을 정도를 알 수 있게 합니다.

팀원들은 이미 각자 담당 기능을 시험하고 있으므로, 결과는 한꺼번에 내지 않고 나오는 대로 나눠 공유합니다(5장).

## 2. 근거 표시

시험이 끝나면 안내 문서의 각 사례에 아래 표시 중 하나 이상을 붙입니다.

| 표시 | 뜻 |
|---|---|
| 시험 | 이 계획서의 시험으로 안내 문서 예제를 재현·확인함 (시험 ID 함께 표시) |
| 시험(서비스 브리지) | 서비스 브리지 시험으로 같은 규칙을 확인함. 안내 문서 예제와 다른 코드(시험용 최소 브리지)임을 함께 표시 |
| 공식 문서 | ROS 2 공식 문서에 적힌 동작. 링크로 확인 |
| 측정 | 우리 장비에서 잰 값. 환경이 다르면 달라짐 |
| 경험 | 팀이 겪은 사례. 재현 시험 없음 |

## 3. 시험 항목

우선순위는 L(손실) → G(사례 재현) → EX(예제 검사)·DOC(공식 문서 대조) 순서입니다.

### 3.1 토픽 손실 시험 (L) — 1순위

팀원이 겪은 증상의 원인으로 가장 유력한 두 가지를 모두 시험합니다.

| 원인 후보 | 설명 | 시험 |
|---|---|---|
| 연결되기 전에 보냄 | 발행 노드가 시작 직후 1회만 보내면, 상대 노드를 아직 찾지 못해(discovery 진행 중) 메시지가 버려짐. 여러 번 보내다 보면 그사이 연결이 생겨 받게 됨 | L-01 |
| best_effort와 Wi-Fi | 신뢰성이 best_effort이면 Wi-Fi에서 빠진 패킷을 다시 보내지 않음 | L-02 |

느린 구독자 때문에 메시지가 버려지는 경우(사례 9)도 손실의 한 종류라 L-03으로 함께 잽니다. 로봇 통합 운영(AMR 3대, 로봇 팔 3대) 조건에서의 손실과 heartbeat 끊김은 L-04로 잽니다.

참고로 QoS 불일치(사례 6)는 아무리 보내도 받지 못하므로 이번 증상과는 맞지 않습니다. G-08에서 따로 확인합니다.

팀 계약(`interfaces/fleet_interfaces/contract.yaml`)의 프로필과의 관계입니다.

| 프로필 | 설정 | 관련 시험 |
|---|---|---|
| `STATE` | best_effort, volatile, depth 5 | L-01 D, L-02, L-03 |
| `LATCHED` | reliable, transient_local, depth 1 | L-01 C, E |
| `EVENT` | reliable, volatile, depth 50 | L-01 A, B, E (`/central/events`가 이 프로필) |

#### L-01 시작 직후 1회 발행

| 항목 | 내용 |
|---|---|
| 준비 | 구독 노드를 먼저 띄워 둠. 발행 노드는 시도마다 새 프로세스로 실행하고, 메시지 1건을 보낸 뒤 2초간 spin하고 종료 |
| 반복 | 변형마다 50회. 메시지에 시도 번호를 넣어 구독 측에서 시도별 수신 여부를 셈 |
| 장비 | L-01: PC 1대(두 프로세스), 모든 변형. L-01-W: 발행 노드를 라즈베리파이에 두고 Wi-Fi로 모든 변형 반복. 저녁 시간이 모자라면 A, B, C, F를 먼저 실행 |

| 변형 | 구분 | 방법 | 판정 |
|---|---|---|---|
| A | 재현 | `EVENT` 프로필. `create_publisher` 직후 바로 1회 발행 | 측정. 손실이 1건 이상이면 "재현됨"으로 기록 |
| B | 규칙 | A와 같은 프로필. `get_subscription_count()`가 1 이상이 될 때까지(최대 5초) 기다린 뒤 1회 발행 | 50회 모두 수신하면 통과 |
| C | 규칙 | `LATCHED` 프로필(양쪽). 바로 1회 발행 | 50회 모두 수신하면 통과 |
| D | 참고 | `STATE` 프로필(best_effort). 바로 1회 발행 | 측정 |
| E | 늦게 뜬 구독자 | 발행 노드가 1회 발행 후 계속 실행. 구독 노드는 1초 뒤에 시작. `EVENT`(volatile)와 `LATCHED`(transient_local) 각각 | volatile: 측정(설계상 받지 못함). transient_local: 50회 모두 수신하면 통과 |
| F | 반복 발행 | `EVENT` 프로필. 시작 직후부터 10 Hz로 계속 발행 | 측정: 처음 받은 메시지의 순번과 발행 시작부터 첫 수신까지 걸린 시간. "여러 번 보내야 받음"을 수치로 확인 |
| S | 규칙 | 서비스 클라이언트가 `wait_for_service()` 후 1회 호출 | 50회 모두 응답받으면 통과 |

- transient_local depth 1은 마지막 1건만 보관합니다. 짧은 시간에 여러 건을 보내면 늦게 뜬 구독자는 마지막 것만 받습니다. 이 점은 결과와 함께 규칙에 적습니다.
- B의 `get_subscription_count()`는 발행 측이 구독자를 찾았다는 뜻입니다. 50회 모두 받는지로 충분한지 판단합니다.

#### L-02 Wi-Fi 주기 메시지 손실률 (저녁)

| 항목 | 내용 |
|---|---|
| 장비 | 발행: 라즈베리파이. 구독: PC. 같은 공유기에 연결 |
| 조건 | 신뢰성 2가지(best_effort, reliable) × 크기 3가지(1 KB, 64 KB, 500 KB) × 속도 2가지(10 Hz, 50 Hz) = 12조합. 조합마다 30초, 3회 반복. depth는 50, durability는 volatile로 모든 조합에 고정(작성자 결정: 손실이 depth가 아니라 신뢰성과 Wi-Fi 때문인지 구분하기 위함) |
| 측정 | 보낸 수, 받은 수, 손실률(순번 빈자리), 수신 간격의 최대값. 라즈베리파이의 Wi-Fi 신호 세기(`iwconfig`)를 조합마다 기록 |
| 판정 | 측정(합격 기준 없음). 결과로 "토픽별 QoS·크기·속도 선택표"를 만듦 |

- 기존 선택 항목 M-01(메시지 크기)은 L-02에 포함합니다.
- 두 장비의 시계가 맞지 않으므로 한쪽 방향 지연은 판정에 쓰지 않습니다.

#### L-03 느린 구독자와 depth (PC)

| 항목 | 내용 |
|---|---|
| 조건 | 발행 50 Hz, 메시지에 증가하는 순번. 구독 콜백은 처리마다 100 ms 소요(10 Hz 처리). depth 3가지(1, 5, 50) × 신뢰성 2가지(best_effort, reliable). 조합마다 20초 |
| 규칙 변형 | 블록 22 방식: 수신 콜백은 최신 메시지만 저장하고, 타이머가 최신 것만 처리 |
| 측정 | 처리한 수, 버려진 수, 처리 시점의 "묵은 정도"(처리 시각 − 메시지 발행 시각). 같은 PC라 시계가 같음. 발행 시각은 메시지에 넣음 |
| 판정 | 규칙 변형: 5회 반복 모두에서 모든 처리의 묵은 정도가 150 ms 이하이면 통과(처리 주기 100 ms + 발행 주기 20 ms + 여유 30 ms). 나머지 조합은 측정(대조: depth 50 reliable에서 묵은 정도가 계속 커지는지 기록) |

- 기존 G-10은 L-03에서 함께 확인합니다.
- "받은 최신 순번 − 처리한 순번"은 규칙 변형에서 항상 0이 되어 판정이 안 되므로, 발행 시각 기준으로 잽니다(작성자 결정). 메시지가 DDS 큐에서 기다린 시간까지 포함됩니다.

#### L-04 통합 운영 모의 부하 (저녁)

통합 운영 때 같은 Wi-Fi에 AMR(핑키) 3대, 로봇 팔 3대, 관제 PC가 함께 붙습니다. 장비 6대를 모두 준비할 수 없으므로, 라즈베리파이 1대가 로봇 6대 분량의 토픽을 보내고 PC가 관제 역할을 합니다.

| 항목 | 내용 |
|---|---|
| 로봇 쪽 (라즈베리파이) | `/pinky1~3/state`(`STATE`), `/arm1~3/state`(`STATE`), `/arm1~2/vision/items`(`LATCHED`). 로봇마다 노드 1개, 이름과 QoS는 `contract.yaml` 그대로 |
| 관제 쪽 (PC) | `/fleet/heartbeat` 2 Hz(`STATE`), `/fleet/robots` 1 Hz(`LATCHED`), `/central/events`(`EVENT`) 수시 발행. 로봇 상태 토픽 구독 |
| 발행 속도 | 정해진 것은 그대로: heartbeat 2 Hz, `/fleet/robots` 1 Hz(`docs/관제_동작.md`). 로봇 상태와 비전 결과의 주기는 아직 미정이므로 세 단계로 나눠 잼: 낮음(상태 5 Hz, 비전 1 Hz), 중간(상태 10 Hz, 비전 5 Hz), 높음(상태 20 Hz, 비전 10 Hz). 단계 값은 설정으로 바꿀 수 있게 함 |
| 비전 결과 | 카메라 영상은 ROS 2로 보내지 않고, 비전 결과만 `/arm1~2/vision/items`로 보냄. 메시지 크기는 물체 10개 분량을 기본으로 함(작성자 가정) |
| 조건 | 주기 3단계 × 배경 2가지 = 6조합, 조합마다 2분. 배경: (1) ROS 2 토픽만. (2) GStreamer 영상 전송을 같은 Wi-Fi에서 함께 실행. 영상은 ROS 2와 별도로 GStreamer로 보내지만 같은 공유기를 쓰므로 대역을 나눠 씀. 시험 영상은 `videotestsrc`로 만들고 해상도·프레임·비트레이트는 설정값(기본 640×480, 15 fps, 약 2 Mbps, 작성자 가정) |
| 측정 | 토픽별 손실률, 로봇 쪽에서 본 heartbeat 최대 끊김 시간, 1.5초 넘게 끊긴 횟수(핑키가 스스로 서는 조건), 관제 쪽에서 본 로봇 상태 최대 끊김 시간 |
| 판정 | 측정. 다만 heartbeat가 1.5초 넘게 끊긴 경우가 있으면 "통합 운영 위험"으로 표시하고 원인(조건, 시각)을 기록. 결과로 "주기 단계별 손실·끊김 표"를 만들어 상태·비전 주기를 정하는 근거로 씀 |

- 팀의 실제 영상 설정(해상도, 비트레이트, 대수)이 정해지면 그 값으로 다시 실행합니다.
- 한계: 로봇 6대의 무선 송신을 라즈베리파이 1대의 무선 송신 하나로 흉내 내므로, 실제 6대가 공유기를 나눠 쓰는 상황보다 덜 혼잡할 수 있습니다. 결과는 "최소한 이만큼은 생긴다"는 하한으로 읽습니다.
- heartbeat 끊김은 G-02(관제 노드 중단)와 다릅니다. G-02는 관제가 멈췄을 때, L-04는 관제가 살아 있는데 Wi-Fi 때문에 끊겨 보이는 경우입니다.

- Humble용으로 적은 줄(`rclpy.qos_event`)은 실행하지 않고 공식 문서 대조(DOC-03)로 확인합니다.
- 알려진 문제: 블록 19 `on_goal_response`의 `order_id`는 정의되지 않은 이름입니다(실행 시 `NameError`). EX-01에서 실패로 잡혀야 하며, 안내 문서를 고친 뒤 다시 실행합니다.

## 6. 결과 기록 방식

| ID | 결과 | 관측값 | 안내 문서 반영 |
|---|---|---|---|
| L-01 | | | |

- 결과는 `통과`, `실패`, `미실행`, `판정 불가` 중 하나로 적습니다. 측정 항목은 `측정`으로 적고 값을 남깁니다.
- 시험 코드는 `service_bridge/evidence/`와 같은 형식의 JSON을 항목마다 하나씩 출력합니다. 포함할 것: 시험 ID, 변형, 결과, 관측값, 반복 회차, 실행 시각, 환경(`ROS_DISTRO`, `RMW_IMPLEMENTATION`, `ROS_DOMAIN_ID`, 장비).
- 실행마다 `ros2 doctor --report` 출력을 결과 폴더에 함께 저장합니다.
- 실행 결과 폴더는 커밋하지 않습니다. 근거로 인용할 공식 실행만 `ros2_guide/evidence/<실행 ID>/`에 사본으로 남깁니다(서비스 브리지와 같은 방식).
- 예제가 실패하면 안내 문서의 예제를 고치고, 같은 시험을 다시 실행합니다.
- 잘못된 예가 설명한 문제를 재현하지 못하면, 설명을 고치거나 근거를 "경험"으로 낮춥니다.
- 시험 코드는 팀 저장소 `tests/ros2_guide/`에 둡니다.
