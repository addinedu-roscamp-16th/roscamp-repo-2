# 브랜치 운영 안내

- 버전 v1.0 (2026-11-24)
- 대상: 팀원 모두. 처음 PR을 하는 사람도 이 문서만 보고 따라 할 수 있게 씁니다.

## 1. 브랜치 구조

| 브랜치 | 역할 | 들어오는 길 |
|---|---|---|
| `main` | 시연 · 제출 기준 안정판 | `dev`에서만. 스프린트 끝 통합 시험을 통과하면 병합하고 태그를 붙임 |
| `dev` | 통합 개발 (개발 시작 기준) | 작업 브랜치에서 **PR로만** |
| 작업 브랜치 | 각자 개발 | `dev` 최신에서 만듦. 병합 뒤 지움 |

- `dev`와 `main`에 직접 푸시하지 않습니다.
- 작업 브랜치는 **작업마다 짧게** 씁니다(Jira 이슈 하나 = 브랜치 하나 권장). 오래 쓴 브랜치는 `dev`와 많이 벌어져 병합 때 충돌이 커집니다.
- 이름: `feat/…` · `fix/…` · `docs/…` · `test/…` · `refactor/…`, 이슈 번호를 넣으면 좋습니다. 예: `feat/TT-25-report-trip`, `fix/pode-dock-retry`.
- 병합 담당자는 따로 없습니다. **각자 자기 PR을 병합합니다.** 대신 아래 절차와 검사(4장)를 지킵니다.

## 2. 작업 순서 (처음부터 병합까지)

**① `dev` 최신에서 작업 브랜치 만들기**

```bash
git switch dev
git pull
git switch -c feat/TT-25-report-trip
```

**② 작업 · 커밋.** 커밋은 여러 번 해도 됩니다. 메시지는 Conventional Commits(`feat:` · `fix:` · `docs:` · `test:` · `refactor:`).

**③ 원격에 올리기**

```bash
git push -u origin feat/TT-25-report-trip
```

**④ GitHub에서 PR 열기**
- Pull requests → **New pull request**.
- 위쪽 두 칸: **base: `dev`** ← **compare: 내 브랜치**. base 기본값이 `main`이므로 꼭 바꿉니다.
- 제목은 Conventional Commits 형식(squash 병합 때 이 제목이 `dev`의 커밋 메시지가 됨). 예: `feat(order): ReportTrip 서버 반영 판정`.
- 본문: Jira 번호, 바꾼 것, 시험한 방법. 인터페이스를 바꿨으면 그 이름(IR-90).

**⑤ 확인**
- "Files changed" 탭에서 내가 바꾼 파일만 보이는지 봅니다. 수백 개가 보이면 base를 잘못 골랐거나 다른 브랜치가 섞인 것입니다.
- 검사(4장)가 있으면 모두 초록색이 될 때까지 기다립니다. 빨간색이면 같은 브랜치에 고쳐서 다시 푸시합니다(PR이 그대로 갱신됨).

**⑥ `dev`가 앞서 나갔거나 충돌 표시가 뜨면**: 내 브랜치에서 `dev`를 받아 병합하고 푸시합니다. 충돌은 **PR을 연 사람이** 풉니다.

```bash
git fetch origin
git merge origin/dev
git push
```

**⑦ 병합**: 병합 버튼 옆 ▾에서 방식을 고르고(3장) **Confirm**. 리뷰 승인 없이 본인이 병합합니다. 예외: `interfaces/` · `contract.yaml`을 바꾼 PR은 관련 담당 1명의 확인을 받은 뒤 병합합니다.

**⑧ 정리**: 병합 뒤 나오는 **Delete branch**를 누르고, 로컬도 정리합니다.

```bash
git switch dev
git pull
git branch -D feat/TT-25-report-trip
```

squash 병합은 작업 브랜치의 커밋을 그대로 넣지 않아 `git branch -d`가 "병합 안 됨"으로 거절합니다. 그래서 `-D`를 씁니다.

## 3. 병합 방식

| 방식 | 언제 | 이유 |
|---|---|---|
| **Squash and merge** | 보통의 작업 브랜치 (기본) | 기능 하나가 `dev`의 커밋 하나가 되어 이력이 읽기 쉽고, 되돌리기도 PR 하나 단위 |
| **Create a merge commit** | 오래 쓴 브랜치 통합, 커밋을 나눠 남겨야 할 때 (예: 인터페이스 추가와 이름 변경을 따로 되돌릴 수 있게) | 커밋 이력이 그대로 남음 |
| Rebase and merge | 쓰지 않음 | 팀 안에서 방식을 줄이기 위해 |

## 4. 자동 검사 (준비 중)

PR을 열 때(`dev` 대상) 통신 규칙을 검사하는 것을 목표로 합니다. 아직 설정하지 않았고, 정해지면 이 장을 고칩니다.

| 단계 | 검사 | 잡는 규칙 |
|---|---|---|
| 정적 검사 | `contract.yaml`이 바뀌었는데 같은 PR에 명세가 없음 · 코드의 토픽 · 서비스 이름이 contract에 없음 · 콜백 안 `wait_for_service` · 옛 이름 `arm[123]` | IR-90, 이름 규칙, IR-32 |
| 빌드 · 단위 시험 | `colcon build` · `colcon test`, ROS 없는 pytest | 깨진 코드 |
| 실행 대조 | fake로 띄운 뒤 `scripts/check_interfaces.py --mode fake` | 이름 · 타입 · QoS 실제 일치 |

저장소가 공개라 GitHub branch protection을 쓸 수 있습니다. 설정하면 `dev` 직접 푸시 금지, 검사 통과 전 병합 금지, `interfaces/` 변경 시 CODEOWNERS 승인을 GitHub가 강제합니다. 설정 전까지는 약속으로 지킵니다.

## 5. 버전 규칙

| 대상 | 형식 | 올리는 때 |
|---|---|---|
| contract (`contract.yaml`의 `version`) | `0.N` | 인터페이스(이름 · 타입 · 칸 · QoS)가 **조금이라도** 바뀌면 N+1. ROS 2는 칸 하나만 더해도 타입이 달라져 다르게 빌드한 노드끼리 통신하지 못하므로, "호환되는 작은 변경"을 따로 두지 않습니다. 바뀌면 모두 다시 빌드합니다. |
| 제품 (`main` 태그) | `vMAJOR.MINOR.PATCH` | 스프린트 끝 `dev` → `main` 병합 때 MINOR+1(스프린트 4 → `v0.4.0`), `main` 긴급 수정은 PATCH+1, 최종 시연은 `v1.0.0`. 태그 설명에 그때의 contract 버전을 적음 |
| 설계 문서 | `vX.Y` | 각 문서 머리와 변경 이력 (지금 방식) |

- 제출물 표시 태그 `submit/날짜-…`는 그대로 씁니다.
- `package.xml` 버전은 제품 태그를 붙일 때 한꺼번에 맞춥니다.

## 6. 자주 생기는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| PR 화면에 바뀐 파일이 수백 개 | base를 `main`으로 둠, 또는 다른 작업 브랜치를 섞음 | base를 `dev`로 바꿈. 섞였으면 `dev`에서 새 브랜치를 만들어 필요한 커밋만 옮김 |
| 로컬에서는 깨끗한데 GitHub가 충돌 표시 | 두 브랜치가 서로를 병합해 공통 조상이 둘(교차 병합) | 내 브랜치에 `origin/dev`를 병합해 푸시(2장 ⑥). 처음부터 `dev`에서 만들고 `dev`만 받으면 생기지 않음 |
| 잘못 병합함 | – | 병합된 PR 화면의 **Revert** 버튼 → 되돌리는 PR이 생기고, 같은 절차로 병합 |
| `git branch -d`가 거절 | squash 병합 | `git branch -D` |
