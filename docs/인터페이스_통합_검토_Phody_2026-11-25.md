# 인터페이스 통합 검토 — Phody(포디, 양팔 JetCobot)

2026-11-25 작성. 팀 설계와 우리 코드(`jetcobot_dual`)를 비교해, 팀 쪽에 고쳐 달라고 할 것과 우리가 만들어야 할 것을 정리했다. 팀 브랜치는 읽기만 했고 고치지 않았다.

## 설계에서 포디의 자리 (요약)

- 이름은 **Phody**, 팔 `arm_left` · `arm_right`, 작업대 `WORK`, 하는 일 `fill`(`config/robots.yaml`).
  - Phony는 `arm_ship`(출고 팔), Pode는 `pode1~3`(이동 로봇)이다.
- 포디가 받거나 내야 하는 것 (명세 3.5 · 4.5 · 4.6):

| 이름 | 종류 | 방향 | 타입 |
| --- | --- | --- | --- |
| `/workcell/fill_basket` | 액션 | fleet → 포디 (두 팔 공용 목표 하나) | `FillBasket` |
| `/{arm}/state` | 토픽 STATE, 초당 5번 | 포디 → fleet | `ArmState` |
| `/{robot}/set_lock` | 서비스 | fleet(비상정지 때는 estop 노드) → 포디 | `SetLock` |
| `/{robot}/set_mode` | 서비스 | fleet → 포디 | `SetMode` |
| `/{robot}/force` | 서비스 | fleet → 포디 (시험 모드만) | `ForceInput` |
| `/{arm}/fault_resolved` | 서비스 | fleet → 포디 | `RobotCommand` |
| `/fleet/heartbeat` | 토픽 | fleet → 포디. 1.5초 끊기면 멈춤 | `std_msgs/Header` |
| 팔 멈춤 · 이어서 | 미정 (Q-05) | fleet → 포디 | |

## 2. 넣어 달라고 할 것 (우리 코드에 꼭 필요한데 명세에 없음)

| # | 빠진 규칙 · 인터페이스 | 왜 필요한가 (우리 코드 근거) | 제안 |
| --- | --- | --- | --- |
| R-1 | **바구니 위치.** C(담기)는 바구니(틴케이스) 위치를 `config/tin_case.yaml`의 고정 좌표로 쓴다. 실제 바구니는 도킹한 Pode 위에 있어서 도킹 오차만큼 위치가 바뀐다. | `stage3_place.py`, `case_arrival_pose` | ① 도킹 허용 오차(예: ±10 mm, ±3°)를 규칙으로 정하거나 ② 바구니 자세를 알려주는 인터페이스, 또는 ③ 포디가 카메라로 직접 잰다는 결정. 어느 쪽인지 정해 달라 |
| R-2 | **상품 코드 표.** `OrderItem.kind`(상품 코드)만 정해져 있고 목록이 없다. 포디 인식 클래스는 `chocolate_bar`(멘토스 꺼짐)다. | YOLO `classes ['chocolate_bar']` | 상품 코드 목록, 포디가 집을 수 있는 상품, 코드 ↔ 인식 클래스 대응표 |
| R-3 | **선반(작업판) 재고 · 인식.** 포디는 `FillBasket` 목표를 받으면 양팔 `see_center`에서 스테레오로 찍어 물체 위치를 구한다. 요청한 개수보다 적게 보이면 `OUT_OF_STOCK`인지 `RECOGNITION_ERROR`인지 가를 기준이 없다. | `sam_multi_real.py` 캡처·매칭 | 판정 기준과 `missing` 보고 규칙 |
| R-4 | **`set_lock`의 물리적 뜻.** JetCobot은 서보 토크를 풀면 팔이 떨어진다. "락 해제"가 토크 해제인지, 업무에서만 빼는 것인지 정해져 있지 않다. | 브리지 `handeye_free_mode`(토크 해제) | 포디의 락 해제 = 안전 자세로 옮긴 뒤 업무 제외(토크 유지)로 정의 제안. 토크 해제가 필요하면 별도 명령 |
| R-5 | **관리 명령 2초 한도 vs 포디 복구 시간.** `fault_resolved`를 받으면 게이트 고장 잠금을 풀어야 하는데, 그 전에 "2초 정지 + 충돌 없음"을 확인한다(`_confirm_recovery_stopped`). 2초 한도(IR-40)를 넘는다. | `execution_gate.reset_execution_fault` | `fault_resolved`는 "접수"만 즉시 응답하고 결과는 상태(`ArmState.state`/`detail`)로 보이게 하거나, 한도를 이 명령만 늘려 달라 |
| R-6 | **heartbeat 끊김 때 팔 동작.** IR 표: 0.5초 주기, 1.5초 끊기면 로봇이 멈춤. 실측으로 Wi-Fi 구간에서 7~8초 끊김이 있었다(11-25 19:43 · 19:49). 팔이 이동 중 서면 상품을 쥔 채 공중에 멈춘다. | 11-25 로그 | 팔은 "진행 중 관절 골 1개는 마치고 멈춤"인지 "즉시 정지"인지 정하고, 멈춘 뒤 이어서 하기 규칙(Q-05와 같이) |
| R-7 | **팔 고유 사유 코드.** 2.2 표에 팔 장애 원인이 `ARM_FAULT` 하나뿐이다. `ArmState.detail`에 넣을 코드가 없다(IR-05: 표에 먼저 넣고 써야 함). | 게이트 실패 사유 | `ARM_FEEDBACK_LOST`(관절 상태 끊김), `ARM_UNREACHABLE`(IK 해 없음), `ARM_COLLISION_CHECK`(충돌 검사 실패), `GRIPPER_FAULT` 추가 제안 |
| R-8 | **`placed_confirmed`의 기준.** 포디는 담긴 것을 따로 재는 센서가 없다. | C 흐름 | "케이스 위에서 그리퍼 열기 성공 = 확인된 담기"로 정의 제안 |
| R-9 | **취소 때 쥔 상품.** `FillBasket`이 취소될 때 상품을 쥐고 있으면 바구니에 넣고 끝낼지, 선반에 되돌릴지, `uncertain`으로 들고 멈출지 없다. | | 정해 달라 (Q-03과 연결) |
| R-10 | **두 팔 동시 작업.** 포디는 두 팔이 병렬로 집고(A) 담는다(C). 바구니 공간에는 한 팔만 들어간다. dev `ArmState` 주석 "PLACING은 두 팔 동시에 보고하면 안 된다"와 맞다. 다만 A · B · C와 상태 값의 대응이 없다. | [구간_정의.md](구간_정의.md) | 포디 대응 제안: A=`PICKING`, B 진입·C·B 복귀=`PLACING`(바구니 점유 구간), 바구니 대기=`PLACE_WAITING` |

설계 검토 사항 중 포디가 답할 수 있는 것:

- **Q-05 (멈춤 · 이어서):** 포디는 관절 골 단위로 움직인다. 제안은 `/{arm}/set_pause`(목표 값 `paused=true/false`, IR-21)다. 받으면 지금 골을 마치거나(R-6 결정에 따름) 멈추고, `false`에서 다음 골부터 잇는다.
- **Q-06 (한 팔만 락 해제):** 포디는 한 팔만으로도 순차 작업이 된다(`first_arm` 지정 실행). 제안: 남은 팔이 닿는 상품만 이어서 담고, 못 닿는 것은 `missing` + `ARM_UNREACHABLE`.
- **Q-03 (`holding` · `uncertain`):** 포디는 그리퍼 닫힘 기록(`gripper_close_complete.json`)과 바구니 담기 체크포인트로 쥔 상태를 안다. `holding`은 이 값으로 낼 수 있다.

## 4. 우리 내부 인터페이스 (팀에 보일 필요 없음)

Pi 브리지(`/left` · `/right`), state_aggregator, MoveIt(`/jetcobot_dual`), 실행 게이트, 카메라 UDP(5000/5001)는 포디 내부다. 팀 인터페이스는 U-1 ~ U-5 노드 하나가 바깥에 내놓으면 된다. 자세한 내부 목록은 [INTERFACES.md](../INTERFACES.md)에 있다. 다만 11-20 기준이라 11-25 변경(게이트 lane, 담기 worker 노드 이름)은 아직 반영되지 않았다.
