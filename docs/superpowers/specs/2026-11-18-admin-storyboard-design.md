# 관리자 페이지 스토리보드 설계

- 작성일: 2026-11-18
- 상태: 승인됨 (2026-11-18), v1.1 · v1.2 변경 승인 (2026-11-19, 9절)
- 산출물: `design/diagrams/관리자_스토리보드.drawio` (탭별 PNG로 내보내 제출)

## 1. 목적

관리자 웹 페이지의 화면 구성과 동작 흐름을 장면 단위로 그린다. 팀이 "어떤 상황에서 관리자가 무엇을 보고 무엇을 누르는지"를 맞춰 보는 **검토용 초안**이다. 검토를 마치면 탭별 PNG로 내보내 제출한다. 1주차 스프린트 계획의 "GUI 화면 구성 및 사용자 동작 흐름에 따른 스토리보드 작성"에 해당한다.

### 목표
- 관리자 화면 기능이 모두 어느 장면엔가 나온다. 기준은 기능 검토 시트(https://docs.google.com/spreadsheets/d/12uOX_Ejw0S146HjWJncUS-gS1C0r7bTAZSmQPOKKJ7U)의 "기능 목록" 탭에서 사용 역할이 관리자 · 공통이고 구현 계획이 포함 · 일부 포함인 화면 · 주문 관리 기능이다:
  - SCR-01 로그인 · 역할 구분, SCR-06 로봇 상태 · 위치(일부), SCR-07 주문 현황, SCR-08 결품 알림 · 보충 결과 입력, SCR-10 로봇 장애 알림, SCR-11 Pode 장애 조치 결과 입력(일부), SCR-12 Phody 이상 · 장애 처리 입력(일부), SCR-16 작업 시작 · 일시 정지 · 재시작, SCR-18 재고 관리, SCR-19 이력 · 통계(일부: 이력 조회만), SCR-20 로봇 화면 · SCR-21 간편 처리 패널(11-19 추가)
  - OMS-03 재고 초과 주문 거절(관리자 알림), OMS-08 입고 · 반출 기록(11-19 이름 변경), OMS-09 재고 부족 알림(일부: 기준 수량 설정), OMS-16 중요 알림 상태 관리(일부: 알림 목록), OMS-18 마감 · 수시 조정 · CEN-13 마감 중 배정 보류(11-19 추가)
  - 비상정지는 COM-02 (화면 부분은 비상정지 제안 페이지 기준)
- 장면마다 기능 ID와 시퀀스 메시지 번호를 적어, 상태 · 시퀀스 다이어그램 v2.4과 바로 대조할 수 있다.
- 비상정지는 "비상정지 시나리오 (제안)" 페이지(Confluence 13139970)를 따른다.

### 하지 않는 것
- 픽셀 단위 디자인 · 색상 체계 · 실제 문구 확정 (와이어프레임 수준)
- 사용자(고객) 화면 (주문 · 상품 검색). 로그인 장면만 공통으로 둔다
- 개발자 화면 (SCR-17 상태 강제 변경)
- 구현 계획 미포함 기능 (SCR-13 · 14 · 15, 새 Pode 대체 배정, 통계 화면)
- 웹 코드 작성

### 실패로 보는 경우
- 장면 흐름이 시퀀스 다이어그램 v2.4과 어긋난다 (예: 사용자 취소를 배정됨 이후에 받는 장면, 비상정지 해제 직후 바로 RUN).
- 관리자 입력 버튼이 시퀀스의 관리자 입력 메시지와 1:1로 대응하지 않는다.

## 2. 정한 내용 (사용자 결정)

- **화면 배치: B안 "관제실 한 화면형"**
  - 첫 화면(현황)은 왼쪽에 지도 · 로봇 상태 · 주문 진행 요약, 오른쪽에 **항상 보이는 알림 칸**이 있다.
- **위쪽 고정 줄**
  - IFP · 메뉴(현황 | 주문 관리 | 로봇 | 재고 | 이력) · 작업 상태(실행 중 · 서비스 일시 정지, 마감 중이면 "· 마감")
  - 오른쪽 끝에 **크게 키운 비상정지 버튼** (다른 요소보다 먼저 눈에 띄는 빨간 채움)
- **주문 관리 화면 추가**
  - "조치 필요 / 진행 중 / 완료"로 나눠 본다. 조치 필요 주문은 위로 올려 강조하고, 그 줄에서 바로 처리 버튼을 누른다.
- **알림 나누기**
  - 알림 칸은 일어난 일(이벤트)만 보여 준다. 알림의 버튼은 담당 화면으로 이동([주문 관리로] · [로봇으로] · [재고로])과 [확인]뿐이다 (11-19 변경).
  - 주문 조치는 주문 관리에서, 로봇 조치(운행 복귀 확인, 장애 처리 완료, 팔 재개, 락 해제 · 잠금)는 로봇 화면에서 한다 (11-19 변경).
  - 작업 모드 조절(서비스 일시 정지 · 재시작 · 비상정지 해제 뒤 재개)은 **위쪽 고정 줄에만** 둔다 (SCR-16, 아래 "만드는 사람의 판단" 참고).
- **도구: draw.io 와이어프레임 스토리보드** (아래 3. 방식)
- **비상정지 포함**

### "조치 필요 주문"의 기준 (다이어그램 v2.4)

| 주문 상태 | 원인 | 관리자 조치 (버튼) | 기능 · 시퀀스 |
|---|---|---|---|
| 담기 일시 중지 (FILLING_PAUSE) | 결품 (작업대 도착 때 DB 재고 확인) | 담기 재개 / 보충 불가 · 못 담음 | SCR-08 · 6-2 #14 · #18 |
| 담기 일시 중지 (FILLING_PAUSE) | 담는 도중 집기 실패 · 인식 오류 | 담기 재개 / 보충 불가 · 못 담음 | SCR-08 · 12 · 4. Phody |
| 주문 처리 보류 (HELD) | Pode 장애 (운반 중) | 강제 출고 처리 | SCR-11 · 6-5 #14 |
| 주문 처리 보류 (HELD) | Phody 장애 (담는 중) | 일부 출고 강제 처리 | SCR-12 · 6-6 #13 |
| 운반 중 (출고 구역, Phony 장애) | Phony 장애 | 강제 출고 처리 | SCR-11 · 6-7 #9 |

### 용어 (사용자 결정, 11-18)

| 화면에 쓰는 말 | 뜻 | 기능 · 상태 |
|---|---|---|
| 서비스 일시 정지 | 관리자가 전체 작업을 멈춤. 로봇은 하던 동작을 마치고 멈춘다. Phody 장애 때도 이 상태가 된다 | SCR-16, 운행 모드 PAUSE (6-6 MODE_PAUSE) |
| 팔 일시 정지 | Phody 두 팔만 멈춤 (거리 정지 · 집기 재시도 초과 · 인식 오류). 다른 로봇은 계속 | SCR-12, Phody PAUSED (PHD-08) |
| 담기 일시 중지 | 주문 상태. 결품 · 집기 실패 · 인식 오류로 그 주문의 담기가 멈춤 | SCR-08, 주문 FILLING_PAUSE |

멈추는 대상(서비스 · 팔 · 담기)을 이름 앞에 붙여 구분한다. 로봇 · 운행 상태는 "정지", 주문 상태는 "중지"를 쓴다. "담기 보류"는 주문 처리 보류(HELD)와 헷갈려 쓰지 않는다. 다이어그램 v2.4 · 기능 검토 시트도 같은 용어로 맞췄다.

## 3. 방식 (Approaches)

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **1. draw.io 와이어프레임 (선택)** | 탭 = 시나리오, 탭 안에 장면 칸을 왼쪽 → 오른쪽으로 배치 | 기존 다이어그램과 같은 버전 · CHANGELOG · PNG · Confluence 방식. 팀원이 직접 수정 | 실제 화면처럼 보이지 않음 |
| 2. HTML 시안 캡처 | 시안을 HTML로 만들고 장면별 캡처 | 실제 화면에 가깝고 웹 개발 출발점 | 팀원이 고치려면 코드 필요, 장면 연결 표시가 번거로움 |
| 3. Confluence 표 | 장면마다 표 한 줄 + 작은 그림 | 쓰기 쉬움 | 흐름이 잘 안 보이고 PNG 한 장으로 내기 어려움 |

선택 이유: 목적이 "팀 검토 → PNG 제출"이고, 지금까지 다이어그램을 같은 방식으로 관리 · 게시해 왔다.

## 5. 장면 칸 형식

한 장면 칸은 아래를 담는다.

```
┌ 장면 번호 · 제목 ───────────────────────────┐
│ [화면 와이어프레임: 위쪽 고정 줄 + 본문]      │
│  눌러야 할 곳에 번호 표시 ①                   │
├────────────────────────────────────────────┤
│ 관리자: ① 무엇을 누름                         │
│ 시스템: 무엇이 바뀜 (주문 · 로봇 상태)        │
│ 근거: SCR-08 · 6-2 #14                        │
└────────────────────────────────────────────┘
        → 다음 장면 (분기가 있으면 갈래 라벨 [ ])
```

- 장면 사이 화살표에 분기 조건을 `[보충 가능]` 처럼 적는다 (시퀀스 alt 조건과 같은 말).
- 상태 이름은 다이어그램 v2.4의 한국어 이름을 쓰고, 처음 나올 때 영문 코드를 괄호로 붙인다.

## 6. 미결 · 가정 (스토리보드에 노트로 표시)

- 지도 · Pode 위치(SCR-06)는 "일정에 따라 결정"이다. 지도 자리는 그리되 "일정에 따라" 표시를 단다.
- 비상정지 제안 P-01 ~ P-14는 팀 검토 전이다. 비상정지 탭에 "제안 페이지 기준, 채택 전" 노트를 단다.
- 결정 필요 D-06(관리자 알림 방식), D-14(결품 취소)는 해당 장면에 표시한다.
- 작업 모드 조절은 "서비스 일시 정지(하던 동작을 마치고 멈춤) → 재시작"만 그린다 (사용자 결정, 11-18). SCR-16의 "취소하고 멈춤"과 정지(STOP) 표시는 별도 논의가 필요해 스토리보드에서 뺀다. 작업 상태 표시는 실행 중 · 서비스 일시 정지 두 가지다.

## 7. 설계자 판단 (검토 질문에 대한 답)

- **재시작 · 재개 버튼 위치**: 6-6 #22 재시작(SCR-16)과 비상정지 해제 뒤 재개(제안 P-11)는 같은 작업 모드 조절(PAUSE → RUN)이므로 위쪽 고정 줄의 작업 상태 조절 한 곳에만 둔다. 알림 칸의 Phody 장애 알림은 장애 처리 완료 뒤 "위쪽에서 재시작" 안내만 보여 준다. 버튼과 시퀀스 메시지가 1:1로 대응한다.
- **비상정지 근거**: Confluence "비상정지 시나리오 (제안)" v3(2026-11-17)를 따르고, 장면 근거에는 제안 ID(P-01 ~ P-14)를 적는다. 저장소의 `design/diagrams/비상정지_순서도.drawio` v1.1은 이 페이지의 첨부 원본과 같은 판이다. 비상조치 화면은 제안 5-5의 예시(로봇별 상태 · 락 · 조치, 출고 대기 주문 [수동 출고 완료], 체크리스트, 조건을 채우면 켜지는 [해제])를 와이어프레임으로 옮긴다.
- **못 담음 처리와 보충 불가**: '2. 주문'에서 둘 다 담기 일시 중지 → "보충 불가 입력 (SCR-08)" 한 전이다. 그래서 주문 관리의 조치 필요 줄에는 원인과 상관없이 [담기 재개] [보충 불가 · 못 담음] 두 버튼을 그린다. 결품 쪽 근거는 6-2 #14 · #18, 집기 실패 · 인식 오류 쪽은 '2. 주문' 전이 이름으로 적는다. '4. Phody' 노트의 "(SCR-12)" 표기는 용어 통일 과제로 노트에 남긴다.
- **거리 정지 재개**: 주문은 담는 중을 유지하므로(PHD-08) 주문 조치가 아니다. 로봇 화면의 [팔 재개] (SCR-12, 팔 일시 정지 해제)로 그린다 (11-19: 알림 칸에서 로봇 화면으로 옮김).

## 9. v1.1 변경 (2026-11-19, 사용자 결정)

- **알림은 상태, 조치는 담당 화면.** 알림에는 이동 버튼과 [확인]만 둔다. 로봇 조치는 새 **로봇 화면**(SCR-20)에서 한다.

  - (11-19 추가) Phony에는 락 해제가 없다. Phony 장애는 관리자 수동 처리(손으로 바구니 정리 · 교환 → [강제 출고 처리] · [운행 복귀 확인])다.
  - (11-19 추가) 락 해제 · 잠금은 관리 명령이라 서비스 브리지 → fleet → 로봇으로 간다. 받을 수 있는지(멈춘 상태인지)는 fleet이 먼저 보고, 로봇 노드가 한 번 더 확인한다. 거절되면 화면에 거절 안내를 보인다 (v1.4 "명령 경로").

- **검수(검수자 3명) 뒤 바뀐 것:** 비상조치 화면의 [해제]를 [비상정지 해제]로 바꿨다(락 해제와 혼동 방지). 알림은 담당 화면에서 조치를 마치면 자동 해결되고 수동 [해결]은 없앴다. 버튼 순서 조건(일부 출고 강제 처리 전 [재시작] 꺼짐, 강제 출고 처리 전 Phony [운행 복귀 확인] 꺼짐)을 넣었다. 마감 중에는 입고 · 반출 · 수시 조정을 끈다.

### v1.3 (2026-11-19, 사용자 결정) — 마감 탭

**목적.** 마감(OMS-18 · CEN-13)을 재고 탭의 장면 세 개가 아니라 한 탭에 따로 그린다. 주문 DB 설계(`2026-11-18-order-db-design.md` 5절)와 마감 토의 결정(`2026-11-19-close-db-discussion.md` 7장)을 화면으로 옮긴다.

**사용자 결정**
- 관리자 스토리보드에 마감 탭을 더한다. 시험 탭은 10번으로 미룬다 (아래 v1.4).
- **탭 순서** (사용자가 draw.io에서 바꿈): 6. 재고 · 이력 (7 → 6) · 7. 마감 (새로) · 8. 서비스 일시 정지 · 재시작 (6 → 8) · 9. 비상정지 (8 → 9). 재고 · 이력 다음에 마감을 두어 재고 업무를 이어서 보게 했다.
- 재고 · 이력 탭의 마감 장면 7 ~ 9는 마감 탭으로 옮긴다. 재고 · 이력 탭(6번)은 수시 조정 · 이력 조회 · 알림 목록이 장면 7 ~ 9가 되고, 부제에 "[마감]은 7번 탭"을 적는다. 2번 탭의 "7번 탭 장면 10"(수시 조정)은 "6번 탭 장면 7"로 고쳤다.

**7번 탭(마감) 장면**
1. 마감 시작: 재고 화면 [마감] → 확인 창 (새 배정 멈춤, 나뉜 주문의 남은 운반 건은 계속, 반출 · 수시 조정 꺼짐, 입고는 실사 전까지 됨). 주문 처리가 배정 보류를 반영하면 "배정 보류 반영됨"
2. 남은 운반 건 기다림: 남은 운반 건 목록과 막힌 이유, 기다린 시간, 대기 중인 새 주문
3. 기다리는 중 결품: DB 재고 부족이면 추가 입고 뒤 담기 재개 (실사 전이라 입고 열림), 선반만 비었으면 창고에서 갖다 놓음
4. 실사 입력: 남은 운반 건 0 + 배정 보류 반영 뒤 엶. 빈칸으로 시작, 칸마다 바로 저장, 두 명이 나눠 셈, 입고도 꺼짐
5. 차이 사유 · 확정 조건: 사유는 고르는 목록. 안 센 상품 · 사유 없는 차이가 있으면 [마감 확정] 꺼짐
6. 마감 확정: 장부 수량 기록, 차이만큼 마감 조정
7. 대기 주문 재확인: 접수 순으로 쌓아 비교, 넘는 주문은 주문 전체 취소됨 (사유: 마감 뒤 재고 다시 확인), 뒤의 작은 주문은 계속 확인
8. 마감 취소: "입력한 수량은 재고에 반영되지 않음 (기록은 남음)", 바로 배정 다시 시작
9. 마감 기록 조회: 이력의 [마감]

**고친 문구**: 이전 재고 · 이력 탭의 "마감 이전 날짜의 입고 · 반출", "입력한 수량은 버려짐"은 설계와 달라 지웠다 (검사기 금지 문구에 넣음).

**만드는 법**: 2 · 3 · 4번 탭은 draw.io에서 손으로 고친 배치(화살표 경로 등)가 있어 다시 만들지 않고 글만 바꿨다. 나머지 탭은 `admin_scenes.py`로 다시 만들었다.

### v1.4 (2026-11-19 사용자 결정, 반영함) — 운영 모드 · 시험 화면 (SCR-16 · SCR-17 · OMS-21 · COM-06, 개발자)

**목적.** 실제 장비의 장애는 언제 날지 모르므로, 기능 개발을 위해 상태를 일부러 만들어 1 ~ 9번 탭의 운영 절차(장애 알림 → 보류 → 조치)가 실제로 도는지 확인한다 (SCR-17). 운영 중 복구 도구가 아니다. 운영 중 복구는 지금처럼 로봇 화면(SCR-20)의 절차 버튼으로만 한다.

**사용자 결정 (11-19)**
- 개발 단계 또는 **시험 모드에서만** 쓴다. 관리자 안에 등급을 두는 대신 **개발자 역할**(`account.role` = `DEV`, 주문 DB 설계 4.1)을 둔다.
- 시험 모드는 **서비스 전체**의 모드다. 켤 때 정하고, 모드마다 **DB를 따로** 쓴다. 그래서 알림 · 기록에 "[시험]" 표시를 붙이지 않는다.
- 시험 주문은 **정해 둔 시나리오**와 **개발자 직접 주문**으로 만든다 (OMS-21).
- **진입 · 해제 때 마감을 강제한다.** 시험 때문에 생긴 차이의 사유는 "시험 영향"(`TEST_RUN`).
- 시험 모드 동안 사용자 화면은 **"점검 중"**으로 안내한다 (사용자 스토리보드 설계 8절).
- **운영 모드는 8번 탭(서비스 일시 정지 · 재시작)에서 바꾸고, 진입 · 해제 마감은 모달 창으로 진행한다.**
- **로봇에게 모드를 알린다.** 로봇은 시험 모드일 때만 강제 입력을 받고, 정상 운영에서는 무시한다.
- **로봇은 강제한 값에 맞는 동작을 실제로 한다.** 예: 실제 배터리는 정상이어도 강제로 낮추면 충전하러 간다. PC가 상태 이름만 덮어쓰지 않는다 (덮어쓰면 현장과 화면이 달라짐).
- 탭: 8번 탭 이름을 **"8. 서비스 일시 정지 · 재시작 · 운영 모드"**로 넓히고, **10번 탭 "10. 시험 (개발자)"**를 더한다. 버전 v1.4, 탭 11개.

아래 "설계자 제안"은 11-19 사용자가 "이 안으로" 승인한 것이다. 같은 날 설계 검토 의견을 모두 받아들여 고쳤다: 정상 운영에서도 개발자 로그인, 시험 DB에 계정 복사, 모드를 알리는 때를 늘림, 시험에서 멈춘 로봇은 해제를 막지 않고 알림, [진입 취소], 시트 변경 이력.

**잠금 (설계자 제안)**
- 서버가 시험 모드로 켜졌을 때만 시험 메뉴와 API가 있다. 정상 운영에서는 메뉴도 API도 없다.
- 정상 운영에서도 `DEV`는 로그인할 수 있다. 정상 운영에서 개발자가 쓰는 것은 관리자 화면 전부와 8번 탭 [시험 모드로]뿐이다.
- 시험 모드 안에서도 계정 역할이 `DEV`일 때만 메뉴 "시험"이 보인다. 개발자는 관리자 화면 전부를 쓰고 "시험"을 더 본다.
- 시험 모드에서는 위쪽 고정 줄에 주황 띠 "시험 모드"가 모든 관리자 화면에 보인다 (관리자 계정에도).
- 로봇 노드도 시험 모드일 때만 강제 입력을 받는다. 정상 운영에서 받은 강제 입력은 무시하고, 무시했다는 기록을 남긴다.

**운영 모드 바꾸기 — 8번 탭 (설계자 제안)**
- 말 구분: 위쪽 줄의 **작업 모드**(RUN · PAUSE · STOP, [서비스 일시 정지] · [재시작])와 다른 **운영 모드**(정상 운영 · 시험)다. 화면에는 "운영 모드: 정상 운영"처럼 적는다.
- 버튼: [시험 모드로]는 정상 운영에서 개발자에게만 보인다. [정상 운영으로]는 시험 모드에서 관리자 · 개발자 모두에게 보인다 (개발자가 없어도 운영을 되돌릴 수 있게).
- **모달은 닫아도 끝나지 않는 단계형**이다. 진행 상태는 서버(`stock_close`)에 있어 닫았다 다시 열 수 있다. 닫혀 있는 동안 위쪽에 "시험 모드 진입 중 · [열기]" 줄이 보인다. 실사 표는 7번 탭(마감)과 같은 부품이다.
- **진입** (정상 운영 → 시험 모드, `TEST_ENTRY` 마감)
  1. [시험 모드로] → 확인 창 (새 배정 멈춤 · 끝나면 서비스가 다시 켜짐 · 그동안 고객 화면은 "점검 중")
  2. 모달: 남은 운반 건 기다림 (7번 탭 장면 2와 같은 목록)
  3. 모달: 실사 입력 · 차이 사유 → [진입 확정]. 보통 마감과 달리 대기 주문 재확인 · 배정 재개는 하지 않는다 (접수됨 주문은 운영 DB에 남음)
     - 2 · 3단계에는 **[진입 취소]**가 있다. 누르면 마감이 취소되고(`CANCELLED`) 배정을 다시 시작하며 정상 운영을 그대로 이어 간다 (7번 탭 마감 취소와 같은 처리).
  4. 서비스가 다시 켜짐 → "연결 중…" → 시험 모드로 다시 연결 (주황 띠). 시험 DB 재고 = 진입 마감 실사 수량. 관리자 · 개발자 계정은 운영 DB에서 복사해 둔다
- **해제** (시험 모드 → 정상 운영, `OPS_RESUME` 마감)
  1. [정상 운영으로] → 확인 창. 시험 DB의 진행 중 운반 건이 0이 아니면 버튼이 꺼지고 남은 수를 보인다
  2. 서비스가 다시 켜짐 → "연결 중…" → 로봇에 정상 운영 알림 (강제 값을 모두 지움)
  3. 정상 운영으로 다시 연결되면 모달이 저절로 열림: 운영 재개 마감(취소 없음), 실사 입력, 차이 사유 기본값 "시험 영향"
     - **시험에서 멈춘 로봇** (11-19 설계 검토): 강제 값을 지워도 멈춤 계열 상태(Pode CAUTION · ERROR, Phody 팔 PAUSED · ERROR, Phony ERROR)는 그대로 남는다. 해제를 막지 않고, 모달 위쪽에 "시험에서 멈춘 로봇: Pode 2 (ERROR)"처럼 보이며, 알림 목록에도 "시험 모드에서 멈춘 채 넘어옴"으로 남긴다. 되돌리는 것은 로봇 화면의 보통 복구 절차(운행 복귀 확인 · 팔 재개 · 장애 처리 완료)다. 서버는 그 멈춤이 강제 입력 때문인지 실제 장애인지 구분할 수 없으므로, 운영 재개 마감 중에 멈춤 계열 상태로 보고된 로봇은 원인과 상관없이 모두 이 목록 · 알림에 올리고, 로봇이 보고한 원인을 함께 보인다.
  4. [마감 확정] → 대기 주문 재확인 → 배정 시작
- 서비스를 내렸다 다시 켜는 방법(실행 관리)은 화면 밖이다. 스토리보드에는 "연결 중…" 장면과 노트로만 적는다.

**로봇에게 모드 알리기 (설계자 제안)**
- 로봇 노드에 운영 모드를 알리는 때. 로봇은 서비스와 함께 꺼지지 않으므로 알림으로 맞춘다.
  - 서비스가 켜질 때 (로봇 모두)
  - 로봇이 다시 연결될 때 (통신 끊김 복구 · 로봇 재시작)
  - 로봇이 보고한 모드가 서비스와 다를 때
- 로봇이 켜질 때 기본값은 **정상 운영**이다. 시험 모드는 알림을 받아야만 켜진다.
- 로봇은 상태 보고에 자기 모드를 넣는다. 다시 알린 뒤에도 서비스와 모드가 다른 로봇은 배정에서 빼고 관리자에게 알린다 ("모드가 다른 로봇", 위험한 쪽은 정상 운영인데 시험 모드로 남은 로봇).
- 정상 운영 알림을 받으면 강제 값을 모두 지우고 실제 값으로 돌아간다.

**강제 입력 (SCR-17, 설계자 제안)**
- **조건 바꾸기 (주력):** 로봇이 판단에 쓰는 값을 덮는다. 로봇의 FSM이 원래 규칙대로 상태를 바꾸고 동작하므로 상태 전이 규칙까지 시험된다. 목록(제안, 로봇 담당과 확인):
  - Pode: 배터리 값, 장애물(앞 막힘), 통신 끊김, 이동 · 도킹 실패
  - Phody 팔: 집기 실패, 인식 오류(인식 안 됨), 두 팔 거리 정지
  - Phony: 동작 실패
  - 남은 빈 바구니 수는 넣지 않는다. 다이어그램이 빈 바구니가 늘 충분하다고 가정해 부족 처리(6-3)를 구현하지 않으므로, 그것을 구현할 때 더한다 (11-19 UML 검수 뒤 사용자 결정).
- **상태 바꾸기 (보조):** 원인만 있으면 되는 **멈춤 계열**만 고른다. Pode ERROR · CAUTION(예약 상태 — CAUTION을 구현한 뒤에 씀, 11-19 사용자 결정), Phody 팔 PAUSED · ERROR, Phony ERROR와 원인. 로봇이 실제로 멈추고 그 상태를 보고한다.
  - 목적지 · 주문이 있어야 하는 상태(MOVING · DOCKING · PICKING · PLACING · TAKING_FULL 등)는 강제하지 않고 시나리오 주문으로 만든다.
- **충전 끝내기 (Pode, 11-19 사용자 결정):** 충전 중(CHARGING)인 Pode에 [충전 끝내기]를 보내면 남은 충전을 건너뛰고 대기(IDLE)로 간다. 시험 중 충전을 기다리는 시간을 줄이기 위한 것이다.
  - **실제 배터리가 이동 기준(35%, FLT-03과 같은 설정) 이상일 때만** 받는다. 판단은 로봇이 실제 배터리로 한다. 기준 미만이면 거절하고 화면에 "실제 배터리 n% — 기준 미만"을 보인다.
  - 값을 실제보다 좋게 만드는 것이 아니라 기다리는 시간만 줄이므로 "나쁜 쪽으로만" 원칙과 맞는다.
  - 배터리 조건을 강제 중이면 받지 않는다 (설계자 판단: 강제한 낮은 값으로 곧 다시 충전하러 가므로). 먼저 [강제 해제]를 안내한다.
  - 상태를 덮는 것이 아니라 로봇의 보통 전이(충전 완료 → IDLE)를 앞당기는 것이므로 강제 중 항목(`forced`)에 남지 않는다.
- **명령 경로 (11-19 사용자 결정):** 업무 명령(담기 지시, 서비스 일시 정지 때의 정지 · 이어서 지시)은 주문 처리(central)가 로봇에 보낸다. 관리 명령(락 해제 · 잠금, 운행 복귀 확인 · 다시 투입, 강제 입력, 운영 모드 알림)은 서비스 브리지 → fleet → 로봇으로 보낸다. 관리 명령의 판단은 fleet이 먼저 하고, 로봇 노드가 마지막 안전장치로 한 번 더 한다. central은 락 상태를 fleet의 로봇 상태(`/fleet/robots`)로 알고, 락이 풀린 로봇에는 업무 명령을 보내지 않는다.
- **규칙**
  - 우선순위: 강제 입력은 보통 전이보다 앞서고, 하드웨어 비상정지(COM-02)보다는 뒤다.
  - **나쁜 쪽으로만:** 실제 값과 강제 값 중 나쁜 쪽을 쓴다 (실제 배터리가 낮은데 강제로 높이면 주행 중 멈출 수 있음). 실제 장애는 언제나 강제 값보다 우선한다.
  - [강제 해제]는 강제 값만 지운다. 복귀는 정상 절차(운행 복귀 확인 · 팔 재개 · 장애 처리 완료)로 해서 복구 절차까지 시험한다.
  - 로봇은 상태 보고에 강제 중인 항목을 넣는다 (`forced`, 예: `battery=20%`). 시험 화면과 로봇 화면에 "강제" 표시로 보인다.
  - 모든 강제 입력은 확인 창(대상 · 지금 값 → 바꿀 값)을 거친다. 기록은 시험 DB의 `admin_action`(`FORCE_CONDITION` · `FORCE_STATE` · `FORCE_CLEAR` · `CHARGE_END`).
- 주문 상태를 직접 바꾸는 기능은 없다. 주문은 로봇의 실제 동작을 따라 운영 절차대로 바뀐다.

**시험 화면 (10번 탭, 메뉴 "시험", 설계자 제안)**
- 위: **시험 주문** 칸. [시나리오 실행](정해 둔 시나리오 목록에서 고름) · [직접 주문](시험 계정 · 상품 · 수량, 재고 초과 · 최대 개수 검사는 실제 주문과 같음). 최근 시험 주문 몇 줄과 [주문 관리로]. 진행은 주문 관리 화면에서 그대로 본다.
- 아래: **로봇 6대**(Pode 1 ~ 3 · Phody 왼팔 · 오른팔 · Phony) 줄마다 모드 · 실제 상태 · 강제 중 항목 · [조건 바꾸기] · [상태 바꾸기] · [강제 해제]. Pode 줄에는 충전 중일 때 [충전 끝내기]가 더 보인다 (실제 배터리가 기준 미만이면 꺼짐). 모드가 다른 로봇은 버튼이 꺼진다.

**8번 탭에 더할 장면 (설계자 제안)**
1. [시험 모드로] 확인 창 (개발자 로그인, 버튼은 개발자에게만)
2. 진입 모달: 남은 운반 건 기다림 · [진입 취소], 모달을 닫으면 위쪽 "시험 모드 진입 중 · [열기]"
3. 진입 모달: 실사 · [진입 확정] · [진입 취소]
4. "연결 중…" → 시험 모드로 다시 연결 (주황 띠, 메뉴 "시험")
5. [정상 운영으로] 확인 창 (시험 DB 진행 중 운반 건 0일 때만 켜짐)
6. 정상 운영으로 다시 연결 → 운영 재개 마감 모달: "시험에서 멈춘 로봇" 목록 · 실사, 사유 "시험 영향" → [마감 확정] → 배정 시작
- 노트: 서비스를 다시 켜는 방법은 화면 밖, 로봇이 다시 연결되면 모드를 다시 알림, 그래도 모드가 다른 로봇은 배정에서 빠지고 알림, 시험에서 멈춘 로봇은 로봇 화면의 보통 복구 절차로 되돌림.

**10번 탭 장면 (설계자 제안)**
1. 개발자로 현황 (주황 띠 "시험 모드", 메뉴 "시험")
2. 시험 화면: 시험 주문 칸 + 로봇 6대
3. [시나리오 실행] (예: 주문 3건, 나뉜 주문 1건 포함) → 확인 → 주문 관리에 시험 주문 (OMS-21)
4. [직접 주문] 시험 계정 · 상품 · 수량 → 접수됨
5. Pode 1 [조건 바꾸기] 배터리 20% (실제 80%) → 확인 창 → 출고 뒤 복귀하면 충전(CHARGING)으로 감, 줄에 "강제: 배터리 20%" (FLT-03)
6. 운반 중인 Pode 2 [상태 바꾸기] ERROR · 원인 "주행 불가" → 확인 창 → Pode 2가 실제로 멈춤 → 현황 장애 알림 · 주문 처리 보류 → 이후 3번 탭과 같음
7. Phody 왼팔 [조건 바꾸기] 집기 실패 → 재시도 초과 → 팔 일시 정지(PAUSED) → 2번 탭 장면 4의 흐름 (집기 재시도 초과는 주문 관리 [담기 재개], [팔 재개]는 거리 정지 때)
8. Pode 2 [강제 해제] → 강제 값만 지워지고 ERROR는 그대로 → 로봇 화면 [운행 복귀 확인]으로 복귀 (정상 절차)
9. 충전 중인 Pode 3 (실제 배터리 50%) [충전 끝내기] → 확인 창 → 대기(IDLE), 바로 배정 받음. 실제 배터리 30%면 버튼이 꺼지고 "기준 35% 미만"
- 0번 탭: 화면 규칙 노트에 "운영 모드(정상 운영 · 시험) · 개발자 역할 · 주황 띠" 한 줄. 정상 운영 장면은 그대로(시험 메뉴 없음).

**함께 고친 문서 (11-19)**
- 기능 검토 시트: SCR-16(운영 모드 바꾸기) · SCR-17(강제 입력) · COM-06(로봇에 모드 알림).
- 다이어그램 수정 요청 R-20: 8번 탭 모드 바꾸기, 로봇 모드 알림, 강제 입력 규칙.
- 주문 DB 설계 5절 "시험 모드"와 `admin_action` 값, 6절 인터페이스 미결.
- 사용자 스토리보드 설계 8절: 모드는 관리자 화면에서 바꾸고 그때 서비스가 다시 켜짐.
- 11-19 설계 검토 반영: 주문 DB 설계 4.1 · 4.9 · 5절 · 6절, R-20, 시트 SCR-16 · SCR-17 · COM-06과 "변경 이력" 31번 줄부터.

**만들 때 검사기**: 탭 이름 11개(8번 이름 바뀜), 버전 v1.4, 근거 줄에 SCR-17 · OMS-21 · COM-06.

**미결 (팀 확인)**: 조건 바꾸기 목록의 세부(로봇 담당), 시나리오 주문의 모양, 서비스를 다시 켜는 방법(실행 관리).

## 10. 만드는 사람에게 맡기는 것

- 장면 칸의 크기 · 배치, 와이어프레임의 세부 모양
- 버튼 · 안내 문구의 구체적 표현 (위 기준과 뜻이 같으면 됨)
- 탭 안 장면 수 (시나리오 흐름을 빠짐없이 덮는 선에서)
