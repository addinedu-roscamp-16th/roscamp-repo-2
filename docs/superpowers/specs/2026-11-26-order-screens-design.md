## 1. 목적과 이유

이번 주 목표는 주문 한 건이 화면에서 출고 완료까지 흐르는 것이다([계획] 1장). 2단계는 화면을 빼고 API · WS만 만들었고, 완료 기준 1번(고객 화면이 바뀜)을 WS 사건 순서로 대신 확인했다. 이 일은 그 자리에 **실제 화면**을 넣는다.

- 고객이 상품을 골라 주문하고, 내 주문의 상태가 접수됨 → 준비 중 → 출고 중 → 출고 완료로 저절로 바뀌는 것을 본다.
- 관리자는 같은 주문의 운반 건 진행과 Pode 상태를 본다.

백엔드(2단계 Task 5 ~ 7)는 아직 개발 중이다. 그래서 두 단계로 나눈다(사용자 결정 2026-11-26).
1. **가짜 데이터 단계**: 백엔드를 기다리는 동안 화면 안 가짜 데이터로 모양 · JS 동작 · CSS를 검토한다.
2. **실제 서버 단계**: 백엔드가 끝나면 같은 화면을 실제 API · WS에 붙여 주문 한 건을 끝까지 돌린다.

## 2. 목표 · 하지 않는 것 · 실패로 보는 경우

**목표**
1. 고객 화면(`/customer/`, `/`는 여기로 넘김)에서 상품을 검색 · 골라 주문하면 내 주문 목록에 줄이 생기고, 상태가 새로고침 없이 바뀐다(SCR-02 · 03 · 04).
2. 주문 거절(재고 초과 · 최대 수량 초과 · 점검 중 · 잠시 바쁨)을 [주문하기] 아래에 다음에 할 일과 함께 안내한다(OMS-03).
3. 관리자 화면(`/admin/`)에서 주문 진행(운반 건 단위)과 Pode 상태 · 작업 상태를 본다(SCR-06 · 07 일부).
4. 가짜 데이터 단계에서 3장의 장면을 모두 재현해 사용자가 브라우저에서 검토할 수 있다.
5. 실제 서버 단계에서 화면 코드 중 연결 부분만 바꾸고(4.2), 그리는 코드는 그대로 쓴다.

**하지 않는 것** (백엔드 검토 목록 8.3)
- 로그인(SCR-01). 계정은 주소의 `?account=<번호>`로 고른다.
- 주문 취소(SCR-05), 주문 상세 패널, 위쪽 알림 줄(SCR-09 · OMS-13), 관리자 알림 칸(SCR-10), 관리 버튼 동작(SCR-16), 지도(SCR-06 위치), 팔 로봇 카드, 관리자 다른 메뉴(주문 관리 · 로봇 · 재고 · 이력)
- 모바일 화면. PC 브라우저만.
- 프레임워크 · 빌드 도구 · npm. 정적 HTML + 순수 JS(ES 모듈)만 쓴다([계획] 5.3).
- 백엔드 코드 고치기. 화면 쪽이 필요한 API 변화는 백엔드 검토 목록 N-05 ~ N-08로 요청했다.

**실패로 보는 경우** (기술적으로 돌아가도)
- 고객 화면에 대응표에 없는 상태 말이나 내부 사정(장애 · 보류 · 일시 중지 · 마감 · 결품 처리)이 보인다(사용자 스토리보드 1절).
- 고객 화면에 다른 계정의 주문이 보인다.
- 가짜 데이터가 실제 메시지와 다른 모양이라, 실제 서버에 붙일 때 그리는 코드를 고쳐야 한다.
- 실제 서버 단계에서 주소에 `?demo`가 없는데 가짜 데이터가 켜진다.
- 응답이 늦어 [주문하기]를 두 번 눌렀을 때 주문이 두 개 생긴다(같은 `Idempotency-Key`를 다시 써야 함).

## 3. 화면과 장면

### 3.1 고객 주문 화면 (`/customer/`, 밝은 톤)

스타일 3안 시안 배치를 따른다.

```
┌ IFP 주문 ─────────────────────────────── 계정 1 · [연결됨●] ┐
│ [점검 중입니다. 잠시 뒤 다시 주문해 주세요]  ← 점검 중일 때만      │
│ 상품 검색 [상품 이름      ]          │ 내 주문                    │
│ ┌상품┐ ┌상품┐ ┌상품┐                │ ┌ 주문 O-…-0002   준비 중 ┐ │
│ │이미지│ │이미지│ │이미지│ (품절 흐림) │ │ 미니멘토스 2 · 과즙팡 1 │ │
│ │이름 │ │이름 │ │이름 │             │ │ ▮▮▯▯ 접수됨 준비 중 …  │ │
│ │재고 12│ │재고 5│ │품절 │           │ └────────────────────────┘ │
│ │[-] 2 [+]│ …                        │ ┌ 주문 O-…-0001 출고 완료 ┐ │
│ 고른 상품 3개 · 한 주문 최대 8개 [주문하기] │ …                      │
│ (거절 안내 자리)                     │                            │
└──────────────────────────────────────────────────────────────────┘
```

- 상품 카드: 이미지 · 이름 · 재고(`stock_qty`, 0이면 "품절"이고 카드가 흐려지며 수량을 못 고름) · 수량 버튼.
- 수량 버튼은 재고와 남은 최대 수량(`max_order_items` − 다른 상품에 고른 합) 안에서만 올라간다.
- 이름 검색: 입력한 글자가 이름에 들어간 상품만 보인다(화면 안에서 거름).
- 내 주문 줄: 주문 번호 · 상태 말 / 품목 한 줄 / 4칸 진행 막대(접수됨 · 준비 중 · 출고 중 · 출고 완료). 시안의 "주문 번호 누르면 상세"는 이번 주 없음(밑줄 없음).
- "일부 출고" · "취소됨"은 진행 막대 대신 상태 말만 보인다(이번 주에는 나오지 않지만 대응표에 있으므로 그린다).
- 최근 주문이 위에 온다(`created_at` 역순).
- 연결 표시: 위쪽 오른쪽에 연결됨 · 다시 연결 중을 작게 보인다. 다시 연결 중에는 [주문하기]를 막는다.

**상태 말 규칙**: 화면은 서버가 준 `status_text`를 그대로 보이고 스스로 만들지 않는다. 다만 진행 막대 칸 수를 정하려고 상태 말 → 칸 수 표를 공용 모듈 한 곳에 둔다(접수됨 1 · 준비 중 2 · 출고 중 3 · 출고 완료 4). 표에 없는 말이 오면 막대 없이 말만 보이고 콘솔에 경고를 남긴다.

**주문 보내기 순서**
1. [주문하기]를 누르면 새 UUID를 만들어 `Idempotency-Key`로 쓰고, 버튼을 "주문 중…"으로 막는다.
2. 202: 고른 수량을 0으로 돌린다. 내 주문에 줄을 넣는다(품목은 보낸 본문, 상태는 접수됨). 같은 번호의 `order_changed`가 먼저 와 있었으면 그 상태를 쓴다.
3. 503 `BUSY`: `Retry-After`초 뒤 **같은 키 · 같은 본문**으로 다시 보낸다(최대 3번). 그 동안 "잠시 기다려 주세요"를 보인다.
4. 응답이 없거나 망 오류: 같은 키로 한 번 다시 보낸다. 그래도 실패하면 "주문이 접수됐는지 확인 중입니다"를 보이고 스냅샷을 다시 읽은 뒤 버튼을 푼다. 응답만 잃었으면 서버에 주문이 이미 있을 수 있으므로, **고른 상품 · 수량이 그대로인 동안은 같은 키를 다시 쓴다.** 키는 202를 받거나 고른 상품 · 수량이 바뀔 때만 새로 만든다(만드는 사람 질문 2, 제 판단). 409 `IDEMPOTENCY_CONFLICT`는 이 규칙에서는 나오지 않아야 하므로 그 밖 오류로 안내하고 키를 버린다.
5. 그 밖의 거절은 3.3 표대로 안내하고 버튼을 푼다.

**모르는 주문 번호**: `order_changed`가 모르는 `order_id`로 오면 2초 동안 202 답을 기다린다. 그래도 모르면 `GET /api/snapshot?view=customer&account_id=…`를 다시 읽는다(백엔드 검토 목록 8.2 N-06 보충).

### 3.2 관리자 상태 표시 (`/admin/`, 다크 톤)

스타일 3안 관리자 시안의 "현황" 화면에서 이번 주 데이터가 있는 부분만 그린다.

```
┌ IFP 관제 [현황] 주문 관리 · 로봇 · 재고 · 이력(흐림) ● 실행 중  [서비스 일시 정지](막힘) [비상정지](막힘) ┐
│ 알림                │ 로봇 상태                                                     │
│ (이번 주 없음)       │ [Pode 1 대기 82%] [Pode 2 운반 중 #O-…-1] [Pode 3 …]          │
│                     │ 주문 진행                                                      │
│                     │ ┌조치 필요 n┐ ┌진행 중 n┐ ┌접수됨 n┐ ┌완료 n (최근 24시간)┐    │
│                     │ │O-…-1 담기 일시 중지│ │O-…-2 담는 중 · Pode 1│ │O-…-3│ …      │
│ 재고: A 20 · B 18 … │                                                               │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

- 작업 상태: `work_state.system_mode`(NORMAL → "실행 중", TEST → "시험 모드"). 이번 주는 켤 때 정해져 바뀌지 않는다.
- 로봇 카드: `robots`의 항목마다 하나. 이번 주 `robots`에는 Pode만 온다(2단계 설계 11장). 그래서 거르지 않고 모두 그리며, 이름 자리에 `robot_id`를 그대로 보인다(`fake_fleet`이면 `fake1`). 팔 카드와 이름 표는 `RobotStatus`에 `kind`가 생긴 뒤 정한다. 카드 내용은 이름 · 상태 · 보조 줄(배터리 또는 맡은 운반 건). `fault`가 `NONE`이 아니면 빨강 "오류"류, 아니면 `fsm_state`. `fsm_state` → 화면 말 표는 공용 모듈에 두고, 표에 없는 값은 원래 값을 그대로 보인다(관제 FSM 값 목록은 만드는 사람이 `fleet_core`에서 확인).
- 주문 진행: 운반 건(`trips`) 단위 카드. 칸은 관리자 스토리보드 "조치 필요 · 진행 중 · 접수됨"에 이번 주 끝난 것을 볼 "완료" 칸을 더한다(제 판단).
  - 조치 필요: `FILLING_PAUSE` · `HELD`
  - 진행 중: `ASSIGNED` · `FILLING` · `TRANSPORTING`
  - 접수됨: `RECEIVED`
  - 완료: `SHIPPED` · `PARTIAL` · `CANCELLED`
  - 카드 말은 관리자 스토리보드의 상태 이름(배정됨 · 담는 중 · 담기 일시 중지 · 주문 처리 보류 · 운반 중 · 출고됨 · 일부 출고됨 · 취소됨)과 로봇 번호, 품목.
- 재고: 왼쪽 아래에 상품별 재고 한 줄(`stock`). 알림 칸은 "이번 주 없음"으로 비운다.

### 3.3 고객 거절 안내 문구

| 경우 | 안내 (다음 할 일을 말함) |
|---|---|
| 422 `OUT_OF_STOCK` | "<상품> 재고가 <n>개뿐입니다. 수량을 줄여 다시 주문해 주세요." 고른 수량을 `detail`의 재고까지 낮춤(사용자 스토리보드 7절) |
| 422 `OVER_MAX_ITEMS` | "한 주문은 최대 <n>개까지입니다." (수량 버튼이 막으므로 보통 안 나옴) |
| 422 `UNKNOWN_PRODUCT` | "상품 정보가 바뀌었습니다. 화면을 새로 불러옵니다." → 스냅샷 다시 읽기 |
| 503 `MAINTENANCE` | "점검 중입니다. 잠시 뒤 다시 주문해 주세요." 위쪽 점검 줄도 켬 |
| 503 `BUSY` (3번 넘김) | "주문이 몰려 처리하지 못했습니다. 다시 눌러 주세요." |
| 404 `UNKNOWN_ACCOUNT` · 400 · 409 · 그 밖 | "주문을 보내지 못했습니다. (코드)" 개발 중 확인용으로 `code`를 보임 |

`detail`의 정확한 모양은 백엔드 구현(`web/app.py`)에서 확인해 맞춘다.

## 4. 구조

### 4.1 파일

백엔드 검토 목록 N-07 제안대로 웹이 내주는 폴더에 둔다.

```
pc/service_bridge/service_bridge/web/static/
├─ common/
│  ├─ source.js      메시지 출처: 실제(fetch · WebSocket) / 가짜(demo) 고르기
│  ├─ live.js        실제 연결: 스냅샷 · WS · 다시 연결 · 주문 보내기
│  ├─ demo.js        가짜 데이터: 장면 대본을 시간차로 흘림, 주문 보내기 흉내
│  ├─ words.js       상태 말 → 진행 칸, 관리자 상태 이름, fsm_state 말 (표는 여기 한 곳)
│  └─ base.css       공용 초기화 · 글꼴
├─ customer/  index.html · app.js · style.css (밝은 톤)
├─ admin/     index.html · app.js · style.css (다크 톤)
└─ img/       상품 이미지 <kind>.png (없으면 시안처럼 "상품 이미지" 자리 상자)
```

- `static/index.html`은 고객 화면으로 넘기는 작은 파일이다. 주소의 `?…`를 그대로 붙여 `customer/`로 보낸다.
- **주소와 경로** (만드는 사람 질문 1, 제 판단)
  - `static/` 폴더 전체를 웹 뿌리(`/`)에 그대로 붙인다(FastAPI `StaticFiles(directory=…, html=True)`를 `/`에, API · WS 경로보다 뒤에 마운트). 그러면 고객 `/customer/`, 관리자 `/admin/`, `/`는 고객으로 넘어간다. N-07 제안을 이 모양으로 백엔드 검토 목록에 고친다.
  - HTML · JS · CSS 안의 모든 경로는 **상대 경로**(`../common/source.js`, `../img/A.png`)로 쓴다. 그래서 `python3 -m http.server`로 띄우든 실제 서버에 붙이든 같은 파일이 그대로 돈다.
  - API · WS 주소만 `location`에서 만든 절대 경로(`/api/…`, `/ws/…`)다. 이것은 `live.js` 한 곳에만 있다.
- 이 폴더 밖(백엔드 `web/*.py`, `setup.py`)은 고치지 않는다. 마운트(N-07)는 백엔드 담당이 한다.
- 실제 서버 단계 전까지 파일을 띄우는 방법: `static/` 폴더에서 `python3 -m http.server`를 켜고 `/customer/?demo=…`로 연다. 가짜 데이터만 쓰므로 CORS 문제가 없다.

### 4.2 메시지 출처 하나로 모음

```
demo.js (장면 대본) ─┐
                     ├─▶ source.js ─▶ onMessage({type, seq?, ts, data}) ─▶ 그리기
live.js (WS · fetch) ┘                placeOrder(body, key) → {status, body, headers}
```

- 그리는 코드(`customer/app.js` · `admin/app.js`)는 `source.js`가 주는 두 가지만 안다.
  - `onMessage(handler)`: 명세 3.1 겉모양 그대로의 메시지. 첫 메시지는 `snapshot`.
  - `placeOrder(body, key)`: 고객만. 실제 HTTP 응답과 같은 `{status, body, headers}`.
- `?demo=<장면>`이 있으면 `demo.js`, 없으면 `live.js`를 쓴다. 기본은 실제 연결이다.
- 가짜 메시지 모양은 2단계 설계 5.5 · 7장, [계획] 5.2, 백엔드 검토 목록 8.2(N-05 · N-06 · N-08 반영 모양)를 따른다. 백엔드가 N-05 ~ N-08을 다르게 정하면 `demo.js`와 그리는 코드를 함께 고친다.

### 4.3 가짜 데이터 장면 (`?demo=<이름>`)

| 이름 | 화면 | 흐름 |
|---|---|---|
| `normal` (기본) | 고객 · 관리자 | 스냅샷(상품 3종 · 지난 주문 하나) → 주문하면 1 ~ 2초 간격으로 접수됨 → 준비 중 → 출고 중 → 출고 완료. 관리자는 같은 흐름을 운반 건 · Pode 카드로 |
| `stock` | 고객 | 재고보다 많이 고르게 해 둔 뒤 주문 → 422 `OUT_OF_STOCK`, 수량 낮춤 |
| `busy` | 고객 | 첫 두 번 503 `BUSY`, 세 번째 202. 같은 키로 다시 보내는지 콘솔로 보임 |
| `maintenance` | 고객 · 관리자 | 스냅샷 `notice` MAINTENANCE · `customer_notice`, 주문 → 503 `MAINTENANCE`. 관리자는 "시험 모드" |
| `reconnect` | 고객 · 관리자 | 흐름 중간에 끊김 → "다시 연결 중" → 3초 뒤 스냅샷 다시 받아 이어짐 |
| `race` | 고객 | `order_changed`(접수됨)가 202보다 먼저 옴 → 줄이 하나만 생김 |
| `many` | 고객 · 관리자 | 주문 여러 개 · 운반 건 여러 개(8개 주문 → 운반 건 2개), 조치 필요 칸에 `FILLING_PAUSE` · `HELD` 카드, 끝난 주문 |

- **화면마다 따로 돈다** (사용자 결정 2026-11-26). 고객 · 관리자 화면은 각자 자기 대본만 돌리고 서로 잇지 않는다(탭 사이 공유 상태 없음). 관리자 대본은 주문이 들어와 진행되는 흐름을 스스로 재생한다. 두 화면이 함께 움직이는지는 실제 서버 단계에서 확인한다.
- 가짜 상품 이름은 스토리보드의 세 상품(미니멘토스 레인보우 · 과즙팡 비타민 마이구미 · 자유시간 Mini)을 쓴다. 실제 서버의 시험 상품은 seed의 A ~ D다.
- 가짜 데이터 단계에서는 화면 위쪽에 "가짜 데이터: <장면>" 띠를 보여 실제와 헷갈리지 않게 한다.

### 4.4 실제 연결 (`live.js`)

- 주소: 화면과 같은 출처. `GET /api/snapshot`, `POST /api/orders`, `ws(s)://<host>/ws/customer?account_id=…` · `/ws/admin`.
- 고객 계정: 주소 `?account=<번호>`. 번호는 숫자 `account_id`다. 머리에는 "계정 <번호>"를 보인다(계정 이름을 주는 API가 없음). 없으면 "주소에 ?account=번호를 붙여 주세요"를 보이고 연결하지 않는다.
- 다시 연결: WS가 닫히면 1 → 2 → 5초 간격(최대 5초)으로 다시 붙는다. 붙으면 첫 메시지 스냅샷으로 화면 전체를 다시 그린다(`since_seq`는 다음 주). 닫힘 코드 4404(모르는 계정)는 다시 붙지 않고 안내한다.
- 같은 `seq`를 두 번 받으면 두 번째는 버린다(마지막 `seq`를 기억, 스냅샷을 받으면 초기화).
- **N-05 ~ N-08이 아직 없을 때의 대체 표시** (만드는 사람 질문 4, 제 판단). 실제 서버 단계는 N-05 ~ N-08이 들어간 뒤 시작하는 것이 원칙이다. 다만 그리는 코드는 칸이 없어도 멈추지 않게 한다.
  - `name` 없음 → "상품 <product_id>", 이미지는 자리 상자, 검색은 이 이름으로
  - `items` 없음 → 내 주문의 품목 줄을 비움(이 브라우저에서 넣은 주문은 보낸 본문으로 채움)
  - `created_at` 없음 → 받은 순서를 거꾸로
  - `limits` 없음 → 최대 수량 8, 콘솔에 경고
  - 가짜 데이터 장면을 따로 두지 않는다. 대체 표시는 실제 서버 단계에서 확인한다.

## 5. 확인 방법

자동 브라우저 시험 도구(node · Playwright)가 없다. 확인은 앱 안 브라우저 창으로 한다.

**가짜 데이터 단계**
- 4.3 장면마다 화면을 열어 눌러 보고, 캡처를 남겨 사용자에게 보인다.
- 콘솔 오류가 없는지 본다.
- 고객 화면 검사(손으로): 상태 말이 대응표 말뿐인지, 내부 말이 없는지, [취소]가 없는지.
- 스타일: 3안 시안과 나란히 놓고 색 · 간격 · 글자 크기를 비교한다. 1440 × 900 기준.

**실제 서버 단계** (백엔드 Task 7과 N-07이 들어간 뒤, 별도 시험 계획)
- 브리지 `mode:=NORMAL` · `central` · `fake_fleet`을 켜고 `http://localhost:8000/customer/?account=<tester의 account_id>`에서 주문 → 출고 완료까지. 관리자 화면을 옆에 띄워 함께 본다.
- `mode:=TEST`로 켜서 점검 중 안내.
- 브리지를 껐다 켜서 다시 연결 · 스냅샷.
- 재고 초과: 재고보다 많이 주문.
- 가짜 데이터 단계에서 미뤄 둔 것: HTTP 오류 모양(`detail`), 실제 다시 연결, 같은 키 다시 보내기.

## 6. 방식 (Approaches)

| 안 | 내용 | 장점 | 대가 |
|---|---|---|---|
| **화면 안 가짜 데이터 + 실제 서버 대기 (선택)** | 백엔드가 끝날 때까지 화면 안 가짜 데이터로 검토하고, 끝나면 연결 부분만 실제로 바꿈 | 따로 만들 서버가 없어 가장 가볍다. 지금 바로 모양 · 동작을 검토한다. 그리는 코드는 실제 서버 단계에서도 그대로 쓴다 | HTTP · WS 오류 처리, 다시 연결, 같은 키 다시 보내기는 실제 서버 단계에서야 확인된다 |
| 가짜 서버로 먼저 | 설계 모양대로 답하는 시험용 FastAPI 서버를 만들어 붙임 | 지금도 HTTP · WS 길까지 시험한다 | 서버를 하나 더 만들고 백엔드와 두 벌로 맞춰야 한다 |
| 실제 서버만 기다림 | Task 6 · 7 뒤에 바로 실제 서버로 만듦 | 만드는 것이 가장 적다 | 그동안 화면 일이 멈춘다. 거절 · 끊김 장면 재현이 어렵다 |

사용자가 첫 안을 골랐다(2026-11-26). 가짜 데이터가 실제 메시지와 같은 모양이어야 한다는 조건(4.2)을 붙였다.

## 7. 정한 사람

**사용자가 정한 것 (2026-11-26)**
- 화면은 2단계 API에 붙여 주문 한 건을 돌려 보는 실제 화면이다.
- 백엔드 완료를 기다리고, 그동안 화면 안 가짜 데이터로 화면을 검토한다.
- 화면 쪽 요청 · API 제안은 백엔드 검토 목록에 둔다(v0.10 8장).
- 가짜 데이터는 화면마다 따로 돌리고 두 화면을 잇지 않는다(4.3).

**이 문서에서 제가 정한 것** (검토 때 확인 부탁드립니다)
- 이번 주 화면 범위: 고객 주문 화면 · 관리자 현황(로봇 · 주문 진행 · 재고)만. 빼는 것은 백엔드 검토 목록 8.3
- 주소: 고객 `/customer/`(`/`는 여기로 넘김), 관리자 `/admin/`, 계정 `?account=<account_id 숫자>`, 가짜 데이터 `?demo=`
- 화면 파일 안의 경로는 모두 상대 경로, API · WS 주소는 `live.js` 한 곳
- 망 오류 뒤에는 고른 상품 · 수량이 그대로인 동안 같은 `Idempotency-Key`를 다시 씀
- N-05 ~ N-08이 없을 때의 대체 표시(4.4)
- 관리자 로봇 카드는 `robots`를 거르지 않고 모두 그리며 이름은 `robot_id` 그대로
- 파일 위치 `web/static/`과 모듈 나누기(4.1)
- 4.3 가짜 데이터 장면 목록
- `BUSY` 다시 보내기 최대 3번, 망 오류 때 같은 키로 한 번 더
- 관리자 주문 진행에 "완료" 칸을 더함
- 고객 거절 문구(3.3), 연결 표시, "가짜 데이터" 띠
- 확인은 앱 안 브라우저로 손으로 하고 캡처를 남김
