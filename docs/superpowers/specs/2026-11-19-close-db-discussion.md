## 2. 합의한 것

| # | 내용 | 누가 냄 |
|---|---|---|
| 1 | **입고에도 사유 자리가 필요하다.** 지금 설계는 반출 사유만 있다. 사유 칼럼 하나(`reason`)를 두고 종류마다 허용 값을 CHECK로 건다. 입고: 정기 입고 · 보충 · 입력 오류 · 기타, 반출: 파손 · 유통기한 · 입력 오류 · 기타. 기타는 설명 필수 | A · B |
| 2 | **"마감 이전" 막기는 날짜가 아니라 시각으로.** 날짜로 막으면 하루 두 번 마감할 때 오후 입고를 못 넣는다. 입고 창에 날짜 칸도 없으니 `business_date`는 없앤다. 서버가 UTC라 날짜 계산이 9시간 어긋나는 문제도 같이 없어진다 | A · B · C |
| 3 | **마감 중에는 입고 · 반출 · 수시 조정 · 바로잡기를 DB가 막는다** (화면 버튼만 끄면 다른 관리자 화면에서 들어올 수 있다). 출고 차감은 받는다 (남은 주문, 비상정지 수동 출고) | A · B |
| 4 | **재고는 원장 트리거 한 길로만 바꾼다.** 원장에 한 줄 넣으면 트리거가 상품 재고를 바꾸고 `qty_after`를 채운다. 원장은 고치거나 지울 수 없다. 마감 시작 · 확정 · 취소와 원장 쓰기는 같은 잠금으로 줄을 세운다 | B |
| 5 | **실사 입력은 그때그때 저장하고, 장부 수량은 확정 순간에 찍는다.** 새로 고침 · 두 명이 나눠 세기를 지원하면서도 장부 수량이 낡지 않는다. 확정 때 DB가 "모든 상품을 셌나 · 차이에 사유가 있나 · 진행 중 주문이 0건인가"를 검사한다. 실제 수량 칸은 빈칸으로 시작한다 (DB 값으로 미리 채우면 안 세고도 차이 0이 된다) | A · B · C |
| 6 | **차이 사유는 고르는 목록.** 자유 글이면 "인식 오류가 몇 번이었나"를 셀 수 없다. 값은 팀 확인 필요 (안: 재고 조사 차이 · 인식 오류 · 파손 발견 · 분실 · 입력 오류 · 기타) | A · B |
| 7 | **결품 중 수시 조정은 막는다.** 수시 조정의 기준은 "재고 − 바구니에 담긴 수"인데, fleet-v1은 출고 전에는 담은 수를 알려 주지 않는다. 그 상품을 담는 진행 중 주문이 있으면 수시 조정을 막고, 하는 경우에는 그때의 재고와 바구니 수를 따로 남긴다. 화면은 "재고 2 (바구니 1) · 선반에 있어야 할 수 1" | A · B · C |
| 8 | **실사를 여는 최소 조건**: DB 기준 진행 중 주문 0건 + central이 "보류를 주문판에 반영했다"고 답한 시각(`hold_acked_at`)이 있음. central과 수를 자동으로 맞춰 보는 것은 나중에 | B · C |
| 9 | **central 통보는 "지금 상태"를 다시 보내는 방식.** central은 DB가 없어 재시작하면 보류 여부를 잃는다. 웹이 "보류 여부 + 배정할 접수됨 목록"을 보내고, central이 반영했다고 답한 시각을 `stock_close`에 적는다. 답이 없으면 웹이 다시 보낸다 | B · C |
| 10 | **끝난 주문에 늦게 온 출고 보고는 덮어쓰지 않는다.** 같은 결과가 다시 온 것(관제의 재전송)은 조용히 무시하고, 결과가 다르면 알림(`LATE_REPORT`) + 관리자 확인 뒤 출고 차감 | A · B · C |
| 11 | 마감 시작 · 확정 · 취소는 `admin_action`(버튼과 central 전달 결과)과 `stock_close`(업무 원본)에 둘 다 남긴다. 중복이 아니라 역할이 다르다 | B |
| 12 | 마감에 시간 제한은 두지 않는다. 화면에 기다린 시간을 보여 주고, 끝내려면 관리자가 마감 취소 | A · C |

## 3. 토의에서 새로 드러난 것

1. **fleet-v1에서는 "배정됨"을 알 수 없다** (C, 코드 확인함). Pode가 작업대로 가는 동안에는 관제가 그 Pode에 주문을 묶지 않으므로 `/fleet/assignments`의 주문 번호가 비어 있다. 주문은 접수됨에서 담는 중으로 바로 넘어간다. 설계안 4.6 신호 표를 고치고, 이 전이를 받아야 한다.
2. **출고 차감이 재고 0 아래로 가면 출고 보고까지 사라진다** (B). 재고 CHECK가 차감을 거절하면 같은 트랜잭션의 출고됨 기록도 함께 취소된다. 제안: 차감만 따로 시도해 실패하면 출고됨은 남기고 `NEGATIVE_STOCK` 알림을 연다.
3. **조정으로 재고가 바뀔 때도 재고 부족 알림을 열고 닫아야 한다** (A). 기준 이상으로 오르면 자동 해결, 아래로 내려가면 새로 연다 (장면 12 "조치를 마치면 자동 해결").
4. **마감 직후 입고는 두 번 셀 위험이 있다** (A). 마감 전에 선반에 올린 물건을 마감 뒤에 입고로 넣는 경우. 화면 확인 창으로 막는다 (DB 변경 없음).
5. **주문판에 무엇을 실을지 웹이 정하는 편이 낫다** (C). central은 비어 있는 패키지이고, 원본이 DB 하나면 재시작 복구가 쉽다. 인터페이스 작업에 넘길 제안.

## 4. 의견이 갈린 것 · 사용자 결정 필요

### D-1. 입력 오류를 바로잡는 기록의 모양

> 관리자가 사이다 입고를 10개 대신 100개로 넣었다.

| 안 | 기록 | 장점 | 단점 |
|---|---|---|---|
| **가. 원래 종류의 반대 (추천)** | "반출 −100, 사유 입력 오류, 원래 기록 #N" 후 "입고 +10" | 스토리보드 장면 4("반대 기록, 예: 반출 '입력 오류'")와 같다 | "반출 합계"에 입력 오류가 섞인다 → 합계를 낼 때 사유 입력 오류를 빼야 한다 |
| 나. 바로잡음 종류 | "바로잡음 −100, 원래 기록 #N" 후 "입고 +10" | 입고 · 반출 합계가 깨끗하다 | 스토리보드 장면 4와 다르다. 화면 종류 필터에 "바로잡음"을 더해야 한다 |

1차에서 A는 나, B는 가를 냈는데 2차에서 둘 다 상대 안으로 입장을 바꿔 결론이 나지 않았다 (C는 어느 쪽이든 영향 없음). **추천은 가** — 스토리보드가 우선이고, 합계 문제는 통계 화면이 없어(SCR-19) 당장 생기지 않는다.

### D-2. 마감 뒤 대기 주문 재확인 방식

> 마감 확정 뒤 콜라 재고 11개. 대기 주문 #1027 콜라 6개, #1028 콜라 6개.

| 안 | 결과 | 찬성 |
|---|---|---|
| **가. 접수 순으로 쌓아서 비교 (추천)** | #1027 배정, #1028 거절(취소됨). 넘는 주문은 건너뛰고 뒤의 작은 주문은 계속 본다 | A · C — 마감 직후 결품을 막으려는 목적에 맞다. 관제도 주문판 순서가 우선순위 |
| 나. 주문마다 따로 비교 | 둘 다 배정. #1028은 작업대에서 결품 → 일부 출고됨 | B — 접수 때도 주문마다 비교하고 예약이 없으니(OMS-07 미포함) 마감 여부로 결과가 달라지면 안 된다 |

### D-3. 상품을 담은 채 대기로 돌아간 주문 (fleet-v1)

> 운반 중 Pode가 고장 나 관리자가 치웠다. 관제는 주문을 대기로 되돌렸다. 바구니에는 상품이 들어 있다.

| 안 | 내용 | 찬성 |
|---|---|---|
| **가. 주문 처리 보류(HELD), 사유 Pode 장애 (추천)** | 보류 주문은 주문판에 싣지 않으므로 관제가 다시 담지 못한다. 진행 중으로 세므로 실사도 막힌다. 담은 게 있는지 모르면 보류로 둔다. 끝내는 길: 기존 강제 출고 처리, 또는 새 "바구니 상품을 선반에 되돌림" → 접수됨 (담은 수 0으로) | C (+ A의 되돌림 버튼) — v2.4 "운반 중 Pode 장애 → 보류"와도 맞다 |
| 나. 접수됨, 사유 재배정, 담은 수 유지 | 진행 중 정의에 "접수됨인데 담은 수 > 0"을 더한다 | B — 다만 접수됨은 주문판에 실리므로 관제가 다시 담는다 |

가를 고르면 보류 → 접수됨("선반에 되돌림") 전이가 새로 생기므로 다이어그램 수정 요청이 필요하다.

### D-4. 결품 중 수시 조정 (스토리보드 장면 10과 충돌)

합의 7대로 막으면, 장면 10("인식 오류 뒤 DB 2 · 선반 0")은 그 주문이 끝날 때까지 할 수 없다. 장면 10을 살리려면 담기 일시 중지 때 담은 수를 알려 주는 인터페이스가 필요하다 (지금 fleet-v1에는 담기 일시 중지 상태도 없다).

- 나. 장면 10을 바꾼다 (주문이 끝난 뒤 수시 조정)

## 5. 마감 DB 설계안 (합의 + 추천안 기준)

### stock_ledger (바뀜)

| 칼럼 | 바뀐 점 |
|---|---|
| entry_type | 'INBOUND', 'OUTBOUND', 'SHIP', 'CLOSE_ADJUST', 'SPOT_ADJUST' (D-1 가: `CORRECTION` 없앰) |
| reason | `outbound_reason` 대신. 'REGULAR' 정기 입고, 'RESTOCK' 보충, 'DAMAGED', 'EXPIRED', 'INPUT_ERROR', 'OTHER' |
| corrects_ledger_id | reason이 `INPUT_ERROR`일 때만, 그리고 반드시 채움. UNIQUE |
| business_date | **없앰** |
| account_id | 관리자 기록과 `LATE_REPORT` 확인 뒤 출고 차감 때 채움 |

CHECK:

```sql
CHECK (entry_type <> 'INBOUND'  OR (change_qty > 0 AND reason IN ('REGULAR','RESTOCK','INPUT_ERROR','OTHER'))),
CHECK (entry_type <> 'OUTBOUND' OR (change_qty < 0 AND reason IN ('DAMAGED','EXPIRED','INPUT_ERROR','OTHER'))),
CHECK (entry_type <> 'SHIP' OR (change_qty < 0 AND order_id IS NOT NULL)),
CHECK ((entry_type IN ('CLOSE_ADJUST','SPOT_ADJUST')) = (count_id IS NOT NULL)),
CHECK ((reason = 'INPUT_ERROR') = (corrects_ledger_id IS NOT NULL)),
CHECK (reason <> 'OTHER' OR note IS NOT NULL)
```

트리거 (BEFORE INSERT, 하나로):
1. 공유 잠금(`pg_advisory_xact_lock_shared`).
2. 진행 중 마감이 있으면 INBOUND · OUTBOUND · SPOT_ADJUST 거절 (SHIP · CLOSE_ADJUST는 받음).
3. 바로잡기면: 원래 기록이 같은 상품, 입고 또는 반출, 부호 반대, 같은 수량인지 확인. 원래 기록이 마지막 확정 마감보다 앞서면 거절.
4. `product.stock_qty`를 바꾸고 `qty_after`를 채움.

UPDATE · DELETE 금지 트리거. `product.stock_qty`는 이 경로로만.

### stock_close (바뀜)

| 칼럼 | 바뀐 점 |
|---|---|
| business_date | **없앰** (시각 칼럼으로 충분) |
| counting_started_at | 새로. 실사를 연 시각 (이력에 "기다린 시간" 표시용) |
| hold_acked_at | 새로. central이 배정 보류를 주문판에 반영했다고 답한 시각. 이 값이 있어야 실사를 연다 |
| release_acked_at | 새로. 확정 · 취소 뒤 central이 배정 재개를 반영했다고 답한 시각. 비어 있으면 웹이 다시 보냄 |
| note | 취소 사유 |

`CHECK ((status = 'IN_PROGRESS') = (finished_at IS NULL))`. 시작 · 확정 · 취소는 배타 잠금(`pg_advisory_xact_lock`)을 먼저 잡는다. 나중에: `central_active_count` · `central_active_at` · `central_active_ids`.

### stock_count (바뀜)

| 칼럼 | 바뀐 점 |
|---|---|
| counted_qty | 마감 중 임시 저장 때 NULL 허용 |
| book_qty | 확정 때 채움 (마감). 수시 조정은 그 순간의 `stock_qty` |
| in_transit_qty | 새로. 수시 조정 때 바구니에 있던 수. 마감이면 0 |
| diff_qty | `counted_qty − (book_qty − in_transit_qty)` 생성 칼럼 |
| reason | 고르는 목록 (합의 6, 값은 팀 확인) |
| account_id · updated_at | 마지막으로 입력한 관리자와 시각 (두 명이 나눠 셀 때) |

- 확정 트리거(stock_close가 CONFIRMED로 바뀔 때): 모든 상품에 행이 있고 `counted_qty`가 채워졌는지, 차이가 있는 행에 사유가 있는지, 진행 중 주문이 0건인지 확인. 하나라도 어기면 확정을 막는다.
- 마감을 취소해도 행은 감사용으로 남긴다. 원장이 취소된 마감의 행을 가리키지 못하게 막는다. 화면 문구는 "입력한 수량은 재고에 반영되지 않음" ※ (A는 버리자고 했으나, 남겨도 재고에 섞일 길이 없으므로 진행자 판단).

### 진행 중 주문 (뷰 하나로)

`v_in_flight`: status IN (ASSIGNED, FILLING, FILLING_PAUSE, TRANSPORTING, HELD). 결품 사전 확인, 실사 여는 조건, 수시 조정 막기가 같이 쓴다. (D-3 나를 고르면 "접수됨인데 담은 수 > 0"을 더한다.)

### 마감 흐름

1. **시작**: 배타 잠금 → `stock_close` IN_PROGRESS → `admin_action` CLOSE_START → central에 "보류 + 주문판 목록" 전송 → 답이 오면 `hold_acked_at`.
2. **기다림**: 남은 주문은 `v_in_flight`와 열린 알림을 함께 보여 준다. 접수됨 → 담는 중(보류 반영 전에 묶인 주문)은 받는다.
3. **실사**: `hold_acked_at` 있음 + 진행 중 0건이면 `counting_started_at`을 적고 입력을 연다. 입력은 그때그때 저장한다.
4. **확정** (한 트랜잭션): 배타 잠금 → 검사(확정 트리거) → `book_qty := stock_qty` → 차이 행만 CLOSE_ADJUST → 대기 주문 재확인(D-2) → 넘는 주문은 취소됨 `STOCK_RECHECK` + 재고 부족 알림에 합침 → 커밋 → central에 재개 전송 → 답이 오면 `release_acked_at`.
5. **취소**: CANCELLED + 사유, 재고는 그대로, central에 재개 전송.

### 마감 밖의 규칙 (같이 고침)

- 접수됨 → 담는 중 전이를 받는다 (3절 1번). 4.6 신호 표의 "배정됨 = TO_WORK"를 고친다.
- 출고 차감 실패 시 출고됨은 남기고 `NEGATIVE_STOCK` 알림 (3절 2번).
- 재고 부족 알림: 재고가 바뀐 모든 기록(입고 · 반출 · 출고 차감 · 조정) 뒤에 열고 닫는다 (3절 3번).
- 늦은 출고 보고: 같은 결과면 무시, 다르면 `LATE_REPORT` 알림 (합의 10).

## 6. 인터페이스 작업에 넘길 것

- central ↔ 웹: "보류 여부 + 주문판 목록" 보내기와 반영 답 (hold · release). central 재시작 때 웹에 먼저 묻기
- 담기 일시 중지 상태와 그때까지 담은 수 (D-4, 결품 사전 확인 전제와 같은 문제)
- 나중에: central이 보는 진행 중 주문 수 · 목록 (자동 대조)

## 7. 결정 결과 (2026-11-19)

사용자가 추천안을 모두 받았다. 최종 설계는 `2026-11-18-order-db-design.md`에 반영했고, 이 문서 5장은 토의 당시의 설계안으로 남긴다.

| # | 결정 |
|---|---|
| D-1 | 가. 입력 오류는 원래 종류의 반대 기록 (`CORRECTION` 종류 없음) |
| D-2 | 가. 마감 뒤 재확인은 접수 순으로 쌓아 비교, 넘는 주문은 건너뜀 |
| D-3 | 가. 보류(Pode 장애) + "선반에 되돌림"(보류 → 접수됨). 다이어그램 수정 요청 R-16 |
| D-4 | 가. 결품 중 수시 조정은 막고, 담은 수를 알리는 인터페이스가 생기면 연다 |
| D-5 | 가. 바구니 용량을 넘는 주문은 운반 건(바구니 하나 분량)으로 나누고, 운반 건 테이블에 Pode · 상태 · 담은 수량을 둔다. 주문 상태는 운반 건 요약. R-15 |
| D-6 | 주문 한 건의 최대 상품 개수 · 바구니 하나의 최대 상품 개수는 DB 설정 테이블(`app_setting`) |

함께 정한 것:

- **시작된 나뉜 주문은 마감 중에도 남은 운반 건까지 끝내고, 실사는 그 뒤에 연다.** 마감 뒤 재확인은 아직 시작하지 않은 주문만, 주문 전체 단위. 이로써 주문 하나가 마감 앞뒤로 갈라지는 경우(일부 출고 + 거절)가 생기지 않는다. R-17
- **재고의 기준은 창고다.** 창고와 작업대 선반 사이를 오가는 수량은 관리하지 않는다. 결품 때 선반만 비었으면 창고에서 갖다 놓으며 입고가 아니다. DB 재고가 부족하면 창고에도 없으므로 추가 입고가 필요하다. R-18
  - **합의 3을 고침: 입고는 실사를 열기 전까지 받는다** (사용자 결정). 마감 기다리는 중 DB 재고 부족 결품을 추가 입고로 채울 수 있게 한다. 반출 · 수시 조정은 마감 시작부터 막는다.
  - 입고 사유 "보충"(`RESTOCK`)은 창고 보충과 같은 말이라 "추가 입고"(`ADDITIONAL`, 비정기 입고)로 바꿨다 (사용자 결정).
  - 수시 조정 · 마감 실사는 창고(작업대 선반 포함) 전체를 센다.
- 진행 중 판단(`v_in_flight`)은 주문이 아니라 운반 건 기준이다.
