## 사용자가 원하는 동작 (확정)

- 두 팔이 **병렬**로 움직인다. 한 팔이 움직일 때 다른 팔이 멈추는 직렬 진행은 원하지 않는다.
  - 예: 왼팔이 C(내려가기 · 그리퍼 열기 · 올라가기)를 하는 동안 오른팔 A(접근 · 미세조정 · 잡기)가 **멈추지 않고** 계속 진행한다.
  - 예: 왼팔이 리프트하는 동안 오른팔이 미세조정을 하고 있어야 한다.
- 유일한 제약: **B끼리만 겹치지 않는다.** (B와 상대 팔 A/C는 겹쳐도 된다.)
- 팔이 따로 움직일 때 충돌 검사: **상대 팔의 현재→목표 남은 경로 전체**와 모든 조합을 검사한다(1° 간격). 현재·목표 자세만 보는 방식은 쓰지 않는다.
- 최후의 목표: 두 팔이 서로 피하며 움직인다(다른 팔이 비켜 주거나, B끼리 겹쳐도 서로 피해 도착).
- 작업 방식: 요청하지 않은 검사·제한·장치를 넣지 않는다. 넣어야 하면 먼저 설명하고 승인받는다([AGENTS.md](../../AGENTS.md) 규칙).

## 오늘 할 일 1: B도 팔별 실행 (게이트)

### 현재 문제 (11-25 20:16 로그로 확인)

게이트(`jetcobot_dual_control/execution_gate.py`)가 B 궤적(`guarded_both_controller`)을 **단독 실행**한다. 단독 실행은 두 팔 lane이 모두 빌 때까지 기다리고, 실행 중에는 상대 팔의 새 골도 기다리게 한다. 그래서 왼팔 B 동안 오른팔 A가 선다.

```
20:16:27.5 Combined route 1/2: left endpoint            ← 왼팔 B 복귀 시작
20:16:27.8 right goal waiting for the running motion to finish
20:16:35.7 right joint goal ... sending                  ← 왼팔 B 끝난 뒤에야 오른팔
```

B끼리 겹치지 않는 것은 앱의 바구니 점유(`WorkState.basket_owner`)가 이미 보장한다. 게이트가 B를 단독으로 돌릴 필요는 없다.

### 할 일

- 한 팔 B 궤적(6관절 `guarded_both_controller` 요청)을 그 팔의 **lane**에서 실행한다. 상대 팔 lane(A/C 골, 그리퍼)과 동시에 돈다.
- 충돌 검사: B 경로 전체(궤적 점 폴리라인) × 상대 팔 남은 경로(현재→lane 목표)의 모든 조합. `coordinated_route.independent_arms_valid(left_points, right_points, valid)`가 폴리라인끼리 검사할 수 있다.
  - 겹치면: 상대 팔 lane이 끝날 때까지 기다렸다가 새 측정값으로 다시 검사. 그래도 안 되면 Pi로 보내지 않고 실패.
- 실행 방식: 지금 B는 `endpoint` 구간 1~2개로 실행된다(로그 `Combined route 1/2: left endpoint`). lane에서도 같은 구간 분할을 쓰되, 각 구간 출발 전 검사에 상대 팔 경로를 넣는다. 직선이 안 되면 drag 경로.
- 12관절(양팔) 궤적·골만 단독 실행으로 남긴다.
- 주의
  - 지금 `_execute_section`은 시작 자세 이탈 5°를 12관절 전체로 본다 → lane에서는 자기 팔만.
  - 큰 경로 × 큰 경로(B × 상대 접근)는 검사 수가 수천 개가 될 수 있다(19:01 양팔 골 하나에 4.3초). 실물에서 게이트 로그 `checked in …s`를 확인한다.
  - 기존 lane 구현: `_acquire / _release`(lane·단독 순서), `dispatch_lock`(검사와 출발을 한 팔씩, 교착 방지), `_arm_goal_path_valid`, `execute_arm_goal`. 이 구조를 그대로 B에 확장한다.
- 테스트: `jetcobot_dual_control/test/test_execution_gate.py` 끝의 lane 테스트에 "B lane과 상대 lane 동시 진행" 추가.

  - `serve_worker()` / `run_via_server()`
  - 소켓 `~/.cache/jetcobot_move_worker.sock`
  - ROS 노드와 관절 구독을 유지한다.
  - 앱은 단계마다 짧은 클라이언트 프로세스를 띄우고, 클라이언트는 argv를 서버로 넘긴다.
  - 20:15:39에 서버가 떠 있었다(코드가 바뀌면 첫 요청에서 서버를 새로 띄운다).

  - `_ros_context()`가 단계 시작마다 이전 관절 메시지를 버리고 **새 샘플을 기다린다**. Pi 발행이 2 Hz이고, 1.1~1.8초 공백도 자주 있다(Pi `STATE DIAG` 경고).
  - `fresh_state()`, `fresh_peer_state()`를 여러 번 호출하고, 각 호출이 새 샘플을 기다릴 수 있다.

   ```bash
   ssh jetcobot@192.168.0.33 'iw dev wlan0 get power_save; grep -n ROS_STATIC_PEERS ~/.bashrc; echo $ROS_STATIC_PEERS'
   ```
3. **Pi 각도 읽기 1.1~1.5초**: 그리퍼 동작 중이나 직후 `get_angles`가 느리다. PC 쪽은 한 팔이 1.5초 넘게 안 오면 양팔 합친 상태 발행을 멈춘다.

   - 동시 모드 중 정지 시 복구 흐름은 손대지 않았다.
5. **한 팔 실패 시 양팔 모두 정지**: 오른팔 A 계획이 실패해 일시정지하면 진행 중인 왼팔 B까지 취소된다(20:0x). 실패한 팔만 멈추게 할지 결정이 필요하다.

8. `fine_moveit_planning:=true`면 미세조정이 Pi로 직접 가서 게이트 검사를 거치지 않는다. 동시 모드는 `false`로 실행한다.
