# 2026년 11월 13일 작업 정리

## 오늘 한 일

- 오른팔 `sdk_drag_bridge`로 MoveIt 계획 경로를 SDK drag 명령으로 변환해 주행하는 실험을 이어갔다. 목표는 경로를 완벽히 재현하는 것보다, 정지와 끊김을 줄이면서 경로를 대략 따라가는 것이다.
- 속도 설정을 크게 올려도 전송 간격이 0.8초일 때는 움직임이 간헐적으로 확 가는 느낌이 남고, 속도만 높이는 것으로 전체 주행이 빨라지지 않는 것을 로그에서 확인했다.
- 속도 200, `drag_step_deg=5`, 전송 간격 0.4초 설정으로 다시 주행했다. 189개 계획점이 11개 SDK 패킷으로 변환됐고, 경로 진행 속도는 일부 구간에서 약 13~16°/s까지 나왔다. 마지막에는 `Drag path final pose measured; packets=11`로 완료됐다.
- 이 주행 로그의 corridor error는 최대 약 1.25°였다. 이는 브리지의 관절 경로 편차 지표이며, 로봇 간 실제 충돌 여유나 충돌 회피 안전성을 입증하는 값은 아니다.
- `drag_step_deg=8` 시험에서는 진행이 17.6/68.1°에서 멈춘 채 유지되다가 제한 시간 초과로 실패했다. 사용자는 물리적으로 걸린 것은 없다고 확인했다. 원인은 현재 로그만으로 확정할 수 없다.
- PC 실행 게이트에 `sdk_drag_hybrid`를 추가했다. MoveIt 충돌 장면에서 현재 자세부터 목표까지 직선 관절 경로를 검사하고, 통과하면 SDK 끝점 명령, 충돌하면 드래그 경로를 선택한다. 드래그용으로 줄이고 둥글린 경로도 전송 전에 검사하며, 검사에 실패하면 실행을 거부한다. Pi에는 두 방식을 하나의 직렬 연결로 처리하는 `sdk_drag_hybrid_bridge.py`를 추가했다.
- 오른팔 실기에서 새 하이브리드 경로를 한 번 실행했다. PC 로그에 `direct joint segment collides; validated drag detour with 46 packets`가 목표 접수와 전송 직전에 각각 출력됐고, MoveIt 실행은 `SUCCEEDED`로 끝났다. 이는 **전체 계획을 드래그로 선택한 실행**이며, 경로의 일부만 드래그로 보낸 것은 아니다.
- 실행 완료 직후 MoveIt이 최신 관절 상태를 받지 못했다는 경고가 한 번 나왔다. 최종 실행 상태는 성공이지만, 상태 시각 지연의 재현 여부는 확인하지 않았다.
- 최소 드래그 구간 시험용 `trial_minimal_drag_route.py`를 추가했다. RViz의 오른팔 또는 왼팔 계획을 받아 직선 충돌 검사로 최대 세 구간을 고른다. 기본 실행은 선택 결과만 출력하며, `--execute`를 지정해야 기존 `sdk_drag_hybrid` 게이트로 구간별 목표를 순서대로 보낸다. 드래그 구간은 경유점 축약·모서리 둥글림 후 다시 검사한다. Python 문법 검사만 완료했고 ROS 실행이나 실물 시험은 아직 하지 않았다.
- 양쪽 Pi의 끝점·드래그 액션, PC 게이트와 MoveIt 계획 토픽을 확인하고 오른팔 시험 코드를 `--execute`로 실행했다. 90초 동안 새 RViz Plan이 들어오지 않아 `No matching RViz plan received`로 종료됐다. **이 시도에서 로봇 이동 명령은 전송되지 않았다.**
- 이후 사용자가 오른팔 시험 코드를 직접 실행해 RViz Plan 303개 지점 중 `ENDPOINT 0->302` 한 구간이 선택됐고 `DONE 1/1 ENDPOINT`로 완료됐다. PC 게이트에서도 시작→끝 관절 직선 경로가 충돌하지 않는다고 두 번 판정했다. **이 실행에는 드래그 회피 구간이 없었다.** MoveIt 계획점 303개가 장애물 회피 발생을 뜻하지는 않는다.
- 다음 오른팔 시험에서는 416개 계획점이 `ENDPOINT 0->342`와 `ENDPOINT 342->415` 두 구간으로 나뉘어 모두 완료됐다. **드래그 패킷은 0개**였다. 전체 시작→끝 직선 대신 중간 계획점을 거치는 두 끝점 명령으로 실행한 사례이며, 이 로그만으로 실제 장애물 회피가 필요한 경로였는지는 확인할 수 없다.

## 해결한 이슈

- 이전처럼 명령 전송 간격 0.8초를 기다리는 시간이 주요 병목인 시험 조건을 확인하고, 전송 간격을 0.4초로 줄여 5° 간격 경로 주행을 완료했다.
- 같은 경로 종류에서 전송 수 11개로 완료된 실행 로그를 확보했다. 다만 사용자가 체감하는 끊김이 완전히 해결된 것은 아니다.
- 충돌 장면 검사에 따라 오른팔 회피 경로를 드래그로 선택하고 실행을 완료하는 기본 하이브리드 동작을 확인했다.

## 해결하지 못한 이슈

- `drag_step_deg=8` 실행이 중간 진행도에서 멈춘 원인은 미확정이다. 충돌이나 물리적 걸림으로 단정할 근거는 없다.
- 속도를 높인 뒤에도 관절 목표가 바뀌는 순간의 끊김·튀는 느낌이 남는다. 0.4초 간격 실행은 더 빨랐지만, 사용자가 원하는 수준의 부드러움에 도달했다고 확인되지는 않았다.
- 더 큰 경로점 간격이 패킷 수를 줄이면서 부드러움과 추종성을 유지할지는 아직 시험하지 않았다.
- 이번 실행은 오른팔의 한 경로 로그에 대한 확인이다. 양팔 동시 실행, 다양한 회피 경로에서의 반복성, 실제 충돌 안전성은 검증되지 않았다.
- 현재 `sdk_drag_hybrid`는 시작점에서 끝점까지 직선 경로가 충돌하면 **계획 전체를 드래그**로 실행한다. 사용자가 원하는 것은 안전한 앞·뒤 구간은 `send_goal`, 필요한 우회 구간만 드래그로 실행하는 것이다. 구간별 선택과 실행은 아직 구현되지 않았다.
- `send_goal`의 실제 펌웨어 보간 경로와 MoveIt에서 검사한 직선 관절 경로가 일치하는지 검증되지 않았다. 경유점을 줄인 드래그 경로도 샘플링 검사일 뿐 실제 연속 운동을 보증하지 않는다.
- 최소 드래그 시험 코드는 구간 전환에서 실측 자세가 계획 경계와 3° 넘게 다르면 중단한다. 3° 이내일 때는 다음 구간의 시작점을 실측 각도로 바꾸고 첫 구간 시간도 기존 0.08 rad/s 제한에 맞춰 늘린다. 기존 게이트가 변경된 구간의 충돌을 다시 검사한다. 남은 구간을 자동 재계획하는 기능은 아직 없다.

## 최소 드래그 시험 코드 사용

1. 기존 양팔 Pi의 `sdk_drag_hybrid_bridge.py`와 PC `trajectory_backend:=sdk_drag_hybrid`를 실행한다. PC의 새 터미널에서 ROS Jazzy와 `~/pinky_ws/install/setup.bash`를 source하고 `ROS_DOMAIN_ID=42` 및 기존 정적 피어를 설정한다.
2. `python3 ~/camera_code/trial_minimal_drag_route.py --arm right`를 먼저 실행하고 RViz에서 **Plan만** 누른다. 스크립트가 `ENDPOINT`, `DRAG`, `ENDPOINT` 구간과 예상 드래그 패킷 수를 출력한다. 기본 모드에서는 이동 명령을 보내지 않는다.
3. 선택 결과가 의도대로 나오면 같은 준비 상태에서 `python3 ~/camera_code/trial_minimal_drag_route.py --arm right --execute`를 실행한 뒤 RViz에서 **Plan만** 누른다. RViz의 Execute를 추가로 누르지 않는다. 스크립트가 각 구간을 기존 게이트를 통해 순서대로 보낸다.
4. 실행 중에는 구간 완료 뒤 새로운 실측 상태를 받아야 다음 구간으로 넘어간다. 전환 오차가 3°를 넘거나 게이트가 변경된 구간을 거부하면 나머지 구간은 보내지 않는다. 이 시험은 재계획 기능과 실제 경로의 안전성을 검증한 결과가 아니다.

## 11월 13일 다음 작업: 드래그를 필요한 구간에만 사용

1. 새 PC 시험 스크립트의 미리보기와 구간별 실기 결과를 확인한다. 기존 RViz Execute는 여전히 한 계획 전체에 대해 `endpoint` 또는 `drag` 한 가지를 고른다. 시험이 성립하면 구간 선택·순차 실행을 `execution_gate.py`에 통합한다.
2. MoveIt 계획의 경유점을 전환 후보로 두고, 각 후보에 대해 시작→후보 및 후보→끝의 관절 직선 경로를 현재 충돌 장면에서 샘플링 검사한다. 충돌하지 않더라도 원래 계획에서 과도하게 벗어나는 지름길은 제외한다. 안전한 앞·뒤 구간을 길게 잡되 드래그 거리와 명령 전환 횟수를 함께 줄이는 경계를 선택한다. 경유점 하나를 거치는 끝점 명령 두 번으로 충분한 경우도 비교하되, 불필요하게 많은 끝점 명령으로 쪼개지 않는다.
3. 가운데 우회 구간은 실제 Pi가 사용하는 경유점 선택·모서리 둥글림 설정으로 변환한다. 변환된 목표와 목표 사이의 보간 상태를 다시 검사한다. 검사 실패나 장면 조회 실패 시 끝점 명령으로 우회하지 말고 그 계획의 실행을 거부한다.
4. 각 구간 전환에서 실측 관절과 반대 팔 상태를 확인한다. 현재 시험 코드는 전환 오차가 3°를 넘으면 중단한다. 자동 실행으로 발전시킬 때는 **남은 구간을 실측 자세에서 재계획하고 다시 분류**한다. 정밀한 최종 목표 보정 기능은 별도 후속 과제로 둔다.
5. 처음에는 계획만 생성해 선택된 구간·충돌 검사 결과·예상 드래그 패킷 수를 로그로 확인한다. 그다음 오른팔 한 팔과 여유 있는 짧은 경로에서 실기 비교한다. 전체 드래그 대비 드래그 패킷 수, 총 시간, 전환점의 멈춤, 최종 오차, 성공/실패를 기록한다. 부드러움이 나빠지면 구간 전환 수를 더 줄인다.
