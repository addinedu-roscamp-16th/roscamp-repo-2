# 2026년 11월 20일 작업 기록

이 문서는 다음 작업자가 11월 20일의 변경과 검증 범위를 이어받기 위한 기록이다. 근거는 사용자와 주고받은 터미널 출력, PC 로컬 파일, `state_pick/sam_yaw_output/` 캡처·worker 로그다. **로컬 코드 수정·문법 검사 통과 ≠ Pi에 복사된 버전 ≠ 실물 성공**이다. 11월 19일의 PC/Pi 실행 구성과 gate 주의 사항은 [전날 기록](2026-11-19_작업정리.md)을 참고한다.

## 0. 작업 규칙 (오늘 재확인)

- AI는 Pi에 SSH/SCP 하지 않고 로봇 명령도 보내지 않는다. 필요한 것은 사용자에게 묻고 **붙여넣기만 하면 되는 전체 명령**을 준다.
- 로컬 검증은 `py_compile` 문법 검사와 로봇과 무관한 순수 계산 확인까지만 한다. **가상환경(venv)·unittest 검증은 사용자가 요청할 때만** 한다(오늘 명시). 토큰을 적당히 쓴다.
- PC 패키지 `jetcobot_dual_real`은 symlink-install이다. `execution_gate.py` 등 PC 코드 수정은 **재빌드 없이 PC launch 재시작**으로 반영된다(오늘 `colcon build` 명령을 안내했지만 필요 없다. 해도 해는 없다). Pi 파일은 사용자가 복사·재시작해야 반영된다.

## 1. 양팔 협동 상태 설계 대비 구현 현황

원래 요구사항: [양팔 협동 상태 설계](2026-11-20_양팔_협동_상태_설계.md). 구현은 `state_pick/`(기존 `multi_pick/`, `moveit_pick/`, `right_place_trial/`의 사본)에서만 했다.

| 설계 항목 | 현재 구현 | 설계와 다른 점 |
| --- | --- | --- |
| 팔별 상태 `idle`~`error`, `retrying` 제외 | `state_pick/multi_pick/state_machine.py`에 구현 | 같음 |
| 상품 좌·우 교대 배정 | `sam_multi_real.py` `_order_by_side`: 교대는 유지하고, 각 팔 차례에 남은 상품 중 **그 팔 베이스에 가까운 것**을 고름 | 첫 팔은 `--first-arm`으로 수동 지정(기준 미정 항목) |
| 상품 구역 점유·해제 | 리프트 후 실측 TCP `z ≥ see_center z − 15 mm`이면 해제(`release_pick_at_height`, 허용오차 15 mm) | 설계는 정확히 `≥ see_center z`. 실물 복귀 오차 때문에 15 mm 여유 |
| 바구니 점유·해제 | 놓은 팔이 `see_center`로 복귀한 뒤 해제 | 같음 |
| 바구니 점유 중이면 든 채 `see_center`에서 `place_waiting` | **사용 안 함.** 리프트 후 곧바로 담기(직접 담기) | 실제 동작이 순차라서 두 팔이 동시에 물체를 드는 상황이 생기지 않음 |
| 다음 팔 **담기** 경로를 미래 상태(양팔 `see_center`)에서 미리 계획 | 대신 다음 팔의 **접근** 경로를 백그라운드 계획. 가정: 놓는 팔 = SRDF `see_center`, 다음 팔 = 현재 관절. 실행 직전 실제 관절이 가정과 1° 넘게 다르면 다시 계획 | 미리 계획하는 대상이 담기 → 접근으로 바뀜 |
| 한 팔 작업 중 다른 팔도 가능한 작업 진행 | **미구현.** PC gate가 동작 목표를 한 번에 하나만 받음. 양팔 동시 동작은 PLACE의 양팔 묶음 경로(오른팔은 비켜주기)뿐 | 아래 "다음 할 일" 1단계/2단계 참고 |
| `paused`(거리 정지, 재시도 초과, `PHD-08`), `error` | 상태 전환과 계획 실패 시 `pause(..., release_pick=...)`까지 | 거리 정지·`PHD-08` 입력 연결, `paused` 복구 키는 미구현 |

이전의 "두 팔이 물체를 든 채 `see_center`에 모여 둘째 담기 경로를 미리 계획" 방식(`HOLD_RETURN`/`PREPLAN_PLACE`)은 오전에 제거했다. 이전 버전: `state_pick/multi_pick/sam_multi_real.py.before_direct_place.bak`.

### 현재 한 사이클 흐름

1. 캡처 → ROI → `M` 매칭 → 첫 접근 계획 → `E` 실행.
2. 접근 → (자동) 미세조정 → 하강·닫기·리프트.
3. 리프트 성공 → 상품 구역 해제 → 바로 PLACE worker(`right_place_trial/coordinated_right_case.py --execute --place --from-pick --arm <팔>`) 실행.
4. PLACE 로그에 `TIME plan case arrival`이 찍히면(PLACE 계획 완료, 실행 시작) 다음 상품의 접근 계획을 백그라운드로 시작.
   - 오전에는 `TIME setup` 때 시작했으나 계획끼리 겹쳐 MoveIt 응답이 끊겨서 오후에 옮겼다.
5. PLACE가 놓기·`see_center` 복귀까지 끝나면 바구니 해제 → 백그라운드 계획 채택(나이·팔·실행 허용 확인) → 다음 팔 실행. 계획이 실패했거나 쓸 수 없으면 `start_next_object`로 새로 계획.

## 2. 스테레오 매칭 문제

### 원인 진단

- 오전: 보정 파일을 보드 캡처로 여러 번 갱신했다(최종 `state_pick/moveit_pick/calibration/stereo_see_center_correction_20261117.json`, 원본 캡처 `board_capture_20261120_113655_490122`). 원본 `moveit_pick` 보정 파일은 건드리지 않았다.
- 새 도구 `state_pick/moveit_pick/compare_board_captures.py`: 보드를 움직이지 않은 채 찍은 캡처들을 비교한다. 카메라별로 관절+핸드아이로 계산한 보드 월드 자세가 얼마나 변하는지 보여 준다. **시스템 `python3`로 실행**한다(venv의 cv2에는 `ArucoDetector`가 없음).
  ```bash
  cd ~/camera_code/state_pick/moveit_pick && python3 compare_board_captures.py -n 6
  ```
- 결과:
  - 정지 상태 반복 오차: 약 0.2–1 mm, 0.26° 이하.
  - 오른팔을 갔다 오면 오른쪽 카메라가 17 mm·2.4° 어긋난 채 유지됐다.
  - 사용자 확인: 왼쪽 카메라 마운트는 손으로 흔들면 움직이고, 오른쪽은 안 움직인다.
  - 조이고 재보정한 뒤 오른팔 왕복은 1.7 mm·0.44°.
  - 그 뒤에도 11:50경 "왼팔 접근 + C 복귀" 후 에피폴라 오차 약 20 px로 매칭 0개가 재발했다. 관절은 1° 이내로 일치했다.
- 결론: 복귀할 때마다 카메라가 1–2°(사용자 체감 2–3°) 어긋나는 것은 고정 보정으로 따라갈 수 없다. 매 캡처 자가 보정을 넣었다.
- 참고: 09:59와 10:58 보드 캡처 비교는 그 사이 사용자가 보드를 건드려 무효다(AI가 처음에 "보드 높이 차이"라고 잘못 말했다가 정정).

### 매 캡처 자가 보정 (신규)

- 파일: `state_pick/multi_pick/stereo_self_correct.py`의 `correct_right_rotation`.
- `sam_multi_real.py`가 고정 보정 직후 호출한다. 끄려면 `--no-self-correct`.
- 방법:
  1. 고정된 스테레오 영상 전체에서 SIFT 매칭을 구한다.
  2. RANSAC 기본행렬로 잘못된 매칭(아웃라이어)을 걸러낸다. 이 단계는 로봇 자세를 쓰지 않는다.
  3. 오른쪽 카메라를 자기 중심에서 조금 회전시켜(3자유도, Huber 가중 Gauss-Newton) 에피폴라 오차를 최소화한다. 왼쪽 카메라가 기준이다.
- 안전장치: 다음 중 하나면 쓰지 않고 원래 자세를 쓴다.
  - 보정 회전이 상한을 넘는다.
  - 보정 후 오차 중앙값이 2 px를 넘는다.
  - 보정 후가 보정 전보다 나쁘다.
- 오프라인 결과(저장 캡처): 실패 캡처 19.0–19.6 px → 0.4 px(보정 1.56–1.57°), 정상 캡처 4.0–4.5 px → 0.4 px.
- 오후 수정: `only 50 scene matches`로 거절된 사례가 있었다. 그래서 최소 매칭 60 → 25, 회전 상한 4° → 5°, SIFT 8000개·대비 임계값 0.02, 비율 테스트 0.8로 완화했다(백업 `.before_relax.bak`). **완화 후 실물 결과는 아직 없음.**
- 로그: `STEREO SELF-CORRECTION: right camera X deg, epipolar A -> B px (N scene points)` 또는 `... not applied: <이유>`.

### 매칭 기준

| 값 | 초기 사본 | 현재 |
| --- | --- | --- |
| `--height-tolerance-mm` | 10 | 15 |
| `--reproj-px-multi` | 8 | 12 |
| `--epipolar-px` | 6 | 10 |

사용자 요청("초코바끼리 그 정도로 붙어 있진 않다")으로 완화했다. 2° 어긋남(약 20 px)을 기준 완화로 통과시키지 않고 자가 보정으로 해결한다. 기준을 20 px 이상으로 올리면 붙은 상품끼리 잘못 짝지어질 수 있다.

## 4. 오른팔 미세조정: 수직 유지 (오후)

## 5. 하드웨어·통신 진단

### J4 처짐·떨림 (부하)

- 증상: 어제는 오른팔, 오늘은 왼팔에서 J4가 순간 처진 뒤 그 자리에 고정됨. 강사 의견은 부하.
- 정지 상태 서보 측정(사용자 실행):
  - 왼팔: J4 53°C(나머지 29–41°C). 전압 J1–3 약 12.3 V, J4–6 약 7.4 V.
  - 오른팔: J4 42°C, J5 45°C. J5 7.1 V. 상태 코드 0.
- 판단: 양팔 모두 J4 부하·발열 가능성. 처짐 순간의 온도를 보려고 상태 노드에 온도 발행을 추가했다.
- `pinky_ws/src/jetcobot_dual_real/robot_bridge/read_joint_states.py`:
  - 온도 발행: `/{side}/servo_temps`(`Float64MultiArray [unix_time, J1..J6]`). 쉬는 동안 10초마다 읽고, 55°C 이상이면 `SERVO HOT` 경고(`.before_temps.bak`).
  - 한 주기에 추가 시리얼 질의 1개만(그리퍼 → 온도 → 좌표 순). 각도 발행이 밀리지 않게 하려는 것이다. LIFT 실패의 오른팔 1.5초 공백 대응(`.before_roundrobin.bak`).
  - **Pi 복사 여부는 사용자 확인 필요.** 두 Pi `~/jetcobot_dual_bridge/`에 복사 후 브리지를 재시작해야 반영된다.

### 토픽이 안 들어오는 문제 (통신)

- 증상: 팔을 놔두면 노트북에서 토픽이 끊긴다. Pi 자체 `echo`는 정상이고 브리지를 재시작하면 회복된다. 강사 의견은 DDS/QoS 확인.
- 측정:
  - 그래프 규모: 노드 16, 토픽 31, 서비스 133.
  - 대역폭: `/right/real_joint_states` 316 B/s. Pi 수신 7–8 KB/s, 송신 106/201 KB/s(대부분 카메라 gst 스트림). Pi CPU 여유. **토픽 수·대역폭은 문제 수준이 아니다.**
  - 환경: 세 대 모두 Jazzy, FastDDS 기본, `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET`, `ROS_STATIC_PEERS` 비어 있음, **WiFi 절전 on**.
  - 도메인: Pi `.bashrc`는 `ROS_DOMAIN_ID=42`, UI는 83.
  - IP: PC `wlo1` 192.168.0.15, Pi 192.168.0.33·192.168.0.22.
- QoS: Pi 발행은 RELIABLE depth 10, PC 구독은 `qos_profile_sensor_data`(BEST_EFFORT)라 WiFi에서 연속 유실 가능.
- 유력 원인: WiFi 절전 + 멀티캐스트 탐색 끊김.
- 안내한 조치(사용자 실행 여부 미확인): 세 대 모두 절전 끄기(`iw ... power_save off`, NetworkManager `wifi.powersave = 2`), `ROS_STATIC_PEERS="192.168.0.15;192.168.0.33;192.168.0.22"` 추가. 그 뒤 새 터미널, `ros2 daemon stop`, 전체 재시작.
- 권장: 공유기 DHCP에서 IP 고정, 도메인 ID 통일.
