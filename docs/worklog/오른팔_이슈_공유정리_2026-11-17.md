# 오른팔 접근·그리퍼 자세 이슈 정리

작성일: 2026-11-17  
대상: `camera_code`의 ROI → SAM2/LightGlue → 양팔 MoveIt 접근 → 미세 조정 → `G` 파지 작업

## 한눈에 보기

- **접근 위치가 크게 빗나간 문제는 개선됨.** 실제 두 로봇 베이스 간격이 모델의 30 cm와 달리 35 cm였고, 실물을 30 cm로 다시 맞춘 뒤 스테레오 보정을 새로 계산했다. 오른팔 목표를 임의로 `+Y 4 cm` 옮기는 보정은 적용하지 않았다.
- **가장 오래 반복된 문제는 오른팔의 도착 자세다.** MoveIt이 계획한 자세와 SDK가 실제로 도착한 자세가 모두 사용자가 원하는 직각에서 조금씩 다르다. 현재는 수동으로 맞춘 그리퍼 방향과 최근 두 번의 반복 오차를 이용해 오른팔 목표 회전에 사전 보정을 넣었다. 사용자는 적용 후 자세가 나아졌다고 보고했으며, 도착 회전 오차의 정량 재측정은 아직 없다.
- **로그의 실패가 모두 같은 원인은 아니다.** 목표 거부·상태 시간차·각도 도착 판정·미세 조정 기울기 제한·`G` 하강 거리 제한은 서로 다른 단계에서 발생했다. `APPROACH COMPLETE`도 실제 파지 성공을 뜻하지 않는다.

## 반복해서 발생한 문제

| 문제 | 관찰된 증상과 근거 | 확인된 원인·현재 처리 |
|---|---|---|
| 오른팔 접근 위치가 물체에서 약 3~4 cm 벗어남 | 왼팔보다 오른팔의 초기 접근 위치가 크게 달랐고, 사용자가 오른팔 베이스 `+Y` 방향 부족을 관찰 | 실물 베이스 간격이 35 cm였으나 모델은 30 cm였다. 실물을 30 cm로 맞춘 뒤 위치가 개선됐다고 사용자가 확인. 고정 스테레오 보정도 `capture_20261117_145527_358826`으로 갱신 |
| 오른팔이 계획 관절 끝점에 정확히 도착하지 않음 | `capture_20261117_150328_525173`: 잔차 1.94°에서 재이동 후에도 1.77°로 남아 접근 실패. 이후 `capture_20261117_151830_925861`에서 1.79°, `capture_20261117_154125_422792`에서 1.33° 기록 | 최근 사용된 SDK 끝점 전송에서는 MoveIt 경로를 추종하지 않고 최종 관절 목표를 한 번 보낸다. 같은 목표를 재전송해도 잔차가 충분히 줄지 않았다. 오른팔의 1° 완료 실패 판정과 자동 재이동은 제거하고, 잔차를 로그에 표시하도록 변경. 목표 자체의 거부·실행 실패는 계속 오류로 처리 |
| 도착 후 오른쪽 그리퍼가 직각에서 기울어짐 | 사용자가 수동으로 맞춘 자세: 관절각 `[49.57, -37.44, -69.69, 16.78, -3.25, -35.24]`°. 비교한 도착 자세: `[42.8, -93.95, 52.82, -53.26, -3.33, -47.63]`°. URDF FK의 TCP 아래방향 기울기는 각각 3.25°와 5.44° | 두 자세의 위치가 달라 관절각을 그대로 복사할 수 없다. 오른팔 접근 목표에는 수동 자세의 **방향만** 사용한다. 최근 기록에서 목표 방향 대비 계획 끝점 회전 차이는 2.61°, 계획 끝점 대비 실제 도착 회전 차이는 3.35°였다. 계획과 실제 도착 양쪽이 기울기에 기여 |
| 오른팔 도착 기울기가 비슷하게 반복됨 | 수동 방향 기준이 적용된 두 접근(`151830`, `154125`)의 오른팔 베이스 기준 X/Y 회전 오차가 각각 약 `(+2.46°, -2.91°)`, `(+3.22°, -3.46°)` | 평균인 **X `+2.84°`, Y `−3.19°`**를 오른팔 목표 방향에 미리 적용. 물체의 파지 회전각을 유지하기 위해 Z축 보정은 적용하지 않음. 다른 물체 위치·회전각에서도 같은 오차인지는 미확인 |
| 오른팔 목표가 거부되거나 상태 오류 발생 | `right goal rejected`와 `Combined state stale or clocks differ` 로그가 별도로 발생 | 이 오류들은 그리퍼 기울기와 동일한 원인으로 확인되지 않았다. 해당 시점의 Pi/PC 상태, 게이트, 시간 동기화를 각각 확인해야 한다 |

## 함께 겪은 작업 흐름 문제

오른팔 고유의 기계 문제로 확인된 항목은 아니지만, 같은 파지 작업을 진행하며 반복해서 막혔다.

| 단계 | 이전 증상 | 현재 코드 |
|---|---|---|
| 스테레오 3D | LightGlue 2D 매칭은 수백 개여도 유효 3D 점이 0~2개였음 | 베이스 간격을 30 cm로 맞추고 고정 스테레오 보정을 새 캡처로 갱신. 보정 캡처에서 좌측 ChArUco 마커는 2개뿐이어서 더 많은 마커가 보이는 재확인은 남아 있음 |
| Y 미세 조정 | ROI 중앙을 화면 밖의 목표 Y=563.8 px로 보내려 해 의도와 반대로 움직임 | Y는 **ROI 윗변을 화면 중앙 Y=240 px**로 보내도록 변경. X 계산은 유지 |
| 미세 조정 자세 검사 | 왼팔 Y 조정에서 예상 기울기 2.4°→3.4°가 `+1°` 증가 제한을 조금 넘어, 이동 전 실패 | `+1°` 증가 제한을 제거. 현재는 전체 TCP 기울기 8°와 방향 변화 3°를 검사. 이 사례에서는 실제 이동 명령이 전송되지 않았음 |
| `G` 하강 | 현재 TCP Z=42.8 mm, 목표 Z=38.0 mm로 하강 거리 4.8 mm였지만 코드의 최소 10 mm 조건에 걸림 | PC와 로컬 Pi 브리지 소스의 허용 범위를 `−10~100 mm`로 변경. 첫 `G`는 현재/목표 Z와 이동 거리를 출력하고, 두 번째 `G`에서 SDK `MoveL` 직선 수직 이동을 요청한 뒤 성공 시 그리퍼를 닫음. 음수 거리는 위쪽 이동 |

## 코드와 실행 방식

- [오른팔 수동 방향·도착 보정 및 접근 판정](moveit_pick/dual_arm_coordinator_real.py): 오른팔 목표 회전만 보정한다. 목표 XYZ와 왼팔 목표 방향은 바꾸지 않았다. 계획 방향 허용 오차는 원래 값인 **2°**다.
- [ROI 화면, Y 미세 조정, 두 번 누르는 G](moveit_pick/sam_dual_yaw_moveit.py), [Y ROI 계산](moveit_pick/fine_roi_real.py).
- [미세 조정 검사와 하강 실행](moveit_pick/move_right_sam_yaw.py), [Pi SDK 브리지 소스](../pinky_ws/src/jetcobot_dual_real/robot_bridge/sdk_goal_bridge.py).
- `G`의 수직 이동은 Pi SDK의 `send_coords(..., mode=1)`로 X·Y·방향을 유지하며 Z를 바꾸도록 요청한다. 이는 SDK의 직선 이동 요청이며, 실제 TCP 궤적의 직선성은 별도 실측으로 확인되지 않았다.
- 오른팔 Pi는 `192.168.0.22`, 왼팔 Pi는 `192.168.0.33`으로 기록돼 있다. 로컬 URDF의 좌우 TCP 고정 변환과 로컬 브리지의 처리 방식은 동일하다. 실제 두 Pi 파일은 SSH 인증이 거부돼 이번 점검에서 직접 비교하지 못했다.

## 현재 상태와 다음 확인점

1. PC 프로그램을 다시 켜고 **새 캡처·새 계획**을 만든 뒤 오른팔 접근 자세를 눈으로 확인한다. 기존 저장 계획에는 마지막 회전 보정이 반영되지 않는다.
2. 사용자는 사전 회전 보정 후 오른팔 자세가 나아졌다고 보고했다. 새 계획에서 오른팔 목표 방향, 계획 끝점 방향, 실제 도착 방향을 같은 TCP/베이스 좌표계로 비교해 개선량을 수치로 확인한다. 현재 보정값은 두 번의 접근을 근거로 한 초기값이다.
3. `G`의 `−10~100 mm` 변경을 실제 Pi에 적용하려면 수정된 `sdk_goal_bridge.py`를 해당 Pi로 전송하고 실행 중인 `sdk_drag_hybrid_bridge.py`를 정상 재시작해야 한다. PC 프로그램의 두 번 누르는 `G` 동작도 재시작 후 적용된다.

> 기록 범위: 코드·로그·사용자 관찰을 정리한 것이다. 마지막 오른팔 사전 회전 보정은 사용자 눈으로 개선을 확인했지만 수치 검증은 없고, 새 `G` 입력 방식의 실기 성공도 아직 확인되지 않았다.
