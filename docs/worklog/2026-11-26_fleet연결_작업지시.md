# 작업 지시서: Phody ↔ 팀 관제(fleet) 연결 1차 (2026-11-26~)

> **AI는 이 문서를 처음부터 끝까지 읽은 뒤에만 작업을 시작한다.** 대충 읽고 짐작해서 코드를 쓰지 않는다.
> 사용자는 인터페이스 설계에 익숙하지 않다. AI가 틀린 방향으로 가도 사용자가 바로 알아채기 어렵다. 그래서 **아래 규율이 사용자 대신 안전장치 역할을 한다.** 규율을 어기면 2026-11-25처럼 하루가 꼬인다.

## 0. 이 문서가 생긴 이유 (11-25에 실제로 꼬인 것)

1. 사용자의 "시작만 같게"를 AI가 "pre_place 도착 때 두 팔을 한 골로 동시 출발"로 잘못 이해해 구현했다. 사용자가 원한 건 "두 팔 병렬"이었다.
2. AI가 요청하지 않은 검사, 대기, 골 분할(`fraction`), 출발 전 검사 10여 개를 넣었다. 설명도 없어서 사용자가 확인할 수 없었다.
3. 동시 모드 작업 중에 순차 모드 동작까지 바뀌었다(다음 팔 선행 계획이 꺼짐).
4. "B는 한 팔씩"을 "B 동안 다른 팔도 정지"로 잘못 옮겼다.
5. 그날 기록 파일(`11.25한일.md`)의 오전 내용을 덮어써 지웠다.

**이번 작업에서 같은 일이 생기지 않게 하는 것이 최우선이다.** 기능이 늦어지는 것보다 꼬이는 것이 훨씬 나쁘다.

## 1. 반드시 지킬 규율 (AI용, 예외 없음)

### 1-1. 시작 전

- **R1.** 작업 전에 이 문서, [`AGENTS.md`](../../AGENTS.md), [설계안](../설계안_Phody_fleet_연결.md), [검토](../인터페이스_통합_검토_Phody_2026-11-25.md)를 읽는다.
- **R2.** 코드를 하나라도 바꾸기 전에 **소스 전체 tar 백업**을 만들고 경로를 사용자에게 알린다. 9장 기록표에도 적는다.
  ```bash
  cd ~/pinky_ws/src && tar -czf ~/pinky_ws/backups/jetcobot_dual/jetcobot_dual_before_fleet_$(date +%Y%m%d_%H%M%S).tar.gz --exclude=.git --exclude=__pycache__ --exclude=.pytest_cache --exclude=sam_yaw_output --exclude=models jetcobot_dual
  ```
- **R3.** 4장 "시작 전 확인 3가지"를 사용자에게 **먼저 묻고 답을 받는다.** 답을 받으면 4장에 그대로 적는다. 답 없이 권장안으로 진행하지 않는다.
- **R4.** git 브랜치 생성, 커밋, 푸시는 사용자가 시킬 때만 한다. **팀 저장소(`origin`)에는 절대 푸시하지 않는다.** 팀 브랜치(`origin/dev`, `origin/docs/design`)는 읽기만 한다.

### 1-2. 범위

- **R5.** 이번 작업은 **"fleet 연결 1차"(6장 단계 1~7)뿐**이다. 병렬 진행(게이트 lane, B 팔별 실행, A 대기 줄이기)은 하지 않는다. 그 코드도 건드리지 않는다. 그 작업은 [2026-11-26_할일.md](2026-11-26_할일.md) 할 일 1·2에 그대로 남아 있다.
- **R6.** **`fleet:=false`(기본값)일 때 동작이 1비트도 바뀌면 안 된다.**
  - fleet 연결 코드는 새 파일에만 쓴다.
  - 기존 파일에는 5장 "고쳐도 되는 곳"에 적힌 연결 지점만 넣는다.
  - 기존 파일에 넣는 모든 줄은 `if fleet 켜짐:` 안에 있거나, 켜지지 않았을 때 아무 일도 하지 않아야 한다.
- **R7.** 5장 목록 밖의 파일을 고쳐야 하면, **고치기 전에 사용자에게 파일 이름과 이유를 말하고 승인받는다.**
- **R8.** `fleet_interfaces`(팀 정의 패키지)는 가져온 그대로 둔다. 안의 msg · srv · action 파일을 **고치지 않는다.** (11-26 사용자 승인 예외: Phody 전용 작업공간 `~/phody_fleet_ws` 복사본의 `CMakeLists.txt`에 `msg/ArmState.msg` 한 줄만 추가. 팀과 달라진 점은 `~/phody_fleet_ws/src/fleet_interfaces/PHODY_변경사항.md`에 적는다.) 팀 정의에 없는 칸이나 서비스가 필요하면 만들지 말고 [AI용 요청 문서](../인터페이스_요청_Phody_AI용.md)에 항목을 더한 뒤 사용자에게 알린다.

### 1-3. 구현 방식

- **R9.** 요청 · 명세에 없는 검사, 대기, 재시도, 대체 경로, 시간 제한, 새 옵션을 넣지 않는다. 꼭 필요하면 **무엇을, 왜** 넣는지 먼저 말하고 승인받는다(AGENTS 규칙 8).
- **R10.** 인터페이스 이름 · 타입 · 칸은 **팀 문서에 있는 것만** 쓴다(7장 표). 이름을 지어내지 않는다.
  - 팀 contract에 아직 없는 이름(`/{arm}/state`)은 `jetcobot_dual_app/config/fleet_names_pending.yaml`에만 적고, 출처(명세 절 번호)를 주석으로 단다.
- **R11.** 팀 설계에서 **"열림" 상태인 결정(Q-nn, DECIDE-n)** 에 걸리면 짐작하지 않는다. 8장 "임시 동작"에 적힌 것만 하고, 코드에 `TODO(Q-nn)` 또는 `TODO(DECIDE-n)` 주석을 단다.
- **R12.** 팀 통신 규칙을 지킨다.
  - IR-30: 서비스는 비동기로 부르고 콜백 그룹을 나눈다.
  - IR-31: 콜백 안에서 기다리지 않는다.
  - IR-21: 같은 `request_id`는 같은 답(최근 32건, 60초).
  - IR-33: 발행 · 구독 QoS를 같게.
  - fleet 연결 노드의 콜백은 앱 객체를 **직접 바꾸지 않는다.** 명령 큐에 넣기만 한다(2장).
- **R13.** 화면(OpenCV)과 앱 상태는 메인 스레드만 만진다. fleet 연결 스레드는 스냅샷을 읽기만 한다.

### 1-4. 진행과 보고

- **R14.** 6장의 **한 단계를 끝낼 때마다 멈추고 보고한 뒤** 다음 단계 승인을 받는다. 여러 단계를 한 번에 하지 않는다.
- **R15.** 단계 보고에는 다음을 빠짐없이 쓴다(AGENTS 규칙 10). 같은 내용을 9장 기록표에도 적는다.
  1. 바꾼 파일 / 새 파일
  2. 새로 넣은 검사 · 대기 · 제한 (없으면 "없음")
  3. `fleet:=false` 동작이 그대로인지와 그 근거 (예: `git diff`에서 기존 경로 변경 없음)
  4. 확인 방법: 단위 테스트 / 로컬 시험 명령 / 실물. **실물을 안 돌렸으면 "실물 미확인"이라고 쓴다.**
- **R16.** 문서는 덮어쓰지 않고 **덧붙인다.** 특히 `docs/worklog/*한일.md`. 고쳐야 하면 고치기 전 파일을 백업한다.
- **R17.** 사용자 말이 두 가지로 읽히면 **구현하지 말고 짧게 되묻는다.** 3장 용어표에 없는 말이 나오면 무엇을 뜻하는지 확인한다.
- **R18.** 로봇을 움직이는 명령은 AI가 실행하지 않는다. 사용자가 복사해 실행할 **전체 명령**을 준다(AGENTS 규칙 5). Pi에 접속하지 않는다.

## 2. 무엇을 만드는가 (한 문단 요약)

지금 Phody는 사람이 화면에서 캡처 → `M`(인식) → 실행하는 단독 장치다. 팀 관제(fleet)가 "이 상품 N개 담아라"(`/workcell/fill_basket` 액션)를 보내면, **사람 대신 같은 함수들을 자동으로 불러** 담고 결과를 돌려준다. 또 팔 상태(`/arm_left/state`, `/arm_right/state`)를 내보내고, 운영 모드(`set_mode`)를 받는다.

구조: 픽 앱 프로세스 안에 **fleet 연결 노드**(새 파일)를 얹는다.
- 이 노드는 자기 실행기 스레드에서 돈다.
- 앱에 시킬 일은 **명령 큐**로 넘기고, 앱 상태는 **스냅샷**으로 읽는다.
- 켜는 법: `pick.launch.py ... fleet:=true`

| 칸 | 값 |
| --- | --- |
