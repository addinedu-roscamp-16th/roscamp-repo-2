## 0. 작업 규칙 (사용자가 오늘 다시 명시)

- **Pi(192.168.0.33, 192.168.0.22, 사용자 `jetcobot`, 경로 `~/jetcobot_dual_bridge/`)에 AI가 SSH/SCP 하지 않는다.** 모르는 것은 사용자에게 묻고, 사용자가 실행할 **완전한 명령어(붙여넣기만 하면 되는 전체 명령)**를 준다. "이 인자 추가" 식으로만 주면 사용자가 귀찮아한다 — 바뀐 값 요약 + 전체 명령을 둘 다 준다.
- AI는 로봇 명령을 보내지 않는다. 로컬에서는 문법 검사(`py_compile`)와 로봇과 무관한 순수 함수 오프라인 시험만 한다. PC의 `~/.ros/log` 읽기, `ps` 확인 정도는 했다.
- 토큰을 적당히 쓴다. 짧고 직접적으로 설명한다.
- 하드웨어 허용오차를 1~2°처럼 촘촘하게 만들지 않는다(사용자는 5° 수준을 원함). 수치를 임의로 바꾸지 말고, 바꿀 때는 이유를 먼저 말하고 기본값은 기존 동작을 유지하는 파라미터로 넣는다.
- PC 패키지 `jetcobot_dual_real`은 **symlink-install**이다(`build/.../launch/*.py`와 패키지 python이 `src`로 링크). 따라서 PC 코드 수정은 **재빌드 없이 PC launch 재시작**만으로 반영된다. Pi 파일은 사용자가 복사·재시작해야 반영된다.

### PC MoveIt + gate

```bash
ros2 launch jetcobot_dual_real dual_real.launch.py execution_arm:=both trajectory_backend:=sdk_drag_hybrid coordinated_execution:=true collision_padding_m:=0.005 gripper_padding_m:=0.010 tin_case_enabled:=false rviz:=true hybrid_drag_step_deg:=8.0 hybrid_drag_corner_trim_deg:=0.0 state_gap_grace_s:=4.0
```

- `hybrid_drag_step_deg`/`hybrid_drag_corner_trim_deg`는 **반드시 Pi의 `drag_step_deg`/`drag_corner_trim_deg`와 같아야** 한다(PC가 Pi가 실제로 보낼 축약 경유점을 미리 충돌검사하기 때문).
- launch 정상 기동 확인 문구: `both SDK connections enabled; coordinated controller enabled`.
- launch는 **Ctrl+C로 끈다. Ctrl+Z 금지.** 오늘 Ctrl+Z로 일시정지된(`ps` 상태 `Tl`) 이전 launch의 `move_group`/`execution_gate`/`state_aggregator`가 남아, 새 launch의 gate가 뜨지 못하고 스크립트가 `Coordinated execution gate unavailable`을 냈다. 일시정지 프로세스는 `kill`이 안 먹고 `kill -9 <PID>`가 필요했다. 확인: `ps aux | grep -E "ros2 launch|rviz2|robot_state_publisher|move_group|execution_gate|state_aggregator|tin_case_scene" | grep -v grep`.

### 실행이 실패해서 PC gate에 fault latch가 걸렸을 때

```bash
ros2 service call /jetcobot_dual/reset_execution_fault std_srvs/srv/SetBool '{data: true}'
```

latch가 걸리면 그리퍼 명령까지 전부 거절된다(오늘 `RIGHT GRIPPER CLOSE rejected`의 원인이 이것: 직전 실행 중 취소 → `User canceled; remote stop requested` → latch). reset은 현재 자세가 MoveIt 충돌 상태면 거부된다 — 그때는 사용자가 팔을 떼어 놓아야 한다. PC launch 재시작으로도 latch는 풀린다.

## 3. 시스템 구조 요약 (오늘 기준으로 이해해야 할 것)

- PC: MoveIt `both_arms` 12관절 그룹. `execution_gate`(PC 패키지 `jetcobot_dual_real/execution_gate.py`)가 `coordinated_execution:=true`에서 12관절 컨트롤러 `/jetcobot_dual/guarded_both_controller`를 제공한다. 스크립트는 여기에 12관절 경로 하나를 보낸다.
- gate는 받은 경로를 **사전검사(preflight)**: 두 Pi가 같은 시계를 쓰지 않으므로 "왼팔 진행 위치 × 오른팔 진행 위치" 모든 조합을 1° 간격으로 MoveIt `check_state_validity`에 물어본다(`coordinated_route.py`의 `safe_sections`, `continuous_sections`, `independent_path_valid`, `independent_arms_valid`). 그 결과로 경로를 여러 route로 나누고 각 route를 `endpoint`(Pi SDK `send_angles` 한 번) 또는 `drag`(Pi가 축약 경유점을 실측 진행에 맞춰 `SET_ENCODERS_DRAG` 패킷으로 보냄)로 보낸다(`_minimal_drag_routes`).
- 실행 중 gate는 실측 12관절을 계속 MoveIt 충돌검사한다(라이브 감시). 충돌이면 `Measured arms entered a MoveIt collision state` + `Collision-triggering measured joints_deg=[...]; contacts=[(...)]` 로그 후 중단·latch.
- Pi: `sdk_drag_hybrid_bridge.py`(= `SDKDragBridge`(drag) + endpoint 액션). 클래스 계층 `HardwareBridge` → `SDKGoalBridge` → `SDKDragBridge` → `SDKDragHybridBridge`.
- 스크립트(`right_place_trial/`): `coordinated_right_case.py`(케이스 도착), `coordinated_see_center.py`(복귀), 공용 `paired_progress_route.py`, `dual_arm_coordinator_real.py`(MoveIt 클라이언트 `DualArmCoordinator`), `place_right_in_case.py`(상수·헬퍼: `RIGHT_ARRIVAL_JOINT_DEG=(160.86,-62.04,0.02,-24.11,0.09,70.71)`, `URDF`, `CASE_CONFIG` 등).
- 충돌 패딩(실행 감시 기준, launch 값): 팔 링크 5 mm(`collision_padding_m`), 그리퍼 14링크 10 mm, 카메라 2링크 15 mm. 케이스 객체는 꺼져 있음(`tin_case_enabled:=false`) — **실물 케이스와의 충돌은 검사하지 않는다.** 케이스 목표 위치는 `pinky_ws/src/jetcobot_dual_real/config/tin_case.yaml`(`bottom_center_xyz_mm: [-230,155,-10]`).
- 오전(이 대화 이전, 같은 날)에 이미: 손가락 끝 20 mm 충돌 형상 추가(실제 손가락 접촉 후), small_yield 금지(좁은 양보가 그리퍼 패딩에 들어감)·wide_yield만 사용, 두 팔을 각각 계획한 뒤 진행도 격자로 동시 구간을 찾는 paired 방식 도입. 자세한 건 `right_place_trial/COORDINATED.md`(단, 이 문서는 오늘 오후 변경을 반영하지 않음 — 아래가 최신).

## 4. 오늘 이 대화에서 한 변경 (시간순, 이유·근거 포함)

### 4.1 drag route가 Pi에서 즉시 거절되던 문제 — PC gate 수정 (사용자 실행: 이후 성공)

- 증상(11:58 실행 gate 로그): route 1~3 `both endpoint` 성공 후 route 4/5 `both drag`를 보내자마자 0.03초 만에 `right Pi rejected the combined section`.
- 원인: `execution_gate._execute_section`이 drag 경로의 첫 점을 계획 시작점 대신 **실측 자세(`actual`)**로 바꿔 보낸다. 앞 endpoint의 도착 오차(최대 5°) + 첫 구간(최대 5°) → 첫 구간이 Pi drag 한 칸 제한(`drag_step_deg` 5°)을 넘어 Pi `select_waypoints`가 `A planned segment exceeds the SDK waypoint step`으로 goal 거절. 오프라인 순수 함수로 재현 확인(Pi 로그 직접 확인은 못 함).
- 수정 1 (`execution_gate.py` `_execute_section`): drag일 때 실측 시작점→다음 점 첫 구간만 `dense_path(..., 0.95*step)`로 쪼갬. 그리고 보내기 전에 Pi와 같은 `select_waypoints`/`round_joint_path`를 PC에서 돌려, Pi가 거절할 goal이면 `"{side} drag goal would be rejected by Pi: ..."` 또는 `"... over 60 Pi packets"`로 PC에서 멈춤.
- 수정 2 (`coordinated_route.py` `dense_path`): 간격을 `step*0.999`로. 30°/5°처럼 정확히 나눠떨어지면 부동소수점으로 1ulp 초과 → Pi 거절되는 잠재 버그.

### 4.2 drag 떨림 — waypoint 간격 8°, 코너 둥글리기 끔 (launch 인자만, 사용자 실행: "훨씬 나아")

- 로그 분석(33패킷, J1 35→120°, 27초): SEND 3~8, 26~30처럼 0.3~0.6°짜리 작은 패킷 묶음에서 `path_speed`가 0~1.7°/s로 섰다 갔다 → **떨림의 직접 원인은 `drag_corner_trim_deg=3`의 코너 둥글리기**(코너마다 점 5개 추가).
- 조치: Pi `drag_step_deg:=8.0 drag_corner_trim_deg:=0.0`, PC `hybrid_drag_step_deg:=8.0 hybrid_drag_corner_trim_deg:=0.0`. Pi 코드는 `drag_step_deg ≤ 8`로 제한(`sdk_drag_bridge.py` 파라미터 검사), `drag_lead_deg ≥ step`(기본 10). 사용자가 "8개 정도 waypoint면 덜 떨린다"고 했지만 85° 이동을 8패킷으로 하려면 간격 ~11°가 필요하고 이는 Pi 코드 상한 변경 필요 — **미착수**.

### 4.3 `coordinated_right_case.py` 계획 실패 `No simple paired case route` — 재계획 추가

- 원인: RRT 결과가 `simple_enough`(관절 이동량이 직선의 1.6배 초과면 거부)에 걸리면 재계획 없이 바로 실패.
- 수정: 왼팔 양보 계획은 최대 3번 재시도. 오른팔 케이스 도착은 **3번 계획해서 관절 이동 합(`joint_travel`)이 가장 작은 것 선택**(사용자: 오른팔이 과하게 움직임). 출력 `RIGHT CASE ARRIVAL: chose shortest of N paths (X deg joint travel)`. 오늘 마지막 값 496° — J1만 ~125° 돌아서 크다. 더 줄일 여지는 미검토.

### 4.4 endpoint 구간마다 오래 서는 문제 — 시도 두 개, 둘 다 기본 꺼짐

- 관찰: 경로가 endpoint 4~5개로 나뉘면 구간마다 SDK가 완전히 멈추고 Pi가 도착 판정한 뒤 다음 구간. PC gate 대기는 0.2초 정도로 작음. Pi endpoint 도착 판정(`sdk_goal_bridge._execute_sdk_goal`)은 "5° 이내 + 0.5초 동안 0.2° 이상 안 움직임"이고 관절 상태가 2 Hz라 실제로는 1초 이상 정지.
- 시도 A `merge_endpoint_routes` (PC launch 인자, 기본 false, `execution_gate._merged_routes`): 여러 route를 연속 drag 하나로 합침. **실패** — `Route merge skipped ... Reduced continuous drag route collides`. 이유: drag는 두 팔이 독립 진행하므로 "왼팔은 마지막 구간, 오른팔은 첫 구간" 조합까지 검사하는데, 구간이 나뉜 이유가 바로 그 조합의 충돌이라 통째 합치기는 원리적으로 안 됨. 코드에는 남아 있지만 쓰지 말 것.
- 시도 B `endpoint_settle_s` (Pi 파라미터, 기본 0.5 = 기존 동작, `sdk_goal_bridge.py`): 0이면 5° 안에 처음 들어온 순간 다음 구간. **0으로 했더니 충돌 판정 발생**(구간 끝을 최대 5° 덜 가고 꺾음 → `left_2_Link`–`right_gripper_left1`). **0.5로 되돌림. 0 쓰지 말 것.**
- 결론: 구간 사이 정지는 아직 남아 있다(현재 구간당 정지 약 1초 수준으로 추정, 미측정). 사용자는 "잠깐 멈칫"은 괜찮다고 함.

### 4.5 see_center 복귀 재작성 (`coordinated_see_center.py`)

- 기존 문제: 12관절 RRT 한 번에 계획(구불구불, `simple_enough` 검사도 없음, 106초 사전검사, 9개 route로 덜덜), 왼팔 양보 목표를 **현재(이미 양보한) 자세 기준으로 또 +28°** 계산, 실패 시 home(전 관절 0) 시도.
- 새 방식 `choose_return`: 오른팔을 왼팔 현재 자세 고정으로 3번 계획해 최단 선택 → 왼팔을 오른팔 see_center 가정으로 계획 → 두 경로를 `sample_arm` 후 **시간 역순으로 뒤집어** 케이스 도착과 같은 `first_safe_overlap`/`make_phase(..., reverse=True)`로 묶음(= 두 팔 같이 출발, 왼팔이 마지막에 혼자 마무리). 왼팔이 이미 see_center(1° 이내)면 오른팔만. 추가 양보·home·12관절 RRT 없음. `make_phase`에 `reverse`, `label` 인자 추가(`paired_progress_route.py`).

### 4.6 반복 충돌 판정 → "계획할 때만 여유를 넓히기" (사용자가 좋다고 확인한 방식)

- 증상: 계획과 실행 감시가 같은 패딩을 쓰므로 계획 경로가 패딩 경계에 붙어 있으면 실제 오차 1°에도 감시에 걸림. 기록된 접촉: `left_2_Link`–`right_gripper_left1`, `left_4_Link`–`right_gripper_left1`, `right_jetcocam`–`left_4_Link`.
- 또 하나의 원인: **SDK endpoint(`send_angles`)는 관절을 동기화해 움직이지 않는다**(예: 1.8초에 J1 1°, J6 26°). 1. 케이스 위 도착(기존).
2. **케이스 중심 맞추기 + 놓는 높이**: `move_to()` — 실측(측정 관절 FK) 기반 보정 루프, 최대 3회, 매번 `명령 = 목표 − 직전 관측 편차`. 목표 오차 5 mm에서 멈춤, 끝까지 10 mm 넘으면 실패. **실패해도 집게 끝이 림보다 5 mm 이상 위면 그 자리에서 놓음**(사용자: 지금 위치에서 열어도 괜찮다). 놓는 높이 기본 `--below-rim-mm -13`(집게 끝 림 위 13 mm ≈ 물체 바닥 림 위 10 mm).
3. 그리퍼 조금 열기: 모델 손가락 간격 = 물체 폭 + 5 mm(초코바 40 mm → joint +0.138, `--release-gap-mm`). SDK 값 매핑은 모름.
4. `held_object.apply(remove=True)`.
5. 30 mm 상승(`--lift-mm`) — gate 경유.
6. 복귀: `choose_return`(see_center 방식). 시작 자세가 넓힌 계획 여유 안이면 자동으로 여유 0으로 재계획(`coordinated_see_center.py`에도 동일 fallback).

### 놓기 개발 중 확인된 사실 (근거 로그 포함)
- **SDK MoveL은 케이스 자세에서 쓰면 안 됨**: 31.3 mm 하강 시 Pi 로그 start `[-220.4,148.8,176.3,-179.71,0.55,-0.35]`, 집기용 보정 포함 command `[-218.6,151.2,151.0,-177.91,-1.85,0.25]`, 45 s 후 last `[-219.2,149.1,141.6,-179.8,-4.76,0.67]` → ry 5.3° 기울며 집게 끝이 로봇 쪽(+X)으로 쏠려 케이스 로봇 쪽 벽에 쓸림, `did not reach target in 45 s`. 집기용 보정이 이 자세에선 역효과. → 놓기 하강은 기본 `--descent-method moveit`(관절공간, gate 경유). `sdk`는 옵션으로 남김. 집기용 SDK 하강·보정은 건드리지 않음.
- **오른팔이 케이스 자세에서 처짐**: 계획 TCP `[-229.7,153.5,105.2]` → 도착 실측 `[-221.0,153.7,94.9]`(로봇 쪽 +9 mm, 아래 −10 mm, Pi는 관절 5° 이내라 도착 처리, 관절 차 2.2°). 하강 중에도 +6.4 mm X, 요청보다 13.5 mm 더 내려감. → 측정 기반 보정 루프(2단계)를 넣은 이유.
- **MoveIt `compute_cartesian_path`가 이 자세에서 0 % 반환**(9 mm 이동, 로그에 이유 없음). → `cartesian_move()`를 **MoveIt FK로 만든 수치 Jacobian + damped least squares**(`solve_small_move`)로 대체. 5 mm 간격 경유점, gate 경유.
- 처음 버전은 오차가 2→4→6→9 mm로 누적(케이스 자세가 **손목 특이점 근처, J5≈0**) → 위치 우선(rot_weight 0.01 m/rad), damping 0.01, 반복 15회, 한 번에 최대 5°. 10 mm/10° 넘으면 실패, 2 mm/3° 넘으면 경고. 장난감 특이점 팔 시험에서 30 mm 상승 위치 오차 0.2 mm 이하, 자세 3~6° 변화. **이 수정판은 실제 로봇에서 아직 안 돌림.** 마지막 성공 실행은 수정 전 버전(중심 맞추기 실패 → 림 위 10.3 mm, TCP X −220.2에서 그대로 놓음 → 그래도 케이스 안에 들어감).
- 사용자 요구 재확인: **mm 단위로 촘촘하게 막지 말 것.** 하드웨어 오차가 1 cm까지 난다. 허용치는 ~10 mm 수준으로.
- 케이스는 MoveIt 장면에 없음(`tin_case_enabled:=false`) → 하강/상승은 수직이라 괜찮지만 **복귀 경로는 케이스 벽을 검사하지 않는다.**
- 초코바 긴 변 90 mm가 케이스 안쪽 긴 변 95 mm 방향 → 그 방향 여유 한쪽 2.5 mm. 위에서 떨어뜨릴 때 Y·각도가 틀어지면 림에 걸칠 수 있음(이번엔 들어감).

## 11.6 계획 시간
- 두 팔 조합 검사 `first_safe_overlap`: 행을 3개씩 건너뛰며 검사, 실패 행이 나오면 그 사이만 촘촘히(단조 가정 시험 2000건 일치). 복귀 계획 46.2 s → 21.9~25.7 s.

# 12. 사용자의 목표 (다음 작업자가 방향을 잃지 않도록)

## 12.1 최종 목표 (사용자 표현)
**"양팔이 협동해서 바구니(틴케이스)에 물품을 최대한 빨리 담는 것."** 카메라로 물체를 찾고, 두 팔이 서로 부딪히지 않으면서 동시에 일해 여러 개의 물체를 가능한 짧은 시간에 케이스에 넣는다.

## 12.2 왜 이 목표인가 (대화에서 드러난 맥락 + 작업자 해석 구분)
- 사용자가 직접 말한 것: 목표는 "양팔로 바구니에 최대한 빨리, 둘이 협동해서 물품을 담기". 오늘 우선순위로 ①픽앤플레이스 시간 줄이기 ②양팔 경로 최적화 ③**집을 물체가 2개 이상일 때 양팔이 안 겹치고 최대한 빠르게 잡고 넣기**를 정했다. 실제 하드웨어는 오차가 1 cm까지 나므로 mm 단위로 막는 정밀 제어보다 **안정적으로 끝까지 도는 것**과 **충돌 없음**을 중시한다.
- 작업자 해석(사용자가 이유를 직접 말한 것은 아님): 한 팔보다 두 팔이 동시에 일하면 처리량이 늘지만, 작업 공간과 케이스를 공유해 충돌·대기가 생긴다. 그래서 "협동"의 핵심은 (a) 충돌 없이 (b) 서로 기다리는 시간을 최소화하는 계획·스케줄링이다. 오늘 한 작업(계획 여유, 비키는 방향 선택, 동시 진행 조합 검사, 시간 측정)이 모두 이 두 가지를 향한다.

## 12.3 현재 위치 (2026-11-19 끝)
- 물체 1개(초코바), 한 번에 한 팔이 집고 다른 팔은 비키는 방식으로 **카메라 인식 → 집기 → 케이스에 넣기 → 복귀가 자동으로 끝까지 성공**(왼팔·오른팔 모두 동작 확인; 왼팔은 픽 UI 전체 흐름으로 확인).
- 1회 사이클 약 170 s(캡처부터). 큰 덩어리: 케이스 도착 계획·실행, 복귀 계획, 접근·미세조정.
- 멘토스는 비활성(처리 미완성). 지그(작업대 배치) 맵은 아직 최종이 아님.

## 12.4 앞으로 디벨롭할 것 (권장 순서)
1. **사이클 시간 단축 계속** — 11.7 효과 확인, 복귀 RRT 정책, 구간 사이 정지(4~8 구간), SDK 끝점 속도 10 고정(Pi 수정 필요), worker 시작 비용(접근·미세조정도 별도 프로세스).

# 13. 마지막 단계: 경로 선택·gate 검사 간격 (12장 이후)

**사용자 확인:** 아래 설정으로 왼팔 픽→케이스→놓기→복귀가 충돌 판정 없이 끝까지 성공. 마지막 실행: 캡처→리프트 끝 63.4 s, 케이스 도착 계획 12.7 s / 실행 **14.5 s**, 놓기 7.1 s, 복귀 계획 8.2 s / 실행 10.7 s, 놓기 worker 합계 **56.5 s**, 캡처부터 **119.9 s**(오늘 처음 ~170 s).

## 13.1 RRT 경로 선택 정책 (도착·복귀 공통)
- 운반 팔 케이스 도착(`coordinated_right_case.checked_goal`)과 see_center 복귀(`coordinated_see_center.plan_simple`) 모두: 최대 5회 계획, 단순 경로(≤1.6배)를 **최대 3개 모아 관절 이동이 가장 짧은 것** 사용. 하나도 없으면 가장 덜 우회한 것을 ≤2.5배일 때만 사용(`travel_ratio`), 그 이상이면 실패.
- 경위: "첫 단순 경로 사용"으로 바꿨더니 계획은 빨라졌지만 429° 경로가 나와 실행이 늘어서, 계획이 1 s 수준으로 빨라진 뒤 다시 "최대 3개 중 최단"으로.
- 관찰: 집은 위치에서 케이스로 한 번에 가는 RRT는 위치에 따라 1.7~3.4배 우회가 자주 나온다(5회 모두 우회인 실행 있음). 근본 해결은 12.4의 "중간 자세" 방식(지그 맵 확정 후).

## 13.2 gate 두 팔 사전검사 간격 `coordinated_check_step_deg` (신규, PC gate)
- 두 팔 사전검사 격자 간격은 `coordinated_route.CHECK_STEP`에 1°로 **하드코딩**되어 있었다(`hybrid_check_step_deg`는 한 팔 검사용이라 효과 없음). gate 파라미터 `coordinated_check_step_deg`(기본 1.0, 0.5~2.0) 추가 → gate 시작 시 `coordinated_route.CHECK_STEP`을 그 값으로 설정. launch 인자 같은 이름.
- 2.0으로 실행: 도착 사전검사 12.8 → 2.8 s, 복귀 5.4 → 1.5 s, 도착 실행 32.0 → 14.5 s(이번 경로가 drag 없이 끝점 3구간이었던 영향도 섞임).
- 실행 중 실시간 충돌 감시와 계획 단계의 1° 검사(넓힌 여유 포함)는 바뀌지 않음.

> ⚠️ **경고 (사용자 판단: "너무 아슬아슬하다")** — `coordinated_check_step_deg:=2.0`은 사용자가 표준 명령에 넣기로 했지만, **실물에서 팔·그리퍼·초콜릿이 상대 팔에 아슬아슬하게 붙어 지나가는 경우가 나온다.** 2°면 J1 기준 팔 끝이 검사점 사이에 약 1 cm 움직이므로 실행 패딩(팔 5, 그리퍼 10, 카메라 15 mm) 기준의 마지막 확인이 거칠어진다. 지금 안전은 계획 단계 여유(팔 +15, 그리퍼·카메라 +25, 물체 +10/긴 변 +20 mm, 1° 검사)에 크게 기대고 있다. 또 SDK 끝점 이동은 관절이 동기화되지 않아 검사한 직선 경로를 벗어난다(10장·오후 기록). **실제로 붙는 게 보이거나 충돌 판정이 다시 나오면 즉시 `coordinated_check_step_deg:=2.0`을 빼서 1.0으로 되돌리고**, 필요하면 `endpoint_as_drag:=true`나 계획 여유 증가를 검토할 것. 다음 작업자는 이 값을 근거로 여유를 더 줄이지 말 것.

## 14.1 사용자 결정
- 단일 물체 코드는 그대로 두고 **사본**으로 개발(폴더 `~/camera_code/multi_pick/`).

- 최종 목표는 양팔 동시 진행이지만 첫 버전은 **한 물체씩 순서대로**, 큐 구조로 만들어 나중에 스케줄만 바꾸게(작업자 추천, 사용자 동의). gate가 실행을 하나만 받으므로 동시 진행은 12관절 결합 계획이 필요.

## 14.2 multi_pick 구성
- `sam_multi_real.py`: 실물 픽 UI(`moveit_pick/sam_dual_yaw_moveit.py`)의 `SAMYawApp`을 상속(`MultiApp`), `sam.SAMYawApp = MultiApp` 후 원래 `main()` 호출. 원래 UI의 카메라·LivePoses·스테레오 보정·`a` 보드 캡처·접근/미세조정/집기/놓기/복귀를 그대로 사용. 기본 플래그(`--fine-roi --match-rotation --auto-fine --enable-execute`)는 `manual_roi_drag.py`처럼 자동 추가.
  - ROI: 첫 왼쪽 드래그로 고정 → 물체마다 ROI 하나씩 왼/오 각각(순서 무관, 최대 12), 오른쪽 클릭 삭제. `M` = 인식.
  - 인식 후 확정 물체 → 큐(`queue.json`) → `start_next_object()`가 물체별 `run_NN_object_k/moveit_target.json`(실물 형식)을 쓰고 `select_object_type('chocobar')`로 계획 → `E`(또는 `--auto-execute`) → 기존 체인 → 놓기 성공(`PLACE` 단계 exit 0)이면 다음 물체 자동 시작. 실패면 `MULTI STOPPED`.
  - 다음 물체 시작 시 캡처 시각·관절을 현재값으로 갱신(위치는 world 좌표라 유효). 
  - 결과 창: 짝마다 같은 색으로 ROI·연결선·**SAM 마스크**(반투명+테두리). 위에서 본 지도 창(`Top view | objects, case, pick order`, 캡처 폴더 `topdown_map.png`): 물체 사각형·순서 번호·케이스·양팔 베이스, 자동 축척. (예전 검은 `Top-down grasp preview` 창은 내용 없이 비워 둔 것이었음)
  - 여러 물체용 옵션: `--auto-execute`, `--object-height-mm 15`, `--floor-z-m 0.007`(윗면 prior 22 mm; 단일 인식의 윗면 Z 21~24 mm 기준), `--height-tolerance-mm 10`, `--reproj-px-multi 8`, `--epipolar-px 6`, `--min-valid-points-multi 8`, `--min-valid-ratio 0.3`, `--assignment-margin 0.2`. 나머지는 원래 UI로 전달.
- `multi_roi_perception.py`, `multi_roi_geometry.py`, `rotation_matching.py`, `surface_geometry.py`: 가제보에서 복사. 원래 UI 모듈에 같은 이름·인자의 함수 7개(`project_points, mask_filtered_features, segment_with_sam, triangulate_matches, normalize_yaw_deg, save_xyz_csv, draw_grasp_axes`)가 있어 `import sam_dual_yaw_moveit as sam`만 바꿔 사용. 짝 맞추기: ROI별 SAM 마스크 안 SuperPoint 특징, 윗면 평면 투영 검사, 오른쪽 0/90/180/270° 회전 + 윗면 평면 펴기 후보, LightGlue, 에피폴라·재투영·높이 검사, 전역 일대일 최대 점수 연결(애매하면 확정 안 함). 초코바 크기 범위(길이 50~120, 폭 15~50 mm, 점 퍼짐 140 mm)로 바꿈.
- `README.md`: 사용법·주의.

## 14.3 실물 시험에서 고친 것
1. **두 번째 물체 직전 크래시** (`float(self.capture_time_unix)`): 원래 UI `reset()`이 놓기 후 캡처 시각을 지움 → `multi_capture_time`에 따로 저장.
