# 2026년 11월 17일 작업 정리

작성: 2026-11-17. 범위는 오늘의 대화, PC 코드와 저장된 캡처·worker 로그, 사용자가 전달한 Pi SDK 출력이다. **오른팔 fine XY 자세·높이 보정은 미해결로 미뤄 둔다.** PC/SDK의 `SUCCESS`는 실제 파지 안정성이나 명령 궤적의 재현성을 뜻하지 않는다.

## 오늘 한 일

1. **스테레오·접근 위치:** 실제 두 팔 베이스 간격이 한때 35 cm였는데 모델은 30 cm였다. 사용자가 실물 간격을 30 cm로 다시 맞춘 뒤, [`capture_20261117_145527_358826`](sam_yaw_output/capture_20261117_145527_358826/)을 기준으로 [고정 스테레오 보정](moveit_pick/calibration/stereo_see_center_correction_20261117.json)을 갱신했다. 사용자는 오른팔의 처음 접근 위치가 개선됐다고 확인했다. 오른팔 목표를 임의로 `+Y 4 cm` 옮기는 보정은 넣지 않았다.
2. **오른팔 초기 접근 자세:** 사용자가 손으로 맞춘 직각 자세의 SDK 관절각 `[49.57, -37.44, -69.69, 16.78, -3.25, -35.24]°`에서 TCP **방향**을 추출했다. 관절 1~3의 각도를 목표 위치에 그대로 복사하지 않고, 물체 yaw에 맞춰 회전한 방향을 [오른팔 접근 목표](moveit_pick/dual_arm_coordinator_real.py)에 사용한다. 두 번의 도착 오차에서 구한 오른팔 베이스 기준 X `+2.84°`, Y `−3.19°` 사전 회전을 적용했다. 사용자는 도착 자세가 전보다 괜찮아졌다고 했지만, 여러 위치에서의 반복 정확도는 측정하지 않았다.
3. **접근 완료 판정:** 오른팔 끝점 관절 잔차가 약 1~2° 남아도 같은 목표 재전송으로 충분히 줄지 않았다. 1° 잔차만으로 실패 처리하고 재이동하는 동작을 제거하고, 잔차는 출력만 하게 했다. 목표 거부나 실행 자체의 실패는 별도 오류로 남는다. MoveIt 목표 자세 허용오차는 원래 2°로 복구했다.
4. **ROI fine와 `G`:** Y fine은 ROI 윗변을 화면 Y=240 px로 맞추도록 변경했다. 기본 fine XY는 Pi의 `/side/sdk_linear_xy_tenth_mm`를 호출해 SDK Cartesian MoveL을 한 번 요청한다. 이전 관절 목표 방식은 `--fine-joint-goal`로만 선택한다. 첫 `G`에서 현재 모델 TCP Z·목표 Z·예상 하강량을 보여주고, 다음 `G`에서 수직 MoveL과 그리퍼 닫기를 실행하도록 했다. 짧은 하강이 막히던 10 mm 최소 조건은 제거했다.
5. **파지 높이·닫기 판정:** 오른팔 닫힌 집게 끝과 모델 TCP 간 오프셋을 현재 **25 mm**로 두어, 바닥 기준 −5 mm와 끝 여유 3 mm를 포함한 오른팔 모델 TCP 목표 Z는 **23 mm**다. 왼팔은 오프셋 40 mm, 목표 Z **38 mm**다. Pi 브리지의 닫힘 후보 판정은 사용자 요청으로 측정 그리퍼 값 `≤50/100`까지 넓혔다. 이 판정은 실제 물체 파지 확인이 아니다.
6. **통신·자료 정리:** 좌우 `/real_joint_states`가 PC에서 간헐적으로 보이지 않거나 수신 시각이 벌어져 계획·fine·복귀가 실패하는 현상을 점검했다. Pi 로컬 발행과 PC 구독이 항상 같게 보이지 않았고, SSH/핑 및 일반 멀티캐스트만으로 ROS 2 DDS 원인을 확정할 수 없었다. [코드 확인 목록](코드_확인_목록_2026-11-17.txt), [GPT 이어가기 프롬프트](GPT_이어가기_프롬프트_2026-11-17.txt), [check_code 사본](check_code/), [오른팔 이슈 공유 정리](오른팔_이슈_공유정리_2026-11-17.md)를 만들었다. 앞선 오른팔 공유 문서는 이후 fine 보정·파지 높이 변경을 포함하지 않으므로 현재 값은 이 문서와 코드가 우선이다.

## 특히: 오른팔 fine XY 보정은 보류

### 문제와 실제 관찰

- 왼팔은 fine 이동 때 비교적 수직을 유지했지만, 오른팔은 XY만 요청해도 그리퍼가 더 숙여지고 Z가 내려갔다. 사용자는 양옆 높이는 맞아졌어도 손목이 약 95°로 숙이는 느낌이 남았다고 했다.
- 오른팔의 초기 접근 자세 보정과 **접근 후 fine 이동 중의 기울기**는 다른 문제다. 초기 접근이 개선돼도 이후 SDK MoveL이 Z·방향을 유지한다는 뜻은 아니다.
- 오른팔 fine 두 번에서 SDK 플랜지 Z가 시작보다 약 5~6 mm 낮고 X/Y 각도가 각각 약 −2.1°/−0.7° 돌아간 것으로 관찰됐다. 이후 보정 적용 시에도 [`194121` 캡처의 Y/Y/X fine](sam_yaw_output/capture_20261117_194121_705562/)에서 모델 TCP 아래방향 기울기가 `2.52→4.23°`, `4.32→5.06°`, `5.06→6.33°`로 증가했다. 마지막 X fine은 요청 XY `[-5.0,+8.7] mm`에 대해 실측 TCP 변화 `[-7.57,+5.26,−3.95] mm`였다. XY 목표 오차 4.3 mm로 성공 처리됐지만, Z와 기울기는 유지되지 않았다.

## 다음에 해야 할 일

1. **오른팔 fine 보정은 나중에 별도 작업으로 진행한다.** 물체가 없는 높은 위치에서 시작 SDK `get_coords()`와 실측 TCP를 기록하고, 짧은 `+X/−X/+Y/−Y` fine 명령별로 실제 XY·Z·플랜지 각도·TCP 기울기를 비교한다. 시작 자세와 이동 방향에 따라 오차가 달라지는지 확인한 뒤, SDK MoveL 명령·대체 제어 방식·목표 자세 계산 중 어디를 바꿀지 결정한다. 지금의 `+6 mm/+3.4°/+0.7°`는 검증된 범용 보정값이 아니다.
2. 사용자가 재시작하는 Pi/PC 브리지의 **실행 중 버전**과 PC 정본 소스가 일치하는지 확인한다. 오른쪽/왼쪽 Pi의 파일 버전은 달랐고, PC의 `camera_code/sdk_goal_bridge.py`도 별도 오래된 사본이므로 파일 이름만으로 현재 동작을 판단하지 않는다. 재시작·실물 동작은 사용자가 직접 한다.
3. 간헐적 관절 상태 실패 시 Pi 로컬 발행 시각, PC 수신 시각, ROS 도메인·DDS 참가자/인터페이스 상태를 같은 시각에 한 번씩 기록해 어디서 끊기는지 좁힌다. 연결만 되거나 SSH가 되는 사실로 ROS 토픽 수신을 대신 판단하지 않는다.
4. 오른팔 초기 접근이 좋아진 상태에서 파지 높이 23 mm와 실제 물체 접촉 높이를 대조한다. `G` 요청·FK 실측·카메라에서 보이는 실제 집게 끝을 함께 확인하고, 반복 파지 성공률을 기록한다. 왼팔 목표 38 mm와 혼동하지 않는다.
5. 조명·반사가 일정한 조건에서 ROI/LightGlue 매칭의 2D 점, 재투영 오차, 유효 3D 점과 실제 물체 높이를 비교해 3D 목표 신뢰도를 확인한다. 베이스 간격 30 cm가 유지되는지도 확인한다.

### 틴케이스 포함 MoveIt 실행

실물 케이스의 위치를 `tin_case.yaml`에 먼저 적은 뒤 PC에서 실행한다. 아래 명령은 MoveIt과 scene 노드를 시작하며 로봇 이동 명령은 보내지 않는다. 평소 물리 실행이 가능한 launch 구성임은 구별해야 한다.

```bash
source /opt/ros/jazzy/setup.bash
source ~/pinky_ws/install/setup.bash
export ROS_DOMAIN_ID=42
ros2 launch jetcobot_dual_real dual_real.launch.py \
  execution_arm:=both trajectory_backend:=sdk_drag_hybrid \
  collision_padding_m:=0.06 rviz:=true
```

실행 중 케이스 위치만 수정한 경우, 새 `tin_case.yaml` 값을 같은 MoveIt에 다시 적용한다. 적용 뒤에는 이전 저장 계획 대신 새 계획을 만든다.

```bash
ros2 run jetcobot_dual_real tin_case_scene --ros-args \
  -p config_file:=/home/ane/pinky_ws/src/jetcobot_dual_real/config/tin_case.yaml
```

## 추가 작업: 초코바·멘토스 2개 MoveIt 형상 등록

- 사용자가 알려 준 **초코바 9×3.5×1.5 cm**를 90×35×15 mm 직육면체로, **멘토스 2개**를 각각 지름 16 mm·길이 50 mm의 원통으로 정의했다. 두 원통을 짧은 Y 방향으로 붙이고 긴 X 방향으로 10 mm 어긋나게 배치해 전체 외형을 약 60×32×16 mm로 맞췄다. X 어긋남은 전체 길이 6 cm를 만족시키기 위한 가정이다. 모두 짧은 **세로(Y) 방향을 집게로 물리는 물체**로 기록했다. 치수·원통 간격은 [pick_objects.yaml](../pinky_ws/src/jetcobot_dual_real/config/pick_objects.yaml)에서 수정한다.
- 카메라 UI에 `--object-type chocobar|mentos_pair`를 추가했다. 물체 분류를 자동으로 하지는 않으며, 이 선택을 새 `moveit_target.json`에 기록한다. 기존 픽업 계획·이동 계산은 이 선택으로 바꾸지 않았다.
- [pick_object_scene.py](../pinky_ws/src/jetcobot_dual_real/jetcobot_dual_real/pick_object_scene.py)가 캡처의 `right_base_link` 좌표와 물체 긴 축 yaw를 읽어 `pickup_object` 충돌 형상을 만든다. `mode:=world`는 작업 공간에 놓인 형상을 표시한다. `mode:=attach`는 `G` 닫기 완료 직후, `L` 리프트 전의 현재 TF를 이용해 실제로 잡은 팔의 TCP에 부착한다. `mode:=remove`는 부착 물체를 장면에서 제거한다. 이 명령들은 로봇을 움직이지 않는다.
- **기존 픽업은 world 충돌 물체를 자동으로 켜지 않는다.** 집게가 잡으려는 물체와 충돌하는 것으로 처리되면 접근 계획이 막힐 수 있기 때문이다. 부착 형상은 이후 놓기 경로의 충돌 검사에 사용할 수 있지만, 실제 케이스 안으로 내려놓기·그리퍼 열기·팔 빼기 코드는 아직 없다.
- 실제 사용 명령과 좌표·형상 가정은 [PICK_OBJECTS.md](../pinky_ws/src/jetcobot_dual_real/config/PICK_OBJECTS.md)에 적었다. 카메라의 `center_xyz_mm`를 표면 근처 추정점으로 보고 물체 중심을 높이의 절반만큼 아래에 두므로, 실물 Z와 원통 배치는 후속 확인이 필요하다.
- 패키지 빌드와 두 형상 생성, TCP 부착 메시지 생성, 카메라 UI 문법을 최소 범위로 확인했다. 실행 중인 MoveIt의 장면 반영·실물 파지 후 부착·케이스 배치 경로는 아직 검증하지 않았다.

### 틴케이스를 빼고 MoveIt 실행

`dual_real.launch.py`에 `tin_case_enabled` 인자를 추가했다. 기본값은 `true`다. 케이스 충돌 물체 없이 시작하려면 평소 명령 끝에 `tin_case_enabled:=false`를 붙인다. 이미 켜진 MoveIt의 장면은 이 인자로 바뀌지 않으므로 사용자가 기존 런치를 종료하고 새로 시작한다.

```bash
source /opt/ros/jazzy/setup.bash
source ~/pinky_ws/install/setup.bash
export ROS_DOMAIN_ID=42
ros2 launch jetcobot_dual_real dual_real.launch.py \
  execution_arm:=both trajectory_backend:=sdk_drag_hybrid \
  collision_padding_m:=0.06 rviz:=true tin_case_enabled:=false
```
