# 2026년 11월 18일 작업 기록 · 다음 작업자 인계

이 문서는 사용자가 다음 대화에서 오늘의 작업과 시행착오를 다시 설명하지 않아도 되도록 남긴다. 근거는 오늘 대화, 현재 PC 로컬 코드, 저장된 캡처·worker 로그, 사용자가 붙여 준 Pi 로그다. **로컬 코드의 존재, 문법 통과, MoveIt 계획 성공, Pi 액션 성공, 실물의 정확한 움직임은 각각 다른 사실이다.** 아래에서 관찰과 추정을 구분한다. 이 문서 작성 자체는 로봇을 움직이거나 Pi에 접속하지 않았다.

## 먼저 읽을 핵심

1. 사용자의 **주행 방식에 대한 핵심 요구는 최소 drag**다. 보통은 빠른 SDK `send_goal` 끝점 이동을 쓰고, **그 끝점 직선 이동이 MoveIt 충돌 장면에서 막히는 우회 부분에만** 기존에 조정한 drag 경로 주행을 쓴다. 관련 시험 코드가 이미 [`trial_minimal_drag_route.py`](trial_minimal_drag_route.py)에 있다. 이 요구를 전체 경로 항상 drag 또는 양팔 계획을 짧은 drag section으로 전부 나누는 방식으로 바꾸지 말 것. 장기 목표는 **양팔이 협조하여 같은 역할로 물체를 최대한 빨리 집어 틴케이스에 담는 것**이다. 현재는 카메라 파지, 케이스 위 도착, 양팔 동시 실행을 각각 시험 중이며, 케이스 내부 하강·놓기·반복 적재는 완성되지 않았다.
2. 기존 drag 주행은 **필요한 우회 구간에서 사용해야 할 검증 후보**다. [11월 13일 기록](2026-11-13_작업정리.md)에는 MoveIt 경로 전체를 연속 drag로 실행하여 `drag_speed=200`, `drag_step_deg=5`, `drag_send_interval_s=0.4`에서 계획점 189개가 SDK 패킷 11개로 줄고 최종 포즈 측정까지 완료된 오른팔 사례가 있다. 당시 전체 drag는 추종성 시험/기존 하이브리드 구현의 상태였고, **사용자가 원하는 최종 선택 정책은 아니었다.** 그 기록은 한 번의 성공이며 반복 재현성은 미확인이다.
3. **오늘 새로 만든 양팔 협조 래퍼가 이 방식을 바꿨다.** `coordinated_route.safe_sections()`가 한 MoveIt 경로를 짧은 section으로 나누고, `execution_gate._section_goal()`이 section마다 최대 4° 간격의 새 경로를 만들어 각 Pi drag 액션을 반복 시작한다. 사용자가 겪은 `path_progress=1.5/4.0deg`, 무속도 정체, `Drag path did not reach measured final goal in time`은 이 새 실행에서 나왔다. 원래 검증해 둔 **전체 경로 연속 주행 조건으로 시험한 로그가 아니다.** 새 코드의 section 분할·정지·재시작을 사용자에게 충분히 설명하지 않고 기존 drag와 같다고 취급한 것이 이번 회귀의 핵심이다. 1.5°에서 멈춘 장치 내부 원인은 로그만으로 확정할 수 없다.
4. 새 협조 모드에서 오른팔 Pi가 위 timeout을 낸 뒤 PC의 `BOTH SEE_CENTER failed: status=6, code=-4, Combined state stale or clocks differ`도 나왔다. 후자는 양팔 상태 시각 검사 실패이며, 오른팔 주행 정체의 물리적 원인이라는 증거는 없다. 11월 17일에도 관절 상태의 간헐적 수신 문제가 있었다.
5. **다음 작업에서 사용자가 요청하지 않은 추가 완료 조건·짧은 이동 분할·새 속도값을 임의로 넣지 말 것.** 실제 하드웨어는 1 mm/1°/2° 같은 촘촘한 기준으로 안정적으로 움직이지 않는다. 사용자는 5° 수준으로 넉넉히 보고 싶어 한다. 오류를 통과시키기 위해 수치만 낮추거나 높이는 것과 기존 주행을 회복하는 것은 다르다.
6. 사용자는 이제 **양쪽 Pi에 SSH로 접속하거나 파일을 전송하지 말라고 명시했다.** PC 로컬에서 작업하고, 필요한 파일 전송·실행 명령을 사용자에게 준다. Pi에서 실제로 돌아가는 파일/프로세스는 로컬 소스와 다를 수 있다. 실물 검증도 사용자가 한다. 사용자는 불필요한 테스트 대신 코드 문법 검사만 원한다고 했다. 이 문서 작성 이후 로봇 명령은 보내지 않았다.

- 오른팔에서 XY fine과 그립/수직 하강이 실제로 곧게 내려가지 않는 문제를 계속 보고했다. 사용자는 **이미 수직 하강용 보정으로 하강 자체는 수직에 가깝게 맞춘 상태이고, fine 도중에만 수직 유지 보정이 추가로 필요하다**고 정정했다. 하강 보정을 임의로 풀거나 자동 하강을 없애는 것은 요구가 아니다. Pi 로그의 수직 하강 예시는 요청 25.4 mm, SDK 시작 `[189.3,138.3,128.7,178.13,-2.74,18.82]`, 보정 명령 Z 109.3, 실측 `[187.5,135.9,102.2,176.37,-0.16,18.16]`; 다른 21.6 mm 요청도 X/Y·자세 변동이 있었다. 현재 오른팔 native XY 소스에는 명령 Z `+6 mm`, 플랜지 X `+3.4°`, Y `+0.7°`의 경험적 사전 보정이 남아 있다. **범용으로 검증된 수직 유지가 아니다.**
- 사용자가 로봇 속도가 느려졌다고 물었다. 현재 로컬 `sdk_goal_bridge.py`에서 native fine XY `send_coords(...,10,1)`, 수직 MoveL 속도 10, 일반 slow joint/XY 경로는 별도 1 설정이다. 정확히 어느 실행 경로가 느렸는지 Pi 실행 버전과 로그를 확인해야 한다.

### 틴케이스 좌표와 사용자의 실제 목표

- 사용자는 케이스 중앙을 **`right_base_link` 기준 X=−27.5 cm, Y=+15.5 cm, 바닥 Z=−1 cm**로 처음 설명했다. `+Y`가 상자의 긴 가로, `−X`가 세로 방향이다. 이후 중앙 X를 **−23 cm로 변경**했다. 현재 정본 `pinky_ws/src/jetcobot_dual_real/config/tin_case.yaml`은 `bottom_center_xyz_mm: [-230,155,-10]`, `yaw_deg: 90`이다. 외형 98×74×60 mm, 내부 95×71×57 mm, 바닥 3 mm와 벽 1.5 mm의 모델이다. 과거 문서의 `[300,150,-5]`나 오른팔/왼팔 TCP Y `−136 mm`로 되돌리지 말 것. 사용자는 케이스 Y **+155 mm 유지**를 분명히 답했다.
- 원래 시험 의도는 물체 집기는 빼고 **`see_center`에서 그리퍼를 닫아 이미 물체를 잡았다고 가정한 뒤 케이스 중앙 위로 이동**하는 것이다. 처음에는 케이스 위 5 cm 접근→수직 유지로 6 cm 하강→케이스 안 약 1 cm 진입→그리퍼 열기를 논의했다. 계획 실패가 이어져 사용자가 **하강·열기를 빼고 닫은 채로 케이스 림 3 cm 위 도착까지만** 시험 범위를 줄였다. 현 `left_place_trial/place_left_in_case.py`, `right_place_trial/place_right_in_case.py`는 이 마지막 범위다. `--execute`가 없으면 plan only다. `--excute` 오타는 인식되지 않는다.
- 그리퍼의 집게 방향은 도착 시 **TCP 로컬 Y축이 로봇 베이스 Y축과 평행**하면 된다. +/− 부호 일치는 필요 없다. TCP는 아래로 향해야 하지만 사용자는 6번 관절의 불필요한 완전 고정은 풀어 달라고 했다. 왼팔 목표는 사용자가 손으로 맞춘 관절각 `[-133.33,-50.8,-17.05,-22.67,-5.71,-39.63]°`를 토대로 조정했다. 처음 이 값을 오른팔로 오인했으나 사용자가 **왼팔 자세이고 앞으로 왼팔을 움직일 것**이라고 바로잡았다. 현재 왼팔 케이스 도착 후보 `[-133.56,-57.02,-0.05,-29.60,-0.66,-45.0]°`는 모델상 X/Y와 손목 방향을 맞춘 계획 후보이지 실기 성공 기록이 아니다. 오른팔 후보는 별도로 `right_place_trial`에 있으며 `see_center` 시작을 요구한다.
- 케이스 scene이 RViz에 보여도 Python 측 `tin_case.yaml`과 실행 중 MoveIt scene의 pose가 다르면 `Active MoveIt case pose differs ... reapply the scene`이 난다. 사용자가 scene을 다시 적용한 뒤 일치 메시지는 확인했다. 이후 `POSE PLAN ... code=99999`는 목표 계획 실패였고, 또 다른 시점에는 `Current right-arm state is in collision` 또는 `left_gripper_right1 - open_tin_case`의 **시작 상태 충돌** 때문에 계획이 막혔다. RViz에서 크게 떨어져 보인다는 사용자 관찰도 기록한다. 충돌 패딩이 상자에도 적용되는 것을 사용자가 확인하고 설정을 바꾼 뒤 "아 되네"라고 했다. 이 조정이 실제 여유 거리를 측정한 증거는 아니다.
- 왼팔 `PLAN ONLY COMPLETE`는 케이스 중심 XY 오차 약 9 mm, 닫힌 집게 끝이 림 위 약 18 mm였던 한 시점의 모델 계획 기록이다. 같은 실행을 `--execute`했을 때는 **그리퍼 닫기 뒤 수동 도착 자세로의 MoveIt 계획이 실패**했다. 이후 목표를 림 30 mm 위로 조정했다. 최종 로컬 코드의 계획 가능 여부는 당시 scene/팔 시작 상태에 좌우된다.
- 오른팔은 같은 케이스 도착 목표를 별도 코드로 만들었으나 `MoveIt could not plan to the 30 mm-above-case right pose`가 보고됐다. 오른팔 코드가 경로를 여러 번 찾도록 바뀌어도 고정된 왼팔이 통로를 막으면 단독 오른팔 계획만으로 해결되지 않는다. 사용자는 **왼팔을 실제로 비켜 주거나 양팔을 동시에 협조 계획/실행**하기를 원한다.

## 가장 중요한 기존 요구: 최소 drag 경로 (`trial_minimal_drag_route.py`)

이 요구는 11월 13일부터 명확했다. [당시 작업 기록](2026-11-13_작업정리.md)은 “안전한 앞·뒤 구간은 `send_goal`, 필요한 우회 구간만 drag”를 미완료 목표로 적었다. **MoveIt이 만든 원래 경로가 충돌한다는 뜻이 아니다.** 현재 자세에서 특정 끝점까지 SDK `send_goal` 한 번으로 가는 **관절 공간 직선 지름길**을 충돌 장면에서 검사하고, 그 지름길이 막히는 부분에만 MoveIt의 안전한 우회 경유점을 Pi drag에 넘기는 뜻이다. 직선 검사를 통과해도 SDK 펌웨어의 실제 보간 경로가 그 직선과 같다는 실물 검증은 아직 없다.

[`trial_minimal_drag_route.py`](trial_minimal_drag_route.py)를 오늘 다시 직접 읽어 확인한 현재 동작은 다음과 같다.

1. **한 팔 전용 시험**이다. RViz의 `arm_left` 또는 `arm_right` **Plan**으로 나온 한 팔의 MoveIt 경로를 `/jetcobot_dual/display_planned_path`에서 읽고, 양팔 실측 관절 상태와 `/jetcobot_dual/check_state_validity`를 이용한다. 반대 팔은 그 시점의 실측 자세에 고정해 검사한다. 두 팔의 동시 진행 경로를 검사하거나 실행하는 코드는 아니다.
2. 시작→끝 **하나의 지름길이 충돌하지 않으면 `ENDPOINT` 한 구간**을 고른다. 충돌하면 후보 경계점을 찾아 원래 계획에서 지나치게 벗어나지 않는 안전한 앞·뒤 `ENDPOINT` 구간을 최대한 확보하고, 가운데 필요한 부분만 `DRAG`로 둔다. 출력은 최대 `ENDPOINT → DRAG → ENDPOINT` 세 구간이다. 중간 지름길까지 안전하면 가운데도 `ENDPOINT`가 될 수 있다. 후보는 원래 경로의 최대 약 24개 경계점으로 제한하고, 끝점 지름길의 원 계획 대비 관절 편차 기본 상한은 3°다.
3. drag 구간은 `select_waypoints(..., 5.0, 1.5)`와 `round_joint_path(..., 3.0)`로 Pi에 보낼 경유점을 축약·둥글린 뒤 그 **축약된 실제 전송 후보**를 다시 충돌 검사한다. 60패킷 초과 또는 검사 실패면 이동 전에 오류로 중단한다. `ENDPOINT` 구간은 관절 지름길을 1° 간격으로 샘플링해 검사한다. 이는 이산적 모델 검사다.
4. 기본 실행은 **미리보기만** 한다. `--execute`일 때만 각 구간을 기존 `guarded_{side}_controller`로 순서대로 보내며, `sdk_drag_hybrid` 게이트가 각 구간을 다시 분류·검사하고 Pi로 전달한다. 이때도 **RViz에서는 Plan만 누른다. RViz Execute를 추가로 누르면 별도 전체 계획 실행이 될 수 있으므로 누르지 않는다.** 각 구간 후 새 실측 상태를 기다리고, 전환점과 계획점 차이가 3°를 넘으면 남은 구간은 중단한다. 자동 잔여 경로 재계획은 없다.
5. 이 시험 코드는 아직 **평소 `manual_roi_drag.py`/RViz Execute 경로에 통합되지 않았다.** 현재 `trajectory_backend:=sdk_drag_hybrid` 게이트의 일반 RViz Execute는 **계획 전체를** endpoint 또는 drag **하나로** 분류한다. 따라서 평소 UI에서 실행할 때 이 “최소 drag”가 자동으로 적용된다고 주장하면 틀리다. 더구나 오늘의 `coordinated_execution:=true`는 별도의 양팔 section 로직이어서 이 시험 코드와 다르다.
6. 이 스크립트에는 계획 시작과 실측 차이 `0.02 rad` 이내라는 오래된 시작 검사, 구간 전환 `3°` 검사가 남아 있다. 사용자가 오늘 양팔 게이트에서 거부한 촘촘한 기준과 혼동하지 말고, 실기 통합 전에 하드웨어 허용오차와 맞는지 따로 검토한다. **값만 임의로 완화해서 검증을 건너뛰지 말 것.** 11월 13일의 기록상 미리보기/일부 끝점 구간 실행은 있었으나, 최소 drag가 섞인 실물 경로의 반복 성공은 아직 확인되지 않았다.

다음 코드 작업의 방향은 **이 시험 코드의 선택 정책을 평소 게이트에 통합**하는 것이다. 안전한 구간은 `send_goal`, 우회가 필요한 연속 구간만 기존 drag 설정으로 실행한다. 구간 전환 시 실측 자세와 다른 팔 위치를 반영하고, 전환 실패 뒤에는 남은 경로를 실제 자세에서 다시 계획·분류해야 한다. 양팔 협조 실행에도 적용하려면 다른 팔이 동시에 움직이는 경우의 충돌 검사를 별도 설계해야 한다. 오늘 만든 “경로 전체를 작은 drag section으로 분할”을 최소 drag 구현이라고 부르지 말 것.

## 저녁: 양팔 협조 실행과 drag 회귀

### 구현 범위와 실제로 생긴 실패

- Gazebo에서는 통합 URDF로 양팔을 함께 계획해 한 팔이 다른 팔에게 길을 내주는 방식을 이미 해 봤다고 사용자가 말했다. 실물에서도 양팔을 실제로 동시에 움직이도록 **Pi 제어까지 새로 구현**하길 선택했다. 다만 현재 구현은 완성된 자동 양팔 적재가 아니라 opt-in 시험이다.
- 현재 추가된 파일: `pinky_ws/src/jetcobot_dual_real/jetcobot_dual_real/coordinated_route.py`, 수정된 `execution_gate.py`, `launch/dual_real.launch.py`, PC 시험 `right_place_trial/coordinated_see_center.py`, `coordinated_right_case.py`, 설명 `right_place_trial/COORDINATED.md`. `coordinated_execution:=true`는 MoveIt `both_arms`의 12관절 계획을 한 컨트롤러로 받고, 양쪽 Pi에 drag 목표를 보내는 구조다. 단일 팔 RViz 명령도 다른 팔을 측정 자세로 유지한 12관절 요청으로 확대한다. 이 구조는 코드에 있지만 사용자 시험에서 안정 완료되었다는 뜻은 아니다.
- 초기에는 충돌 검사와 section 동시 실행을 위해 허용오차를 2°로 강제하거나 PC 시작 오차를 0.02 rad로 제한하는 코드/설정이 들어갔다. 사용자는 JetCobot의 실제 오차를 수차례 설명하며 **2°/0.02 rad는 비현실적이고 5° 정도로** 요구했다. 이후 PC/Pi 로컬 소스에서 시작/끝 일부 조건을 5°로 느슨하게 했지만, 작은 요청에 `effective_goal_tolerance_deg(initial,target,configured)`가 **요청 진폭의 절반**으로 최종 허용오차를 다시 낮추는 코드가 남아 있다. 4° section이면 configured 5°라도 실효 목표 오차는 최대 2°다. 이 결합을 다음 작업자가 반드시 인식해야 한다.
- 오른팔 Pi 로그는 `DRAG FEEDBACK ... path_speed=0.00deg/s`, `joint_speed_deg_s=[0,...,0]`, `path_progress=1.5/4.0deg`, `corridor_error=0.58deg`가 여러 초 지속되다가 `Drag path did not reach measured final goal in time`이었다. **corridor error 0.58°가 작다는 것과 최종 목표까지 움직였다는 것은 다르다.** 진행이 4° 중 1.5°에서 멈춰 timeout난 것이다. 사용자는 실제로 목표 근처에서 멈춘 느낌이라고 했다. 원인은 이 로그만으로 기계적 걸림/SDK 자체/송신 시점 중 하나로 확정할 수 없다.
- PC `BOTH SEE_CENTER plan attempt 1/6` 뒤 `status=6, code=-4, Combined state stale or clocks differ; Pi cancellation does not prove physical stop`도 보고됐다. 별도 사례에서는 `left Pi rejected the combined section`이었다. 취소 요청이 두 Pi에서 실제 정지를 보증하지 않는다는 문구는 현재 게이트의 제한이다. 물리 상태를 확인하지 않고 같은 명령을 반복하면 안 된다.
- 오전/오후의 `SDK GOAL MOVE speed=10`은 native SDK 단일 끝점 명령이다. MoveIt preview 시간/경로를 추종하지 않는다. 이 경로와 **Pi drag 경유점 주행**을 같은 것으로 설명하면 안 된다. 양팔 협조 구현도 원래 전체 경로 drag를 그대로 보존한 것이 아니다.
- 오늘 마지막에 PC 로컬 `robot_bridge/sdk_drag_bridge.py` 기본 `drag_speed`를 200, `drag_send_interval_s`를 0.4로 바꿨다. **이 변경이 현재 양쪽 Pi에서 실행 중인 프로세스에 적용되었다는 확인은 없다.** 기존 tuned 5° waypoint 설정과 현재 런치 인자도 각각 대조해야 한다. 수치 기본값만 복구해도 section 분할 문제가 해결되는 것은 아니다.

### 다음 작업자가 drag를 다룰 때

1. **최종 목표는 `trial_minimal_drag_route.py`의 최소 drag 정책이다.** 보통의 안전한 지름길은 SDK `send_goal`, 충돌 회피가 필요한 우회 부분만 drag. [11월 13일 기록](2026-11-13_작업정리.md)의 **전체 MoveIt 경로 1회 drag 성공**은 drag 추종성에 대한 근거이지, 사용자가 전체를 항상 drag로 돌리고 싶다는 뜻이 아니다. 현 `safe_sections()`의 **전체 경로 section별 Pi drag action 반복**과도 다르다.
2. 양팔 충돌 안전을 위해 독립 진행 속도에서 각 팔의 가능한 위치 조합을 검사해야 한다는 목표는 유지할 수 있다. 다만 그 검사를 **주행 경로의 잘게 자르기/강제 정지·재시작**으로 해결하는 현재 구현은 사용자의 검증된 추종성을 잃었다. 향후 변경 전에 최소 drag 선택을 양팔 동시 움직임에 어떻게 확대할지, 서로 다른 진행 속도에서 충돌 여유를 어떻게 검증할지 설계를 분명히 하자. 현재 상태를 실기 안전/성공으로 주장하지 말 것.
3. 실패 원인 확인 시 PC gate가 실제 Pi에 보낸 trajectory 길이, Pi의 축약된 패킷 수, `drag_speed`/`drag_step_deg`/`drag_send_interval_s`, 각 Pi의 **실행 중 버전**을 비교한다. 11/13의 8°/0.8초 시험도 중간 정체했으며 원인은 미확정이므로 단순히 모든 정체를 section 분할 하나로 단정하지 않는다.
4. 사용자에게는 PC **로컬 수정만** 하고 전송할 파일과 명령을 제공한다. SSH/SCP를 대행하지 않는다. 실물 동작이나 Pi 재시작도 사용자가 한다. Pi 예시 명령에 사용자가 요청하지 않은 `max_move_deg` 숫자를 끼워 넣지 말 것. 물리 검증을 했다고 쓰지 말 것.

## 사용자 선호·주의 사항

- 사용자는 **짧고 직접적인 설명**을 선호하며, 수차례 보고한 하드웨어 오차나 이미 설정한 drag 조건을 다시 무시하는 변경에 강하게 불만을 표했다. 코드 변경 시 이유와 원래 방식에서 달라지는 점을 먼저 명확히 설명한다.
- UI에 검정 배경/패널로 카메라 영상을 가리지 않는다. 영어 간결 표기, 박스·현재선·허용 범위·BEST X/Y만. 노란 구형 오버레이와 수동 ROI 조작을 되살리지 않는다.
- 오른팔 fine XY의 수직 유지 문제와 수직 하강 보정은 구분한다. 사용자가 보정 해제나 자동 하강 제거를 요청한 적이 없다.
- 단독 팔 계획에서 `START_STATE_IN_COLLISION`이면 목표가 아니라 **현재 scene의 시작 자세**가 차단된 것이다. 충돌 패딩은 팔 간 거리만이 아니라 케이스에도 적용된다. RViz 외관과 실제 MoveIt 충돌 접촉 목록은 다를 수 있다.
- 코드를 바꾸면 **로컬 소스와 실행 중 Pi 버전을 구분**하고, 사용자에게 파일 전송/재시작 명령을 제공한다. 실기 성공 여부는 사용자가 보내는 로그와 실제 관찰로만 확정한다.
