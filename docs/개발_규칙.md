# 개발 규칙

## 작업 공간

저장소를 어디에 받을지는 사람마다 다르므로 고정하지 않습니다. 이 문서의 명령은 아래 두 변수를 씁니다. 각자 `~/.bashrc`에 자기 경로로 적어 둡니다.

| 변수 | 뜻 | 예 |
|---|---|---|
| `IPONIC_WS` | colcon 작업 공간 (`src/` 위 폴더) | `~/gg_ws`, `~/dev_ws` |
| `IPONIC_REPO` | 저장소를 받은 폴더 (`$IPONIC_WS/src/` 아래) | `$IPONIC_WS/src/roscamp-repo-2` |

`~/.bashrc` 예 (경로와 도메인 번호는 자기 것으로 바꿈):

```bash
# ---- iponic 개발 ----
export IPONIC_WS="$HOME/gg_ws"                       # 내 colcon 작업 공간
export IPONIC_REPO="$IPONIC_WS/src/roscamp-repo-2"   # 저장소를 받은 곳

source /opt/ros/jazzy/setup.bash   # net_ds.sh도 이 줄을 부름
[ -f "$IPONIC_WS/install/setup.bash" ] && source "$IPONIC_WS/install/setup.bash"

# 통신 설정은 tools/net/net_ds.sh 하나로 (docs/설계/디스커버리_서버_안내.md 5절).
# 새 터미널의 기본값은 혼자 하는 시험: 내 도메인 + 내 PC 안에서만, 서버 없음.
# 도메인 번호는 팀원끼리 겹치지 않게 각자 정함 (예: 41 ~ 49). 6은 쓰지 않음.
export IPONIC_MY_DOMAIN=43
iponic_local() { FLEET_DOMAIN_ID=$IPONIC_MY_DOMAIN FLEET_LOCAL=1 source "$IPONIC_REPO/tools/net/net_ds.sh"; }
iponic_real()  { source "$IPONIC_REPO/tools/net/net_ds.sh"; echo "실물 망: 도메인 6, 서버 $ROS_DISCOVERY_SERVER"; }
iponic_super() { SUPER=1 source "$IPONIC_REPO/tools/net/net_ds.sh"; ros2 daemon stop; ros2 daemon start; }
iponic_local

# 자주 쓰는 이동 · 빌드
alias cdi='cd "$IPONIC_REPO"'
alias cbi='(cd "$IPONIC_WS" && colcon build --symlink-install) && source "$IPONIC_WS/install/setup.bash"'

# Gazebo 시뮬레이션을 쓰는 사람만 (시뮬 launch와 모델은 이 저장소 밖 작업 공간에 있음)
# Jazzy의 짝은 Gazebo Harmonic(gz sim)이며, 모델을 못 찾을 때만 모델 폴더를 더함.
# export GZ_SIM_RESOURCE_PATH="$HOME/<시뮬 작업 공간>/install/<모델 패키지>/share/<모델 패키지>/models${GZ_SIM_RESOURCE_PATH:+:$GZ_SIM_RESOURCE_PATH}"
# 실물 Pode 시험 도구(tools/real_pode)가 쓰는 Nav2 작업 공간 위치가 기본값과 다를 때
# export NAV2FLEET_WS_SETUP="$HOME/<경로>/nav2fleet_ws/install/setup.bash"

# 장치 정체(로봇 장치에서만): 저장소 밖 파일에 둠
[ -f "$HOME/.iponic_env" ] && source "$HOME/.iponic_env"   # 예: export ROBOT_NS=pode1
```

- `.bashrc`를 고친 뒤에는 `source ~/.bashrc`를 하거나 새 터미널을 엽니다.
- Gazebo 줄은 주석으로 두었습니다. 이 저장소에는 Gazebo launch가 없고(시뮬은 별도 작업 공간), 환경 변수가 필요한지는 그 시뮬 패키지에 따라 다릅니다. 시뮬 패키지 launch가 모델 경로를 스스로 잡으면 필요 없습니다.
- 기본값을 혼자 하는 시험으로 두는 이유: 실수로 로봇 네트워크에 명령을 보내지 않게 하려는 것입니다. 실물 망에 붙을 터미널에서만 `iponic_real`을, 전체 그래프를 볼 터미널(`ros2` · RViz)에서는 `iponic_super`를 부릅니다. 바꾼 뒤에는 그 터미널에서 띄운 노드를 다시 띄웁니다.
- 로봇 · 팔 본체처럼 늘 실물 망에서만 도는 장치는 `iponic_local` 줄 대신 `iponic_real`을 둡니다. systemd로 띄우는 노드는 `.bashrc`를 읽지 않으므로 서비스 안에서 `net_ds.sh`를 `source`합니다.

## 빌드

저장소를 `$IPONIC_WS/src/` 아래에 받은 뒤 장치에 필요한 패키지만 빌드합니다.

```bash
cd "$IPONIC_WS" && source /opt/ros/jazzy/setup.bash
colcon build                                                                   # 관제 PC
colcon build --packages-up-to pode_fsm pode_dock pode_nav_config pode_avoidance pode_peer_obstacles pode_scan_filter iponic_bringup  # 핑키 Pi
colcon build --packages-up-to arm_control arm_vision iponic_bringup                 # 팔 PC
source install/setup.bash
```

핑키 Pi에는 제조사 패키지 `pinky_pro`도 있어야 합니다(`iponic.repos`에 고정한 커밋).

### 주문 처리(브리지) 개발 환경

`service_bridge`는 PostgreSQL(`psycopg`)과 웹(`fastapi` · `uvicorn`)을 씁니다. 시스템 파이썬을 어지럽히지 않도록 ROS 패키지를 그대로 볼 수 있는 공용 가상환경 `~/venv/iponic` 하나를 씁니다. 넣을 패키지와 버전은 `pc/requirements.txt` 한 곳에 적고, 패키지를 더할 때는 이 파일을 고친 뒤 다시 설치합니다.

```bash
python3 -m venv --system-site-packages ~/venv/iponic
~/venv/iponic/bin/pip install -r pc/requirements.txt
```

colcon이 저장소를 찾으려면 `$IPONIC_WS/src/` 아래에 있어야 합니다(없으면 연결).

```bash
mkdir -p "$IPONIC_WS/src" && ln -s "$IPONIC_REPO" "$IPONIC_WS/src/roscamp-repo-2"
```

시험은 DB가 떠 있어야 합니다. ROS 없이 `core`만 시험합니다.

```bash
docker compose -f design/db/compose.yaml up -d
~/venv/iponic/bin/python -m pytest pc/service_bridge/test -q
```

`service_bridge`의 실행(브리지 · 시험 도구)은 `ros2 run`으로 띄우지 않고, 가상환경의 파이썬으로 모듈을 실행합니다(`python -m service_bridge.…`). `ros2 run`이 꼭 필요한 실행이 아니고, `ros2 run`으로는 가상환경의 psycopg를 못 찾기 때문입니다. `--symlink-install`(`cbi`)로 빌드하면 colcon이 `setup.cfg`의 `[build_scripts]`를 무시하고 실행 파일 첫 줄에 `#!/usr/bin/python3`를 박습니다. 그래서 가상환경을 켜도 시스템 파이썬으로 돌아 `ModuleNotFoundError: No module named 'psycopg'`가 납니다. 가상환경이 필요 없는 `central` · 관제 노드 · `ros2 launch`는 그대로 `ros2 run` · `ros2 launch`로 띄웁니다.

ROS와 `install/setup.bash`를 `source`한 **뒤에** 가상환경을 켭니다(모듈은 `install`에서 찾음). `--ros-args`는 `ros2 run` 때와 똑같이 뒤에 붙입니다.

```bash
source /opt/ros/jazzy/setup.bash && source "$IPONIC_WS/install/setup.bash"
source ~/venv/iponic/bin/activate
iponic_local                                   # 개인 도메인 + LOCALHOST
python -m service_bridge.main --ros-args -p mode:=TEST
```

브리지 · central을 띄우는 터미널마다 `net_ds.sh`를 `source`합니다(`iponic_real` 또는 `iponic_local`). 브리지는 가상환경을 켠 뒤 같은 터미널에서 합니다.

| 실행 | 명령 |
|---|---|
| 브리지(웹 포함) | `python -m service_bridge.main --ros-args -p mode:=NORMAL` |
| 시험 DB 만들기 | `python -m service_bridge.tools.setup_db` |
| 주문 보내기 | `python -m service_bridge.tools.order --account 1 --items 3:2,5:1` |
| WS 보기 | `python -m service_bridge.tools.ws_watch --account 1` |
| 운반 건 직접 넘기기 | `python -m service_bridge.tools.submit_trip --items A:1,C:1` |
| fleet 대역 | `python -m service_bridge.tools.fake_fleet` |

손으로 한 바퀴 시험(터미널 넷, 모두 위처럼 준비, 저장소 폴더에서):

```bash
docker compose -f design/db/compose.yaml up -d && python -m service_bridge.tools.setup_db   # IPONIC_DB_DSN의 *_test DB를 지우고 다시 만듦
python -m service_bridge.main --ros-args -p mode:=TEST     # 브리지 대신 python -m service_bridge.tools.board_trips_stub [--trips FILE.json]도 됨
ros2 run central central
python -m service_bridge.tools.fake_fleet     # 매개변수 step_s · duplicate_every_report · missing
python -m service_bridge.tools.submit_trip --items A:1,C:1
```

central은 브리지의 `/bridge/list_board_trips`와 `/system/mode`가 보여야 실행 중이 됩니다. 브리지 없이 central만 볼 때는 위 브리지 줄 대신 `board_trips_stub`을 띄웁니다. `setup_db`는 DB 이름이 `_test`로 끝날 때만 돕니다. `fake_fleet`은 관제의 `fleet_manager_node`와 같이 켜지 않습니다.

## 실행

도메인 6은 로봇 네트워크(실물 망)이고, 모든 장치가 디스커버리 서버로 서로 찾습니다(IR-81 · IR-82, [디스커버리 서버 안내](설계/디스커버리_서버_안내.md)). 혼자 시험할 때는 반드시 다른 도메인 · `LOCALHOST` · 서버 없음으로 띄웁니다.

```bash
FLEET_DOMAIN_ID=43 FLEET_LOCAL=1 source "$IPONIC_REPO/tools/net/net_ds.sh"   # 또는 iponic_local
ros2 launch iponic_bringup pc.launch.py use_fake:=true scenario:=real_three_orders
```

ROS 없이 관제 로직만 시험할 때(저장소 폴더에서):

```bash
cd "$IPONIC_REPO"
pip install pytest pyyaml
PYTHONPATH=pc/fleet_core python -m pytest pc/fleet_core/test -q
```

## 규칙

- 개발 기준 브랜치는 `dev`입니다. 작업 브랜치는 `dev`에서 만들고 PR로 병합합니다. 브랜치 · PR · 버전 규칙은 [브랜치 운영 안내](브랜치_운영_안내.md)를 따릅니다.
- 브랜치는 `feat/…` `fix/…` `docs/…` `test/…` `refactor/…`, 커밋은 Conventional Commits.
- 인터페이스 이름·타입·QoS는 `interfaces/fleet_interfaces/contract.yaml`이 원본입니다.
- 로봇마다 다른 값(초기 위치, 도킹 보정, 카메라 보정, 팔 오프셋 등)은 코드나 브랜치에 두지 않고 `config/robots.yaml`의 그 로봇 항목에 둡니다. 장치가 누구인지는 저장소 밖 `~/.iponic_env`의 `ROBOT_NS`로 정합니다.
- Python 패키지 `setup.py`에는 `tests_require=['pytest']`를 넣습니다. 없으면 colcon이 시험을 한 건도 돌리지 않습니다.

## 이름 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 패키지 | snake_case, 앞말은 역할 | `fleet_core`, `pode_fsm` |
| 실행 파일 | 노드 이름 + `_node` | `fleet_manager_node` |
| 로봇별 노드 | 이름은 같게, namespace로 구분 | `/pode1/pode_fsm` |
| 토픽·서비스·액션 | `/{주인}/{무엇}` | `/fleet/zones`, `/pode2/move_to` |
| 로봇 ID | 소문자 + 번호 | `pode1`, `arm_ship` |
| 지점·구역 ID | 데이터에만 쓰고 ROS 이름에 넣지 않음 | `P-3`, `WORK` |
| 타입 | PascalCase, 목록은 `~Array` | `ZoneStateArray` |
| 상수·이벤트 코드 | UPPER_SNAKE | `STATE_MOVING`, `GOAL_RETRY` |
| 파라미터 | snake_case + 단위 | `release_distance_m` |
| launch | `{장치}.launch.py` | `pc.launch.py` |
| 브랜치 | `feat/` `fix/` `docs/` `test/` `refactor/` (+ 이슈 번호) | `feat/TT-25-report-trip` |
