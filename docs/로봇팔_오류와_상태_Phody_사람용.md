# Phody 로봇팔: 어떻게 움직이고, 어디서 멈출 수 있나 (사람용)

- 작성: Phody 담당, 2026-11-26 초안. AI용: [로봇팔_오류와_상태_Phody_AI용.md](로봇팔_오류와_상태_Phody_AI용.md)
- 목적: 관제(fleet) 쪽에서 `FillBasket`의 실패 사유(`reason`), 진행 단계(`phase`), 팔 상태(`ArmState`) 값을 정할 때 참고하도록, **로봇팔을 다뤄 보지 않은 사람 기준**으로 설명한다.
- 이 문서는 제안이다. 정한 것은 팀 명세에 넣고 다시 회의한다.

## 1. Phody가 하는 일 한 장 요약

Phody는 팔 두 개(`arm_left`, `arm_right`)가 작업판 위의 상품을 집어, 작업대(`WORK`)에 도킹한 Pode의 바구니에 담는다.

관제가 "초코바 3개 담아" (`/workcell/fill_basket`)를 보내면:

1. **사진 찍기**: 두 팔 손목 카메라로 작업판을 찍어 상품 위치를 계산한다.
2. 찾은 상품을 두 팔에 번갈아 나눠 준다.
3. 각 팔이 상품 하나마다 아래 **A → B → C → B**를 한다. 두 팔은 **동시에** 움직이지만, 바구니 근처(B · C)에는 **한 팔만** 들어간다.

| 구간 | 하는 일 | 쉽게 말하면 |
| --- | --- | --- |
| **A 집기** | 관찰 자세 → 상품 위로 이동 → 카메라로 위치 다시 맞추기(미세조정) → 내려가기 → 집게 닫기 → 들어 올리기 → 관찰 자세 | 상품을 집는다 |
| **B 옮기기** | 관찰 자세 ↔ 바구니 위 자세 | 바구니 쪽으로 간다 / 돌아온다 |
| **C 담기** | 바구니 위 → 내려가기 → 집게 열기 → 바구니 위 | 바구니에 놓는다 |

## 2. 로봇팔을 처음 보는 사람이 알아야 할 것

- **관절 골**: 팔은 "관절 6개를 이 각도로 만들어라"라는 명령을 하나씩 받는다. 상품 하나에 이런 명령이 10개 넘게 들어간다.
- **계획(IK)**: "집게를 여기 놓고 싶다" → "그러려면 관절 각도가 몇 도여야 하나"를 계산하는 것. 팔이 닿지 않는 곳이면 **답이 없다**.
- **충돌 검사**: 두 팔이 같은 공간을 쓰기 때문에, 움직이기 전에 "가는 길에 다른 팔이나 바닥에 부딪히지 않나"를 컴퓨터로 확인한다. 부딪힐 것 같으면 **출발하지 않는다**.
- **관절 상태**: 팔이 "지금 내 관절 각도는 이렇다"를 Wi-Fi로 계속 알려 준다. 이게 끊기면 PC는 팔이 어디 있는지 모르므로 **멈춘다**.
- **힘 빼기(토크 해제)**: 모터 힘을 빼면 팔이 사람 손으로 움직일 수 있게 되지만, **받쳐 주지 않으면 팔이 자기 무게로 떨어진다.** 상품을 쥐고 있으면 상품도 떨어진다.
- **집게**: 열기 / 닫기만 있다. 상품을 제대로 쥐었는지 재는 센서는 따로 없다.

## 3. 어디서 멈출 수 있나 (실제로 겪은 것)

Phody는 문제가 생기면 **그 자리에서 멈추고(일시정지) 사람을 기다린다.** 사람이 확인한 뒤 이어서 하거나 처음 자세로 되돌린다. 지금 자동으로 다시 시도하지는 않는다.

| # | 어디서 | 무슨 일 | 왜 생기나 | 상품 상태 |
| --- | --- | --- | --- | --- |
| 1 | 사진 찍기 | 요청한 개수보다 적게 보임 | 실제로 상품이 적거나(재고 부족), 가려져서 못 봄(인식 오류). **Phody는 둘을 구분하지 못한다** | 아직 안 집음 |
| 2 | A 계획 | 팔이 상품에 닿는 각도를 못 찾음 | 상품이 팔 끝 쪽이나 애매한 방향에 놓임 | 안 집음 |
| 3 | A · B · C 출발 전 | 충돌 검사에서 막힘 | 두 팔 경로가 겹침 | 그때 상태 그대로 |
| 4 | A 미세조정 | 카메라가 상품을 안정적으로 못 봄(20초) | 조명, 가림, 상품이 집게에 가려짐 | 안 집음 |
| 5 | A 집기 | 집게를 닫았는데 상품이 안 잡히거나 미끄러짐 | 위치 오차. **센서가 없어 Phody가 바로 알지 못한다**(다음 단계에서 사람이 봄) | 모름 |
| 6 | 어디서든 | 관절 상태가 끊김(몇 초) | Wi-Fi 끊김, 팔 쪽 컴퓨터가 각도를 느리게 읽음. 11-25에 7~8초 끊김을 실제로 겪음 | 쥔 채 공중에 멈출 수 있음 |
| 7 | 어디서든 | 움직이는 중 오류 → **고장 잠금** | 6번, 또는 팔이 명령대로 도착하지 않음. 잠기면 두 팔 모두 멈추고, 사람이 팔을 확인한 뒤 풀어야 한다 | 쥔 채 멈출 수 있음 |
| 8 | C 뒤 | 담고 나서 관찰 자세 높이로 못 돌아옴 | 6 · 7번과 같은 원인 | 이미 담음 |

## 4. 관제에 알려 줄 수 있는 것과 없는 것

| 알려 줄 수 있음 | 알려 주기 어려움 |
| --- | --- |
| 각 팔이 지금 A · B · C 중 어디인지 | 상품을 **진짜로** 쥐었는지 (센서 없음) |
| 멈췄는지, 멈춘 이유(위 표의 #) | 재고 부족인지 인식 오류인지 (#1) |
| 바구니 위에서 집게를 연 횟수 = 담은 수 | 바구니 안에 실제로 들어갔는지 (센서 없음) |
| 사람이 이어서 하기 / 되돌리기를 눌렀는지 | |

## 5. 제안: 관제에 보낼 값

**`FillBasket` 결과 `reason`** (실패할 때)

| 값 | 위 표 # | 뜻 |
| --- | --- | --- |
| `OUT_OF_STOCK` | 1 | 요청보다 적게 보임. 11-26 회의대로 지금은 재고 부족으로 본다(인식 오류와 구분 못 함) |
| `PICK_FAILED` | 2, 4, 5 | 상품을 못 집음. 팔은 멀쩡함 |
| `ARM_FAULT` | 3, 6, 7, 8 | 팔 쪽 문제. 사람이 봐야 함 |
| `CANCELED` | — | 관제가 취소 |

**`ArmState.detail`** (자세한 이유, 사람이 화면에서 보는 용도)

| 값 | 위 표 # |
| --- | --- |
| `ARM_UNREACHABLE` | 2 |
| `ARM_COLLISION_CHECK` | 3 |
| `FINE_ALIGN_FAILED` | 4 |
| `ARM_FEEDBACK_LOST` | 6 |
| `ARM_FAULT_LATCHED` | 7, 8 |

**`FillBasket` 피드백 `phase`**: `CAPTURING`(사진) · `PICKING`(A) · `TO_BASKET`(B 진입) · `PLACING`(C) · `RETURNING`(B 복귀)

## 6. 회의에서 정해 주셨으면 하는 것

1. 실패가 나면 관제는 무엇을 하나? (Phody는 멈추고 사람을 기다린다. 관제가 목표를 실패로 끝내길 원하는지, 사람이 이어서 할 때까지 기다리길 원하는지)
2. 위 `reason` · `detail` 값을 명세에 넣을지
3. 락 해제 = 힘 빼기(11-26 회의)일 때: **쥔 상품과 팔이 떨어지는 것**을 어떻게 할지 (예: 사람이 팔을 받친 뒤에만 해제, 또는 상품을 내려놓고 해제)
