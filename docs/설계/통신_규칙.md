# 통신 규칙

- 버전 v1.3 (2026-11-25). 사람과 AI(Claude · ChatGPT 등)가 **ROS 2 노드 사이 통신 코드를 쓰거나 고칠 때** 따르는 규칙입니다.
- **적용 범위:** 서비스 브리지 · central · fleet · 로봇 노드(Pode · Phody · Phony) 사이의 토픽 · 서비스 · 액션과 `fleet_interfaces` 정의. 화면 ↔ 웹(HTTP · WS)은 IR-50번대만 적용합니다.
- **적용 밖:** 화면 디자인, DB 스키마, 영상 전송(ROS 2 밖). 이 작업만 한다면 이 문서는 읽지 않아도 됩니다.
- 함께 볼 문서: [인터페이스 명세](인터페이스_명세.md)(이름 · 타입 · 정의), [설계 검토 사항](설계_검토_사항.md)(미확정 항목), [개발 규칙](../개발_규칙.md)(빌드 · 실행), [ROS 2 QoS 호환과 통신 안내](ROS2_QoS_통신_안내.md)(이 규칙의 배경 해설과 예제. 다르면 이 문서를 따름), [디스커버리 서버 안내](디스커버리_서버_안내.md)(IR-81 · IR-82의 설정 방법).
- 규칙 번호 `IR-nn`은 코드 리뷰 · 커밋 메시지에서 그대로 인용합니다. 근거의 "결정 #n"은 검토 기록(커밋 `869c359`의 `docs/통신_규칙_인터페이스_검토.md` 3장)의 번호입니다.

## 요약 (먼저 읽기)

1. 이름 · 타입 · QoS는 `contract.yaml`이 원본이다. 코드에 이름을 직접 쓰지 않는다. (IR-01)
2. 한 번 보내고 끝나는 토픽은 쓰지 않는다. 요청은 서비스, 결과 보고는 `Report*` 서비스다. (IR-10 ~ IR-12)
3. 모든 요청 · 보고에 번호를 붙이고, 받는 쪽은 같은 번호를 한 번만 반영한다. (IR-20)
4. 로봇 명령은 "켜기/끄기 전환"이 아니라 목표 값으로 보낸다. (IR-21)
5. 서비스는 비동기로 부르고 콜백 그룹을 나눈다. 콜백 안에서 블로킹 호출을 하지 않는다. (IR-30 · IR-31)
6. 시간 한도 · 다시 보내기는 IR-40 표를 따른다.
7. 관리 명령은 "접수 응답 + `ReportCommand` 결과 보고" 두 단계다. 시간 초과는 실패가 아니라 "결과 모름"이다. (IR-60 ~ IR-62)
8. 노드는 다시 켜질 수 있다고 가정한다. 켜지면 지금 상태를 다시 받고 나서 움직인다. (IR-70 ~ IR-73)
9. 실물 망은 도메인 6 + 디스커버리 서버(`tools/net/net_ds.sh` 한 곳)로 찾는다. 같은 서버면 도메인이 달라도 섞이므로 혼자 하는 시험은 서버 없이 LOCALHOST로 돌리고, 이름은 시스템 전체에서 겹치지 않게 한다. (IR-81 ~ IR-83)
10. 인터페이스를 바꾸면 `contract.yaml` · 명세 · (필요하면) 이 규칙을 같은 커밋에서 고친다. (IR-90)
11. [설계 검토 사항](설계_검토_사항.md)에 "열림"인 항목은 짐작해서 구현하지 않고 먼저 묻는다. (IR-92)

| IR-04 | 운반 건 번호 `trip_id`는 웹이 만든다. fleet 메시지의 칸 이름 `order_id`에는 `trip_id` 값을 넣는다. 상품은 `OrderItem.kind`(상품 코드)로 주고받는다. | 결정 #2 · #35 |
| IR-05 | 사유 코드는 contract의 사유 코드 표 한 곳에서만 새로 만든다. DB CHECK와 로봇 `detail` 코드도 같은 이름을 쓴다. 바깥(웹 · DB)으로 나가는 취소 철자는 `CANCELLED`다. | 결정 #18 · #37 |

## 2. 메시지 종류별 방식

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-10 | 메시지는 아래 표에서 종류를 먼저 고르고, 그 종류의 방식과 QoS를 쓴다. 토픽마다 따로 정하지 않는다. | 결정 #33 |
| IR-11 | **한 번 보내고 끝나는 토픽은 쓰지 않는다.** 받는 쪽이 준비되기 전 메시지는 잃는다(사전 시험: 같은 PC에서도 50/50). 한 번 보내야 하는 것은 서비스로, 상태는 주기적으로 다시 보내는 토픽으로 한다. | 사전 시험 L-01 |
| IR-12 | 결과 · 진행 · 알림 보고는 `Report*` 서비스(`ReportTrip` · `ReportCommand` · `ReportEvent`)로 보낸다. 브리지는 DB에 쓴 뒤 응답한다. | 결정 #18 · #25 · #28 |

| 종류 | 방식 | QoS |
|---|---|---|
| 한 번 보내는 요청 | 서비스 + 곧바로 접수 응답 | 서비스 기본 |
| 결과 · 진행 · 알림 보고 | `Report*` 서비스, 응답 없으면 같은 번호로 다시 (포기하지 않음) | 서비스 기본 |
| 오래 걸리는 작업 | 액션 | 액션 기본 |
| 지금 값 (상태판) | 토픽, 바뀔 때와 주기적으로 발행 | LATCHED: reliable · transient_local · depth 1 |
| 주기 상태 | 토픽, 받는 쪽은 최신 값만 | STATE: best_effort · volatile · depth 5 |
| 기록용 사건 | 토픽 (WARN 이상은 `ReportEvent`로도) | EVENT: reliable · volatile · depth 50 |
| 관제 신호 | 토픽, 0.5초 주기, 1.5초 끊기면 로봇이 멈춤 | HEARTBEAT: reliable · volatile · depth 1 |
| 영상 | ROS 2 밖 (GStreamer, UDP) | — |

## 3. 번호와 중복

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-20 | 모든 요청에 보내는 쪽이 만든 번호(`request_id`, UUID 문자열)를 넣는다. 받는 쪽은 같은 번호를 한 번만 반영하고 같은 결과를 돌려준다. 그래서 "응답이 없으면 같은 번호로 다시 보냄" 한 줄로 재시도가 끝난다. | 결정 #25 · #34 |
| IR-21 | 로봇 명령은 목표 값으로 보낸다 (`set_lock(locked=true)`). 증감 · 전환 명령을 만들지 않는다. 로봇은 최근 32건의 `request_id`를 60초 기억한다. | 결정 #25 ⑦ |
| IR-22 | `ReportTrip` 번호는 `(report_epoch, report_n)`이다. fleet은 켜질 때 `Hello`로 `epoch`를 받고, 받기 전에는 `Report*`를 보내지 않는다. `report_n`은 fleet 안에서 1씩 늘린다. | 결정 #18 · #36 |
| IR-23 | 보고에는 늘 **지금 상태 전체**를 싣는다(상태 · 누적 `placed` · `missing`). 기다리는 보고가 있으면 최신 상태로 바꿔 끼우고 새 `n`을 붙인다. | 결정 #18 · #34 |
| IR-24 | 웹은 운반 건마다 더 큰 번호만 반영한다. 같거나 더 작은 번호는 아무것도 바꾸지 않고 `DUPLICATE`로 답한다(재전송 · 재시작 이전의 늦은 보고). 번호는 더 크지만 허용되지 않는 전이(주문 DB 설계 5절 "허용 전이")는 덮어쓰지 않고 `LATE_REPORT`로 남긴다. 셋 다 `accepted=true`로 답해 다시 보내지 않게 한다. | 결정 #12 · #18, SB-01 · SB-03 (2026-11-24 확정) |
| IR-25 | 늦게 온 메시지는 시각이 아니라 번호로 가린다. 상태 값의 순서로도 가리지 않는다(접수됨 복귀가 정상 전이). | 결정 #18 · #36 |

## 4. 구현

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-30 | 서비스는 비동기로 부르고(`call_async`), 응답 콜백은 별도 콜백 그룹(MultiThreadedExecutor)에 둔다. | 결정 #34, 브리지 시험 IT-01 |
| IR-31 | 콜백 안에서 다른 서비스를 동기로 부르거나 기다리지 않는다. 블로킹 호출이나 DB 락을 잡은 채 응답을 기다리지 않는다. (교착 시험에서 실제로 멈춤) | 결정 #34, IT-01 |
| IR-32 | 서비스를 부르기 전 `wait_for_service`는 5초 이상 기다린다. | 결정 #34 |
| IR-33 | 발행 쪽과 구독 쪽은 같은 QoS 프로필을 쓴다. LATCHED 토픽을 구독할 때도 transient_local로 받아야 켜진 뒤 마지막 값을 받는다. | 결정 #33 |
| IR-34 | 상태 토픽은 주기적으로 다시 보낸다(로봇 상태 초당 5번 안팎). 받는 쪽은 1.5초 넘게 끊겼다가 다시 오면 "다시 연결"로 본다. | 결정 #26 · #30 |

## 6. 화면 ↔ 웹 (HTTP · WS)

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-50 | 주문 · 취소 · 관리 명령 요청에는 `Idempotency-Key`를 넣고, 같은 키면 같은 결과(관리 명령은 같은 `request_id`)를 돌려준다. 주문 · 관리 명령은 202 접수 후 결과를 WS 사건으로 보낸다. HTTP 한도 2초. | 결정 #32 · #34 |
| IR-51 | WS는 "상태"(최신 값만, 순번 없음)와 "사건"(DB 순번 `seq`, `since_seq`로 다시 받기) 두 가지다. 겉모양은 `{type, seq(사건만), ts, data}`. 연결하면 첫 메시지로 스냅샷. | 결정 #32 |
| IR-52 | 고객 WS에는 자기 주문 · 재고만, 고객 말로 바꿔 보낸다. 내부 상태 말 · 장애 사정은 싣지 않는다. | 결정 #32 |

## 7. 역할과 상태의 주인

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-55 | 운영 DB(주문 · 재고 · 운반 건 · 알림 등)의 주인은 웹이다. central은 운영 DB가 없고 웹과의 창구 · 주문판만 맡는다. 로봇 상태 · 이벤트 로그는 개발과 장애 분석에 쓰도록 운영 DB와 **나눈 로그 DB**에 기록한다. 로그는 짧은 시간에 많이 생기고 ROS 2 토픽 · 서비스를 받아 바로 써야 하므로 운영 DB와 나눈다. 로그 DB의 값으로 운영 상태를 정하거나 바꾸지 않는다(IR-57). 위치 · 종류 · 기록 노드는 Q-22. | 결정 #1 · #24, 사용자 결정 2026-11-25 |
| IR-56 | 업무 명령(이동 · 도킹 · 담기 · 교환 · 정지 · 이어서 하기)과 관리 명령은 모두 fleet이 로봇에 보낸다. central은 로봇에 직접 명령하지 않는다. | 결정 #24 |
| IR-57 | 상태의 주인은 하나다. 로봇은 몸 상태(이동 · 도킹 · 충전 · 오류 · 막힘 · 락 등), fleet은 업무 단계와 운반 건 상태를 정하고 `ReportTrip`으로 보고한다. 고객 취소는 웹이 직접 기록한다. 같은 값을 두 곳에서 정하지 않는다. | 결정 #22 · #24 · #29 |

## 8. 관리 명령

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-60 | 관리 명령은 두 단계다. ① 브리지 → fleet 서비스는 fleet 자기 판단만 담아 곧바로 응답(`accepted` · `reason` · `request_id` · `detail`) ② 최종 결과는 fleet → 브리지 `ReportCommand`. 로봇에 보내지 않는 명령도 처리 직후 `ReportCommand`를 한 번 보낸다. | 결정 #25 |
| IR-61 | fleet이 먼저 판단하고, 로봇 노드가 마지막 안전장치로 한 번 더 판단한다. 로봇의 거절은 서비스 응답으로 받고, 상태 토픽으로 거절을 알리지 않는다. | 결정 #7 · #25 |
| IR-62 | `ROBOT_TIMEOUT`은 실패가 아니라 "결과 모름"(UNCONFIRMED)이다. 늦은 응답이나 `/fleet/robots` 관측으로 끝 상태를 한 번만 정하고, 30초 안에 못 정하면 TIMEOUT으로 확정하고 알린다. | 결정 #25 ⑥ |
| IR-63 | 시험용 강제 입력(`force`)은 시험 모드에서만 받는다. 정상 운영이면 `NOT_TEST_MODE`로 거절하고 기록한다. | 결정 #13 |

## 9. 재시작과 모드

| 번호 | 규칙 | 근거 |
|---|---|---|
| IR-70 | 모든 노드는 다시 켜질 수 있다고 가정하고, 켜지면 지금 값을 다시 받고 나서 움직인다(LATCHED 토픽 + 켜질 때 확인 서비스). | 결정 #11 · #23 |
| IR-71 | fleet은 켜지면 `Hello` → `ListOpenTrips`(끝나지 않은 운반 건, 처음 접수 시각 순) → 진행 재개 순서를 지킨다. 브리지는 직전 `epoch`에서 진행 중이던 운반 건을 보류(`FLEET_RESTART`)로 쓴다. 기억하지 못하는 상태를 짐작해 보고하지 않는다. | 결정 #14 · #24 |
| IR-72 | 로봇은 켜질 때 모드 `UNKNOWN`(모드를 받기 전 업무 목표는 `MODE_MISMATCH`로 거절), 강제 값 모두 지움, 락은 잠김으로 시작한다. 상태 보고에 `boot_id`를 실어 재시작을 알린다. | 결정 #26 · #30 |
| IR-73 | 운영 모드는 브리지가 `/system/mode`(LATCHED)로 낸다. fleet · central은 켜질 때 읽고 다르면 연결을 거부하고 알린다. fleet은 로봇이 다시 연결될 때 · 보고한 모드가 다를 때 `set_mode`를 부르고, 그래도 다르면 배정에서 뺀다. | 결정 #13 · #30 |

| IR-81 | 로봇 네트워크(실물 망)는 `ROS_DOMAIN_ID=6`이고, 모든 노드가 디스커버리 서버로 서로 찾는다(`tools/net/net_ds.sh`). 혼자 하는 시험은 반드시 다른 도메인 · `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` · 서버 없음(`FLEET_LOCAL=1`)으로 띄운다. 여러 PC 통합 시험의 서버는 Q-18. | 개발 규칙, 2026-11-23 실물 시험(서버 없음: 늦게 합류한 Pode 격리 · 먼저 뜬 Pode 38 ~ 55초 멈춤, 서버 있음: 주문 4건 출고) |

| IR-83 | 디스커버리 서버는 노드보다 먼저 켜져 늘 돌아야 한다. fleet PC(0번) · central PC(1번)에서 부팅 때 켠다(systemd). 서버가 모두 꺼진 동안 새로 뜬 노드는 상대를 찾지 못하므로, 노드는 이를 "연결 안 됨"으로 다루고 서버가 돌아오기를 기다린다(IR-32 · IR-70). 이미 찾은 노드끼리는 서버가 꺼져도 통신이 이어진다. | 디스커버리 서버 안내 6절 · 8절 (C2 · C3: 한쪽 서버로 새 노드가 찾음, C10: 두 서버 모두 꺼도 기존 통신 이어짐, C11: 두 서버 모두 꺼지면 새 노드는 못 찾음), Confluence 2절(2026-11-19 PC 시험) |
