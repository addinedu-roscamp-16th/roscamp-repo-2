## 1. 읽는 법

- **번호는 원래 문서의 번호를 그대로 쓴다.** 새 번호 체계를 만들지 않는다. 원래 번호가 없는 항목만 4장에 `N-nn`(임시)으로 둔다. 이 번호는 설계 검토 사항에 `Q-nn`으로 올리면 지운다.
- 결정이 나면 **원본 문서를 먼저 고치고**, 여기서는 상태 칸만 바꾼다. 규칙 문구를 이 문서에 옮겨 적지 않는다.
- 상태 값:
  - **확정**: 원본에 확정으로 적혀 있음.
  - **합의 · 반영 전**: 토의에서 모두 같은 의견. 원본 문서 · 코드에는 아직 들어가지 않음.
  - **제안**: 원본에 제안으로 있음. 코드에 넣기 전에 사용자에게 확정을 묻는다.
  - **열림**: 정해지지 않음. 짐작해서 구현하지 않는다(IR-92).
  - **갈림**: 토의에서 의견이 나뉨. 사용자가 정한다.
- 중요도 (3장 · 4장은 영역마다 표를 **높음 · 낮음 · 따름** 셋으로 나누고, 각 표 안에서는 이번 주 것을 먼저 둔다):
  - **높음**: 사용자가 정해야 한다. 정하지 않으면 코드 · 인터페이스를 다시 짜거나, 운반 건 · 재고가 틀어질 수 있다.
  - **낮음**: 추천안 · 합의안대로 적용해도 된다. 값 · 이름 · 문서 자리만 남았거나, 나중에 더해도 다시 짤 일이 적다.
  - **따름**: 확정된 규칙이다. 정할 것 없이 지키기만 한다.
  - "시기" 칸에는 **이번 주**(2.1에 순번이 있음), **다음 주**, **상세 개발 때 · 측정 뒤**를 적는다.

## 3. 영역별 목록

### 3.1 관리자 알림

관리자 화면에 알리는 길은 세 가지다.
- **사건**: `ws_event`에 넣고 같은 트랜잭션에서 NOTIFY한다. 다시 연결하면 `since_seq` 뒤만 받는다.
- **상태**: 마감 상태처럼 NOTIFY만 하고 순번이 없다. 다시 연결하면 지금 값 전체를 받는다.
- **처리할 알림**: `alert` 행에 남기고, 해결 처리를 해야 닫힌다.

뿌리 규칙은 IR-51(상태와 사건)과 [DB] 4.8 · 4.14다.

### 3.2 재연결 · 재전송

연결 구간은 다섯 곳이다.
- 화면 ↔ 웹
- 웹 · 브리지 ↔ central
- fleet → 브리지 보고
- 브리지 재시작
- DB 연결

뿌리 규칙은 IR-20 ~ 25(번호와 중복), IR-40 · 41(시간 한도), IR-50 · 51(HTTP · WS), IR-70 ~ 73(재시작)이다.

## 7. 2단계 구현 방식 (2026-11-25 논의)

"2단계-주문 접수 REST API/WS 구현"을 어떻게 만들지 논의한 내용이다. 구현 순서의 이름은 다음과 같이 쓴다:
- **1단계-보고 반영 구현**: 옛 "1조각". `Hello` · `ReportTrip` → DB, PR #14.
- **2단계-주문 접수 REST API/WS 구현**: 옛 "2조각".

설계 문서는 따로 쓴다. 이 절은 방식을 고른 근거와 로봇 상태 전달 절차를 남긴다.

### 7.1 정한 것 (사용자 결정)

| 항목 | 결정 | 이유 |
|---|---|---|
| 범위 | API · WS만 만든다. 고객 · 관리자 화면(HTML · JS)은 따로 만들고, 화면이 나오면 별도 시험 계획으로 확인한다 | 화면은 스토리보드와 스타일만 있어, 함께 만들면 일이 많고 검수가 어렵다 |
| 확인 방법 | 화면 대신 시험 명령(주문 넣기, WS 받아 보기)과 `pytest`. 완료 기준 1번(고객 화면 바뀜)은 WS 사건 순서로 대신 확인 | 화면이 없음 |
| 고객 구분 | 이번 주는 인증 없이 주문 요청 본문과 WS 연결 주소에 `account_id`를 싣는다. 시험 계정은 seed로 만든다. 계정 번호를 읽는 곳은 함수 하나로 모은다 | 인증은 화면과 함께 정한다. 그때 그 함수만 바꾼다 |
| 운영 모드 바꾸기 요청(F-15) | 이번 주에서 뺀다. 모드는 켤 때 실행 인자(`-p mode:=TEST`)로만 정한다 | 화면이 없어 부를 곳이 없고, 이름 · 저장 위치가 아직 열려 있음([계획] 9장) |
| 웹 · 브리지 구성 | **A 안**: 한 프로세스(아래 7.2) | 계획 5.3에서 이미 정한 구성이고, 이번 주 목표에 가장 빠름 |
| 주문 나누는 순서 | 주문한 상품 순서대로 `basket_capacity`(4)씩 채운다 (설계자 판단) | DB 설계 4.6이 만드는 사람에게 맡긴 부분. 고객에게는 운반 건 수만 보임 |

### 7.2 구성 비교

**A 안. 한 프로세스에 웹을 얹음 (선택)**

```
[프로세스 1개]
 메인 스레드: FastAPI · uvicorn ── 비동기 DB 풀 ── LISTEN ifp_events → WS로 보냄
 뒷 스레드:   rclpy 실행기(BridgeNode) ── 동기 DB 풀
                ├ Hello · ReportTrip 서버 (1단계 그대로)
                ├ 1초 타이머: trip_dispatch 빈 줄 → SubmitTrip
                └ /fleet/robots 구독 → 메인 스레드로 넘겨 WS robots
 같은 프로세스 안: 주문 접수가 커밋되면 넘기기 타이머를 곧바로 깨움
```

- 장점: 1단계 코드를 그대로 쓰고, 이번 주에 가장 빨리 끝난다.
- 대가: 웹을 다시 켜면 브리지도 다시 켜진다. fleet이 보고를 다시 보내므로 잃는 것은 없다. 운영에서 나눌 때 `/fleet/robots`를 넘기는 길을 다시 만들어야 한다.

**B 안. 처음부터 두 프로세스, DB로만 이음 (운영에서 나눌 때의 후보로 남김)**

```
[웹 프로세스] FastAPI ── LISTEN ifp_events · robots → WS
[브리지 프로세스] rclpy ── trip_dispatch를 1초마다 확인 → SubmitTrip
                       └ /fleet/robots → pg_notify('robots', …) 초당 5번 이하
```

- 장점: 운영 구성(따로 띄움)과 같다. 웹 ↔ 브리지 내부 REST가 거의 필요 없어진다.
- 대가: 계획 5.3과 명세 1.1(운영은 내부 REST)을 바꿔야 한다. 이번 주 일이 조금 늘어난다.

**뺀 안**: 처음부터 내부 REST로 나누는 안. 이번 주에 만들 것이 가장 많고, 계획에서 이미 미룬 일이다.

### 7.3 로봇 상태가 화면까지 가는 절차

**앞부분 (A · B 공통)**

```
Pode 노드(pode_fsm) ×3 ── /{pode}/state (RobotState, 초당 5번 안팎, IR-34)
        ▼
fleet_manager ── 모아서 ── /fleet/robots (RobotStatusArray, LATCHED, 주기적으로 다시 발행)  ← F-11
        ▼
서비스 브리지가 구독
```

- 로봇 노드가 자기 상태를 초당 5번 안팎 낸다(IR-34). fleet이 여러 대를 한 메시지로 모아 `/fleet/robots`로 낸다.
- 이번 주에는 Pode 3대만 들어간다. contract의 `RobotStatus`에 `kind` 칸이 없어 팔은 다음 주에 넣는다.
- LATCHED라서 브리지가 늦게 켜져도 마지막 값을 바로 받는다.

**뒷부분: A 안 (선택, `pg_notify`를 쓰지 않음)**

```
브리지 구독 콜백 (rclpy 뒷 스레드)
   │ 화면 칸만 골라 바꿈 (robot_id · fsm_state · fault · battery · x · y · trip_id)
   │ 마지막 값 하나만 메모리에 둠 (새 값이 오면 덮어씀)
   ▼ 같은 프로세스 안에서 메인 스레드에 넘김 (asyncio call_soon_threadsafe)
FastAPI(메인 스레드)
   │ 초당 2 ~ 5번으로 줄여서
   ▼
/ws/admin 의 type "robots" ── 관리자 화면  ← F-12
```

- 화면이 새로 연결되면 메모리에 있는 마지막 값을 스냅샷에 넣어 보낸다.
- 로봇 상태는 DB에 쓰지 않는다.

**뒷부분: B 안 (참고)**

```
[브리지 프로세스] 구독 콜백 → 초당 5번 이하로 줄여서
   │  SELECT pg_notify('robots', '{"robots":[...]}')
   ▼
[PostgreSQL] 아무 표에도 쓰지 않고, 'robots'를 듣는 연결에 그대로 전함
   ▼
[웹 프로세스] LISTEN robots 로 받음 → 마지막 값 덮어씀 → /ws/admin "robots"
```

### 7.4 `pg_notify`(NOTIFY · LISTEN)의 역할

PostgreSQL에 들어 있는 간단한 알림 방송이다.

- 한 연결이 `LISTEN 채널이름`을 하면 그 채널을 듣는다. 다른 연결이 `pg_notify('채널이름', '글')`을 부르면, **그 트랜잭션이 커밋될 때** 듣고 있는 모든 연결에 글이 전해진다. 롤백되면 나가지 않는다.
- **저장하지 않는다.** 그 순간 듣고 있지 않던 연결은 받지 못한다. 웹의 LISTEN 연결이 끊긴 동안의 사건은 다시 연결한 뒤 DB에서 다시 읽어야 한다(4장 N-01).
- 글(payload)은 기본 설정에서 **8000바이트보다 짧아야** 한다. 넘으면 오류가 나고 그 트랜잭션도 실패한다.
- 이 프로젝트에서 쓰는 곳: `ws_event` 트리거(채널 `ifp_events`). 주문 · 운반 건 상태가 바뀌면 같은 트랜잭션에서 `ws_event`에 한 줄을 쓰고, `{seq, t, id, status}`처럼 짧은 값만 알린다. 웹은 `seq`로 DB에서 사건을 읽어 WS로 보낸다. 그래서 DB에 없는 사건이 화면에 가지 않는다.
- B 안에서 로봇 상태를 실을 때의 크기: 화면용 칸만 실으면 로봇 하나에 약 125바이트, 6대(Pode 3 · 팔 3)를 다 실어도 800바이트 안팎이라 한도의 10분의 1이다. 경로 좌표 · 오류 기록처럼 칸이 크게 늘 때만 신경 쓰면 된다.
- 같은 길에서 크기보다 신경 쓸 점:
  - 연결이 끊기면 그동안의 알림은 사라진다.
  - 알림은 커밋 때 나가므로 로봇 상태마다 짧은 트랜잭션이 생긴다(초당 5번 정도).
  - 받는 쪽이 느리면 PostgreSQL 공용 대기열(기본 8GB)이 찬다. 이번 규모에서는 걱정할 일이 아니다.

## 8. 화면 연결 요청 (2026-11-26)

고객 주문 화면과 관리자 상태 표시를 2단계 API · WS에 붙여 주문 한 건을 화면에서 끝까지 돌려 보려 한다. 화면은 [계획] 5.3대로 정적 HTML + 순수 JS로 만든다. 화면 모양은 사용자 · 관리자 스토리보드(사용자 v1.1 · 관리자 v1.4)와 화면 스타일 3안을 따른다. 2단계 설계 11장 "화면 담당과 맞출 것"에 대한 화면 쪽 답이기도 하다.

- 기준: [2단계 설계](../superpowers/specs/2026-11-25-order-intake-api-ws-design.md) 5 · 7장, [2단계 계획](../superpowers/plans/2026-11-25-order-intake-api-ws.md) Task 4 · 6, `core/snapshot.py`(`dev` `c023fef`, PR #17 기준. 반영은 `dev` `28f67db` 위 브랜치 `feat/screen-api-links`)
- 상태: 모두 **반영 (2026-11-26)**. 백엔드 담당이 네 건을 모두 받아들여 코드와 2단계 설계 5.5 · 5.6 · 7.4, 계획 Task 4 · 6, [인터페이스 명세](인터페이스_명세.md) 3.1 `stock`에 반영했다. 아래 8.2 표는 제안 당시 그대로 둔다.
- 설치: 화면 파일은 `setup.py` `data_files`가 아니라 `package_data`로 패키지와 함께 깐다(사용자 결정 2026-11-26). 웹은 `web/app.py` 옆 `static/`을 보므로 소스 · 설치본 경로가 같다. `static/test/`는 깔지 않는다.

### 8.2 요청 (제안)

| 번호 | 바꿀 것 | 제안 | 바꿀 곳 | 다른 안 (뺀 이유) |
|---|---|---|---|---|
