# 디스커버리 서버 안내

- 버전 v1.0 (2026-11-24) · 대상: 실물 망에 노드를 띄우는 모든 담당(Pode · 팔 · central · 서비스 브리지 · 관제) · ROS 2 Jazzy, Fast DDS 2.14
- 이 문서가 원본입니다. Confluence [디스커버리 서버 연결 안내](https://iphonic.atlassian.net/wiki/x/AQAlAQ)(관제 담당 작성)의 내용을 바탕으로, 서버 두 대 구성과 이 저장소의 스크립트(`tools/net/`)를 더했습니다. 시험 원자료와 관제 쪽 배포 상황은 그 페이지를 함께 봅니다(9절).
- 규칙은 [통신 규칙](통신_규칙.md) IR-81 ~ IR-83, 정하지 않은 것은 [설계 검토 사항](설계_검토_사항.md) Q-18 ~ Q-20에 있습니다.

## 1. 디스커버리 서버가 하는 일

ROS 2 노드는 통신하기 전에 "누가 어떤 토픽 · 서비스를 내고 받는지"를 먼저 서로 알아야 합니다. 이 과정이 **디스커버리(discovery)** 입니다.

| 방식 | 어떻게 찾나 | 문제 |
|---|---|---|
| 기본(멀티캐스트) | 모든 노드가 망 전체에 "나 여기 있다"를 뿌리고 서로 듣는다 | 노드 수의 제곱으로 알림이 늘고, Wi-Fi에서 멀티캐스트가 잘 빠진다. 장치가 늦게 합류하면 이미 돌던 장치가 흔들린다 |
| **디스커버리 서버** | 모든 노드가 정해진 서버에만 알리고, 서버가 "누구와 통신하면 되는지"를 알려 준다 | 서버가 없으면 새 노드가 상대를 못 찾는다 → 서버를 늘 켜 두고, 두 대로 둔다 |

- 서버는 **찾기만 돕습니다.** 서로 찾은 뒤의 실제 데이터(토픽 · 서비스 · 액션)는 노드끼리 바로 주고받고, 서버를 거치지 않습니다. 그래서 서버가 꺼져도 이미 찾은 노드끼리는 통신이 이어집니다.
- 서버는 ROS 노드가 아닙니다. Fast DDS에 들어 있는 별도 프로그램(`fastdds discovery`)입니다.

**왜 쓰나 (2026-11-23 학원 실물 시험, Pode 2대 · 주문 4건, [Confluence 1절](https://iphonic.atlassian.net/wiki/x/AQAlAQ))**

| 판 | 결과 |
|---|---|
| 서버 없음(멀티캐스트), 두 판 | 두 판 모두 두 번째 로봇이 합류하는 동안 먼저 뜬 로봇이 위치를 다시 잡느라 멈춤(38.6초, 55.5초). 두 번째 로봇은 시작 직후 격리되어 주문을 받지 못함 |
| 서버 있음, 한 판 | 주문 4건 모두 출고, 격리 0 |

## 2. 역할

| 역할 | 누가 | 하는 일 | 설정 |
|---|---|---|---|
| **서버** | fleet(관제) PC · central PC, 각 한 개 | 노드 목록을 모아 알려 줌 | `tools/net/discovery_server.sh <번호>` (systemd로 부팅 때 켬) |
| **클라이언트** | 모든 노드 (Pode · 팔 · central · 브리지 · 관제) | 서버에 자기를 알리고, 통신할 상대만 알려 받음 | `source tools/net/net_ds.sh` |
| **super client** | `ros2` 명령 · RViz 터미널 | 전체 그래프를 받아 봄 | `SUPER=1 source tools/net/net_ds.sh` |

보통 클라이언트는 **자기가 주고받는 상대만** 압니다. 그래서 그냥 `ros2 topic list`를 치면 일부만 보이거나 비어 보입니다. 전체를 볼 터미널만 super client로 엽니다.

## 3. 서버 두 대 구성

| 번호(`-i`) | 위치 | 주소 | 이유 |
|---|---|---|---|
| 0 | fleet(관제) PC | `192.168.0.252:11811` | 지금 쓰는 서버 그대로. 이미 배포된 pode1 · pode2가 이 주소만 알고 있어도 함께 돈다 |
| 1 | central PC | **미정** (Q-20) | 주문 흐름에 늘 필요한 PC. fleet PC가 꺼져도 새 노드가 상대를 찾는다 |

- 두 서버는 서로 목록을 나누지 않습니다. 모든 노드가 두 서버에 함께 붙으므로 각 서버가 전체 목록을 갖습니다. 그래서 서로 다른 서버 하나씩만 아는 두 노드는 서로 찾지 못합니다(C6).
- **이중화는 두 주소를 다 아는 장치에만 적용됩니다.** 서버 0만 아는 장치(이미 배포된 pode1 · pode2 등)는 서버 0이 살아 있는 동안은 함께 돌지만(C8 · C9), 서버 0이 꺼지면 새 연결을 서버 1로 바꾸지 못합니다. 이중화가 필요한 장치에는 두 주소가 든 `net_ds.sh`를 배포합니다.
- central PC 주소가 정해질 때까지는 0번 서버 하나로 돕니다. 정해지면 `tools/net/net_ds.sh`의 `DS_CENTRAL` 한 줄만 채웁니다.

## 4. 지켜야 할 것

1. **서버 목록 순서는 모든 장치에서 같아야 합니다.** Fast DDS는 `ROS_DISCOVERY_SERVER="주소0;주소1"`의 **순서를 서버 번호로** 씁니다. 순서가 다른 장치는 서버에 붙지 못합니다(아래 시험 C4). 순서는 `net_ds.sh` 한 곳에만 적고, 각자 복사해 고치지 않습니다.
2. **실물 망의 모든 장치가 서버를 씁니다.** 서버를 쓰는 노드와 쓰지 않는 노드(멀티캐스트)는 서로 찾지 못합니다. 두 노드는 공통 서버가 최소 하나 있어야 합니다(C6).
3. **같은 서버에 붙으면 도메인 번호로 갈라지지 않습니다.** 도메인만 바꾸고 서버 설정이 남아 있으면 실물 망에 그대로 섞입니다. 혼자 하는 시험은 서버 없이 `LOCALHOST`로 돌립니다(5절).
4. **이름이 시스템 전체에서 겹치면 안 됩니다.** 3번 때문에, 도메인으로 나눠 두던 묶음이 같은 서버에서 섞입니다. 팔 스택의 루트 이름(`/tf`, `/joint_states`, `move_group` 등)은 Q-19의 제안 이름 공간을 검토해 주세요.
5. **서버가 먼저, 노드가 나중.** 서버가 꺼진 동안 새로 뜬 노드는 상대를 못 찾고, 서버가 다시 켜지면 회복합니다. 서버 두 대 중 하나라도 켜져 있으면 됩니다(C2 · C3).
6. **설정을 바꾸면 그 장치의 노드를 모두 다시 띄우고, `ros2 daemon`도 다시 띄웁니다.** daemon은 처음 뜰 때의 설정을 계속 씁니다.
7. Fast DDS XML 설정(`FASTRTPS_DEFAULT_PROFILES_FILE`, `FASTDDS_DEFAULT_PROFILES_FILE`, 실행 폴더의 `DEFAULT_FASTRTPS_PROFILES.xml`)이 남아 있으면 디스커버리 설정을 덮을 수 있습니다. 쓰지 않습니다.

## 5. 언제 무엇을 쓰나

| 상황 | 서버 | 명령 (터미널마다) |
|---|---|---|
| 혼자 하는 개발 · 시험 (한 PC, 가짜 노드, Gazebo) | 쓰지 않음 | `FLEET_DOMAIN_ID=내번호 FLEET_LOCAL=1 source "$IPONIC_REPO/tools/net/net_ds.sh"` |
| 여러 PC 통합 · 연동 시험 | 시험용 서버 (포트 **미정**, Q-18) | `FLEET_DS="$TEST_DISCOVERY_SERVERS" FLEET_DOMAIN_ID=시험번호 source "$IPONIC_REPO/tools/net/net_ds.sh"` (목록은 따옴표로, `;`가 들어감) |
| 실물 운영 · 시연 | 실물 망 서버 (3절) | `source "$IPONIC_REPO/tools/net/net_ds.sh"` |
| 확인 터미널 (`ros2` · RViz) | 위와 같은 서버 | 위 명령 앞에 `SUPER=1`을 붙이고 `ros2 daemon stop; ros2 daemon start` |

- **잘못된 조합은 실패합니다.** 도메인이 6이 아닌데 `FLEET_LOCAL=1`도 `FLEET_DS`도 없으면, 또는 `FLEET_DS`가 빈 값이면 `net_ds.sh`는 아무 값도 바꾸지 않고 실패합니다(같은 서버면 도메인이 달라도 실물 망과 섞이기 때문). 노드는 `source … && ros2 launch …`처럼 이어서 띄워, 설정이 실패하면 뜨지 않게 합니다. 개인 작업에 도메인 6을 주어도 실패합니다.
- `FLEET_*` · `SUPER` 값은 같은 줄에서 `source` 앞에 붙입니다. 따로 `export`하면 셸에 남아 다음 `source`에도 적용됩니다. 의심되면 `unset FLEET_DOMAIN_ID FLEET_LOCAL FLEET_DS SUPER` 뒤 다시 `source`합니다.
- 개인 작업에서 `FLEET_LOCAL=1`을 빼면 서버에 붙어 실물 망에 보입니다. 시작 전에 `echo $ROS_DISCOVERY_SERVER`가 비어 있는지 봅니다. 시험 코드(`pode_fsm` · `fake_robots`의 ROS 시험)는 이 값이 있으면 건너뜁니다.
- **`tools/real_pode`(실물 Pode 실행 · RViz)는 아직 새 설정으로 바뀌지 않았습니다.** `start.sh`가 읽는 `env.sh`와 `rviz_pc.sh`가 도메인 12를 직접 넣고 서버를 설정하지 않으므로, `net_ds.sh`를 먼저 읽어도 실행 중에 다시 도메인 12가 됩니다. 관제 담당이 바꿀 때까지(설계 검토 사항 3장) 이 스크립트로 띄운 장치와 `net_ds.sh`로 띄운 장치를 섞어 시험하지 않습니다. 바꾼 뒤에는 실제로 뜬 노드가 도메인 6 · `rmw_fastrtps_cpp` · 의도한 서버 목록을 물려받았는지 7절 2번으로 확인합니다.
- launch가 띄우는 노드는 터미널 환경을 그대로 물려받으므로 launch 파일은 고치지 않습니다. systemd · 부팅 스크립트 · docker로 띄우는 노드는 `~/.bashrc`를 읽지 않으므로 그 안에서 `net_ds.sh`를 `source`하거나 같은 값을 넣습니다(docker는 `network_mode: host`와 함께).

## 6. 서버 켜기 (fleet PC · central PC)

부팅 때 켜지도록 systemd에 등록합니다(IR-83: 서버는 노드보다 먼저, 늘 켬). 예시 파일: `tools/net/iponic-discovery@.service` (`@` 뒤가 서버 번호).

```bash
# fleet PC는 0, central PC는 1
sudo cp "$IPONIC_REPO/tools/net/iponic-discovery@.service" /etc/systemd/system/
sudo systemctl edit iponic-discovery@0     # [Service] Environment=IPONIC_REPO=... User=... 를 자기 값으로
sudo systemctl enable --now iponic-discovery@0
ss -uln | grep ':11811'                     # 한 줄이 나오면 켜져 있음
```

등록 전에 손으로 켜 볼 때는 터미널에서 `"$IPONIC_REPO/tools/net/discovery_server.sh" 0`(앞에서 돌고, Ctrl+C로 끔). 이미 켜져 있으면(`ss -uln | grep ':11811'`) 또 켜지 않습니다.

## 7. 연결 확인과 문제 찾기

```bash
SUPER=1 source "$IPONIC_REPO/tools/net/net_ds.sh"
ros2 daemon stop; ros2 daemon start
ros2 node list                                        # 모든 장치의 노드가 보이는지
ros2 topic echo /pode1/state --qos-reliability best_effort --once --timeout 10
```

안 보이면 차례로 봅니다.

1. 서버가 켜져 있나: 서버 PC에서 `ss -uln | grep ':11811'`
2. 노드를 띄운 터미널의 값: `echo $ROS_DOMAIN_ID $RMW_IMPLEMENTATION $ROS_DISCOVERY_SERVER` (실물 망이면 `6 rmw_fastrtps_cpp 192.168.0.252:11811…`)
3. 미들웨어가 Fast DDS인가: `ros2 doctor --report | grep -i middleware` (Cyclone DDS는 이 서버를 쓰지 않음)
4. XML 설정 변수가 남아 있지 않은가 (4절 7)
5. 장치에서 서버 PC로 `ping`이 되는가
6. 서버를 켠 뒤에 노드를 다시 띄웠는가
