# 인터페이스 명세 (v0.2)

- 작성: 2026-11-20 · 상태: **초안** (팀 개발 시작용). 제출용(그림 + Confluence "Interface Specip")은 이 문서에서 내부 참조를 빼고 옮긴 것입니다.
- 지켜야 할 통신 규칙은 [통신 규칙](통신_규칙.md)(`IR-nn`), 미확정 항목은 [설계 검토 사항](설계_검토_사항.md)(`Q-nn`)에 있습니다.
- 근거 칸의 "#n"은 검토 기록(커밋 `869c359`의 `docs/통신_규칙_인터페이스_검토.md` 3장)의 결정 번호입니다.
- 기준 버전: contract **1.1** (2026-11-28, `/central/state` · `/bridge/list_board_trips`, 3.2 ~ 3.4 · 4.1). 처음 기준: contract **0.6** (`origin/feat/order-hold-interfaces` `201b2a9`). 2026-11-24 contract **0.7**에 `SubmitTrip` · `Hello` · `ReportTrip` · `SystemMode`(4.1 ~ 4.3)를, 2026-11-25 contract **0.8**에 `SetMode`(`/{robot}/set_mode`)와 `RobotState` 칸 추가(4.4 · 4.5)를, 2026-11-26 contract **0.9**에 나머지 "신규" · "변경"(3장 이름 · 4장 정의)을 넣었습니다. 0.6에 있는 것은 이름 · 타입을 그대로 쓰고, 바꾸거나 새로 만드는 것은 "0.6 대비" 칸에 적습니다 (#16).
- 용어: 검토 기록의 "통로 A ~ E"를 이 문서에서는 "구간 A ~ E"라 부릅니다.
- 표시: **유지** = 0.6 그대로 · **변경** = 0.6에서 칸 추가 · 이름 변경 · **신규** = 새로 만듦 · **미정** = 설계 검토 사항(`Q-nn`)에서 정함
- 이 문서가 다루지 않는 것: 다이어그램 · 스토리보드 수정([통신 규칙 반영 수정 요청](../../design/통신규칙_반영_수정_요청.md)), DB 칸 이름(주문 DB 설계 문서)

## 1. 한눈에 보기

### 1.1 노드와 구간

```
 [화면: 관리자 · 고객]
        │ A. HTTP · WS
 [주문 관리 웹 서비스 + DB]          ← DB 주인 (#1)
        │ REST (내부)
 [서비스 브리지] ──── B ────► [central 주문 처리]
        ▲  ▲                         │ D. 주문판 /central/orders
        │  └──────── C ──────────┐   ▼
        │   관리 명령 (브리지 → fleet) [fleet 관제]
        └─ 보고 (fleet → 브리지)  └────┤ E. 상태 · 액션 · 관리 명령
                                       ▼
            [Pode pode1 ~ pode3] [Phody arm_left · arm_right] [Phony arm_ship]
```

| 구간 | 사이 | 주로 오가는 것 | 근거 |
|---|---|---|---|
| A | 화면 ↔ 웹 | HTTP 요청(주문 · 취소 · 관리 명령), WS 상태 · 사건 | #32 |
| B | 브리지 ↔ central | 운반 건 넘기기 · 취소 · 작업 모드 · 마감 보류 | #22 · #23 |
| C | 브리지 ↔ fleet | 관리 명령(브리지 → fleet), 보고 · 결품 확인 · 복구(fleet → 브리지) | #18 · #24 · #25 · #28 |
| D | central ↔ fleet | 주문판(무엇을 할지), 끝난 운반 건 알림 | #24 |
| E | fleet ↔ 로봇 | 로봇 상태, 이동 · 도킹 · 담기 · 교환 액션, 관리 명령 | #24 ~ #27 · #30 |

역할 (#24 · #29):
- **웹**이 운영 DB를 갖고 주문 번호 · 운반 건 번호(`trip_id`)를 만듭니다. 운반 건 상태는 웹이 기록만 합니다.
- **central**은 웹과의 창구이고 주문판으로 "무엇을 할지"를 fleet에 알립니다. 운영 DB가 없습니다. 로봇 상태 · 이벤트 로그는 운영 DB와 나눈 로그 DB에 기록합니다(IR-55, 설계 검토 사항 Q-22).
- **fleet**이 업무 명령 · 관리 명령을 모두 로봇에 보내고, **운반 건 상태를 정해 브리지에 직접 보고**합니다.
- **로봇**은 몸 상태(이동 · 도킹 · 충전 · 오류 · 락 등)를 보고합니다.

## 2. 공통 값

메시지 종류별 방식 · 다시 보내기 · 중복 처리 · 시간 한도 · 시간 기준은 [통신 규칙](통신_규칙.md) IR-10 ~ IR-42를 따릅니다. 이 장에는 인터페이스에 실리는 값만 둡니다.

### 2.1 운반 건 상태 값

| `ReportTrip.status` | 뜻 | 고객 화면 | 정하는 쪽 |
|---|---|---|---|
| `RECEIVED` | 접수됨 (장애로 되돌아온 것 포함) | 접수됨 · [취소] 있음 | 웹(처음) · fleet(되돌림) |
| `ASSIGNED` | 배정됨 | 준비 중 | fleet |
| `FILLING` | 담는 중 (거리 정지 · 서비스 일시 정지도 이 상태) | 준비 중 | fleet |
| `FILLING_PAUSE` | 담기 일시 중지 (집기 실패 · 인식 오류 · 결품) | 준비 중 | fleet |
| `TRANSPORTING` | 운반 중 | 출고 중 | fleet |
| `SHIPPED` | 출고됨 | 출고 완료 | fleet |
| `PARTIAL` | 일부 출고됨 | 일부 출고 | fleet |
| `HELD` | 주문 처리 보류 (`reason`: `ROBOT_FAULT` · `ARM_FAULT` · `FLEET_RESTART`) | 준비 중 | fleet · 브리지(`FLEET_RESTART`) |
| `CANCELLED` | 취소됨 (사용자 취소는 웹이 직접 씀, 시스템 취소는 `NOTHING_TO_FILL`) | 취소됨 | 웹 · fleet |

0.6 내부 상수 `CANCELED`는 그대로 두고 fleet이 보낼 때 `CANCELLED`로 바꿉니다 (#18). 나뉜 주문의 고객 화면 말은 운반 건들의 요약입니다 (#3).

### 2.2 사유 코드 표 (contract 한 곳, #37)

DB CHECK와 로봇 `detail` 코드도 같은 이름을 씁니다.

| 분류 | 코드 |
|---|---|
| 요청 거절 (공통) | `NOT_FOUND` · `ALREADY_ASSIGNED` · `ORDER_STATE` · `NOT_STOPPED` · `LOCK_RELEASED` · `HOLDING_ITEM` · `NOT_TEST_MODE` · `MODE_MISMATCH` · `BATTERY_LOW` · `UNKNOWN_TARGET` · `NOT_READY`(복구 중) · `NOT_IMPLEMENTED`(받는 쪽 처리가 아직 없음) |
| 관리 명령 결과 | `ROBOT_REJECTED`(상세는 `detail`) · `ROBOT_TIMEOUT` |
| 담기 멈춤 · 실패 | `PICK_FAILED` · `RECOGNITION_ERROR` · `OUT_OF_STOCK` · `DISTANCE_STOP` · `PAUSE_REQUESTED` |
| 보류 | `ROBOT_FAULT` · `ARM_FAULT` · `FLEET_RESTART` |
| 로봇 상태 `detail` | `HEARTBEAT_LOST`(관제 heartbeat가 30 s 끊김, 팔은 작업을 계속하고 `ArmState.detail`로만 알림, 2026-11-27) |
| 취소 | `USER_CANCEL` · `NOTHING_TO_FILL` · `STOCK_RECHECK`(마감 뒤 재고 다시 확인) |
| 관리자 처리 · 되돌림 | `FORCED_SHIP` · `FORCED_PARTIAL` · `RETURNED_TO_SHELF` · `REASSIGN` (주문 DB 설계 이름) |
| 보고 반영 | `APPLIED` · `DUPLICATE` · `LATE_REPORT` |
| 주행 목표 실패 (`MoveTo` · `Retreat`) | `NAV_UNAVAILABLE`(Nav2 서버가 없어 목표를 보내지 못함) |

`NOT_READY` · `NOT_IMPLEMENTED` · `NAV_UNAVAILABLE` · `HEARTBEAT_LOST`만 이 문서에서 붙인 이름입니다. `UNKNOWN_TARGET`은 `FillBasket` 결과 사유(모르는 상품 코드)로도 쓰며 이름은 임시입니다. `OUT_OF_STOCK` · `USER_CANCEL` · `STOCK_RECHECK`와 관리자 처리 코드는 주문 DB 설계 이름 그대로입니다. DB의 옛 이름 `VISION_MISS` · `PODE_FAULT` · `PHODY_FAULT`는 `RECOGNITION_ERROR` · `ROBOT_FAULT` · `ARM_FAULT`로 바꿉니다.

central이 켜질 때 주문판을 세우는 길 (2026-11-28 제안 구현, SB-06 정정 제안과 함께 결정):

1. `CONNECTING`: `/bridge/list_board_trips` 서비스가 보이고 `/system/mode`를 한 번 받을 때까지 기다린다. 이 동안 `SubmitTrip` · `ReportOrder`는 `accepted=false`로 거절하고 `/central/orders`는 발행하지 않는다.
2. `SYNCING`: `list_board_trips`(`epoch=0`)로 끝나지 않은 운반 건을 받아 접수 시각 순으로 주문판에 넣는다. 답이 없거나 `accepted=false`면 1 → 2 → 4 → 8 → 10초(±20%) 간격으로 다시 부른다. `HELD`인 건은 "관리자 조치 대기"로 표시한다.
3. `RUNNING`: 주문판 발행 · `SubmitTrip` · `ReportOrder` 처리를 시작한다. 주문판은 이 단계에 들어간 뒤에만 발행한다.

브리지는 `/central/state`의 `boot_id`가 바뀌면 central이 다시 켜진 것으로 본다.

### 4.6 액션 (변경)

```
# action/FillBasket.action (변경)
# ---- result: reason에 더하는 값 ----
# 결과로 끝난 실패: fleet은 다시 보내지 않고 ReportTrip FILLING_PAUSE, 관리자 [담기 재개] · [보충 불가]를 기다림 (팔 관제 합의 ①, #19 ②)
# 결품인지 미인식인지 모를 때는 RECOGNITION_ERROR. PICK_FAILED는 Phody가 당분간 보내지 않음(관제는 자리만 둠)
string REASON_PICK_FAILED="PICK_FAILED"
string REASON_RECOGNITION_ERROR="RECOGNITION_ERROR"
string REASON_OUT_OF_STOCK="OUT_OF_STOCK"   # 담는 도중 결품
# 복구할 수 없는 팔 장애 (fleet은 ReportTrip HELD · ARM_FAULT, 새 목표를 내지 않음, #20). Phody가 당분간 보내지 않음
string REASON_ARM_FAULT="ARM_FAULT"
# ---- result: 칸 추가 ----
OrderItem[] placed_confirmed # 확인된 담은 수 (#26). 0.6 placed는 호환을 위해 같은 값
OrderItem[] uncertain        # 쥐고 있던 상품 (비어 있지 않으면 반드시 보류)
# ---- contract 1.0 (2026-11-27) ----
# result reason에 더하는 값: NOT_READY(잠깐 받을 수 없음, fleet이 2 s 뒤 다시 보내는 사유는 이것뿐, 첫 실패 뒤 2번까지(잠정), 넘으면 HELD ARM_FAULT)
#   UNKNOWN_TARGET(모르는 상품 코드로 목표 전체를 거절, 다시 보내지 않고 HELD ARM_FAULT, 이름은 임시)
# feedback: phase 값 CAPTURING · PICKING · TO_BASKET · PLACING · RETURNING, placed_total = 이 목표에서 두 팔이 담은 합(누적, 관제는 마지막 값을 씀)
# 스스로 멈춤 · 락 해제 · 거리 정지 한도 초과는 목표를 끝내지 않고 ArmState PAUSED로 두며 [복구]로 이어 감. 서비스 일시 정지 중에는 팔에 신호를 보내지 않고 담던 주문은 끝까지 담음
# 재시작으로 목표가 사라지면 관제가 [복구] 때 남은 상품(goal items 순서대로 placed_total만큼 뺀 나머지)으로 새 목표를 보냄. 재시작 뒤 옛 목표의 늦은 결과는 버림
# 시간 초과(fill_timeout_s = 1200 s, 잠정): 목표를 보낸 뒤 이 안에 결과가 없으면 관제가 목표를 취소. 지금은 PAUSED로 [복구]를 기다리는 동안에도 흐름 (멈출지는 정하는 중)
```

멈춤은 `ArmState`의 `PAUSED`로 알리고, `phase`는 위 5개 값을 씁니다.
`uncertain`이 있거나, 쥔 채 락 해제가 있었던 목표의 결과(`uncertain`이 비어 있어도)는 관제가 HELD(`ARM_FAULT`)로 둡니다 (Q-03 · Q-06 결정). `PICK_FAILED` · `ARM_FAULT`는 Phody가 당분간 보내지 않고, 결품인지 미인식인지 모를 때는 `RECOGNITION_ERROR`를 보냅니다.

`SwapBasket` · `Dock`은 0.6 그대로입니다 (`swap_basket`의 팔 이름만 `arm_ship`). `MoveTo` · `Retreat`은 result 사유에 `REASON_NAV_UNAVAILABLE="NAV_UNAVAILABLE"`(Nav2 서버가 없어 목표를 보내지 못함)만 더합니다.

| 흐름 | 순서 |
|---|---|
| 주문 | 화면 `POST /api/orders` → 웹이 운반 건으로 나눠 DB에 접수됨 → 브리지 `SubmitTrip` → central 주문판 → fleet 배정 → `ReportTrip`(ASSIGNED → FILLING → TRANSPORTING → SHIPPED) → 웹 DB → WS `trip_changed` |
| 취소 | 화면 → 웹 → 브리지 `CancelOrder` → 받아들이면 웹이 취소됨을 씀 (판단 주인은 Q-01) |
| 결품 사전 확인 | fleet `CheckStock` → 브리지 → 웹 REST → 모자라면 `ReportTrip`(FILLING_PAUSE, `OUT_OF_STOCK`) + `ReportEvent` |
| 담기 멈춤 | 집기 실패 · 인식 오류: FillBasket 결과 → `ReportTrip`(FILLING_PAUSE, `placed`) → [담기 재개] `resume_fill` → 새 목표 / 거리 정지 · 서비스 일시 정지: 목표 안에서 멈춤, 상태는 FILLING |
| 장애 | 로봇 상태 ERROR → fleet `ReportEvent` + `ReportTrip`(HELD, `ROBOT_FAULT` · `ARM_FAULT`) → 관리자 `force_partial` · `force_ship` · `return_to_shelf` / 담은 것 0개면 `ReportTrip`(RECEIVED) → 처음 접수 시각 순으로 다시 배정 |
