### 4.1 T-1 ROS 2 서비스 호출

**정해진 모양: central 호출 클라이언트** (한 번에 2초, 실패하면 1초 ±20% 쉬고 다시, 첫 요청 포함 5번, 최대 약 14초)

```python
class CentralCaller:
    TIMEOUT, GAP, MAX_TRIES, MAX_INFLIGHT = 2.0, 1.0, 5, 8
    def __init__(self, node, on_result):            # on_result는 call_soon_threadsafe로 웹에 넘김
        self.on_result, self.lock, self.jobs = on_result, threading.Lock(), {}
        g = MutuallyExclusiveCallbackGroup()
        self.cli = node.create_client(SubmitTrip, '/central/submit_trip', callback_group=g)
        node.create_timer(0.1, self._tick, callback_group=g)
    def submit(self, req):                           # FastAPI 스레드에서 불러도 됨
        with self.lock:
            self.jobs.setdefault(req.trip_id, dict(req=req, tries=0, fut=None, deadline=0.0, next_at=0.0))
    def _tick(self):
        now, finished = time.monotonic(), []
        with self.lock:
            for key, j in list(self.jobs.items()):
                if j['fut'] is not None and now >= j['deadline']:     # 응답 한도 초과
                    self.cli.remove_pending_request(j['fut']); j['fut'] = None
                    j['next_at'] = now + self.GAP * random.uniform(0.8, 1.2)
                    if j['tries'] >= self.MAX_TRIES:
                        del self.jobs[key]; finished.append((key, None, 'UNKNOWN'))   # 결과 모름 (4.3)
            inflight = sum(j['fut'] is not None for j in self.jobs.values())
            if self.cli.service_is_ready():
                for key, j in self.jobs.items():
                    if inflight >= self.MAX_INFLIGHT: break
                    if j['fut'] is None and now >= j['next_at']:
                        j['tries'] += 1; j['deadline'] = now + self.TIMEOUT; inflight += 1
                        j['fut'] = f = self.cli.call_async(j['req'])   # 같은 trip_id로 다시 보냄 (F-04)
                        f.add_done_callback(lambda f, key=key: self._done(key, f))
        for args in finished: self.on_result(*args)
    def _done(self, key, f):                         # 콜백 그룹 밖에서 돎
        with self.lock:
            j = self.jobs.get(key)
            if j is None or j['fut'] is not f: return                  # 이미 시간 초과로 정리됨
            del self.jobs[key]
        try: self.on_result(key, f.result(), 'OK')
        except Exception as e: self.on_result(key, None, f'ERROR:{e!r}')
```

- 서비스가 준비되지 않았을 때는 시도 횟수를 세지 않습니다. "5초 넘게 준비 안 됨 → 연결 안 됨" 표시는 따로 만듭니다.

**정해진 모양: `Hello` · `ReportTrip` 서버** (칸 이름은 명세 4.3)

```python
node.create_service(Hello, '/bridge/hello', self._on_hello, callback_group=MutuallyExclusiveCallbackGroup())
node.create_service(ReportTrip, '/bridge/report_trip', self._on_report, callback_group=MutuallyExclusiveCallbackGroup())

def _on_hello(self, req, resp):
    try:
        resp.epoch = self.db.hello(req.node, req.boot_id)    # 같은 boot_id면 같은 epoch (F-06)
        resp.accepted = True
    except DbError as e:
        resp.accepted, resp.reason = False, 'DB_ERROR'       # fleet이 같은 boot_id로 다시 보냄
    return resp                                              # 반환 = 응답, 커밋은 그 전에 끝남

def _on_report(self, req, resp):
    try:
        resp.result = self.db.apply_report(req)               # 트랜잭션 하나 (4.2 시간 한도)
        resp.accepted = True                                  # APPLIED · DUPLICATE · LATE_REPORT (IR-24)
    except DbError:
        resp.accepted = False                                 # fleet이 같은 번호로 다시 보냄
        return resp
    self.loop.call_soon_threadsafe(self.hub.trip_changed, req.trip_id)   # 커밋 뒤에만 웹 알림
    return resp                                               # 이 안에서 다른 서비스 호출 · 대기 금지 (IR-31)
```

#### 4.2.1 잠금 7001 (PostgreSQL advisory lock)

SB-05의 잠금 순서 맨 앞에 오는 "7001"의 설명입니다. 원본 정의는 주문 DB 설계 5절 "재고 기록"과 `design/db/order_db_extra.sql`(원장 트리거 152행, 마감 트리거 263 · 287행)입니다.

**무엇인가**
- 표의 행이 아니라 **번호로 정한 잠금 하나**입니다(advisory lock, 약속 잠금). 행과 상관없이 "7001번"에 걸고, 같은 번호를 잡으려는 트랜잭션끼리만 서로 기다립니다.
- `pg_advisory_xact_lock…` 계열이라 **트랜잭션이 끝나면(커밋 · 롤백) 저절로 풀립니다.** 따로 푸는 코드가 없어 풀기를 잊을 일이 없습니다.
- 7001은 이 용도로 정한 번호일 뿐 다른 뜻은 없습니다.
- 목적: 마감이 "어느 한 순간의 재고"를 깨끗하게 잡게 하는 것입니다.

**공유 잠금과 배타 잠금**

| | 공유 잠금 | 배타 잠금 |
|---|---|---|
| 잡는 쪽 | 재고 원장에 한 줄 쓰는 트랜잭션: 입고 · 반출 · **출고 차감**(`ReportTrip`의 출고됨 반영) · 조정 | 마감 시작 · 마감 확정 |
| 함수 | `pg_advisory_xact_lock_shared(7001)` | `pg_advisory_xact_lock(7001)` |
| 동시에 잡을 수 있는 수 | 상한 없음 (실제로는 DB 연결 수 · 연결 풀 크기만큼) | 1 |
| 막는 것 | 배타만 | 공유 · 배타 모두 |

- 배타는 진행 중인 공유가 **모두 끝날 때까지 기다리고**, 잡고 있는 동안 새 공유 요청을 모두 기다리게 합니다.
- PostgreSQL은 기다리는 순서를 지킵니다. 마감이 배타를 **기다리는 중**이면, 그 뒤에 온 공유 요청도 마감 뒤에 줄을 섭니다. 그래서 브리지의 `apply_report`는 `lock_timeout`(500ms)을 두고, 넘기면 `accepted=false`로 답해 fleet이 같은 번호로 다시 보내게 합니다.
- 7001을 잡지 않는 일(주문 접수 · 조회 · 이력 기록 등)은 영향을 받지 않습니다.

**공유 잠금의 역할: 왜 "서로 막지도 않는 잠금"을 잡나**

공유 잠금은 원장 기록끼리는 막지 않습니다. 원장 기록이 하는 일은 "지금 재고를 바꾸는 중"이라고 **표시**하는 것입니다. 마감 확정은 이 표시가 모두 사라질 때까지 기다렸다가, 그동안 새 표시가 생기지 못하게 하고 재고를 셉니다. 세 가지 방식을 비교하면 이렇습니다.

| 방식 | 원장 기록끼리 | 마감 확정과 원장 기록 | 결과 |
|---|---|---|---|
| **잠금 없음** | 동시에 진행 | **섞임** | 확정이 장부 수량을 읽은 뒤 · 커밋하기 전에 출고 차감이 끼어들 수 있음 → 장부 수량 · 차이가 어긋남 (아래 예) |
| **모두 배타** | 한 번에 하나씩 | 섞이지 않음 | 안전하지만 출고 보고 · 입고가 서로 줄을 섬. 로봇 여러 대가 동시에 출고하면 `ReportTrip`이 늦어지고 `lock_timeout`에 자주 걸림 |
| **원장 = 공유, 마감 = 배타 (지금)** | 동시에 진행 | 섞이지 않음 | 평소에는 기다림 없이 동시 처리, 마감 시작 · 확정의 짧은 순간에만 원장 기록이 잠깐 멈춤 |

**잠금이 없으면 생기는 일 (예)**

상품 A의 장부 재고가 10이고, 마감 실사에서 선반에 8개를 셌습니다. 그런데 마감 확정과 거의 같은 때에 A 1개의 출고 차감이 들어왔다고 합시다.

| 순서 | 마감 확정 (트랜잭션 ①) | 출고 차감 (트랜잭션 ②) |
|---|---|---|
| 1 | 장부 수량을 읽음: `book_qty = 10` | |
| 2 | | 원장에 `SHIP -1`, 재고 10 → 9, **커밋** |
| 3 | 차이 = 실사 8 − 장부 10 = −2 → `CLOSE_ADJUST -2` | |
| 4 | 재고 9 − 2 = **7**, 커밋 | |

- 선반에는 8개가 있는데 재고는 7이 되고, 마감 기록에는 장부 10 · 차이 −2라는 틀린 값이 남습니다. 맞는 값은 장부 9 · 차이 −1 · 재고 8입니다.
- 7001이 있으면 ②는 ①이 끝날 때까지 기다립니다. 반대로 ①이 먼저 기다리면, ②가 커밋한 뒤 ①이 장부 9를 읽습니다. 어느 쪽이든 결과는 재고 8입니다.
- 지금 설계에서는 마감 확정이 "진행 중인 운반 건 0건"도 검사하므로 이런 출고가 실제로 끼기는 어렵습니다. 그래도 입고 · 반출 · 강제 출고처럼 운반 건 검사로 걸러지지 않는 기록이 있어, 7001이 마지막 안전장치가 됩니다.

**알아 둘 점**
- 공유 잠금은 같은 상품을 동시에 고치는 원장 기록끼리의 충돌을 막지 **않습니다.** 그쪽은 원장 트리거가 `product` 행을 `UPDATE`할 때의 행 잠금이 한 줄씩 차례로 처리합니다. 7001은 "원장 기록 ↔ 마감"만 가릅니다.
- SB-05 순서(7001 → orders → trip → 원장 행)에서 7001을 맨 앞에 두는 이유는 모든 트랜잭션이 같은 순서로 잠가 교착을 없애기 위해서입니다. `apply_report`는 첫 줄에서 공유 잠금을 잡고, 원장 트리거가 같은 트랜잭션에서 다시 잡아도 문제없습니다.

### 4.3 T-3 실패 나누기

업계 기준은 같은 방향입니다.
- gRPC: 다시 보낼 코드는 앱마다 정하라고 하면서, UNAVAILABLE은 같은 호출을 다시, FAILED_PRECONDITION은 상태가 바뀔 때까지 다시 보내지 않음, **DEADLINE_EXCEEDED는 작업이 성공했어도 날 수 있는 "결과 모름"**으로 봅니다([status codes](https://grpc.github.io/grpc/core/md_doc_statuscodes.html), [retry](https://grpc.io/docs/guides/retry/)).
- AWS: 클라이언트 오류는 다시 보내지 않고 서버 오류는 다시 보냅니다. 재시도는 스택의 한 곳에서만 하고, 지수 간격 + 지터 + 재시도 양 제한을 둡니다. 멱등 키가 있으면 검증 오류를 뺀 모든 오류를 다시 보낼 수 있습니다([timeouts · retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), [idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)).
- Google SRE: 요청당 재시도 상한과 프로세스 전체 재시도 예산을 두고, 재시도는 한 층에서만 합니다([cascading failures](https://sre.google/sre-book/addressing-cascading-failures/)).
- Stripe: 500 · 네트워크 오류는 결과 모름이라 같은 키로만 다시 보내고 조회로 맞춥니다. 409는 같은 키가 처리 중이라는 뜻입니다([errors](https://docs.stripe.com/error-low-level), [idempotent requests](https://docs.stripe.com/api/idempotent_requests)).
- "결과 모름"을 화면에 따로 두는 사례: Kubernetes Pod의 `Unknown` 단계([pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)).

**실패 종류별 처리 표**

| 실패 상황 | 분류 | 브리지 동작 | 화면 표시 | 근거 |
|---|---|---|---|---|
| central · fleet 응답 없음(2초) | 결과 모름 | `remove_pending_request` → 같은 번호로 1초 ±20% 간격, 첫 요청 포함 5번 | 처음 2초 "보내는 중", 그 뒤 "다시 시도 중" | IR-20 · IR-40 · IR-41 |
| 5번 모두 응답 없음 | 결과 모름 **(IR-40과 다름, 팀 확인)** | 실패로 확정하지 않습니다. 운반 건은 접수됨으로 남겨 나중에 같은 번호로 다시 보내 확정합니다 | "확인 중(결과 모름)" | IR-40은 "화면에 표시"만 적음. gRPC DEADLINE_EXCEEDED · Stripe 500 |
| 서비스 준비 안 됨(5초) | 일시 · 보내지 않음 | 보내지 않고 기다렸다가 준비되면 보냄 | "연결 안 됨" 배너 | IR-32 · IR-40 |
| `accepted=false` + `NOT_FOUND` · `ALREADY_ASSIGNED` · `ORDER_STATE` · `NOT_STOPPED` · `LOCK_RELEASED` · `HOLDING_ITEM` · `NOT_TEST_MODE` · `UNKNOWN_TARGET` · `BATTERY_LOW` · `MODE_MISMATCH` | 영구 | 다시 보내지 않고 사유 기록 | 바로 사유 문구. 다시 하려면 새 키 | gRPC FAILED_PRECONDITION |
| `accepted=false` + `NOT_READY`(복구 중) | 일시 **(팀 확인)** | 간격을 늘려 같은 번호로 다시(예산 안에서) | "복구 중, 잠시 기다림" | gRPC UNAVAILABLE |
| 응답은 왔는데 형식 오류(표에 없는 사유, 빈 칸) | 결과 모름 + 결함 | 다시 보내지 않음, ERROR 로그 + 알림, 관측으로 확정 | "확인 중" + 관리자 알림 | gRPC INTERNAL |
| 브리지 DB 쓰기 실패(`Report*` 받는 쪽) | 일시 | `accepted=false` → fleet이 같은 번호로 계속 다시 | 없음(오래가면 알림) | 명세 4.3, IR-40 |
| 웹 HTTP 처리 중 DB 실패 | 일시 | 5xx, 키 결과는 저장하지 않음 | "다시 시도" 버튼(같은 키) | IR-50, Stripe |
| 같은 키에 다른 본문 / 같은 키 처리 중 | 영구 / 일시 | 409 | 오류 문구 / 기다렸다가 같은 키로 | IR-50, Stripe |
| `ReportCommand` UNCONFIRMED | 결과 모름 | 30초 안에 끝 상태를 한 번만 반영 | "확인 중" → 끝 상태 또는 TIMEOUT 알림 | IR-62 |
| WS 끊김 | 일시 | 서버는 정리만, 화면이 다시 연결(이번 주는 스냅샷, `since_seq`는 다음 주) | 마지막 값 유지 + "다시 연결 중" | IR-51 |

- 재시도는 브리지 한 층에서만 합니다. 화면 · 웹은 HTTP를 자동으로 여러 번 다시 보내지 않습니다.
- 관리자 화면에는 성공 · 실패와 다른 세 번째 표시("확인 중", 회색, 경과 초)를 둡니다. 고객 화면에는 "처리 중"만 보입니다(IR-52).

### 4.4 T-4 브리지 재시작 때 다시 낼 것

| 사실 | 근거 | 우리 브리지에서는 |
|---|---|---|
| transactional outbox: 업무 변경과 보낼 메시지를 같은 트랜잭션에 쓰고, 중계는 폴링이나 로그 추적으로 합니다. 보낸 뒤 표시하기 전에 죽으면 다시 보내므로 **최소 한 번 전달**이 되고, 받는 쪽이 번호로 중복을 거릅니다. 같은 묶음 안에서는 순서를 지킵니다 | [microservices.io](https://microservices.io/patterns/data/transactional-outbox.html), [Debezium outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) | central은 같은 `trip_id`를 한 번만 처리하므로(F-04) 다시 보내도 안전합니다 |
| 주문 DB에는 outbox 테이블도, "central에 보냄" 표시 칸도 없습니다. 주문 DB 설계는 브리지 자체 저장소(outbox 등)를 설계 범위 밖으로 두었습니다(시험 원형은 SQLite) | 주문 DB 설계 "하지 않는 것" | **팀 확인**: `trip.status = RECEIVED`이면서 아직 보내지 않은 건을 outbox로 볼지, 칸(예: `submitted_to_central_at`)을 더할지 정합니다 |
| transient_local(LATCHED) 마지막 값은 발행자가 가지고 있어, 브리지가 꺼진 동안 새로 켜진 노드는 그 값을 받지 못합니다 | ROS 2 QoS 문서 (Jazzy 원문 재확인 필요) | 브리지는 켜지자마자 `/system/mode`를 다시 발행합니다 |
| 브리지가 없는 동안 fleet의 `Report*` · `Hello`는 시간 초과 뒤 다시 보내지므로 잃지 않습니다 | IR-40 | DB가 준비되기 전에는 서비스 서버를 만들지 않습니다 |

**브리지가 켜질 때 하는 일 (순서)**
1. 설정을 읽고 노드를 만든 뒤 `/system/mode`를 발행합니다. DB와 상관없이 바로 냅니다.
2. 동기 풀을 열고 첫 연결을 확인합니다(`wait(timeout)`). 실패하면 3 ~ 4를 미루고 다시 시도합니다.
3. `bridge_session`을 읽어 로그에 남깁니다. **브리지 재시작은 fleet 재시작이 아니므로 epoch를 올리지 않고 `HELD` 처리도 하지 않습니다.**
4. `/bridge/hello` · `/bridge/report_trip` 서버를 만듭니다. 이때부터 fleet이 다시 보낸 요청이 반영됩니다.
5. `/fleet/robots`를 구독합니다(LATCHED). 1.5초 넘게 끊기면 "다시 연결"로 봅니다.
6. central이 준비되면(`service_is_ready`, 5초 넘으면 "연결 안 됨") 아직 보내지 않은 운반 건을 처음 접수 순으로 다시 보냅니다(동시 요청 상한 적용).
7. 1초 주기 outbox 확인 타이머를 시작합니다. 같은 프로세스 안 즉시 호출은 깨우는 용도로만 씁니다. 읽기 트랜잭션을 끝낸 뒤 `call_async`합니다(IR-31).
8. 웹은 LISTEN 연결을 먼저 연 다음 uvicorn을 시작합니다. 화면 WS는 연결할 때 스냅샷을 받습니다.

- 이번 주(한 프로세스): 웹을 다시 켜면 브리지도 같이 다시 켜집니다. WS가 끊기고 `/system/mode` 발행자가 잠시 사라지며, 처리 중이던 보고는 fleet이 다시 보냅니다.
- 운영(분리): 브리지가 다시 켜져도 WS는 유지됩니다. 웹이 다시 켜지면 브리지의 REST 호출이 실패하므로, 브리지가 3초 안에 `accepted=false`로 답하도록 REST 한도를 2초 이하로 둡니다.

### 4.5 T-5 관측성 (최소)

| 사실 | 근거 | 우리 브리지에서는 |
|---|---|---|
| OpenTelemetry는 이름이 정해진 구조화 로그에 추적 번호를 붙여 요청을 묶습니다 | [OTel logs](https://opentelemetry.io/docs/concepts/signals/logs/) | 이번에는 넣지 않고, 이미 있는 번호로 묶습니다 |
| rclpy 로거는 rcutils 기반이라 Python `logging`과 따로 돕니다. 출력 형식은 `RCUTILS_CONSOLE_OUTPUT_FORMAT`(`{date_time_with_ms}` `{severity}` `{name}` `{message}` 등)으로 바꿉니다 | rclpy `logging.py`, ros2_documentation About-Logging (jazzy) | fleet · central은 `RCUTILS_CONSOLE_OUTPUT_FORMAT='{date_time_with_ms} {severity} {name} {message}'`, `RCUTILS_COLORIZED_OUTPUT=0`, 메시지 안은 `key=value` |
| 시험 원형은 JSONL 사건 로그(`probe.py`)를 남겼지만 묶는 번호가 `order_id` 하나였고, rclpy · uvicorn · probe 형식이 서로 달랐습니다 | 원형 `probe.py` | 브리지 · 웹(한 프로세스)은 `log_event(ev, **kv)` 하나를 Python `logging` + JSON 형식으로 만들고 uvicorn 로그도 여기로 모읍니다 |

**묶는 번호**: 웹이 `Idempotency-Key`를 받아 `trip_id` · `request_id`를 정할 때 셋을 첫 로그에 함께 남깁니다. ROS 구간은 이미 칸으로 있는 `request_id` · `trip_id`만 씁니다(정의를 바꾸지 않음).

**로그 한 줄 예**

```
{"ts":"2026-11-24T10:02:03.120Z","lvl":"INFO","svc":"bridge","ev":"http_accept","idem_key":"6f1c…","trip_id":"T-0412","route":"POST /api/orders","code":202,"ms":14}
{"ts":"2026-11-24T10:02:05.140Z","lvl":"WARN","svc":"bridge","ev":"call_timeout","trip_id":"T-0412","target":"central","srv":"submit_trip","attempt":2,"ms":2003,"next_in_ms":1080}
2026-11-24 10:02:05.212 INFO fleet ev=report_sent trip_id=T-0412 report_epoch=7 report_n=3 status=TRANSPORTING
```

- `ev` 이름은 정해진 목록에서만 씁니다. 묶는 번호 이름은 `idem_key` · `request_id` · `trip_id`로 고정합니다. 시간은 `ms`, 재시도는 `attempt`.

**최소 지표** (이번 주는 구조화 로그를 `jq`로 세고, 지금 값은 `GET /metrics` JSON 하나로 냅니다. Prometheus는 묶음 E에서 검토)
- 구간 · 서비스별 호출 수와 결과별 수(ok · rejected(사유별) · timeout · not_ready · malformed)
- 재시도 수(`attempt > 1`), 5번을 모두 쓴 건수
- 구간별 응답 시간 p50 · p95 · 최대
- 결과 모름 건수(지금 값)와 TIMEOUT 확정 수
- 보내지 못한 운반 건 수와 가장 오래 기다린 건의 나이
- `Report*` 받은 수와 DUPLICATE · LATE_REPORT · DB 실패 수
- WS 연결 수 · 끊김 수 · 대기열 최대 깊이
- 서비스 준비 실패 수

### 4.6 규칙과 다른 제안 · 팀 확인 · 확인 필요

**규칙과 다른 제안 (IR-93에 따라 팀 확인 뒤 설계 검토 사항으로)**
1. **IR-32**: 콜백 · 타이머 안에서는 `wait_for_service`(내부에서 sleep)를 쓰지 않고, `service_is_ready` + "5초 넘게 준비 안 됨 → 연결 안 됨"으로 바꿉니다.
2. **IR-40 "실패하면" 칸**: 브리지 → central · fleet 요청이 5번 모두 응답 없으면 "실패"가 아니라 "결과 모름"으로 두고, 같은 번호로 나중에 다시 보내 확정합니다.
3. **IR-41에 덧붙임**: 노드별 동시 요청 상한은 서비스 QoS depth(10)보다 작게(8). 시간 초과로 버린 future는 내 작업 목록에서도 지워 늦게 온 응답을 거릅니다. 프로세스 전체 재시도 예산 값은 묶음 A에서 정합니다.
4. **IR-12 (운영 분리 뒤)**: 운영에서는 웹이 DB 주인이라(IR-55) 브리지가 DB를 직접 쓰지 않습니다. "DB에 쓴 뒤 응답"은 "웹 REST가 커밋 확인을 돌려준 뒤 응답"으로 읽습니다. 브리지 동기 풀은 이번 주 한 프로세스 구성에만 있습니다.

**팀 확인이 필요한 것**
- 보내지 않은 운반 건을 무엇으로 알아볼지 (`trip.status`만으로 볼지, 칸을 더할지) — 4.4
- `NOT_READY`를 일시 실패로 다시 보낼지 — 4.3
- 웹 사용자 취소가 orders → trip 순으로 잠그면 `apply_report`(trip → orders)와 교착이 납니다. 잠금 순서를 trip → orders → 원장으로 맞춥니다 — 4.2
- `LATE_REPORT`를 같은 번호로 다시 받을 때 알림이 겹치지 않게 `(trip_id, report_epoch, report_n)` 유일 키를 둘지 — 4.2
- fleet 쪽 코드(TT-27)가 `accepted=false`를 받으면 같은 번호로 다시 보내는지

**확인 필요 (자료로 확인하지 못함)**
- Fast DDS에서 서비스 depth 10이 클라이언트별인지 토픽 전체인지, lease duration 기본값과 서버가 사라진 뒤 `service_is_ready`가 false가 되기까지 걸리는 시간
- 서버 `send_response`가 TIMEOUT을 받았을 때 rclpy가 예외를 내는지 로그만 남기는지
- 커밋 도중 연결이 끊겼을 때 psycopg가 내는 예외
- transient_local 값이 발행자가 꺼지면 사라지는지 (Jazzy 원문으로 재확인)
- RFC 9110의 408 · 9.2.2 원문, OpenTelemetry 맥락 전파 문서, Prometheus 문서

이 항목들은 다음 주 묶음 A(장애 주입 시험)에서 직접 재서 확인합니다.

### 5.2 합의된 것 (문서에 반영할 안)

1. **콜백 예외 하나가 ROS 처리 전체를 멈춤** (①⑤): `MultiThreadedExecutor`는 콜백 예외를 `spin` 밖으로 올립니다(`executors.py` 1020-1021). 모든 콜백 · 타이머를 감싸 `accepted=false`로 답하고(서버 콜백은 맨 바깥 `except Exception`), spin 스레드가 죽으면 프로세스가 스스로 끝냅니다(docker는 unhealthy만으로 다시 켜지 않음).
2. **요청마다 절대 마감 하나** (②③): 구간별 한도를 더하지 않고, 받은 시각 + 2.5초를 마감으로 둡니다. 문장마다 남은 시간으로 `statement_timeout` · `lock_timeout`을 걸고(`set_config(..., true)`), 남은 시간이 0.2초 아래면 `accepted=false`, 잠금 실패 · 교착은 남은 시간이 1초 넘을 때만 한 번 더 합니다. `lock_timeout`(500ms)이 `deadlock_timeout`(1초)보다 짧아 교착도 잠금 실패(55P03)로 먼저 나오므로 지표 이름은 "잠금 실패"로 합니다.
3. **결과 모름의 생애 주기** (③, ②⑤ 동의)

   | 상태 | 다음 시도 간격 | 최대 나이 | 그 뒤 | 확정 조건 |
   |---|---|---|---|---|
   | 보내는 중 (1 ~ 5번) | 2초 한도, 1초 ±20% | 약 14초 | 결과 모름으로 | 응답 받음 |
   | 결과 모름 | 5 → 10 → 30 → 60초(상한) ±20%, 재시도 예산 적용 | 처음 보낸 때부터 10분 | 관리자 알림 "확인 필요", 60초 간격으로 계속. **자동 실패 처리 안 함** | 아래 |
   | `NOT_READY` 대기 | 1 → 2 → 4 → 8초, 5번 횟수에 넣지 않음 | 묶음 A에서 측정 | 결과 모름으로 | 일반 응답 |

   - 확정: 같은 `trip_id`로 다시 보낸 요청이 OK, **또는 다시 보낸 건에 `ALREADY_ASSIGNED`가 오면 성공**(4.3 표의 "영구 실패"를 고침), 그 밖의 영구 거절은 실패, 그 건의 `ReportTrip`(ASSIGNED 이상)이 오면 관측으로 확정, 고객 취소 · 관리자 처리가 있으면 멈춤.
   - 상태는 DB에 남겨 재시작 · 스냅샷 뒤에도 이어 갑니다(5.3의 `trip_dispatch`).
4. **동시 요청 상한 · 재시도 예산 · 스레드 · 풀** (①②③)
   - 동시 요청 상한은 서비스 depth가 근거가 아니라 **부하 제한**입니다(대상 노드별 4 ~ 8, 묶음 A에서 확정). 시간 초과로 버린 요청도 서버 큐에 남기 때문입니다.
   - 서버 쪽 서비스 QoS depth를 명시적으로 키웁니다(브리지 서버 · central `submit_trip`: KEEP_LAST 50 · RELIABLE · VOLATILE). 기본값과 다르므로 contract에 서비스별 QoS로 적습니다(인터페이스 변경 절차).
   - 재시도 예산: 대상 노드마다 토큰 통(최대 10, 실패 시 1 빼고 성공 시 0.1 채움, 5 이하면 재시도 멈춤, 첫 요청은 막지 않음). `Report*`는 "포기하지 않음"이라 예산 대상이 아닙니다.
   - `MultiThreadedExecutor(num_threads=6)`, 브리지 DB 풀은 DB를 쓰는 콜백 수(`Hello` · `ReportTrip` · outbox 타이머) 3, 최대 4.
5. **IR-32**: 켜질 때 메인 흐름에서만 `wait_for_service(timeout)`, 콜백 · 타이머 안에서는 `service_is_ready`만. ready는 응답 경로를 보장하지 않습니다. `kill -9` 뒤에는 Fast DDS lease 기본값 때문에 최대 약 20초 ready로 남습니다(①, 확신 중상).
6. **WS 사건 알림은 LISTEN 한 경로** (⑤, ② 지지): `ReportTrip` 반영 알림은 DB 트리거 → `ws_event` → LISTEN으로만 나갑니다. `call_soon_threadsafe`는 `robots` 상태에만 씁니다. 4.1 서버 뼈대의 `hub.trip_changed` 줄은 뺍니다.
7. **켜질 때 · 꺼질 때 순서** (⑤①, 4.4 순서를 바꿈)
   1. 설정 · JSON 로그 적용, `rclpy.init`(시그널 처리 끔), 노드 생성, `/system/mode` 발행, `Hello` · `ReportTrip` 서버와 `/fleet/robots` 구독 생성 (아직 spin하지 않음)
   2. `uvicorn.Server(Config(log_config=None, timeout_graceful_shutdown=5)).run()` → lifespan 시작
   3. `hub.loop = get_running_loop()`
   4. 웹 async 풀 · 브리지 동기 풀 열기(실패하면 readiness false, 백그라운드 재시도)
   5. LISTEN 전용 autocommit 연결 열고 받는 작업 시작
   6. 감싼 spin으로 executor 스레드 시작
   7. central이 준비되면 보내지 않은 운반 건 다시 보내기, outbox 타이머 시작
   8. `yield` → 소켓 열림, `/readyz` true
   9. 꺼질 때: readiness false, `hub.loop=None` → `executor.shutdown(2.0)` → spin 스레드 `join(timeout)` → `destroy_node` → LISTEN 취소 · 풀 닫기 → `rclpy.try_shutdown()`. spin 스레드가 죽어서 끝나면 종료 코드 1.
   - 기본 Executor의 `shutdown`은 진행 중 콜백을 기다리지 않고(289 · 292행), `MultiThreadedExecutor.shutdown`은 스레드 풀을 한도 없이 기다립니다. 종료 시간의 상한은 DB 시간 한도와 `join(timeout)`으로 겁니다(①).
8. **헬스체크** (⑤): `/healthz`(이벤트 루프 응답, spin 스레드 생존, 마지막 타이머 10초 이내), `/readyz`(시작 완료 · 종료 중 아님, DB `SELECT 1` 캐시, LISTEN 생존, 마지막 타이머 3초 이내). central 준비 여부는 정보 칸으로만 냅니다.
9. **`LATE_REPORT` 규칙** (②④): 주문 DB 설계 쪽("같거나 작으면 ACK만")에 맞추되 epoch로 나눕니다. 같은 epoch 안의 더 작은 `n`은 정상(옛 사본이 늦게 도착)이라 알림 없이 지표만, 지금 세션보다 작은 epoch의 보고만 `LATE_REPORT` 기록 · 약한 알림, 번호는 큰데 허용되지 않는 전이는 fleet 결함 알림. 알림 중복은 기존 `alert.event_id UNIQUE`에 `late:trip:e:n` 값 + `ON CONFLICT DO NOTHING`.
10. **fleet 보고 클라이언트(TT-27) 완료 조건** (④①): 지금 `origin/main`의 `ReportOutbox`는 `accepted=false`를 받으면 보고를 버리고, 처리 중 future를 지우지 않고 `retry_s`마다 새로 보냅니다. 이 모양을 따르지 않습니다.
    - `ReportTrip`은 `accepted=false`여도 버리지 않습니다. 운반 건마다 마지막 상태 하나만 두고, 바뀌면 새 `n`으로 바꿔 끼우며(IR-23), `accepted=true`까지 다시 보냅니다.
    - `(epoch, n)`은 보낼 때 붙입니다. `Hello` 전에는 쌓아 둡니다.
    - 처리 중 요청은 운반 건마다 하나, 한도를 넘기면 `remove_pending_request`, 간격 1 → 2 → 4초 · 최대 10초.
    - 시험: 브리지를 30초 끈 뒤 다시 켜면 보고가 빠짐없이 들어오고, 처리 중 future 수가 운반 건 수를 넘지 않음.
11. **DB 세부** (②): 출고 차감 SAVEPOINT에서는 `CheckViolation`(23514)만 잡습니다. 첫 보고는 `report_epoch`가 NULL이라 `(report_epoch, report_n) < (...)` 비교가 NULL이 되므로 `SELECT ... FOR UPDATE`로 현재 값을 읽고 판단합니다. `ALTER ROLE ... SET`은 새 세션에만 적용되고, 연결에 `application_name=bridge|web`을 넣습니다. `synchronous_commit`은 끄지 않습니다. 풀 연결에 세션 advisory 잠금을 걸지 않습니다.
12. **운영 분리 뒤**: 브리지 → 웹 REST는 다시 보내지 않습니다(재시도는 fleet 한 층). 같은 `(trip_id, epoch, n)`이 처리 중이면 웹은 잠금을 기다려(마감 안) 뒤 요청에 `DUPLICATE`로 답하고, 넘으면 503, 409는 "같은 번호에 다른 본문"일 때만. docker에서는 `network_mode: host` + `ipc: host`를 권합니다(SHM 전송 때문, ①).

### 5.4 "확인 필요"에서 답이 나온 것

- 서버 `send_response`가 시간 초과로 못 보내면 rclpy는 예외 없이 경고만 냅니다(①, 바이너리 문자열 확인). 서버 코드는 알 수 없으므로 클라이언트 재시도로 메웁니다.
- transient_local 마지막 값은 발행자 쪽에만 있어, 발행자가 꺼지면 새로 켜진 구독자는 받지 못합니다(①, DDS 정의). 이미 받은 구독자는 같은 값을 다시 받아도 아무 일도 하지 않게 만듭니다.
- 커밋 도중 연결이 끊기면 psycopg는 `OperationalError`를 내고, 커밋 여부는 알 수 없습니다(②, libpq 동작에서 추론, 확신 중간). 처리는 그대로(`accepted=false` → 같은 번호 → `DUPLICATE`).
- 아직 시험으로 확인할 것: 서비스 요청 큐(depth)가 클라이언트별인지 서버 전체인지, `kill -9` 뒤 ready가 false가 되기까지의 시간. 시험 방법은 ①의 의견대로 묶음 A에 넣습니다.

## 6. 주문 흐름 1차 구현 검토 의견 (2026-11-24)

DB 커밋 뒤 응답하고, 응답이 유실되면 같은 번호로 다시 보내며, WS 사건은 `ws_event`에서 한 경로로 전달하는 방향에 동의합니다. 이번 주에는 D-2의 영속 전송 기록을 채택하고, `ReportTrip`의 반영 판정과 D-3의 잠금 순서를 먼저 정할 것을 제안합니다.

1. **종료 보고의 반영과 재전송 종료를 구분합니다.** `LATE_REPORT`에도 `accepted=true`가 돌아오므로, 이 값만 보고 F-10을 호출하면 출고가 DB에 반영되지 않은 운반 건도 central 주문판에서 빠질 수 있습니다. `APPLIED`이거나 같은 종료 보고가 이미 커밋된 `DUPLICATE`일 때만 `ReportOrder`를 호출하는 조건을 제안합니다. 대기 보고를 최신 상태로 합치는 경우에는 `FILLING`이나 `TRANSPORTING`이 생략된 뒤 `SHIPPED`를 받았을 때 허용할 상태 전이도 정해야 합니다. [인터페이스 명세 4.3](인터페이스_명세.md) · [주문 흐름 1차 4.4, F-10](주문_흐름_1차_인터페이스.md)
2. **D-1·D-2에서 브리지와 central의 재시작을 각각 검토합니다.** `trip_dispatch`를 주문 등록과 같은 트랜잭션에 쓰면 브리지가 재시작해도 아직 넘기지 못한 건을 찾아낼 수 있습니다. central이 운반 건을 접수한 직후 응답이 유실되고 central까지 재시작하면, 브리지에는 미확정 건이 남고 central의 메모리 중복 기록은 사라집니다. 이번 주에 central의 주문판 복구를 미룬다면, 재시작을 감지한 뒤 신규 배정과 미확정 건 재전송을 언제 멈추고 다시 허용할지 정해야 합니다. `NOT_READY`는 일시 응답으로 분류해, 같은 `trip_id`의 처음 응답을 돌려주는 규칙이 복구가 끝난 뒤에도 `NOT_READY`를 반환하지 않도록 합니다. [설계 검토 사항 Q-02](설계_검토_사항.md) · [주문 흐름 1차 F-04](주문_흐름_1차_인터페이스.md)
3. **D-3의 잠금 순서를 마감 확정과 맞춥니다.** 출고 보고가 `orders`·`trip`을 먼저 잠근 뒤 원장의 `7001` 공유 잠금을 기다리고, 마감 확정이 `7001` 배타 잠금을 잡은 뒤 같은 주문 행을 기다리면 교착할 수 있습니다. 마감 확정은 접수된 주문도 재검사합니다. 원장에 쓸 수 있는 트랜잭션은 행 잠금 전에 `7001`을 획득하도록 공통 순서를 정하고, 출고 보고와 마감 확정을 동시에 실행해 검증할 것을 제안합니다. [원장 잠금 트리거](../../design/db/order_db_extra.sql) · [주문 DB 설계 5절 마감 확정](../superpowers/specs/2026-11-18-order-db-design.md)
4. **D-5의 서비스 큐 깊이는 측정 뒤 정합니다.** 기본 서비스 QoS와 동시 요청 상한으로 먼저 시험하고, 큐 적체나 유실이 확인되면 `depth=50`을 비교한 뒤 contract 변경을 결정할 것을 제안합니다. 우선 시험할 사례는 브리지가 내려간 동안 출고까지 진행된 뒤, 브리지 재시작으로 최종 보고가 다시 도착하는 경우입니다. DB 출고 반영과 central 주문판 제거가 그 순서로 각각 한 번만 일어나는지 확인합니다. [통신 규칙 IR-10·IR-41](통신_규칙.md)

### 6.1 응답 (2026-11-24)

원문 근거(통신 규칙 IR-24, 인터페이스 명세 4.3, 주문 흐름 1차 F-04 · F-10, 주문 DB 설계 5절, `order_db_extra.sql`)와 대조한 응답입니다.

| 의견 | 응답 | 근거 · 내용 |
|---|---|---|
| 1. 종료 보고 반영 판정 | **문제 제기 동의, 조건은 수정** | `LATE_REPORT`도 `accepted=true`라 DB에 반영되지 않은 건이 주문판에서 빠질 수 있다는 점은 맞습니다. 그러나 `APPLIED` · `DUPLICATE`일 때만 `ReportOrder`를 부르면 `LATE_REPORT` 건은 주문판에 영원히 남습니다. fleet은 `accepted=true`를 받으면 다시 보내지 않으므로 정리할 주체가 없습니다. 예: 비상정지 뒤 관리자가 수동 출고(P-12)한 건에 로봇의 `SHIPPED`가 늦게 오면 허용되지 않는 전이라 `LATE_REPORT`가 되지만 DB는 이미 출고로 끝나 있습니다. 주문판은 로봇 작업 기준이므로 **종료 보고가 `accepted=true`를 받으면 뺀다(지금 F-10 유지)**, DB와 어긋난 부분은 `LATE_REPORT` 알림으로 관리자가 정리합니다. |
| 1-a. `LATE_REPORT` 정의 충돌 | **먼저 풀 것** | IR-24는 "더 작은 번호도 `LATE_REPORT`", 주문 DB 설계 5절은 "같거나 작으면 ACK만, 더 큰 번호의 허용되지 않는 전이만 `LATE_REPORT`". 하나로 맞춰야 1항 판정이 정해집니다. |
| 1-b. `DUPLICATE`의 뜻 | **보완** | `DUPLICATE`만으로는 처음 처리가 반영이었는지 `LATE_REPORT`였는지 알 수 없습니다. 판정에 쓰려면 응답에 처음 결과를 실어야 합니다(응답 칸 변경이면 IR-90 절차). |
| 1-c. 단계를 건너뛴 전이 | **동의** | DB 설계에는 "ASSIGNED는 건너뛸 수 있다"(4.7)만 있고, IR-23으로 `FILLING` · `TRANSPORTING`이 빠진 채 `SHIPPED`가 오는 경우는 정해져 있지 않습니다. 허용 전이 표를 따로 둡니다. |
| 2. central 재시작 | **동의** | F-04 "같은 `trip_id`면 처음 응답 그대로"에 복구 중 `NOT_READY`가 처음 응답으로 저장되면 복구 뒤에도 같은 답이 나갑니다. F-04에 "접수 · 거절처럼 확정된 응답만 기억하고 `NOT_READY`는 기억하지 않음"을 넣습니다. 멈춤 · 재허용(이번 주 안): 브리지가 central 재시작을 알아채면 미확정 건은 다시 보내지 않고 관리자 알림을 열며, 새 운반 건 넘기기는 central이 `NOT_READY`를 그만 보낼 때 다시 허용합니다(D-1 "central 재시작은 지원하지 않음"과 같은 방향). |
| 3. 잠금 순서 | **제안 수용, 근거 수정** | 적힌 교착은 지금 코드에서는 나지 않습니다. 마감 확정은 7001 배타 잠금 바로 뒤 `v_in_flight` 0건을 검사하는데, 커밋 전인 출고 보고의 운반 건은 운반 중으로 보이므로 확정이 주문 행을 기다리기 전에 실패합니다. 재확인 대상도 "모든 운반 건이 접수됨인 주문"이라 출고 중 주문과 겹치지 않습니다. 그래도 "원장에 쓸 수 있는 트랜잭션은 행 잠금 전에 7001부터"는 예외 문서화가 필요 없고 검사 조건이 바뀌어도 안전하므로, D-3을 **7001 → orders → trip → 원장 행**으로 정리합니다. 동시 실행 시험의 기대 결과는 "확정이 '진행 중 운반 건 남음'으로 실패". |
| 4. 서비스 큐 깊이 | **동의** | 측정 뒤 정하는 것은 묶음 A "값은 측정 뒤 고정"과 같습니다. 다만 제시한 시험(브리지가 꺼진 동안 출고 → 재시작 → DB 반영 · 주문판 제거가 순서대로 한 번씩)은 1항 종료 판정을 검증하는 것이라 1항의 완료 조건으로 옮깁니다. |

## 7. 확정할 사항 (개발 단계별)

5장 쟁점(D-n)과 6장 검토 의견에서 남은 결정을 개발 단계별로 나눕니다. 기준은 "정하지 않으면 그 단계 코드를 쓸 수 없는가"입니다.

**쓰는 법 (사람 · AI 공통)**
- 상태가 **확정**이면 그대로 따릅니다. 다른 문서(통신 규칙, 인터페이스 명세, 주문 DB 설계)와 다르면 이 표를 따르고, "고칠 문서" 칸의 문서를 같은 작업에서 고칩니다.
- 상태가 **제안**이면 "안" 칸을 기준으로 논의합니다. 코드에 넣기 전에 사용자(팀)에게 확정 여부를 묻고, 짐작해 구현하지 않습니다.
- 확정되면 상태 · 날짜를 고치고 변경 이력에 남깁니다.
