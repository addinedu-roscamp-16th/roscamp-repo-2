## 2. 항목

### Q-01 고객 취소 판단 주인
- **상태:** 열림 · **근거:** 논의 1, 결정 #5 · #22
- **문제:** 운반 건 상태의 주인이 fleet으로 바뀌었는데(`ReportTrip`도 fleet → 브리지), `CancelOrder` 서버와 "모든 운반 건이 접수됨일 때만" 판단은 아직 central이다. central은 배정 사실을 볼 통로가 없다. 접수됨으로 되돌아온 운반 건의 취소도 허용했으므로(11-20 결정), fleet의 다시 배정과 취소가 겹치면 웹은 취소됨 · fleet은 배정됨(`LATE_REPORT`) · Pode는 취소된 건으로 움직일 수 있다.
- **안:** 판단을 fleet에 묻는 길(central이 fleet에 묻거나 `CancelOrder` 서버를 fleet으로)을 만든다.
- **결정되면 고칠 곳:** 명세 3.2 · 4.2 `CancelOrder`, 다이어그램 6-4, 결정 #5.

### Q-02 central 재시작 복구
- **상태:** 열림 · **근거:** 논의 2
- **문제:** `ListOpenTrips`는 fleet만 부른다. DB 없는 central이 켜질 때 주문판을 어디서 다시 채우는지 없다. 평소 배정 순서는 central 주문판이 정하므로 처음 접수 시각 순 정렬을 central 주문판에도 걸어야 한다. central은 `epoch`를 쓰지 않으므로 재시작 구분 방법도 정해야 한다.
- **결정되면 고칠 곳:** 명세 3.2 · 3.4, IR-70 · IR-71.

### Q-03 Phody 장애 동안 배정과 담은 것 0개 조건
- **상태:** 열림 · **근거:** 논의 3
- **문제:** Phody 장애 + 담은 것 0개 → 접수됨으로 되돌림(11-20 결정)인데, Phody를 고칠 때까지 다시 배정된 건 · 새 건이 계속 작업대로 가면 Pode 3대가 모두 묶인다. "팔 `holding=false`이고 `uncertain`이 빔" 조건이 Pode 장애에만 붙어 있다.
- **안:** 배정 조건에 "Phody 사용 가능"을 넣거나 장애 동안 자동 배정 보류. 쥔 채 장애가 난 Phody에도 조건을 걸고 `uncertain`이 있으면 보류.
- **결정되면 고칠 곳:** 명세 2.1, fleet 배정 규칙, 다이어그램 6-6 (수정 요청 CR-06 · CR-24).

### Q-04 관제 재시작 보류의 버튼 기준

- **상태:** 제안 (팔 담당이 수용 · 수정 · 거절로 답함) · **근거:** IR-82
- **문제:** 같은 서버에 붙으면 도메인으로 나눠 두던 묶음이 섞인다. 팔 스택이 루트 이름(`/tf`, `/tf_static`, `/joint_states`, `/robot_description`, `move_group` 등)을 쓰면 양팔(Phody)과 출고 팔(Phony)이 섞인다.
- **안:** contract에 있는 이름(`/workcell/fill_basket`, `/arm_ship/swap_basket`, `/{arm}/state` 등)은 그대로 두고(IR-01), 그 밖의 내부 이름만 스택마다 이름 공간 아래로 넣는다.

  | 스택 | 제안 이름 공간 | 예 |
  |---|---|---|
  | Phody (양팔 + MoveIt, 한 PC) | `/workcell` | `/workcell/joint_states`, `/workcell/move_group`, `/workcell/robot_description` |
  | Phony (출고 팔) | `/arm_ship` | `/arm_ship/joint_states`, `/arm_ship/move_group` |
  | `/tf` · `/tf_static` | 스택 이름 공간 안으로(`/workcell/tf`) 또는 frame 앞에 붙임(`arm_ship/base_link`) | 둘 중 팔 담당이 고름 |
  | Pode | 이미 `/pode1/…` | Nav2가 `/tf`를 루트에 내는지 통합 시험 때 `ros2 topic list`로 확인 |
- **결정되면 고칠 곳:** 팔 launch · 설정, IR-82 근거 칸, 디스커버리 서버 안내 4절.

### Q-20 central PC 고정 주소
- **상태:** 열림 · **근거:** 디스커버리 서버 안내 3절, 한 PC 시험 C1 ~ C11
- **문제:** 디스커버리 서버 두 대(0번 fleet PC `192.168.0.252`, 1번 central PC)로 하나가 꺼져도 새 노드가 상대를 찾게 하려면 central PC 주소가 고정되어야 한다. central과 fleet이 같은 PC라면 두 번째 서버를 둘 다른 장치를 정한다.
- **안:** 공유기에서 두 PC의 DHCP 예약. 정해질 때까지는 0번 서버 하나로 돈다(이미 배포된 장치와 함께 동작, C8 · C9).
- **결정되면 고칠 곳:** `tools/net/net_ds.sh`의 `DS_CENTRAL`, 디스커버리 서버 안내 3절, central PC systemd 등록(안내 6절).

### Q-21 두 팔 거리 정지 처리
- **상태:** 제안 (2026-11-25, 사용자 제안 · 양팔 담당 확인 전) · **근거:** 결정 #19, 기능 PHD-05 · PHD-08
- **문제:** 지금 문서(PHD-08 · SCR-12, 관리자 스토리보드, 명세 4.6 `PAUSED_DISTANCE`)는 거리 정지가 나면 바로 두 팔을 멈추고 관리자 [팔 재개]를 기다린다. 그런데 거리 정지는 궤적을 계산한 뒤 실행하는 단계에서 두 팔이 부딪히지 않게 멈추는 것으로, 운영 이상과 구분해야 한다.
- **안:**
  1. 궤적 실행 중 거리 정지가 나면 팔 쪽(양팔)이 궤적을 다시 계산해 다시 시도한다. 운영 보고는 하지 않는다.
  2. 궤적 계산 · 실행 기록은 운영과 별개로 **로봇 로그 DB**(IR-55, 2026-11-25 정정)에 남긴다. 로그 DB가 정해지기 전(Q-22)에는 팔 노드 로그 파일에 남긴다.
  3. 다시 시도 횟수는 **팔 노드 설정 값**(실행 매개변수 또는 설정 파일)으로 둔다. 집기 재시도 횟수(PHD-05)와 같은 방식이다. 운영 DB의 설정(`app_setting`)은 웹이 주인이라 팔 노드가 직접 읽지 않는다(IR-55).
  4. 횟수를 넘기면 팔 일시 정지 → fleet에 알림 → 관리자 알림(`alert`, 코드 `DISTANCE_STOP`). 운반 건은 `FILLING` 그대로다. 그래서 `DISTANCE_STOP`은 알림 코드이고 운반 건 이력 사유(`status_history` CHECK)에는 넣지 않는다.
- **양팔 담당에게 확인할 것:** 다시 계산 · 다시 시도를 팔 노드 안에서 할 수 있는지, 기본 횟수, 횟수를 넘겼을 때 fleet에 알리는 방법(`FillBasket` 피드백 `phase` 또는 결과).
- **결정되면 고칠 곳:** 명세 2.2 · 4.6(`PAUSED_DISTANCE`의 뜻) · `/fleet/resume_arm`, fleet 작업 목록 W-35 · W-42, 관리자 스토리보드(거리 정지 재개), 기능 목록 PHD-08 · SCR-12(원본은 Google 시트, 사용자가 고침).

### Q-22 로봇 상태 · 이벤트 로그 DB
- **상태:** 열림 · **근거:** IR-55 (2026-11-25 정정, 사용자 결정)
- **조사:** [로봇 로그 기록 서비스 기술 조사](로그_기록_서비스_기술_조사.md) v0.2 (제안 LG-01 ~ LG-10, 검토 의견 반영, 팀 확인 전)
- **정한 것:** 운영 DB(웹이 주인)와 나눈 로그 DB에 로봇 상태 · 이벤트를 기록한다. 쓰임은 개발과 장애 분석이다. 나누는 이유는 기록이 짧은 시간에 많이 생기고 ROS 2 토픽 · 서비스를 받아 바로 써야 하기 때문이다. 로그 DB의 값으로 운영 상태를 정하지 않는다.
- **정할 것:**
  1. 두는 곳 (예: 관제 PC)과 종류 (예: PostgreSQL의 다른 DB, 시계열 DB, 장치별 SQLite)
  2. 기록하는 노드와 담당 (토픽을 구독해 쓰는 기록 노드 하나 / 로봇 노드가 직접 씀)
  3. 기록 대상: 기록용 사건 토픽 `/central/events`(`FleetEvent`, 명세 3.5 "유지 (기록용)" — 지금 받는 쪽이 없음, 이 로그 DB가 받는 쪽), 상태 토픽(`/{robot}/state`, `/fleet/robots` 등) · 서비스 · 액션 결과, 팔 궤적 기록(Q-21), 주기 · 거르기. 놓치면 안 되는 알림(WARN 이상)은 지금처럼 `ReportEvent` → 브리지 → 운영 DB `alert`로도 보낸다(IR-10, W-24)
  4. 보관 기간 · 지우기, 시험 모드 기록을 나눌지
  5. 관리자 화면에서 볼지 (보더라도 운영 판단에는 쓰지 않음)
- **결정되면 고칠 곳:** 통신 규칙 IR-55, 인터페이스 명세 3.5(`/central/events` 받는 쪽), 주문 흐름 1차 3.3 "E 기록" 줄, 개발 규칙(실행 · 설정), Q-21의 2, 관제 · 로봇 노드.
