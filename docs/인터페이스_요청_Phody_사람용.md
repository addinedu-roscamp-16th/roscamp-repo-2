# Phody 인터페이스 확인 · 요청 (사람용)

작성: Phody 담당, 2026-11-25
받는 사람: 인터페이스 명세 · contract 담당

ROS를 잘 몰라도 읽을 수 있게 썼습니다. 같은 내용을 AI가 바로 작업할 수 있게 정리한 문서는 [AI용](인터페이스_요청_Phody_AI용.md)에 있습니다.

## 먼저: Phody가 하는 일

Phody는 작업대에 놓인 **로봇팔 두 대(왼팔 · 오른팔)** 입니다.

1. Pode(이동 로봇)가 바구니를 싣고 작업대에 와서 멈춥니다.
2. 관제(fleet)가 Phody에게 "이 상품 몇 개를 담아라"라고 시킵니다. 이 명령이 `fill_basket`입니다.
3. Phody는 두 팔 카메라로 작업대 위 상품 위치를 찾습니다.
4. 두 팔이 번갈아, 또는 동시에 상품을 집어 Pode 위 바구니에 넣습니다.
5. 다 담으면 관제에 "몇 개 담았고 몇 개 못 담았다"고 답합니다.

Phody는 관제에게 "지금 무엇을 하는 중인지"를 계속 알려야 합니다. 이것이 팔 상태(`/{팔}/state`)입니다. 관제는 Phody에게 잠그기 · 풀기, 운영 모드, 장애 처리 완료 같은 관리 명령도 보냅니다.

## 1부. 문서끼리 서로 다르거나 틀린 곳 (고쳐 주세요)

### 1-1. 팔 상태를 보낼 자리가 실제 코드에 없습니다

- **명세(설계 문서)**: "팔 상태 토픽 `/{팔}/state`를 되살리고, 내용도 늘린다."
- **팀 실제 코드(dev 브랜치의 contract 0.8)**: 이 토픽이 없습니다. 이름표에 등록된 팔도 `arm_ship`(Phony)뿐이고, Phody의 `arm_left` · `arm_right`는 없습니다.
- 통신 규칙에서 "이름은 contract가 원본"이라고 정했기 때문에, 지금 상태로는 **Phody가 상태를 낼 방법이 없습니다.**
- **부탁:** contract에 팔 상태 토픽을 넣고, 이름표에 `arm_left` · `arm_right` · `arm_ship`을 넣어 주세요.

### 1-2. 팔 상태와 담기 명령의 내용이 옛 버전입니다

- 팀 코드의 팔 상태 메시지는 아직 칸이 4개뿐입니다. 명세에서 새로 정한 칸(락, 쥐고 있는지, 운영 모드, 재시작 번호 등)이 없습니다.
- 담기 명령(`fill_basket`)의 결과에도 명세에서 더한 칸("확인된 담은 수", "쥐고 있던 상품")과 새 실패 이유가 없습니다.
- **부탁:** 명세 v0.2 내용을 팀 코드 정의에도 넣어 주세요.

### 1-3. "지금 어느 단계인지" 값이 정해지지 않았습니다

- 담기 명령은 진행 중에 "지금 단계"(`phase`)를 알려줍니다. 그런데 어떤 단계 이름을 쓸지 정해진 게 없습니다. 명세에는 "거리 때문에 멈춤", "서비스 일시 정지" 두 개만 있습니다.
- **Phody 제안:** 사진 찍는 중 → 집는 중 → 바구니로 가는 중 → 담는 중 → 돌아오는 중, 그리고 멈춤 두 가지.

### 1-4. 설계 브랜치의 이름표가 옛날 이름입니다

- 설계 브랜치(`docs/design`)의 로봇 목록 파일은 아직 `arm1` · `arm2` · `arm3`입니다. 팀 코드(dev)와 명세는 `arm_left` · `arm_right` · `arm_ship`입니다.
- **부탁:** 설계 브랜치도 새 이름으로 맞춰 주세요.

## 2부. 정해진 게 없어서 Phody가 만들 수 없는 것 (정해 주세요)

### 2-1. 바구니가 정확히 어디 있는지

- Phody는 지금 바구니 위치를 **고정된 숫자**로 알고 있습니다.
- 실제 바구니는 Pode 위에 있습니다. Pode가 작업대에 설 때마다 몇 mm씩 다르게 서면, 상품을 바구니 밖에 놓을 수 있습니다.
- **정해 주세요 (셋 중 하나):**
  1. Pode가 지켜야 할 도착 오차를 정한다 (예: 1 cm, 3° 안)
  2. Pode나 관제가 바구니의 실제 위치를 알려준다
  3. Phody가 카메라로 직접 잰다 (이 경우 Phody 일이 늘어납니다)

### 2-2. 상품 이름 목록

- 주문에는 상품이 "상품 코드"로 옵니다. 그런데 어떤 코드가 있는지 목록이 없습니다.
- Phody 카메라는 지금 "초코바"만 알아봅니다. 멘토스는 아직 꺼 두었습니다.
- **정해 주세요:** 상품 코드 목록과, 그중 Phody가 집을 수 있는 것.

### 2-3. "재고 없음"과 "못 알아봄"을 어떻게 나눌지

- 5개를 담으라고 했는데 카메라에 3개만 보이면, 정말 재고가 없는 건지 카메라가 못 본 건지 Phody 혼자서는 알 수 없습니다.
- **정해 주세요:** 이럴 때 어떤 이유로 보고할지.

### 2-4. "락 해제"가 로봇팔에서 무엇을 뜻하는지

- 우리 로봇팔은 모터 힘을 빼면 **팔이 그대로 떨어집니다.**
- 명세에는 "락 해제"만 있고, 그게 "모터 힘 빼기"인지 "일에서만 빼기"인지 없습니다.
- **Phody 제안:** 락 해제 = 안전한 자세로 옮긴 뒤 일에서 빼기. 모터 힘은 유지합니다.

### 2-5. "장애 처리 완료" 명령의 응답 시간

- 규칙상 로봇은 관리 명령에 **2초 안에** 답해야 합니다.
- Phody는 장애를 풀기 전에 "팔이 2초 동안 가만히 있고, 부딪힌 곳이 없다"를 확인합니다. 그래서 2초를 넘습니다.
- **정해 주세요 (둘 중 하나):**
  1. 이 명령만 "받았음"을 먼저 답하고, 결과는 팔 상태로 보여준다
  2. 이 명령만 답하는 시간을 늘린다

### 2-6. 관제 신호가 끊겼을 때 팔은 어떻게 멈출지

- 규칙: 관제 신호가 1.5초 끊기면 로봇은 멈춘다.
- 실제로 무선 연결이 7~8초 끊긴 적이 있습니다(11-25 실험).
- 팔이 상품을 들고 가는 중에 바로 멈추면 상품을 든 채 공중에 섭니다.
- **정해 주세요:**
  - 끊기면 즉시 멈출지, 지금 하던 동작 하나는 마치고 멈출지
  - 다시 연결되면 이어서 할지, 관리자가 확인한 뒤에 이어서 할지

### 2-7. 로봇팔 고장 이유 이름

- 팔 고장 이유가 지금은 "팔 장애" 하나뿐입니다. 관리자가 원인을 알기 어렵습니다.
- 규칙상 새 이유 이름은 팀 표에 먼저 넣어야 쓸 수 있습니다.
- **추가 제안:** 팔 상태 신호 끊김, 팔이 닿지 않는 위치, 충돌 검사 실패, 그리퍼 고장.

### 2-8. "확인된 담기"의 기준

- Phody에는 바구니 안을 세는 센서가 없습니다.
- **Phody 제안:** 바구니 위에서 그리퍼를 여는 데 성공하면 "담음"으로 센다.

### 2-9. 담기 도중 취소되면 들고 있던 상품은?

- 상품을 집은 채로 취소 명령이 오면 어떻게 할지 정해진 게 없습니다.
- **정해 주세요 (셋 중 하나):** 바구니에 넣고 끝낸다 / 작업대에 되돌린다 / 든 채로 멈추고 "쥐고 있음"으로 보고한다

### 2-10. 두 팔이 동시에 일할 때의 상태 이름

- Phody는 두 팔이 따로따로 동시에 움직입니다. 바구니 안에는 한 번에 한 팔만 들어갑니다.
- 팀 정의에도 "담는 중(PLACING)은 두 팔이 동시에 보고하면 안 된다"고 되어 있어서 서로 맞습니다.
- 다만 Phody 동작 단계와 상태 이름의 대응이 없습니다.
- **Phody 제안:**
  - 상품 집기 (작업대 ↔ 관측 자세) = 집는 중(PICKING)
  - 바구니로 가기 · 넣기 · 돌아오기 = 담는 중(PLACING)
  - 바구니가 비기를 기다림 = 담기 대기(PLACE_WAITING)

### 설계 검토 사항(Q)에 대한 Phody 의견

- **Q-05 (팔 멈춤 · 이어서 하기):** "멈춰라 / 이어서 해라"를 목표 값으로 보내는 서비스 하나를 제안합니다. Phody는 동작을 작은 단계로 나눠 하므로, 단계 사이에서 멈추고 다시 이을 수 있습니다.
- **Q-06 (한 팔만 락이 풀렸을 때):** Phody는 한 팔로도 일할 수 있습니다. 남은 팔이 닿는 상품만 담고, 닿지 않는 상품은 "못 담음(팔이 닿지 않음)"으로 보고하는 것을 제안합니다.
- **Q-03 (쥐고 있는지):** Phody는 그리퍼를 닫았는지, 바구니에 넣었는지 기록하고 있어서 "쥐고 있음"을 정확히 알려줄 수 있습니다.
