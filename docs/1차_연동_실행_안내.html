1. 구성 그림

관제 PC 한 대에서 DB · 브리지(웹 포함) · central · fleet이 돕니다. 로봇 쪽(Pode · 팔)은 실물 망(도메인 6)에서 디스커버리 서버로 관제 PC의 노드를 찾습니다. 혼자 시험할 때는 로봇 쪽 대신 fake_fleet(fleet 대역)을 쓰고, 디스커버리 서버 없이 내 PC 안에서만 통신합니다.

이름종류누가 → 누구뜻
/system/mode토픽브리지 → central운영 모드(NORMAL · TEST)
/central/state토픽central → 브리지boot_id, 단계 CONNECTING · SYNCING · RUNNING (1초마다)
/bridge/list_board_trips서비스central이 브리지를 부름끝나지 않은 운반 건 목록. central이 켜질 때 주문판을 다시 세움
/central/submit_trip (SubmitTrip)서비스브리지가 central을 부름접수한 운반 건 넘기기. central이 실행 중이 아니면 NOT_READY
/central/orders토픽central → fleet주문판. central이 실행 중(RUNNING)일 때만 냄
/central/report_order (ReportOrder)서비스fleet이 central을 부름주문판 건의 진행 보고
/bridge/report_trip (ReportTrip)서비스fleet이 브리지를 부름운반 건 상태 보고 → DB 주문 상태

이름 · 타입의 원본은 interfaces/fleet_interfaces/contract.yaml입니다.

2. 처음 한 번 준비

  1. ROS 2 Jazzy와 docker(docker compose 포함)를 설치합니다. 설치 방법은 각 공식 안내를 따릅니다.
  2. colcon 작업 공간 위치를 정합니다. 사람마다 다르므로 이 문서는 $IPONIC_WS(작업 공간) · $IPONIC_REPO(저장소)로 적습니다. .bashrc는 4절에서 넣으므로, 지금은 셸에서 아래 두 줄만 자기 경로로 바꿔 실행합니다.
export IPONIC_WS="$HOME/gg_ws"                       # 내 colcon 작업 공간
export IPONIC_REPO="$IPONIC_WS/src/roscamp-repo-2"   # 저장소를 받은 곳
  1. 저장소는 $IPONIC_WS/src/ 아래에 있어야 colcon이 찾습니다. 다른 곳에 받았다면 연결합니다.
mkdir -p "$IPONIC_WS/src" && ln -s "$IPONIC_REPO" "$IPONIC_WS/src/roscamp-repo-2"
  1. 브리지용 공용 가상환경 ~/venv/iponic을 만들고 pc/requirements.txt를 설치합니다(psycopg · fastapi · uvicorn 등). --system-site-packages라서 ROS 패키지(rclpy)도 그대로 보입니다.
cd "$IPONIC_REPO"
python3 -m venv --system-site-packages ~/venv/iponic
~/venv/iponic/bin/pip install -r pc/requirements.txt
  1. DB 컨테이너(design/db/compose.yaml, PostgreSQL 16, 포트 55432)를 띄웁니다. 데이터는 tmpfs라 컨테이너를 내리면 사라집니다. 띄우는 것은 5절 1번 터미널에서 해도 됩니다.
cd "$IPONIC_REPO"
docker compose -f design/db/compose.yaml up -d

3. 빌드

관제 PC에서는 개발 규칙대로 전체를 빌드하거나, 이 연동에 필요한 패키지만 빌드합니다(iponic_bringup은 fake_robots · fleet_manager를 함께 끌어옴).

cd "$IPONIC_WS" && source /opt/ros/jazzy/setup.bash
colcon build                                                                   # 관제 PC (전체)
source install/setup.bash
cd "$IPONIC_WS" && source /opt/ros/jazzy/setup.bash
colcon build --packages-up-to central service_bridge fleet_manager iponic_bringup
source install/setup.bash
--symlink-install로 빌드할 때(cbi): colcon이 브리지 실행 파일 첫 줄에 #!/usr/bin/python3를 박아, ros2 run service_bridge …로 띄우면 가상환경을 켜도 시스템 파이썬으로 돌아 No module named 'psycopg'가 납니다. 그래서 브리지와 그 시험 도구는 언제나 가상환경의 파이썬으로 python -m service_bridge.…로 띄웁니다. central · 관제 노드 · ros2 launch는 그대로 ros2 run · ros2 launch로 띄웁니다.

4. ~/.bashrc 등록 예

아래는 개발 규칙의 예를 그대로 옮긴 것입니다. 경로와 도메인 번호는 자기 것으로 바꿉니다(도메인은 팀원끼리 겹치지 않게, 예 41 ~ 49, 6은 쓰지 않음).

# ---- iponic 개발 ----
export IPONIC_WS="$HOME/gg_ws"                       # 내 colcon 작업 공간
export IPONIC_REPO="$IPONIC_WS/src/roscamp-repo-2"   # 저장소를 받은 곳

source /opt/ros/jazzy/setup.bash   # net_ds.sh도 이 줄을 부름
[ -f "$IPONIC_WS/install/setup.bash" ] && source "$IPONIC_WS/install/setup.bash"

# 통신 설정은 tools/net/net_ds.sh 하나로 (docs/설계/디스커버리_서버_안내.md 5절).
# 새 터미널의 기본값은 혼자 하는 시험: 내 도메인 + 내 PC 안에서만, 서버 없음.
# 도메인 번호는 팀원끼리 겹치지 않게 각자 정함 (예: 41 ~ 49). 6은 쓰지 않음.
export IPONIC_MY_DOMAIN=43
iponic_local() { FLEET_DOMAIN_ID=$IPONIC_MY_DOMAIN FLEET_LOCAL=1 source "$IPONIC_REPO/tools/net/net_ds.sh"; }
iponic_real()  { source "$IPONIC_REPO/tools/net/net_ds.sh"; echo "실물 망: 도메인 6, 서버 $ROS_DISCOVERY_SERVER"; }
iponic_super() { SUPER=1 source "$IPONIC_REPO/tools/net/net_ds.sh"; ros2 daemon stop; ros2 daemon start; }
iponic_local

# 자주 쓰는 이동 · 빌드
alias cdi='cd "$IPONIC_REPO"'
alias cbi='(cd "$IPONIC_WS" && colcon build --symlink-install) && source "$IPONIC_WS/install/setup.bash"'

개발 규칙의 예에는 이 밖에 Gazebo · 실물 Pode 도구 · 장치 정체(~/.iponic_env) 줄이 있습니다. 필요한 사람은 원본에서 옮깁니다.

브리지 터미널용 함수 (이 안내에서 새로 제안)

브리지와 그 시험 도구는 ROS → install → 가상환경 → net_ds.sh 순으로 준비한 터미널에서 띄웁니다(개발 규칙 "주문 처리(브리지) 개발 환경"의 순서). 이 순서를 한 번에 하는 함수 예입니다. 함수 이름 iponic_bridge는 원본 문서에 없고 이 안내에서만 제안하는 것이므로, 쓰고 싶은 사람만 위 예 아래에 더합니다.

# 브리지 터미널: ROS → install → venv → net_ds.sh 순. 인자 real이면 실물 망, 없으면 혼자 시험
iponic_bridge() {
  source /opt/ros/jazzy/setup.bash && source "$IPONIC_WS/install/setup.bash" || return 1
  source ~/venv/iponic/bin/activate || return 1
  if [ "$1" = real ]; then iponic_real; else iponic_local; fi || return 1
  cd "$IPONIC_REPO"
}

혼자 시험과 실물 망 고르기

상황부를 것결과
혼자 하는 개발 · 시험 (한 PC, fake_fleet)iponic_local (새 터미널 기본값)내 도메인 + LOCALHOST, 서버 없음
실물 망에 붙는 연동 (로봇 · 진짜 fleet)iponic_real도메인 6, 디스커버리 서버 192.168.0.252:11811

한 시험에 쓰는 터미널은 모두 같은 쪽으로 맞춥니다. 바꾼 뒤에는 그 터미널에서 띄운 노드를 다시 띄웁니다. .bashrc를 고친 뒤에는 source ~/.bashrc를 하거나 새 터미널을 엽니다.

5. 실행 절차 (터미널별)

터미널 넷을 씁니다. 모두 저장소 폴더($IPONIC_REPO)에서, 4절처럼 준비한 터미널에서 실행합니다. .bashrc에 넣지 않았다면 터미널마다 아래 줄(4절 예에서 혼자 시험에 필요한 줄만 뽑은 것, 경로 · 도메인은 자기 것으로)을 먼저 실행합니다.

export IPONIC_WS="$HOME/gg_ws"                       # 내 colcon 작업 공간
export IPONIC_REPO="$IPONIC_WS/src/roscamp-repo-2"   # 저장소를 받은 곳
source /opt/ros/jazzy/setup.bash
[ -f "$IPONIC_WS/install/setup.bash" ] && source "$IPONIC_WS/install/setup.bash"
export IPONIC_MY_DOMAIN=43
iponic_local() { FLEET_DOMAIN_ID=$IPONIC_MY_DOMAIN FLEET_LOCAL=1 source "$IPONIC_REPO/tools/net/net_ds.sh"; }
iponic_local
띄우는 순서는 아무래도 됩니다. 권하는 순서는 DB → 브리지(웹) → central → fleet입니다. central을 브리지보다 먼저 켜면 central은 브리지를 기다리며 "연결 중"(CONNECTING)에 머뭅니다. 정상입니다. 브리지가 뜨면 저절로 "주문판 갱신 중" → "실행 중"으로 넘어갑니다.

터미널 1 — DB · 브리지(웹)

브리지 환경(ROS → install → 가상환경 → net_ds.sh)을 준비합니다. iponic_bridge 함수를 쓰면 한 줄이고, 아니면 아래 넷째 줄까지를 실행합니다.

cd "$IPONIC_REPO"
source /opt/ros/jazzy/setup.bash && source "$IPONIC_WS/install/setup.bash"
source ~/venv/iponic/bin/activate
iponic_local                                   # 개인 도메인 + LOCALHOST

시험 DB를 만듭니다. IPONIC_DB_DSN의 DB(기본 ifp_test)를 지우고 다시 만들며, 이름이 _test로 끝날 때만 돕니다. 출력의 계정 id(tester)와 상품 id를 적어 둡니다.

docker compose -f design/db/compose.yaml up -d && python -m service_bridge.tools.setup_db   # IPONIC_DB_DSN의 *_test DB를 지우고 다시 만듦

브리지(웹 포함)를 띄웁니다. mode:=는 꼭 줍니다. 고객 주문을 받으려면 NORMAL입니다(TEST면 주문이 503 MAINTENANCE).

python -m service_bridge.main --ros-args -p mode:=NORMAL

터미널 2 — central

central은 가상환경이 필요 없습니다. ROS · install을 source하고 같은 통신 설정(iponic_local 또는 iponic_real)을 한 터미널에서 띄웁니다.

iponic_local
ros2 run central central

central은 브리지의 /bridge/list_board_trips가 보이고 /system/mode를 한 번 받아야 실행 중이 됩니다. 브리지 없이 central만 볼 때는 브리지 대신 아래 시험 도구를 터미널 1에서 띄웁니다(빈 목록 또는 파일의 목록으로 답하고 /system/mode를 한 번 냄). 진짜 브리지 · fleet이 있는 도메인에서는 띄우지 않습니다. central이 빈 목록으로 실행 중이 되어 빈 주문판을 낼 수 있고, /system/mode를 TEST로 덮어씁니다.

python -m service_bridge.tools.board_trips_stub [--trips FILE.json]

터미널 3 — fleet

혼자 시험은 fleet 대역 fake_fleet(브리지 환경 터미널에서)입니다.

python -m service_bridge.tools.fake_fleet     # 매개변수 step_s · duplicate_every_report · missing

진짜 fleet(fleet_manager_node)을 쓸 때는 pc.launch.py로 띄웁니다. 이때 fake_fleet은 끕니다. 진짜 central과 함께 쓰려면 세 기본값을 바꿉니다.

  • fake_central 기본 true: 가짜 central이 함께 뜨므로 fake_central:=false.
  • use_sim_clock 기본 true: fleet과 가짜 노드가 시뮬 시계를 쓰고 central은 벽시계라 섞이므로 use_sim_clock:=false.
  • monitor 기본 true: 시나리오 감시 노드가 시나리오 주문이 끝나거나 시간 한도가 지나면 launch 전체를 끄므로 monitor:=false.

use_fake:=true라서 이 줄은 fleet_manager_node와 함께 가짜 로봇 · 팔도 띄웁니다(로봇 없이 하는 시험). 실물 로봇을 붙일 때의 인자(fake_robots:=none robots:=… dock_wait_robots:=…)는 pc.launch.py 머리 주석의 "실물 두 대 시험" 예를 봅니다. 이 줄은 pc.launch.py 머리의 실물 시험 예에 맞춰 인자를 고른 것이고 진짜 central과 한 바퀴 돌려 보지는 않았습니다. 1차 연동 전에 관제 담당과 확인합니다.

iponic_local
ros2 launch iponic_bringup pc.launch.py use_fake:=true fake_central:=false use_sim_clock:=false monitor:=false scenario:=real_three_orders

터미널 4 — 확인용

브리지 환경으로 준비한 터미널에서 6절의 확인 명령을 씁니다.

6. 확인

central 단계

혼자 시험이면 iponic_local 한 터미널에서 바로, 실물 망이면 super client 터미널(iponic_super)에서 봅니다.

ros2 topic echo --once /central/state

그 도메인에서 처음 쓰는 ros2 명령이면 daemon이 뜨는 중이라 "does not appear to be published yet"으로 한 번 실패할 수 있습니다. 몇 초 뒤 다시 합니다. state가 RUNNING이면 central이 주문판을 내고 있습니다. CONNECTING이면 브리지(또는 board_trips_stub)를 아직 못 찾은 것입니다.

화면

화면주소볼 것
고객http://<관제 PC>:8000/customer/?account=<id>주문하고 접수됨 → 준비 중 → 출고 중 → 출고 완료
관리자http://<관제 PC>:8000/admin/위쪽 모드 표시 옆 "central: 연결 중 / 주문판 갱신 중 / 실행 중 / 연결 안 됨"

같은 PC에서 보면 <관제 PC>는 localhost, <id>는 setup_db가 출력한 계정 id입니다. 포트는 IPONIC_WEB_PORT(기본 8000)로 바꿀 수 있습니다. order · ws_watch는 이 변수를 읽지 않고 http://localhost:8000을 기본으로 쓰므로, 포트를 바꿨다면 두 도구에 --url http://localhost:<포트>를 함께 줍니다.

화면 없이 보려면 GET /api/snapshot?view=admin의 work_state.central을 봅니다(값은 CONNECTING · SYNCING · RUNNING · LOST, LOST가 화면의 "연결 안 됨"). view는 꼭 줍니다.

명령으로 한 바퀴

브리지(mode:=NORMAL) · central · fake_fleet을 켠 뒤, 터미널 4에서 WS를 지켜봅니다(한 줄에 메시지 하나, JSON).

python -m service_bridge.tools.ws_watch --account 1

다른 브리지 환경 터미널에서 주문을 보냅니다(202면 0으로 끝남). --account는 tester의 id, --items는 상품 id:개수를 쉼표로 잇습니다. 아래 예 3:2,5:1은 "상품 id 3을 2개, 5를 1개"입니다. 상품 id는 setup_db 출력의 상품 {…}에서 골라 바꿉니다.

python -m service_bridge.tools.order --account 1 --items 3:2,5:1

ws_watch와 고객 화면에 접수됨 → 준비 중 → 출고 중 → 출고 완료가 차례로 보이면 한 바퀴가 돈 것입니다. 관리자 WS는 ws_watch --admin입니다.

7. 끄기 · 다시 켜기

  • 끄기: 각 터미널에서 Ctrl+C 한 번. 브리지는 신호를 받고 웹을 닫은 뒤 노드 · DB 풀을 차례로 닫습니다.
  • central만 다시 켤 때: central 터미널에서 Ctrl+C 뒤 다시 ros2 run central central. 관리자 화면에는 central이 꺼진 동안 "연결 안 됨"(3초 넘게 /central/state를 못 받음), 다시 켜지면 "연결 중" → "주문판 갱신 중" → "실행 중"이 보입니다(브리지가 이미 돌고 있으면 앞의 둘은 1초쯤 스쳐 지나가거나 "실행 중"만 보일 수 있습니다). central은 새 boot_id로 브리지에서 끝나지 않은 건 목록을 받아 주문판을 접수 순서대로 다시 세운 뒤에야 주문판을 냅니다. DB alert 표에는 안내 알림 CENTRAL_RESTART(INFO, "central이 다시 켜져 주문판을 다시 세웁니다")가 한 건 남습니다. 관리자가 할 조치는 없습니다. 이 알림은 지금 관리자 화면 · /api/snapshot에는 보이지 않고(알림을 화면에 보내는 방법은 Q-07에서 정함) DB에서만 확인합니다. 아래 줄의 컨테이너 이름 db-pg-1과 DB 이름 ifp_test는 기본값이며, 다르면 자기 것으로 바꿉니다. 
    docker exec -e PGPASSWORD=ifp_test db-pg-1 psql -U postgres -d ifp_test -Atc "select created_at, level, message from alert where code='CENTRAL_RESTART'"
  • 브리지를 다시 켤 때: Ctrl+C 뒤 같은 명령(mode:= 포함)으로. central은 실행 중이면 그대로 실행 중입니다. 브리지가 꺼져 있는 동안 central이 다시 켜졌다면 CENTRAL_RESTART 알림은 남지 않습니다(브리지가 알아챌 수 없음).
  • DB를 다시 켤 때: 컨테이너를 내리면(docker compose -f design/db/compose.yaml down) 데이터가 사라지므로 다시 띄운 뒤 setup_db를 다시 합니다. 주문판이 DB와 어긋나지 않게 브리지 · central · fleet도 다시 켜는 것을 권합니다.

8. 주의 사항

  • 도메인 6은 실물 망(로봇 네트워크)입니다. 혼자 시험은 반드시 개인 도메인 + FLEET_LOCAL=1(iponic_local)로 합니다. 시작 전에 echo $ROS_DISCOVERY_SERVER가 비어 있는지 봅니다.
  • 통신 설정을 바꾼 터미널은 그 터미널에서 띄운 노드를 다시 띄우고, ros2 daemon stop; ros2 daemon start로 daemon도 다시 켭니다(daemon은 처음 뜰 때의 설정을 계속 씀).
  • ROS와 install/setup.bash를 source한 뒤에 가상환경을 켭니다(모듈은 install에서 찾음).
  • 브리지는 ros2 run이 아니라 python -m으로 띄웁니다(ros2 run으로는 가상환경의 psycopg를 못 찾음).
  • mode:=는 꼭 줍니다(NORMAL 또는 TEST). TEST면 고객 주문이 503 MAINTENANCE입니다.
  • setup_db는 _test DB를 지우고 다시 만듭니다. 남길 데이터가 있는 DB에 부르지 않습니다. DB 컨테이너를 다른 사람 · 다른 시험과 함께 쓴다면 IPONIC_DB_DSN의 DB 이름을 내 것(…_test로 끝남)으로 바꾼 뒤 부릅니다.
  • fake_fleet과 진짜 fleet(fleet_manager_node)을 같이 켜지 않습니다. fake_fleet이 fleet을 대신합니다.
  • pc.launch.py의 fake_central 기본값은 true입니다. 진짜 central(ros2 run central central)을 쓸 때는 fake_central:=false를 붙입니다. 같은 launch의 use_sim_clock(기본 true, 시뮬 시계라 벽시계인 central과 섞임)과 monitor(기본 true, 시나리오가 끝나거나 시간 한도가 지나면 launch 전체가 꺼짐)도 false로 둡니다. use_fake:=true면 가짜 로봇 · 팔도 함께 뜹니다(5절 터미널 3).
  • docker로 브리지를 띄우는 운영 구성에서는 host 망을 씁니다(network_mode: host · ipc: host, 디스커버리 서버 안내 4절 9항 · 5절).
  • 웹 포트는 8000(IPONIC_WEB_PORT, 주소는 IPONIC_WEB_HOST 기본 0.0.0.0), DB는 IPONIC_DB_DSN입니다.
  • 디스커버리 서버 1번(central PC) 주소는 아직 정하지 않았습니다(Q-20). 정해지면 tools/net/net_ds.sh의 DS_CENTRAL 한 줄만 채웁니다.

central 재시작 · 디스커버리 서버 연결은 시험 스크립트로 한 번에 확인할 수 있습니다(DB 컨테이너와 빌드가 먼저 있어야 함, 약 3 ~ 4분, 하나라도 실패면 종료 코드 1). 스크립트는 ${IPONIC_WS:-$HOME/iponic_ws}/install/setup.bash와 ~/venv/iponic을 source하므로 작업 공간이 ~/iponic_ws가 아니면 IPONIC_WS를 export한 터미널에서 돌립니다. 디스커버리 서버 포트 11931 · 11932, 웹 포트 8090, DB iponic_restart_test를 따로 쓰므로 평소 시험 DB(ifp_test)는 건드리지 않습니다. 저장소 폴더에서 실행합니다.
