# 통신 규칙 · 인터페이스 초안을 위한 검토와 논의

- 작성: 2026-11-20 · 상태: **검토 완료 (11-20)** — C-01 ~ C-17 결정, C-18만 보류 (R-07). **11-20 검토를 여기서 닫음**: 결정은 3장 #1 ~ #37, 남은 것은 9장 "다음 주 논의 1 ~ 4"와 취합 6.2. 다음은 [인터페이스 명세 초안](인터페이스_명세_초안.md)
- 목적: 통신 규칙과 인터페이스 초안을 쓰기 전에, 설계 문서들과 실제 인터페이스가 어디서 맞지 않는지 모으고, 정해야 할 것을 논의 항목으로 정리합니다.
- 쓰임: 세션(작업자) 사이에 의견을 나누는 공용 문서입니다. 의견은 9장에 남깁니다.

## 이 문서를 읽고 쓰는 법

1. 1장으로 전체를 보고, 5장 논의 항목에서 맡은 것을 고릅니다. 시험 근거는 6장(규칙 후보 · 선택표)과 7장(시험 위치 · 항목)에 있습니다.
2. 의견은 **9장 의견 기록**에 덧붙입니다. 다른 사람이 쓴 글은 고치지 않습니다.
3. 논의 항목이 결정되면, 5장의 그 항목 "상태"를 `결정`으로 바꾸고 결정 내용을 3장 표에 한 줄 더합니다. 10장 변경 이력에도 적습니다.
4. 근거는 문서 이름과 번호로 적습니다 (예: 다이어그램 `6-5 #11f`, 기능 `BRG-05`, 수정 요청 `R-20`).

번호 체계:

| 접두 | 뜻 | 이 문서의 위치 |
|---|---|---|
| `C-` | 논의 항목 (정해야 할 것) | 5장 |
| `TR-` | 통신 규칙 후보 (시험 근거가 있는 것) | 6장 |

| `FL-` | 기능 목록 고칠 곳 | 8장 |
| `R-` · `D-` | 다이어그램 수정 요청 · 기능 시트 "결정 필요" (다른 문서의 번호) | 인용만 |

### 2.1 기준 인터페이스(0.6)를 같이 보는 법 (git worktree)

docs/design 브랜치에는 0.3만 있습니다. 기준인 0.6은 다른 브랜치에 있으므로, 브랜치를 바꾸지 않고 **옆 폴더에 최신본을 받아 두고 같이 봅니다** (git worktree). 문서 작업은 지금 폴더에서, 인터페이스는 옆 폴더에서 읽습니다.

처음 한 번 (저장소 폴더 `roscamp-repo-2`에서):

```bash
git fetch origin
git worktree add --detach ../roscamp-repo-2-ref origin/feat/order-hold-interfaces
```

- 옆 폴더 `../roscamp-repo-2-ref`에 0.6이 풀립니다. 예: `../roscamp-repo-2-ref/interfaces/fleet_interfaces/contract.yaml`
- `--detach`로 받아 **읽기 전용처럼** 씁니다. 이 폴더에서 커밋하지 않습니다 (관제 팀 브랜치를 건드리지 않게).

최신으로 맞출 때 (관제 팀이 push한 뒤):

```bash
git fetch origin
git -C ../roscamp-repo-2-ref checkout --detach origin/feat/order-hold-interfaces
```

자주 쓰는 비교:

```bash
git diff origin/fleet-v1 origin/feat/order-hold-interfaces -- interfaces   # 0.5 → 0.6에서 바뀐 것
git log --oneline -5 origin/feat/order-hold-interfaces                      # 관제 팀 최신 커밋
```

- 관제 팀이 합칠 브랜치를 바꾸면(예: fleet-v1에 합침) 위 명령의 브랜치 이름만 바꿉니다. 그때 이 표와 2장 "기준" 줄도 고칩니다.
- 다 쓰면 `git worktree remove ../roscamp-repo-2-ref`로 지웁니다.
- 0.6의 "Trip → Route" 이름 변경(`3f0e892`)은 관제 코드 안의 **주행 경로** 이름입니다. ROS 메시지 · contract는 그대로이고, 주문 DB의 운반 건(`trip_id`)과는 다른 것입니다 (커밋 설명으로 확인).

### 4.3 설계에서 새로 생긴 통신 성격

- **ROS가 웹을 부르는 방향이 두 군데입니다.** 결품 사전 확인(6-2 #2 ~ #6)과 central 재시작 때 보류 여부 묻기(6-8 노트). 지금 브리지는 웹 → ROS 호출만 있습니다 (C-05).
- **거절 보고가 상태 토픽으로 그려져 있습니다** (6-5 #11f, 6-6 #12f). 상태 토픽은 best_effort라 한 번만 보내는 거절은 잃을 수 있습니다. 3장 #8 원칙대로라면 fleet → 로봇 서비스의 응답으로 받아야 합니다 (C-10).
- **서비스 일시 정지가 두 길로 전달됩니다.** `/central/orders`의 `run_mode`(6-6 #4, 6-9 #7)와 정지 지시(6-6 #5 · #6, 6-9 #8 ~ #10) (C-11).
- **담기 일시 중지 때 담은 수를 알리는 인터페이스**가 생기면 수시 조정 막음이 풀립니다 (마감 DB 토의 D-4, R-17 ③). C-06과 같은 일입니다.
- **설정 값 공유.** `basket_capacity`를 웹과 관제가 같게 쓰는 방법이 정해지지 않았습니다 (OMS-20 비고) (C-16).

- 질문: 주문 전달, 취소, 서비스 일시 정지 · 재시작을 어떤 서비스로 보내는가?
- 제안:
  - 주문 전달: 요청에 `trip_id`와 상품을 넣음 (번호는 웹이 만듦, 3장 #2). 같은 `trip_id`가 다시 오면 처음 응답을 그대로 돌려줌. 서비스 브리지 단위 시험 UT-03(Idempotency-Key 멱등 접수)과 같은 방식입니다.
  - 취소: 주문 단위 요청, 응답에 `accepted` · 거절 사유(`ALREADY_ASSIGNED` 등). 나뉜 주문은 모든 운반 건이 접수됨일 때만.

### C-05 ROS가 웹에 묻는 요청

- 상태: **결정** (11-20, 3장 #23) · 아래는 결정 전 기록 · 관련: 6-2 #2 ~ #6, 6-8 노트 "central 재시작 때 웹에 보류 여부를 먼저 묻기", BRG-01 비고
- 질문: central이 웹(DB)의 값을 알아야 할 때 어떤 길로 묻는가?
- 선택지:
  - 가. 브리지가 ROS 서비스 서버를 열고, 받으면 REST로 웹에 물어 답함
  - 나. 웹이 필요한 값을 미리 밀어 줌. 마감 상태는 브리지가 LATCHED 토픽으로 계속 알리고(central이 다시 켜지면 자동으로 받음), 결품 확인용 가용 수량은 주문 전달 때 함께 줌
- 제안: **마감 상태는 나**, **결품 사전 확인은 가**. 마감 상태는 "지금 값" 하나라 LATCHED가 맞습니다 (사전 시험 C · E-2: Wi-Fi에서는 성공, 같은 PC에서는 가끔 실패하므로 central이 켜질 때 서비스로 한 번 더 확인). 결품 확인은 도착 순간의 가용 수량이어야 해서 미리 줄 수 없습니다.
- 정할 것: 가의 시간 한도와, 웹이 답하지 않을 때 central이 할 일 (담기 대기 유지 + 알림 제안).

### C-06 담기(FillBasket) 멈춤 · 이어서 하기

- 상태: **결정** (11-20, 3장 #19 · #20). 팔 일시 정지(이상)는 새 목표로 이어서 하고, 장애로 취소하면 담은 것만 출고 · 아래는 결정 전 기록 · 관련: 4. Phody 팔 일시 정지 재개, 6-2 #17 · #23, 6-9 #10 · #22, PHD-01 · 08, D-4
- 질문: 실행 중인 담기를 멈추고 이어서 하는 방법은?
- 선택지:
  - 가. **취소 후 새 목표**: 멈출 때 액션을 취소하고, 결과의 `placed`를 받아 둠. 이어서 할 때 남은 상품만 새 목표로 보냄
  - 나. Phody에 멈춤 · 이어서 서비스를 따로 두고, 액션은 열린 채로 둠
- 제안: **가**. 액션이 오래 열린 채 Wi-Fi가 끊기는 경우를 피하고, `placed`가 멈출 때마다 확정되므로 C-03 · D-4도 풀립니다. 팔 일시 정지(PAUSED)는 팔이 스스로 멈추는 것이라, 결과에 멈춘 이유를 넣어야 합니다.
- 정할 것: 결과 · 피드백에 넣을 칸 — 멈춘 이유(`RECOGNITION_ERROR` · `PICK_FAILED` · `DISTANCE_STOP`), 상품별 `placed`, 하던 상품. 화면은 이 이유로 SCR-08과 SCR-12를 나눕니다. "못 담음 처리 후 재개"는 새 목표에서 그 상품을 빼는 것으로 충분한지도 확인이 필요합니다.

### C-09 상태 값 정렬과 상태의 주인

- 상태: **결정** (11-20, 3장 #29) · 아래는 결정 전 기록 · 이전 상태 표기: 열림 · 관련: 4.1 #5 · #6, D-02 · D-03 · D-05
- 질문: 로봇이 보고하는 상태와 fleet이 매기는 상태를 어떻게 나누는가?

### C-12 알림 전달 (D-06)

- 상태: **결정** (11-20, 3장 #28) · 아래는 결정 전 기록 · 이전 상태 표기: 보류 (D-06과 같이 감) · 관련: 4.2 E, CEN-12, OMS-16
- 질문: 장애 · 결품 알림을 놓치지 않고 웹까지 보내는 방법은?
- 사실: `/central/events`(FleetEvent)는 reliable · volatile이라, 브리지가 늦게 켜지면 그 전 알림을 받지 못합니다 (사전 시험 E-1과 같은 상황). 서비스 브리지 단위 시험은 알림에 번호를 붙이고, DB에 저장한 뒤 ACK하는 방식(UT-04 · UT-05)을 확인했습니다.

### 6.1 메시지 종류별 통신 방식 선택표 (의견, 초안의 뼈대)

TR-01 ~ TR-08과 3장 결정을 메시지 종류에 맞춘 표입니다. 통신 규칙 초안의 "QoS 선택표"로 씁니다 (**11-20 결정, 3장 #33**).

| 메시지 종류 | 예 (다이어그램 · 인터페이스) | 방식 | QoS · 설정 | 근거 |
|---|---|---|---|---|
| 한 번 보내는 요청 | 주문 전달(`SubmitTrip`), 취소(`CancelOrder`), 작업 모드(`SetRunMode`), 마감 보류(`SetAssignHold`), 관리 명령 | **서비스 + 곧바로 접수 응답**. 요청 번호를 넣고, 응답이 없으면 같은 번호로 다시 보냄 | 서비스 기본. `wait_for_service` 한도 5초 이상, 응답 한도는 3장 #34 | TR-01, IT-03, 3장 #22 · #25 |
| 결과 · 진행 · 알림 보고 | `ReportTrip`, `ReportCommand`, `ReportEvent` (central · fleet → 브리지) | **서비스, 번호를 붙이고 받는 쪽은 DB에 쓴 뒤 응답, 응답이 없으면 같은 번호로 다시 보냄** (포기하지 않음). 같은 운반 건은 앞 보고가 응답받은 뒤 다음 보고 | 응답 한도 3초, 다시 보내기 1 → 2 → 4초 · 최대 10초 간격 | TR-08, 3장 #18 · #25 · #28 · #34 |
| 오래 걸리는 작업 | MoveTo, Dock, FillBasket, SwapBasket, Retreat | **액션**. 멈출 때는 취소 후 새 목표 (C-06) | 액션 기본. 같은 명령의 재시도와 새 명령을 구분하는 규칙 필요 (K-08, G-09) | 4.1, C-06 |
| 지금 값 (상태판) | `/central/orders`, `/fleet/assignments`, `/fleet/robots`(팔 포함), `/fleet/zones`, 마감 상태, `/system/mode` | **토픽 LATCHED**. 바뀔 때와 주기적으로 발행 | reliable · transient_local · depth 1 | TR-02 |
| 주기 상태 | `/{pode}/state`, `/{arm}/state` | **토픽 STATE**. 받는 쪽은 최신 값만 처리 | best_effort · volatile · depth 1 ~ 5. 초당 5 ~ 20번은 L-04에서 문제없음 | TR-03, TR-04, L-04 |
| 기록용 사건 | `/central/events` (모든 등급) | **토픽 EVENT** (기록용). 놓치면 안 되는 WARN 이상은 위의 `ReportEvent`로도 보냄 | reliable · volatile · depth 50 | 3장 #28 |

| 영상 | 카메라 → vision | **ROS 2 밖** (GStreamer, UDP) | - | TR-05, L-02 |

통신 규칙에 대한 의견입니다. 근거는 6장 · 7장에 있습니다.

1. **규칙은 "메시지 종류"로 정하고, 토픽마다 따로 정하지 않습니다.** 6.1 선택표의 여덟 종류 중 하나를 고르면 방식과 QoS가 정해지게 합니다. 새 메시지를 만들 때 종류만 적으면 되고, `contract.yaml`의 QoS 프로필(STATE · LATCHED · EVENT · HEARTBEAT)과 바로 이어집니다.
2. **"한 번 보내고 끝"인 토픽을 금지합니다.** 사전 시험의 가장 큰 결과입니다 (L-01: 같은 PC 50/50 못 받음). 한 번 보내는 것은 서비스로, 상태는 주기적으로 다시 보내는 토픽으로 합니다. 다이어그램의 "보고"와 "거절 보고"(6-5 #11f, 6-6 #12f)도 이 기준으로 다시 봅니다.
3. **로봇 안 프로그램끼리도 같은 규칙을 씁니다.** Wi-Fi에서는 켜자마자 보내기가 성공했지만(L-01 2단계), 이유를 확인하지 못했습니다. 같은 장비 안의 통신은 1단계(같은 PC)와 같은 조건이라 같은 문제가 생길 수 있습니다.
4. **다시 보내도 안전하게 만듭니다.** 모든 요청에 번호를 넣고, 받는 쪽은 같은 번호를 한 번만 반영합니다. 이것이 되면 "응답이 없으면 다시 보냄" 한 줄로 재시도 규칙이 끝납니다. 마감 보류 · 재개(3장 #11)와 출고 보고의 `LATE_REPORT`(3장 #12)가 이미 이 방식입니다.
5. **상태의 주인을 하나로 둡니다.** 운반 건 상태는 central이 정하고 웹은 기록만, 로봇 몸 상태는 로봇이 정하고 업무 단계는 fleet이 정합니다 (C-03, C-09). 주인이 둘이면 재시작 뒤 어느 값을 믿을지 정할 수 없습니다.
6. **재시작을 정상 상황으로 다룹니다.** central · 브리지 · 로봇이 다시 켜질 때 지금 값을 다시 받는 길(LATCHED 토픽 + 켜질 때 서비스로 확인)을 통로마다 적습니다 (C-05, C-13). 남은 시험 G-02 · G-04 · G-06을 초안 전에 하는 것이 좋습니다 (7.1).
7. **알림(D-06)은 결정을 미루더라도 칸은 먼저 만듭니다.** `FleetEvent`에 알림 번호를 지금 더해 두면, ACK 방식을 나중에 정해도 메시지를 다시 바꾸지 않아도 됩니다 (C-12, K-04).
